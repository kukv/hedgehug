# 長期運用での履歴の増加 設計

- 日付: 2026-11-03
- 親設計: Hedgehug 設計ドキュメント（https://claude.ai/artifact/8d4dcVbePAxR2BxhMtkqnc）の「インデックス」「同期」「フェーズ7の完了条件（性能目標）」
- 前段: CLI の受入テスト（`2026-11-02-cli-acceptance-fixes-design.md`）で「長期運用での履歴の増加は別にブレストから始める」とした件

## 目的

1 Store あたり 10 万コミットまで、履歴を使う操作が遅くならないようにする。対象は 3 つ: 履歴をパスで絞ってたどる処理、first-parent を最後まで読む処理、増え続ける pack。

## 決定の一覧（2026-11-03 に利用者が決定）

| # | 対象 | 決定 |
| --- | --- | --- |
| 1 | 規模の目標 | 1 Store あたり 10 万コミット |
| 2 | 速さの目標 | 10 万コミットで `show`（History 5 件）・`undo`・GUI のタスク詳細は 200ms、`log <id>` の全件と `restore --at` は 1 秒。`undo` の 200ms は自分のコミットを取り消すとき。取り消すものがないとき（first-parent を最後まで読む。計測では約 340ms）は記録だけ（2026-11-03 決定） |
| 3 | 方針 | 履歴の索引、途中で止める読み方、pack の段階的な統合の 3 つを入れる |
| 4 | 古い履歴の切り捨て | しない（「git が唯一の正本」、過去の集計のため） |
| 5 | マージコミット | タスクの履歴には、そのタスクがどの親とも違うときだけ出す（案 A） |
| 6 | 索引の最初の作成 | clone する操作の後とサーバーの起動時に作る。ないときに履歴を使うコマンドが来たらその場で作り、1 秒を超えたら stderr に進みを出す |
| 7 | pack | 小さい pack を段階的にまとめる。64 MiB 以上の pack はまとめ直さない。オブジェクトは捨てない。remote 側の pack は対象外 |
| 8 | 速さの確かめ方 | `make` のターゲットで手元で測り、結果を本 spec に記録する。CI には含めない |

変えないと決めたもの: ディスク容量は減らさない（purge しても内容は履歴に残る。親設計どおり）。remote（GitHub、手元の bare リポジトリ）の pack はまとめない。手元の bare を remote に使うときは利用者が `git gc` を実行する前提にし、ドキュメント（フェーズ7）に書く。`doctor` の Verify は全オブジェクトを読むままにする。

## 1. 計測でわかった現状

2026-11-03 に、使い捨ての計測で 10 万コミット・5,000 タスク・pack 1 つの Store を合成して測った（計測のコードは残していない。6 節の `make` のターゲットで作り直す）。

| 処理 | 使う箇所 | 時間 |
| --- | --- | --- |
| パスで絞った `Repo.Log`、5 件 | `show` の History | 39〜70 秒 |
| パスで絞った `Repo.Log`、全件 | `log <id>`、GUI のタスク履歴 | 15 分 48 秒 |
| 絞らない `Repo.Log`、全件 | 人の一覧、`mv --store` の再開判定 | 5.0 秒 |
| `Repo.LogFrom(head, 0)` | `undo`・`delete` の判定、`restore --at` | 342ms |

- go-git のパスでの絞り込み（`object/commit_walker_path.go`）は、コミットごとに tree 全体の差分（`DiffTree`）を取る。これが遅さの主な原因。
- さらに、比べる相手が「本当の親」ではなく「たどった順で次に出たコミット」になっている。同期でできたマージを含む履歴では、`log <id>` に関係のないコミットが出たり、出るべきコミットが抜けたりする。本 spec で直す。
- Store 全体の `log -n N` は go-git の深さ優先の順で N 件を取ってから時刻で並べるので、マージを含む履歴では「新しい順の N 件」にならないことがある。本 spec で直す。
- go-git の fetch は、取ってくるたびに新しい pack を 1 つ書く（`storage/filesystem` の `PackfileWriter`）。今の `Repo.Repack` はゆるいオブジェクトを 1 つの pack にまとめるだけで pack 同士は統合しないので、pack は増え続ける。go-git はオブジェクトを探すたびに全部の pack の idx を順に見る。
- 自前でパスの tree の hash だけを比べるようにしても、10 万件をたどる限り数秒かかる。200ms に届くには索引が要る。

## 2. 履歴の索引

### 2.1 置き場所と形

- 新しいパッケージ `internal/history` に置く。`gitrepo` と `model` に依存し、`index`・`sync`・`ops`・`server` から使う。
- ファイルは `.hedgehug/local/` の新しいキャッシュ（今の索引の gob とは別のファイル）。消しても作り直せる。今の索引は「HEAD の tree の状態」を持ち、こちらは「コミットの並び」を持つ。更新のきっかけも作り直しの重さも違うので分ける。
- 形式の版を持ち、版が違うか読めなければ作り直す（今の索引と同じ）。

### 2.2 中身

コミットごとに次を持つ。

- hash、時刻（author の時刻）、世代（親がなければ 1、あれば親の世代の最大に 1 を足した数）
- 書いた人（`LogEntry.Writer` と同じ: `Hedgehug-Author`、なければ author の email）
- `Hedgehug-Op`、`Hedgehug-Task`、`Hedgehug-Workspace` の値
- 変わったファイルのパス（すべてのファイル。タスク・コメント・作業記録も 1 ファイルずつ）

親の hash は持たない。増分の更新では親をリポジトリから読む。

索引全体として次の引きを持つ。

- パスから、そのファイルを変えたコミット。同期の修復の作者（`sync.headAuthor` はファイルごとに引く）と、転送ファイルの元の ID（`TaskPath` だけの最後の変更が要る）が使う。
- タスクの ULID から、そのタスクのファイル・コメント・作業記録のどれかを変えたコミット（パスの引きの和。今の `TaskLog` と同じ範囲）。`log <id>` と `show` が使う。
- 書いた人の一覧。

件名と trailer の全体は持たない。表示する数件だけ、その場でコミットを読む。

書いた人・Op・パスは重複が多いので、表を作って番号で持つ。目安は 10 万コミットで数 MB。読み込みと 1 回の引きを 10 万コミットで 50ms 以内にする（6 節で測る）。届かなければ形式を見直す。

### 2.3 「変えた」の意味

`gitrepo.LastChange` と同じ意味にする（2026-11-03 決定、案 A）。

- 親が 1 つのコミット: 親と比べて中身が違えば変えた。
- マージコミット: **すべての親**と比べて中身が違うときだけ変えた（両方の側で同じタスクが変わり、マージの結果がどちらとも違うとき）。片方の側をそのまま取ったマージは変えたことにしない。その変更は元のコミットとして出る。
- 親のないコミット: そのファイルがあれば変えた。

比べ方は、ルートの tree から hash の違う tree にだけ降りる。go-git の `DiffTree` は使わない。

並びは時刻の新しい順。同じ時刻なら世代の大きい方（子孫）を新しいとし、それも同じなら hash の大きい方を新しいとする。「最後に変えたコミット」もこの順で決める。今の `LastChange` は同じ時刻のとき `Between` の順（たどり方で決まる）を使うが、増分で足した索引では同じ順を再現できないので、たどり方によらない世代と hash の規則に変える。違いが出るのは同じ秒に作られたコミットが並んだときだけ。base を持つ `LastChange`（同期のマージ）は今のまま変えない。

### 2.4 更新

- 索引は、どの HEAD まで入れたか（tip）を持つ。
- HEAD が tip と違えば、HEAD から親をたどり、索引にあるコミットに当たったところで止める。同期のマージで入った相手側のコミットもこの方法で拾う。
- たどった中に tip がなければ（HEAD が tip を含まない）、履歴が巻き戻ったか書き換わったということなので、索引を捨てて作り直す（`doctor --fix` での clone し直し、`rebuild-keep` の後など）。
- 保存はロックを取らずに丸ごと書き換える（一時ファイルから rename）。後に書いた方が勝っても、それぞれの tip について正しい。今の索引の `save` と同じ考え方。
- 更新は、履歴を使う操作が来たときに行う。サーバーは、poll で HEAD の移動を見たときにも更新して、GUI の詳細を速く保つ。

### 2.5 最初の作成

- clone する操作の後に作る: `store add`（`store discover` から足すときも、`ops.Session.StoreAdd` が clone する）と、`doctor --fix` の clone し直し。`store init` は新しい Store を作るだけで履歴がないので対象外。サーバーは起動時に、マウントしている Store の分を作る。
- 索引がないときに履歴を使う操作が来たら、その場で作る。CLI は 1 秒を超えたら stderr に `Indexing the history of <store>: <n>/<total> commits` の形で進みを出す（`--json` のときも stderr）。
- 10 万コミットでの作成時間は 6 節で測り、本 spec に記録する。

## 3. 索引を使う箇所

| 箇所 | 今 | 変更後 |
| --- | --- | --- |
| `log <id>`（`ops.Session.TaskLog`）、`show` の History、GUI のタスク履歴（`server/tasks.go`） | パスで絞った `Repo.Log` | 索引でタスクの ULID を変えたコミットを引き、表示する分だけコミットを読む |
| Store 全体の `log`（`-n`、`--workspace`、`ops.Session.LogIn`） | `Repo.Log(nil, n)` を深さ優先でたどる | 索引から時刻の新しい順に取る。`--workspace` の判定（`logWorkspace`: `Hedgehug-Workspace`、なければ `Hedgehug-Task` のタスクの今のワークスペース）は今と同じで、索引の値で行う |
| 人の一覧（`ops/people.go`） | 全コミットを読む | 索引の書いた人の一覧 |
| `mv --store` の再開判定（`movestore.moveInRecorded`） | 全コミットを読む | 索引で Op が `move-in` のコミットだけを読む |
| 転送ファイルの元の ID（`index/forward.go` の `lastTask`・`resolveForwardIDs`） | `LastChange(head, 0, path)` で全履歴 | 索引でタスクのファイル（`TaskPath`）を最後に変えたコミットを引く |
| 同期の修復で最後に変えた人（`sync.headAuthor`） | `LastChange(head, 0, path)` で全履歴 | 索引でそのパスを最後に変えたコミットを引く |

変えないもの: 同期のマージ（`Sides`・`mergeAuthor` は base から先だけを見る）、マージドライバー、inbox（新しく入った分だけ）、サーバーの poll（`LogFrom(head, 1)`）、`doctor` の Verify。

出力の変化: `log <id>`・`show` の History・GUI の履歴は、マージを含む履歴で 2.3 の意味どおりになる（今の誤りが直る）。Store 全体の `log -n N` は新しい順の N 件になる。マージを含まない履歴での出力は変わらない。

`internal/index` が `internal/history` を使うので、`index.Open` の中で履歴の索引を更新する必要があるのは、転送ファイルが増えたときだけにする（毎回の Open で履歴の索引を読まない）。

## 4. 途中で止める読み方

- `Repo.LogFrom` を、呼び出し側が途中で止められる形にする（コールバックで `storer.ErrStop` を返せば止まる、など。形は plan で決める）。
- `undo`（`ops/undo.go` の `undoInTx`）: 取り消す対象のコミットが見つかったところで止める。
- `delete` の時刻の解決（`ops/delete.go` の `commitAt`、`restore --at` が使う）: 指定の時刻以前のコミットに当たったところで止める。
- そのほか `LogFrom(head, 0)` を使う箇所は plan で洗い出し、同じ形にする。

## 5. pack の統合

### 5.1 しくみ

- 新しい `Repo.Consolidate`（名前は plan で決める）は、git の `repack --geometric=2` と同じ考え方で小さい pack をまとめる。
  - 64 MiB 以上の pack は対象にしない（まとめ直さない）。
  - 残りの pack を大きさの順に並べ、「大きい側の各 pack が、それより小さい pack の合計の 2 倍以上」になる境目を探す。
  - 境目より小さい pack のオブジェクトとゆるいオブジェクトを、1 つの新しい pack に書く。大きい pack はそのまま残す。
  - 1 回にまとめる量は 64 MiB 程度までに収まる。go-git の pack の書き出しは差分を計算し直すので、Store 全体（10 万コミットで約 100 MiB）を書き直すと分単位になりうる。上限を設ければ、全体の書き直しは起きない。pack の数は「全体の大きさ ÷ 64 MiB」と、段階の数（対数）の和までに収まる。
- 到達できるかどうかは調べない。オブジェクトは 1 つも捨てない（今の `Repack` と同じ）。退避用の参照や作業中のオブジェクトを消す危険がなく、到達を調べる重い処理も要らない。
- 書き方は今の `writePack` と同じ: 一時ファイルの名前を控え、失敗したら消す。idx を最後に置く。読み取り専用にする。
- 古い pack と、まとめたゆるいオブジェクトは、新しい pack の idx を置いてから消す。Windows で開いているファイルを消せなかったときは残し、次の統合で消す。残った古い pack は中身が新しい pack と重なるだけで、読みには害がない。
- 今の `Repo.Repack`（ゆるいオブジェクトだけをまとめる）は `Consolidate` に置き換える。

### 5.2 いつ行うか

- 今と同じく同期の最後（push の後）。同期は `sync.lock`（その機械の同期どうしを順番に並べるロック）の中で動き、Store の書き込みのロックは取らない。今の `Repack` も同じ。統合が長引いても止まるのは次の同期だけで、書き込みは止まらない。
- 書き込みと並んで動いてよい。まとめる対象は、始めに選んだ pack とゆるいオブジェクトだけで、その後に書かれたものには触れない。ゆるいオブジェクトは go-git が一時ファイルから rename して置くので、見えたものは書き終わっている。
- きっかけは「ゆるいオブジェクトが 6,700 個を超えた」（今と同じ）か「対象になる pack（64 MiB 未満）が 16 個を超えた」とき。
- 失敗しても今と同じく `Result.Warnings` に入れる。
- ほかのハンドル（サーバーと CLI が同時に開いているときなど）がオブジェクトを見失ったら、今ある開き直し（`mount.Mounted.With`）で回復する。古い pack を消した後に、この経路で回復することをテストで確かめる。

## 6. 確かめ方

### 6.1 正しさ（通常のテスト。CI に含める）

- 履歴の索引の意味: 通常のコミット、マージ（どの親とも違う／片方を取っただけ）、親のないコミット、コメントと作業記録の変更、タスク以外のファイル。
- 増分の更新: 同期のマージで相手側のコミットが入る、HEAD が巻き戻る、履歴が書き換わる（作り直す）、索引のファイルが壊れている・版が違う（作り直す）、2 つのハンドルが交互に書く。
- 突き合わせのプロパティテスト: ランダムにマージを含む履歴を作り、索引の答えと、索引を使わずに全部たどる素直な実装（今の `LastChange` の意味に、2.3 の同じ時刻の規則を合わせたもの）の答えが一致することを確かめる。同じ秒のコミットが並ぶ履歴も作る。索引を一度に作った場合と、少しずつ増分で足した場合の両方で確かめる。今あるマージのプロパティテストと同じ形。
- 各箇所の出力: `log <id>`、`show`、Store 全体の `log -n`（新しい順の N 件、マージを含む履歴）、`log --workspace`、人の一覧、`mv --store` の再開、転送ファイルの元の ID、同期の修復の作者、GUI のタスク履歴の API。今の golden テストを更新する。
- 最初の作成の進みの表示（1 秒を超えたときだけ、stderr）。
- 途中で止める読み方: `undo`・`restore --at` の結果が今と同じであること。
- pack の統合: しきい値、段階の選び方、64 MiB 以上の pack に触れないこと、統合の間に書かれたオブジェクトが残ること、途中の失敗で一時ファイルが残らないこと、統合後に全オブジェクトが読めること（Verify）、古い pack を消した後にほかのハンドルが開き直せること。

### 6.2 速さ（`make` のターゲット。CI に含めない）

- Go で 10 万コミット・5,000 タスク（マージを含む）の Store を合成し、次を測る。go-git で 1 コミットずつ作ると合成だけで長くかかるので、合成した Store は条件（コミット数・タスク数・乱数の種）ごとに手元に置いて使い回す。
- 目標: `show` 200ms、`log <id>` の全件 1 秒、`undo` 200ms、`restore --at` 1 秒、索引の読み込みと 1 回の引き 50ms、普段の pack の統合 1 秒。
- `show` は、索引が最新のときと、HEAD が 1 つ進んだ直後（増分の更新と索引の保存を含む）の両方を測る。書き込みのたびに起きるのは後者。保存で 200ms を超えるなら、索引のファイルを追記できる形にする。
- 記録だけするもの: 索引の最初の作成、64 MiB 近くまでまとめる統合、索引のファイルの大きさ。
- 結果は本 spec の末尾に「計測の結果」として足す。

## 7. 親設計への反映

- 「インデックス」の節に、履歴の索引（置き場所、中身、更新、作り直し）を足す。
- フェーズ7の完了条件（性能目標）に、2 の速さの目標と 10 万コミットの規模を足す。
- 「同期」の節に、pack の段階的な統合と remote 側を対象外とすることを足す。
- spec の承認後、plan を書く前に反映する。

測り方と読み方:

- 各項目は、コピーした Store に対して毎回新しい `ops.Session` を作って呼ぶ（Store のハンドルも開き直すので、go-git が読んだものは持ち越さない）。書き込みを伴う `undo`・`restore --at`・「1 つ進んだ直後」は、毎回コピーし直した Store で測る。タスクの索引と履歴の索引は、測る前に作ってある。
- 古いタスクは `ME-1`、新しいタスクは `ME-4999`。`undo` の自分のコミットは、アカウント alice の編集を 100 件前に置き、それより新しい 99 件は bob と carol のものにした。取り消すものがない場合は、コミットのないアカウントで測った。
- 目標に届かなかった 3 項目の共通の原因は、履歴の索引の外にある。新しいプロセスが最初に go-git でオブジェクトを 1 つ読むとき、約 60 万個ある pack の索引（`.idx`）の読み込みに 150ms かかる（`gitrepo.Open` の直後に最初のコミットを読む時間を別に測った。3 回とも 148〜152ms）。`show` の 161ms は、ほぼこの時間である。`undo` は、これに加えて書き込みの 200ms 前後（go-git が約 1 万個のファイルを持つ git の index から tree を組み立てる約 100ms を含む）がかかる。`restore --at` は、指定の時刻まで first-parent を 5 万件ほどたどる。
- 参考: タスクをすべて最上位に置いた Store（兄弟が 5,000 件）では、書き込みのたびに兄弟を読むため、`undo` は 685ms だった。階層のない Store を合成したときの値で、上の値は階層を付けた Store のもの。
- 索引の読み込みは、コミットの文字列を番号で持たせ、hash の引き（`byHash`）を使うときまで作らないことで、フォーマットを変えずに 40〜50ms から 11〜13ms にした。
