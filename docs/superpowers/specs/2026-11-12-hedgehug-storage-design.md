# hedgehug 設計: Store の保存形式と技術構成

この文書は、機能仕様 01〜08(`2026-11-11-hedgehug-functional-spec/`)が「次の段階」に回した、データの保存形式と技術構成を定める。利用者から見た振る舞いは 01〜08 に従う。CLI の仕様はここでは扱わない。仕様の参照は、行番号ではなく節の名前で書く(例: 06「同期のエラー」)。

## 前提として決めたこと(2026-11-12)

- 技術構成は現行の組み合わせ(Go + go-git + huma + cobra、Svelte 5 + Vite、OpenAPI と orval)を使う。コードは 1 から書く。
- 現行の format 4 の Store は引き継がない。変換の機能は作らない。
- Store のファイルは、GitHub 上で人が読める形にする。
- 構成は、このマシンで動くサーバーと、それをトークン付きの URL で開くブラウザの画面である(08「サーバーに接続できない画面とトークンのない画面」)。
- git はアプリに組み込む(go-git)。git を入れていない・設定していない人も使える(01)。
- 利用者の 1 回の操作を 1 コミットにする。履歴は書き換えない(01・08)。

## 保存形式の考え方

エンティティ(Store の設定、メンバー、ワークスペース、プロジェクト、アイテム)ごとにフォルダを 1 つ持ち、次の 2 種類のファイルを置く。

| ファイル | 役割 |
|---|---|
| `log.jsonl` | **正本**。1 行が 1 つの変更(変更記録)。追記だけで、行は書き換えも削除もしない(完全に削除するときを除く。「削除・復元・完全に削除」) |
| `*.yaml` | **読む用**。`log.jsonl` を頭から適用した、いまの値。GitHub 上で読むためのもので、hedgehug は書くたびに `log.jsonl` から作り直す |

アイテムとプロジェクトの説明だけは、`description.md` に本文をそのまま置き、git の 3 方向の行マージで合わせる(06「同時に編集したとき」)。

この形にした理由は次の 2 つである。

- アイテムやプロジェクトを別の Store へ移すと、履歴も一緒に移る(02「移すもの」・02「名前の変更・移動・削除」・03「別の Store へ移動」)。git の履歴は移動先に引き継がれない(03「別の Store へ移動」の冒頭)ので、履歴は Store の中身として持つ必要がある。`log.jsonl` はフォルダごと写せば移る。
- 同時に変えたときの勝ち負けは、項目ごとに最後に保存した時刻で決める(06「同時に編集したとき」)。`log.jsonl` の 1 行が 1 項目の 1 回の変更なので、項目ごとの時刻がそのまま残る。

`*.yaml` を GitHub 上で直接書き換えても、hedgehug は読まず、次の保存で `log.jsonl` から作り直す。書き換えは消える。

## ファイル構成

```
.hedgehug/
  store.yaml            Store であることの目印。Store ID・形式の版
  log.jsonl             保持日数の変更
members/
  members.yaml
  log.jsonl
workspaces/<WS の内部 ID>/
  workspace.yaml        名前・接頭辞・プロパティ・値・ワークフロー・テンプレート・自動化・プロジェクト別のルール・スプリント・リリース
  log.jsonl
projects/<プロジェクトの内部 ID>/
  project.yaml
  description.md
  log.jsonl
items/<アイテムの内部 ID>/
  item.yaml             コメントと作業時間も含む
  description.md
  log.jsonl
transfers.jsonl         転送記録(追記だけ)
purged.jsonl            完全に削除したものの記録(追記だけ)
```

- フォルダの名前は内部 ID で決める。番号の振り直し、接頭辞の変更、親やワークスペースの変更でファイルの場所は変わらない。どのワークスペースに属するかは、ファイルの中の値で持つ。
- コメントと作業時間は、アイテム(プロジェクト)の `log.jsonl` に行として持ち、`item.yaml`(`project.yaml`)に一覧として書き出す。
- プロジェクト別のルール(使わないステータス・遷移の制約・使うテンプレート・種類ごとの既定のテンプレート・動かさないルールの指定・専用ルール)は、ワークスペースの設定の一部なので、ワークスペースの `log.jsonl` に持つ。プロジェクトの内部 ID で結びつけ、プロジェクトのフォルダには置かない(03「プロジェクト別のルール」、06「同時に編集したとき」)。
- 内部 ID は、エンティティ、ステータスなどの値、プロパティ、テンプレート、自動化のルール、スプリント、リリース、コメント、作業時間、変更記録、操作のすべてで ULID とする(01「用語と階層」の「内部の ID」)。
- 時刻は、ミリ秒までの RFC 3339 で、このマシンの時刻帯を付けて書く(例: `2026-11-12T10:03:21.512+09:00`)。比べるときは UTC に直して比べる。

### `.hedgehug/store.yaml`

```yaml
store: 01JC8X4Q2M6Z7H3R9V0T5N1KQB   # Store ID。作ったときに決め、変えない
format: 1
retention_days: 30                  # log.jsonl から作り直す
```

- このファイルがあるリポジトリを hedgehug の Store とする。ワークスペースが 0 件でも、すべて削除済みでも Store である(08「追加」)。
- 新しく作る Store と、空のリポジトリを clone する Store は、最初のコミットで `store.yaml` を書く。このコミットは保存ではないので `Hedgehug-Op` を持たず、アクティビティに出ない。続けて 1 回の保存で、「あなた」のメンバーへの追加(01)と、Store の追加ダイアログで入れた名前と接頭辞(どちらも必須。08「追加」)の最初のワークスペースの作成を書く。hedgehug のデータがあるリポジトリと閲覧のみの Store では、ワークスペースを作らない。
- 新しく作る Store のブランチは `main` にする(GitHub の既定に合わせる。2026-11-12 決定)。
- `format` がこの hedgehug の知らない新しい版のときは、Store を開かない(「仕様 01〜08 へ反映する点」の 2)。

値を内部 ID で指すのは、値の名前を変えてもアイテムの値が変わらないためである(03「値の編集」の「名前」)。人が読めるように、名前と表示の ID を行末のコメントに書き添える。

`*.yaml` は、自分の `log.jsonl` と、ワークスペース・プロジェクト・メンバーの定義から作る。値・プロパティ・ワークスペース・スプリント・リリースの名前、接頭辞、プロジェクトのタイトル、メンバーの表示名を変える保存では、それを書き添えているすべての `*.yaml` を同じコミットで作り直す。同期でも、合わせたあとに、入力が変わったすべての `*.yaml` を作り直す。このため、行末のコメントが古くなることはなく、どのマシンで作っても同じ中身になる。

`items/01JF3KQ8W2…/log.jsonl` に、ステータスを Todo から InProgress に変えた行が 1 行足される。

```json
{"id":"01JH7Q…","op":"01JH7Q…","at":"2026-11-12T10:03:21.512+09:00","by":"taro","actor":"user","t":"set","f":"status","from":"01JD…S1","to":"01JD…S3","prev":["01JF3KQ8…"]}
```

このときのコミットは次のとおりである。

```
HH-12 のステータスを InProgress に変更

Hedgehug-Op: 01JH7Q…
```

作者とコミッターは `taro <taro@hedgehug.invalid>` である(01「「あなた」の決まり方」)。件名は git の履歴を人が読むためのものである。アクティビティの文は、件名ではなく、そのコミットで足された変更記録から作る。

## 変更記録(`log.jsonl` の 1 行)

| キー | 中身 |
|---|---|
| `id` | 変更記録の内部 ID(ULID) |
| `op` | 操作の ID。1 回の操作(1 コミット)で書いた行は、Store をまたいでも同じ値を持つ。削除の復元(08「復元の単位」)と、アクティビティのまとめに使う |
| `at` | 保存した時刻(このマシンの時計。補正しない。06「時計のずれの警告」) |
| `by` | 操作した人のログイン名。人でない実行者の行は `hedgehug[bot]`。自動化の行は、きっかけになった操作をした人 |
| `actor` | 実行者の種類。`user`・`automation:<ルールの内部 ID>`・`github`・`sync`・`none` のどれか。診断の修復と、remote の履歴へののせ直しは `user`(08「結果の表示と修復」「remote の履歴が書き換えられたとき」) |
| `t` | 変更の種類(下の表) |
| `f` | 項目。`status`、`fields/<プロパティの内部 ID>`、`statuses/<値の内部 ID>/name` のように、1 つの値ごとに 1 つ(06「同時に編集したとき」) |
| `from`・`to` | 変更前と変更後の値 |
| `prev` | この項目で、書いた時点に先端だった変更記録の `id` のすべて(勝っていたものだけでなく、負けていた同時の変更も含む)。作成なら空 |
| `root` | `delete` の行だけに付ける。利用者が直接削除したものなら `true`、親と一緒に削除されたもの(02「削除」)なら `false` |

| `t` | 意味 |
|---|---|
| `create` | 作成。作成時の値をすべて `to` に持つ |
| `set` | 値を 1 つ持つ項目の変更。場所(`place`: 親・プロジェクト・ワークスペース・番号をまとめた 1 項目)と順位(`rank`)も含む |
| `add`・`remove` | 値を複数持つ項目への、値 1 つの追加と取り除き(関連システム、複数選択のプロパティ、関連、ウォッチ中の人、PR・Issue のリンク、解除した PR の記録、プロジェクトのリポジトリ、ワークフローの遷移、プロジェクト別のルールの使わないステータス・遷移のチェック(From と To の組ごと)・使うテンプレート・動かさないルールの指定)。リンクの値は「種別・リポジトリ・番号」で、タイトル・状態・レビューは `set` の項目 `links/<種別:リポジトリ#番号>/state` などで持つ。リンクの検出元は保存しない(07) |
| `desc` | 説明を保存した(履歴の「説明の変更」。本文は `description.md`) |
| `comment`・`worklog` | コメントと作業時間の追加・編集・削除。`f` はコメント(作業時間)の内部 ID |
| `delete`・`restore` | 削除と復元。`restore` は戻す削除の `op` を持つ |
| `moved_in` | 別の Store から移ってきた。旧 ID・移動元の Store・ワークスペース・プロジェクト・移した日時を持つ。写した行が指す値・プロパティの内部 ID と、移した時点のその名前の対応(`names`)も持つ |
| `number` | ワークスペースで番号を使った(アイテム用・プロジェクト用)。使った最大番号を作り直すのに使う |
| `close_sprint` | スプリントの完了。確定値(ポイントと件数の、計画と実績)を持つ(05「完了」) |

### いまの値の決め方(`log.jsonl` から `*.yaml` を作る)

項目ごとに、次の順で決める。どのマシンで作っても、行の並びに関わらず同じ結果になる。

0. 検査に合わない行(値の形が違う、接頭辞が空、または接頭辞の文字が使えないなど。GitHub 上で手で書き換えたときに起きる)は、無いものとして扱う。接頭辞の行がこれに当たれば、前の値に戻る(同期で書き戻す修復は持たない)。
1. その項目の行を、`prev` でつないだグラフにする。
2. ほかの行の `prev` に挙がっていない行(先端)が 1 つなら、その値を取る。書いた時点の先端をすべて `prev` に挙げるので、あとから見て書いた変更は、見えていたどの変更にも必ず勝つ(06 の「片方しか変えていない項目は、変えたほうの値を取る」)。時計がずれていても、この順は崩れない。例: A と B が同時に書いて B が勝ち、そのあと C が両方を見て書けば、C の `prev` は A と B の両方なので、C の時計が遅れていても C が勝つ。
3. 先端が 2 つ以上なら、同時の変更である。`at` のあとの行、同じなら `by` を小文字にして辞書順であとの行、それも同じなら `id` の辞書順であとの行が勝つ(06「同時に編集したとき」の後勝ち。最後の決め手は「仕様 01〜08 へ反映する点」の 1)。

`add`・`remove` も、値 1 つごとに同じ手順で決める。一方が足し、他方が取り除いたときは、その値について後勝ちになる(06「同時に編集したとき」の表)。解除した PR の記録も、特別扱いせず、この規則で合わせる(07「解除」)。

使わないステータスを断るのは、利用者の操作のときだけである(03「使うステータス」)。手順 0 の検査には含めず、同期・修復・値の置き換え・移動が書いた使わないステータスの値は、そのまま取る。

## 同期

1. remote を fetch する。同じ remote から前に受け取った先端(下の「このマシンに持つもの」)があり、fetch した先端がその続きでなければ、remote の履歴が書き換えられたとして、合わせずに止める(下の「remote の履歴が書き換えられたとき」)。
2. 自分の先端と remote の先端の、共通の祖先(merge base)を求める。共通の祖先がなく、remote が空でなければ、合わせずに断る。remote が空なら、最初の送信として認める(06「同期のエラー」)。
3. ファイルごとに合わせる。
   - `log.jsonl`、`transfers.jsonl`、`purged.jsonl`: 両方の行を `id` で重ねずに合わせ、`at`・`id` の順に並べて書く。`purged.jsonl` に載っているスプリント・リリース・プロジェクト別のルールの行は、合わせたあとに取り除く(完全に削除したときに取り除いた行が、もう一方から戻らないようにする)。
   - `description.md`: 共通の祖先の版を基準に、行ごとの 3 方向マージを行う。同じ行を両方が変えたときは、両方の版を `-----` の行ではさんで残す。保存の古い版を先にする(06)。
   - `*.yaml`: 合わせた `log.jsonl` から作り直す。
   - 片方だけがフォルダを消していたら、消したほうを取る。完全な削除(06「完全な削除と重なったとき」)と、別の Store への移動(06「別の Store へ移動したものと重なったとき」。移動の保存が勝つだけで、修復の保存は要らない)が、これに当たる。どちらだったかは `purged.jsonl` と `transfers.jsonl` で見分け、変更が反映されなかった人の通知の文を選ぶ。
   - 別の Store へ移ったアイテム・プロジェクト・ワークスペースの下に、他方が作ったフォルダがあれば(祖先が `transfers.jsonl` にあり、そのフォルダがない)、その下のフォルダも消す。子は反映されない(06 の同じ節)。
4. 下の「同期の修復」を行う。
5. 結果を、2 つの親を持つマージのコミットにする。このコミットは保存ではないので、アクティビティに出さない(01「書き込みの単位」)。修復があれば、マージのあとに、`actor: sync` の別のコミットとして保存する。
6. push する。拒否されたら、1 から最大 3 回やり直す(06「同期のエラー」)。
7. remote への同期が成功したら、ミラーにも push する。送るだけで、ミラーからは受け取らない。Store の「GitHub に使うアカウント」で送り、履歴は書き換えない(強制 push をしない)。空のミラーには最初の送信として送る。空でなく、共通の祖先がないミラーと、ミラーにだけある保存があるミラーには送らない。ミラーに送れなくても、Store の状態は変えず、同期の成功は変わらない。結果はミラーごとに、このマシンの状態に持つ(06「同期のエラー」のミラーの段落)。

「上書き」の通知は、同期を受け取ったマシンが手順 3 の結果から作る。自分の行が、項目の先端どうしの比べ合いで負けたら、上書きの通知を作る(06 の「あなたの値が負けたとき」)。

### 同期の修復

修復は、共通の祖先と、合わせたあとの状態から決める。同期する 2 つの先端が同じなら、どのマシンが行っても同じ値になる(06「修復の決まり」)。複数のマシンが同じ修復の行を書いても、値が同じなので結果は変わらない。アクティビティでは 1 行にまとめる(下の「アクティビティと履歴」)。

複数の修復が要るときの順は、06「修復の決まり」で決まっている。表の上から順に並べ、番号がその順である((1)から(9))。06 が順を決めていない 5 つの修復(表の最後)は、(1)の前に、表の上から順に行う。

修復を保存するのは、Store に書き込めるマシンだけである。閲覧のみの Store では保存しない(06「修復の決まり」)。

| 06 の規則と順 | 見つけ方 | 書く行 |
|---|---|---|
| (1) 完全な削除・別の Store への移動と重なった(06「完全な削除と重なったとき」「別の Store へ移動したものと重なったとき」) | 合わせたあとに、祖先(親・プロジェクト・ワークスペース)のフォルダがないアイテムがある。`purged.jsonl` にある相手への関連がある。別の Store へ移ったものの下に作られたフォルダは、手順 3 で消えている | 祖先が `purged.jsonl` にあるときは、そのアイテムのフォルダを消し、`purged.jsonl` に足す。関連は `remove`。移動した相手には、修復の保存を書かない(手順 3 のとおり) |
| (2) 親が削除された(06「親が削除されたとき」) | 削除済みの親(アイテム・プロジェクト・ワークスペース)の下に、削除されていない子がある(子への変更や追加と、親の削除が同時だった) | 子に `root: false` の `delete`(`op` は親の削除と同じ。親を復元すれば一緒に戻る) |
| (3) 番号が重なった(06「番号の重なりの修復」) | 同じワークスペースで、アイテムの `place` の番号、またはプロジェクトの番号が同じ。作成のコミットが remote の先端から辿れる方が番号を残す。両方辿れるなら、`create` の `at` が古い方 | 残さない方に `set`(アイテムは `place`。次の空き番号) |
| (4) 親が循環した(06「親が循環したとき」) | 削除されていないアイテムで、親をたどると自分に戻る輪がある。輪が複数あれば 1 つずつ、なくなるまで繰り返す。輪に入っていたもののうち、親が種類の規則(01)に合わないものも対象にする | 輪の中で番号が最も大きいアイテム(同じなら内部 ID の辞書順があと)に、08「親がない」の修復を書く。`set place` と `set rank` で、アイテムが覚えているプロジェクトの、ツリーの並び順(04)で先頭の Epic(削除済みを除く)の下の末尾へ動かす。Step は `set kind` で Task にする。Epic がなければ「修復で作った Epic」を `create` する。内部 ID は、プロジェクトの内部 ID から決まる値にして、どのマシンでも同じにする。プロジェクトが分からないとき(完全に削除されている)は直さない |
| (5) 親と別のワークスペース・プロジェクトにある子(06「親と別のワークスペース・プロジェクトにある子」) | 削除されていない子の `workspace` か `project` が、親と違う。子の下のものは、親から順に同じに扱う | プロジェクトだけが違うとき: `set place`(番号は変えない)。ステータスが移動先のプロジェクトで使わないものなら、`set status` で同じ分類の移動先の既定のステータスにする。ワークスペースが違うとき: 下の「移動・番号・旧 ID」の、同じ Store の別のワークスペースへの移動と同じ行を書く(番号は移動先の次の番号。旧い番号の小さい順、同じなら内部 ID の辞書順。ステータスは同じ分類の移動先の既定。スプリントとリリースは外す)。`transfers.jsonl` に 1 行足す。親が別の Store へ移ったときは(1)のとおり |
| (6) 存在しないスプリント・リリース(06「存在しないスプリント・リリースを指すとき」) | アイテムの `sprint` か `release` が、完全に削除された(`purged.jsonl`)・定義がない・アイテムのワークスペースのものでない。削除済み(論理削除)のものは存在するものとして扱い、対象にしない(復元で戻る。05)。アーカイブのリリースと削除済みのアイテムも対象にしない | `set sprint`(バックログ)、`set release`(なし) |
| (7) なくなったプロジェクトのプロジェクト別のルール(06「プロジェクトがなくなったときのルール」) | ワークスペースの `log.jsonl` に、持ち主のプロジェクトがそのワークスペースにない(別のワークスペースへ移された、または完全に削除された)プロジェクト別のルールと専用ルールがある。削除済みのプロジェクトは対象にしない | そのプロジェクト別のルールを `remove`、専用ルールを `delete` |
| (8) 削除された値を指すプロジェクト別のルール・既定のテンプレート・自動化(06「削除された値を指すプロジェクト別のルール」) | 値(ステータス・テンプレート)に `delete` があり、それをプロジェクト別のルール、ワークスペースの種類ごとの既定のテンプレート、ルール(ワークスペース全体と専用)のきっかけ・することが指している。値の削除は取り消さない | 使わないステータス・遷移のチェック(その行、またはその許可先)・使うテンプレートは `remove`、種類ごとの既定のテンプレートは `set`(なし)、ルールは `set` で無効にする。使うテンプレートが空になれば限定を外す |
| (9) 1 つしかないものが 2 つ(06「1 つしかないものが 2 つになったとき」) | 名前(ワークスペース・プロジェクト・プロパティ・値・テンプレート・ルール・スプリント・リリース)・接頭辞・プロパティのキー・Issue のリンク・メンバーの重なり。あとから同期した方(番号の重なりと同じ決め方)を直す | 06 の同じ節の表のとおりの `set`・`remove`。名前は末尾に「 (2)」、接頭辞は末尾に数字(WEB → WEB2。10 文字を超えるときは末尾を削る。旧い接頭辞は `prefix` の過去の値に残る)、キーは末尾に数字 |
| 順の指定なし: 削除と変更が重なった(06「同時に編集したとき」の表の最後の行) | 共通の祖先にない `root: true` の `delete` と、同じエンティティの共通の祖先にない変更が、別々の側にある。`root: false`(親と一緒の削除)は対象にしない(上の(2)の行)。プロジェクト別のルールはワークスペースの行なので、プロジェクトへの変更に数えない(プロジェクトの削除と重なっても、削除は取り消さない) | その削除の `op` 全体の `restore`。一緒に削除された子も戻る(08「復元の単位」と同じ) |
| 順の指定なし: 実行中のスプリントが 2 つ(06「スプリントの実行中が 2 つになったとき」) | 開始日、開始の `at`、開始した人のログイン名、開始の変更記録の `id` の順で比べる | 先頭以外に `set` で計画中 |
| 順の指定なし: 削除された値を指す設定(06「削除された値を指す設定」) | 初期ステータス・分類ごとの既定のステータス・初期優先度にした値に `delete` がある。ある分類のステータスが 0 個になる削除がある | 値の `restore`(分類が 0 個になるときは、あとから同期した方の削除) |
| 順の指定なし: 完了・中止の初期ステータス(06「完了・中止の分類にされた初期ステータス」) | 初期ステータスの値の分類が完了・中止 | 初期ステータスの `set`(未着手の既定のステータス) |
| 順の指定なし: 完了したスプリントに入った(06「完了したスプリントにアイテムが入ったとき」) | 完了したスプリントに、未完了のアイテムがある | `set sprint`(バックログ) |

直さないもの: プロジェクトが「使わない」にしたステータスを、別の人が初期ステータスや既定にしたときは、どちらの行も残し、使うものとして扱う(06「外された初期ステータス・既定のステータス」。手順 0・2・3 の結果をそのまま使う)。接頭辞の書き戻しと、消えたワークスペースの書き戻しは持たない(「復活・残すと決めた現行機能の置き場所」)。

同期で直しきれずに残ったものは、診断(08)が同じ直し方で直す。

### remote の履歴が書き換えられたとき

利用者が git で remote の履歴を書き換えたとき(巻き戻しを含む)の扱いである(06「同期のエラー」・08「remote の履歴が書き換えられたとき」)。hedgehug 自身は remote にもミラーにも強制 push をしない。

- **見つけ方**: `state.db` に、Store ごとに、同じ remote から前に受け取った先端を持つ。fetch した先端がその続きでなければ、同期を止める。Store は変えず、未送信の保存はそのまま残る。remote が元に戻って続きに戻れば、次の同期でそのまま再開する。remote を付け替えたとき(違うリポジトリになったとき)、remote を空にしたとき、Store を追加した(clone・フォルダから取り込み)ときは、この先端を持たず、同期の手順 2 の共通の祖先の検査だけを行う。SSH と HTTPS のような同じ remote の書き方の違いでは捨てない。
- **「remote の履歴にそろえる」**(利用者が押したときだけ。閲覧のみの Store でも使える):
  1. 同期で受け取った、書き換えられた remote の履歴を、このマシンの履歴にする。
  2. 未送信の保存(前に受け取った先端から、このマシンの先端まで)の変更記録を、「同期」の手順 3 と同じ合わせ方で、新しい履歴の上にのせる。共通の祖先は、前に受け取った先端である。行の `id`・`at`・`prev` は変えないので、項目ごとの時刻は元のままである。新しい履歴にないエンティティは、完全な削除と重なったときと同じに扱い、そのものへの未送信の変更と、そのものの下に作った未送信のアイテムは、のせ直さない(のせ直せなかった変更の内容は、受信箱の「同期の修復」に出す。通知はこのマシンの状態に持つ)。
  3. のせ直した行は、1 つのコミットにまとめる。作者は「あなた」、各行の `actor` はもとのまま、`Hedgehug-Op` は新しい値、件名は「remote の履歴にそろえ、未送信の保存 N 件をのせ直し」とする。行の `op` は元のままなので、アクティビティの 1 行は、この件名から作る。未送信の保存がなければ、コミットを作らない。閲覧のみの Store では、コミットを作らず、履歴だけを置き換える。
  4. このマシンの古い履歴は残さない。古い先端への参照を捨て、到達できなくなったものは取り除く。途中で止まったときは、参照を付け替える前の状態に戻す。
  5. 続けて、通常の同期を行う。
- **通知を作り直さない**: 通知を判定した保存の記録(下の「このマシンに持つもの」)は、書き換えのあとは、作者・時刻・`Hedgehug-Op` が前の履歴と同じ保存を、同じ保存として照合する(06「通知」)。

## 削除・復元・完全に削除

- **削除**(論理削除): `delete` の行を書く。下にあるものにも、同じ `op` で `delete` を書く(02「削除」・03「削除」)。削除した日時は、その行の `at` である。別の Store へ移しても、行ごと移るので元の日時が残る(03「別の Store へ移動」)。プロジェクトを削除しても、プロジェクト別のルールと専用ルールは削除しない(復元で働く)。
- **スプリント・リリースの削除**: 入っていたアイテムに、同じ `op` で `set sprint`(`set release`)を書く(05「削除」)。削除済みのアイテムの参照は変えない。
- **復元**: 戻す削除の `op` を持つ `restore` を書く。値は、その `op` の行の `from` から戻す。そのあと別の操作でスプリントに入れたアイテムは、`prev` のグラフで、その `op` の行が先端でなくなっているので戻さない(08「復元の単位」)。アイテムを戻すときに、入っていたスプリントが完了済み(アイテムの分類が未着手か進行中のとき)・削除済み・存在しないなら `set sprint`(バックログ)、リリースが削除済み・存在しないなら `set release`(なし)を、同じ `op` で書く(08 の同じ節)。
- **完全に削除**: エンティティのフォルダ(下にあるもののフォルダを含む)を消し、`purged.jsonl` に 1 行足す。ワークスペースの `log.jsonl` の中にあるもの(スプリント・リリース・プロジェクト別のルール・専用ルール)は、その行を `log.jsonl` から取り除いて書き直す。プロジェクトを完全に削除するときは、そのプロジェクト別のルールと専用ルールも、同じ保存で取り除く。git の履歴は書き換えない(08「完全に削除」)。消したものを相手にした関連は、同じ保存で `remove` する。完全に削除するスプリント・リリースを指すアイテムの参照は、同じ保存で `set sprint`(`set release`)で外す(08 の同じ節)。

```json
{"id":"01JK…","at":"2026-12-12T00:00:05.000+09:00","by":"hedgehug[bot]","actor":"none","entity":"item","target":"01JF3KQ8W2…","display":"HH-12"}
```

`entity` は `item`・`project`・`workspace`・`sprint`・`release` のどれかで、プロジェクト別のルール・専用ルールは持たない。`purged.jsonl` は、旧 ID から辿ったときに「完全に削除されました」と言い分けるため(02「関連・転送記録・旧 ID」)と、診断でプロジェクトが分からないことを見分けるため(08「診断と修復」の「親がない」)と、同期の修復(上の表の(1)・(6))に使う。

## 移動・番号・旧 ID

- **同じワークスペースの中**: `set place` と `set rank` を同じ操作で書く(06「同時に編集したとき」)。プロジェクトが変わるときは、移動先のプロジェクトが使わないステータスを、確認ダイアログの「ステータスの置き換え」で選ばせ、`set status` で書く(02。置き換えるものがなければ書かない)。
- **別のワークスペース(同じ Store)**: 内部 ID は変わらない。`set place` で番号を振り直し、`transfers.jsonl` に 1 行足す(02「別のワークスペースと別の Store への移動」)。値は、02「値の引き直し」のとおり、移動先のワークスペースの値の内部 ID に `set` で書き直す(ステータスは、「ステータスの置き換え」で選んだ値。ダイアログを出せない同期の修復では、同じ分類の移動先の既定)。スプリントとリリースは `set` で外す。プロジェクトを移すときは、プロジェクトの `set place` と、プロジェクト別のルールの移動を同じ操作で書く。移動元の分は `remove`・`delete`、移動先の同じ名前のステータス・テンプレートに合うものは `add`・`set`、専用ルールは移動先で `create` する。専用ルールが使うステータスは、選んだ値に `set` で書き換える(削除も無効化もしない)。
- **別の Store**: 移動先にフォルダを写し、`moved_in` の行を足す。移動元はフォルダを消し、`transfers.jsonl` に 1 行足す(02「保存」の順で、Store ごとに 1 コミット)。移動先では、現在の値を、同じ操作の `set` で移動先の値の内部 ID に書き直す(値の決め方は上と同じ)。

```json
{"id":"01JM…","op":"01JM…","at":"2026-11-12T11:00:00.000+09:00","by":"taro","target":"01JF3KQ8W2…","old":"HH-12","new":"WEB-31","to_store":"01JC9…","to_store_name":"team-b","to_remote":"https://github.com/org/team-b"}
```

- 転送記録の「移動先の Store 名」(02「関連・転送記録・旧 ID」)は、移した人のマシンでの名前を `to_store_name` に残す。表示するときは、`to_store` の Store がこのマシンにあればこのマシンでの名前を出し、なければ `to_store_name` を出す。Store の名前はマシンごとのもの(08「追加」の保存先、08「名前の変更」)だからである。
- **使った最大番号**: 番号を振るたびに、ワークスペースの `log.jsonl` に `number` の行を書く。値は行の最大値で決めるので、同時に振っても小さくならない。移したり完全に削除したりしても番号は使い回さない(02「移すもの」)。
- **旧い接頭辞**: ワークスペースの `log.jsonl` に残る、`prefix` の過去の値すべてである。別に記録は持たない(03「接頭辞」)。接頭辞はすべてのワークスペースが持ち、空にはできない。

## アクティビティと履歴

- **アクティビティ**: 保存のコミット 1 つが 1 行である(06「アクティビティ」の「対象」)。行の文・実行者・対象・ワークスペースは、そのコミットで足された変更記録のうち、`op` がコミットの `Hedgehug-Op` と同じものから作る。別の Store から移したときに写した古い行は、`op` が違うので使わない。remote の履歴にそろえたときののせ直しは、上の「remote の履歴が書き換えられたとき」のとおり件名から作る。マージのコミットは出さない。同期の行はコミットではないので、マシン側に記録する(06 の同じ節)。
- **人でない実行者の同じ変更**(06「アクティビティ」の「対象」): `actor` が `user` でなく、対象・項目・`from`・`to` が同じ変更記録を持つコミットが複数あるときは、`at` が最も早いコミットの 1 行だけを出す。
- **移したワークスペースの記録**(06「アクティビティ」の「絞り込み」): 移動元の Store にないワークスペースの内部 ID を指す行は、ワークスペースの絞り込みの選択肢に出さず、「すべて」でだけ出す。
- **アイテム・プロジェクトの履歴**(02「履歴」): その `log.jsonl` の行から作る。履歴に出さない種類(コメント・関連・リンクの追加と解除・作業時間・ウォッチ・削除)は除く。ただし、GitHub から取り直したリンクの状態・タイトル・レビューの `set` と、PR の自動リンクの `add`(`actor: github`)は、履歴に出す(02 の同じ節)。値の名前は、その行を書いたときに属していたワークスペースの定義で引く。そのワークスペースがこの Store にない(別の Store から移ってきた)ときは、`moved_in` の `names` で引く。どちらにもない値は「(削除された値)」と出す(01「画面の移り方と、共通の表示」)。
- **レポート**(05): スプリントの出入りの日は `set sprint` の行、ステータスが変わった時刻は `set status` の行、作成の時刻は `create` の行から取る。ポイントなどの量は、いまの値を使う(05「バーンダウン」)。

## このマシンに持つもの

01 の表の右の列は、すべて Store の外に置く。

| 置き場所 | 中身 |
|---|---|
| `~/.config/hedgehug/config.yaml` | ログイン名、同期のタイミング(自動同期、書き込みのあと同期するまでの時間、GitHub を読む間隔)、Store の一覧(名前・clone の場所・remote・ミラー・アカウント・色・非表示・既定・閲覧のみの印)、アカウント(トークンを除く)、ホストごとのデバイスフローの client ID(`hosts`。前回の実装と同じ形) |
| OS のキーチェーン(go-keyring) | トークン(デバイスフローで得たものを含む。07「デバイスフロー」)。照合のために最後に確かめたトークンの指紋(07「接続のたびの照合」)は、起動後の最初の接続で必ず照合するので、サーバーのメモリにだけ持つ |
| `~/.local/share/hedgehug/stores/<Store ID>/` | Store の clone |
| `~/.local/share/hedgehug/state.db`(SQLite) | 下の 2 種類 |

`state.db` には、作り直せないものと、Store からいつでも作り直せる索引を、テーブルを分けて持つ。

- **作り直せないもの**: 通知と既読、通知を判定したコミット(06「通知」。コミットの SHA と、作者・時刻・`Hedgehug-Op` の組)、同期の結果と同期の行、ミラーごとの送信の結果(最終送信・送れなかった理由。06「同期のエラー」)、同じ remote から前に受け取った先端(Store ごと。上の「remote の履歴が書き換えられたとき」)、保存したビュー(04)、画面の状態、最近開いたアイテム(02)、WIP 上限、レポートの選択、GitHub の前回の読み取りの情報(07「GitHub を読む間隔」)、PR のチェックの結果(最後に読んだ値。保存しない。07)、GitHub App を入れていない組織(07「状態」)、時計のずれ(06「時計のずれの警告」)。
- **索引**: 検索・マイタスク・アクティビティ・履歴・レポートのための、いまの値と変更記録の写し。どの Store のどのコミットまで取り込んだかを覚え、新しいコミットの変わったファイルだけを読み足す。クエリの書き方は暫定(04「クエリ言語」)なので、索引の形は Store の形式に含めない。消しても、次に開いたとき Store から作り直す。

Store をこのマシンから削除したときは、その Store ID の行を `state.db` からすべて消す(06「通知」)。コピーを残して一覧から外したときは、コピーのフォルダは消さず、行は消す(08「このマシンから削除」)。

| git | go-git。go-git にはマージがないので、同期の合わせ方は上の「同期」のとおり自前で行う |

- **同時に書き込むとき**: Store ごとにファイルロックをかけ、1 回の操作のあいだ持つ。画面のサーバーと CLI が同じ Store に書いても、コミットは 1 つずつ順に作られる。
- **1 回の操作の途中で失敗したとき**: 作業ツリーとインデックスを、操作の前のコミットに戻す。1 つも書かなかったことになる(01「書き込みの単位」)。

## テスト

- いまの値の決め方: 同じ変更記録の集まりを、どの順で適用しても同じ `*.yaml` になることを、ファジングで確かめる。
- 同期: 06 の各規則と、モックの同期の場面(P1〜P11)を、2 つのクローンを作って再現する場面のテストにする。両方のマシンで同期した結果が、バイト単位で同じになることを確かめる。
- 時計のずれ: 先に書いた側の時計が進んでいても、あとから見て書いた変更が勝つことを確かめる。2 人の同時の変更のあとに 3 人目が両方を見て書き、3 人目の時計が最も遅れている場面を必ず含める。
- 親と一緒の削除: 親の削除と子の変更が同時なら子は削除済みのまま、親の削除と親の変更が同時なら親も子も戻ることを確かめる。
- remote の履歴にそろえる: 書き換えた remote の履歴の上に、未送信の保存が項目ごとの時刻のままのせ直されることと、新しい履歴にないものへの変更がのせ直されず通知に残ることを確かめる。ミラーには、空のミラーへの最初の送信と、ミラーにだけ保存があるときに送らないことを確かめる。

## 仕様 01〜08 へ反映する点

1. **後勝ちの最後の決め手**(06「同時に編集したとき」・05「同期で実行中が 2 つになったとき」・06「スプリントの実行中が 2 つになったとき」): 「コミットの SHA の辞書順」を「変更記録の ID の辞書順」に替える。変更記録を書いた時点では、自分のコミットの SHA が分からないためである。どのマシンでも同じ結果になる点は変わらない(2026-11-12 承認)。反映済み(06「同時に編集したとき」「スプリントの実行中が 2 つになったとき」・05、2026-11-12)。
2. **知らない形式の Store**(08 の「追加」と 06 の「同期のエラー」): `store.yaml` の `format` がこの hedgehug より新しい Store は開かない。追加のときは「{remote} は新しい版の hedgehug で作られています。hedgehug を更新してください」と断る。同期で受け取った remote が新しい形式になっていたときは、同期エラーにし、短い理由を「hedgehug を更新してください」とする。現行の実装と同じ扱いである。2026-11-12 承認、反映済み(08「追加」の検査、06「同期のエラー」)。
3. **復活と決めた機能と、仕様の食い違い**: 反映済み。同期での自動修復(親の循環ほか、親のワークスペースへの追従)は、仕様 06 が同期で直す形になった(「同期の修復」の表の(4)・(5)・(6))。
