# hedgehug 設計: Store の保存形式と技術構成

この文書は、機能仕様 01〜08(`2026-11-11-hedgehug-functional-spec/`)が「次の段階」に回した、データの保存形式と技術構成を定める。利用者から見た振る舞いは 01〜08 に従う。CLI の仕様はここでは扱わない。

## 前提として決めたこと(2026-11-12)

- 技術構成は現行の組み合わせ(Go + go-git + huma + cobra、Svelte 5 + Vite、OpenAPI と orval)を使う。コードは 1 から書く。
- 現行の format 4 の Store は引き継がない。変換の機能は作らない。
- Store のファイルは、GitHub 上で人が読める形にする。
- 構成は、このマシンで動くサーバーと、それをトークン付きの URL で開くブラウザの画面である(08 の「サーバーに接続できない画面とトークンのない画面」)。
- git はアプリに組み込む(go-git)。git を入れていない・設定していない人も使える(01)。
- 利用者の 1 回の操作を 1 コミットにする。履歴は書き換えない(01・08)。

## 保存形式の考え方

エンティティ(Store の設定、メンバー、ワークスペース、プロジェクト、アイテム)ごとにフォルダを 1 つ持ち、次の 2 種類のファイルを置く。

| ファイル | 役割 |
|---|---|
| `log.jsonl` | **正本**。1 行が 1 つの変更(変更記録)。追記だけで、行は書き換えも削除もしない |
| `*.yaml` | **読む用**。`log.jsonl` を頭から適用した、いまの値。GitHub 上で読むためのもので、hedgehug は書くたびに `log.jsonl` から作り直す |

アイテムとプロジェクトの説明だけは、`description.md` に本文をそのまま置き、git の 3 方向の行マージで合わせる(06 の「説明は行ごとに合わせる」)。

この形にした理由は次の 2 つである。

- アイテムやプロジェクトを別の Store へ移すと、履歴も一緒に移る(02:234・02:557・03:132)。git の履歴は移動先に引き継がれない(03:112)ので、履歴は Store の中身として持つ必要がある。`log.jsonl` はフォルダごと写せば移る。
- 同時に変えたときの勝ち負けは、項目ごとに最後に保存した時刻で決める(06:141)。`log.jsonl` の 1 行が 1 項目の 1 回の変更なので、項目ごとの時刻がそのまま残る。

`*.yaml` を GitHub 上で直接書き換えても、hedgehug は読まず、次の保存で `log.jsonl` から作り直す。書き換えは消える。

## ファイル構成

```
.hedgehug/
  store.yaml            Store であることの目印。Store ID・形式の版
  log.jsonl             保持日数の変更
members/
  members.yaml
  log.jsonl
workspaces/<WS の内部 ID>/
  workspace.yaml        名前・接頭辞・プロパティ・値・ワークフロー・テンプレート・自動化・スプリント・リリース
  log.jsonl
projects/<プロジェクトの内部 ID>/
  project.yaml
  description.md
  log.jsonl
items/<アイテムの内部 ID>/
  item.yaml             コメントと作業時間も含む
  description.md
  log.jsonl
transfers.jsonl         転送記録(追記だけ)
purged.jsonl            完全に削除したものの記録(追記だけ)
```

- フォルダの名前は内部 ID で決める。番号の振り直し、接頭辞の変更、親やワークスペースの変更でファイルの場所は変わらない。どのワークスペースに属するかは、ファイルの中の値で持つ。
- コメントと作業時間は、アイテム(プロジェクト)の `log.jsonl` に行として持ち、`item.yaml`(`project.yaml`)に一覧として書き出す。
- 内部 ID は、エンティティ、ステータスなどの値、プロパティ、テンプレート、自動化のルール、スプリント、リリース、コメント、作業時間、変更記録、操作のすべてで ULID とする(01:51 の決定)。
- 時刻は、ミリ秒までの RFC 3339 で、このマシンの時刻帯を付けて書く(例: `2026-11-12T10:03:21.512+09:00`)。比べるときは UTC に直して比べる。

### `.hedgehug/store.yaml`

```yaml
store: 01JC8X4Q2M6Z7H3R9V0T5N1KQB   # Store ID。作ったときに決め、変えない
format: 1
retention_days: 30                  # log.jsonl から作り直す
```

- このファイルがあるリポジトリを hedgehug の Store とする。ワークスペースが 0 件でも、すべて削除済みでも Store である(08:87・08:91)。
- `format` がこの hedgehug の知らない新しい版のときは、Store を開かない(「仕様 01〜08 へ反映する点」の 2)。

作者とコミッターは `taro <taro@hedgehug.invalid>` である(01:92)。件名は git の履歴を人が読むためのものである。アクティビティの文は、件名ではなく、そのコミットで足された変更記録から作る。

## 変更記録(`log.jsonl` の 1 行)

| キー | 中身 |
|---|---|
| `id` | 変更記録の内部 ID(ULID) |
| `op` | 操作の ID。1 回の操作(1 コミット)で書いた行は、Store をまたいでも同じ値を持つ。削除の復元(08:220)と、アクティビティのまとめに使う |
| `at` | 保存した時刻(このマシンの時計。補正しない。06:132) |
| `by` | 操作した人のログイン名。人でない実行者の行は `hedgehug[bot]`。自動化の行は、きっかけになった操作をした人 |
| `actor` | 実行者の種類。`user`・`automation:<ルールの内部 ID>`・`github`・`sync`・`none` のどれか。診断の修復は `user`(08:331) |
| `t` | 変更の種類(下の表) |
| `f` | 項目。`status`、`fields/<プロパティの内部 ID>`、`statuses/<値の内部 ID>/name` のように、1 つの値ごとに 1 つ(06:143) |
| `from`・`to` | 変更前と変更後の値 |
| `prev` | この項目で、書いた時点に勝っていた変更記録の `id`。作成なら空 |

| `t` | 意味 |
|---|---|
| `create` | 作成。作成時の値をすべて `to` に持つ |
| `set` | 値を 1 つ持つ項目の変更。場所(`place`: 親・プロジェクト・ワークスペース・番号をまとめた 1 項目)と順位(`rank`)も含む |
| `add`・`remove` | 値を複数持つ項目への、値 1 つの追加と取り除き(関連システム、複数選択のプロパティ、関連、ウォッチ中の人、PR・Issue のリンク、プロジェクトのリポジトリ、ワークフローの遷移) |
| `desc` | 説明を保存した(履歴の「説明の変更」。本文は `description.md`) |
| `comment`・`worklog` | コメントと作業時間の追加・編集・削除。`f` はコメント(作業時間)の内部 ID |
| `delete`・`restore` | 削除と復元。`restore` は戻す削除の `op` を持つ |
| `moved_in` | 別の Store から移ってきた。旧 ID・移動元の Store・ワークスペース・プロジェクト・移した日時を持つ |
| `number` | ワークスペースで番号を使った(アイテム用・プロジェクト用)。使った最大番号を作り直すのに使う |
| `close_sprint` | スプリントの完了。確定値(ポイントと件数の、計画と実績)を持つ(05:138) |

### いまの値の決め方(`log.jsonl` から `*.yaml` を作る)

項目ごとに、次の順で決める。どのマシンで作っても、行の並びに関わらず同じ結果になる。

1. その項目の行を、`prev` でつないだ木にする。
2. ほかの行の `prev` に挙がっていない行(先端)が 1 つなら、その値を取る。あとから書いた変更が、前の値を見て書いた変更に必ず勝つ(06 の「片方しか変えていない項目は、変えたほうの値を取る」)。時計がずれていても、この順は崩れない。
3. 先端が 2 つ以上なら、同時の変更である。`at` のあとの行、同じなら `by` を小文字にして辞書順であとの行、それも同じなら `id` の辞書順であとの行が勝つ(06:141 の後勝ち。最後の決め手は「仕様 01〜08 へ反映する点」の 1)。

`add`・`remove` も、値 1 つごとに同じ手順で決める。一方が足し、他方が取り除いたときは、その値について後勝ちになる(06:151)。

## 同期

1. remote を fetch する。
2. 自分の先端と remote の先端の、共通の祖先(merge base)を求める。
3. ファイルごとに合わせる。
   - `log.jsonl`、`transfers.jsonl`、`purged.jsonl`: 両方の行を `id` で重ねずに合わせ、`at`・`id` の順に並べて書く。
   - `description.md`: 共通の祖先の版を基準に、行ごとの 3 方向マージを行う。同じ行を両方が変えたときは、両方の版を `-----` の行ではさんで残す。保存の古い版を先にする(06)。
   - `*.yaml`: 合わせた `log.jsonl` から作り直す。
   - 片方だけがフォルダを消していたら(完全に削除)、消したほうを取る(06:230)。
4. 下の「同期の修復」を行う。
5. 結果を、2 つの親を持つマージのコミットにする。このコミットは保存ではないので、アクティビティに出さない(01:100)。修復があれば、マージのあとに、`actor: sync` の別のコミットとして保存する。
6. push する。拒否されたら、1 から最大 3 回やり直す(06:92)。

「上書き」の通知は、同期を受け取ったマシンが手順 3 の結果から作る。自分の行が、項目の先端どうしの比べ合いで負けたら、上書きの通知を作る(06 の「あなたの値が負けたとき」)。

### 同期の修復

修復は、合わせたあとの状態だけから決める。どのマシンが行っても同じ値になる(06:244)。複数のマシンが同じ修復の行を書いても、値が同じなので結果は変わらない。アクティビティでは 1 行にまとめる(下の「アクティビティ」)。

| 06 の規則 | 見つけ方 | 書く行 |
|---|---|---|
| 削除と変更が重なった(06:161) | 共通の祖先にない `delete` と、同じエンティティの共通の祖先にない変更が、別々の側にある | `restore`(削除前の値は `log.jsonl` に残っている) |
| 番号が重なった(06:185) | 同じワークスペースで `place` の番号が同じ。作成のコミットが remote の先端から辿れる方が番号を残す。両方辿れるなら、`create` の `at` が古い方 | 残さない方に `set place`(次の空き番号) |
| 実行中のスプリントが 2 つ(06:193) | 開始日、開始の `at`、開始した人のログイン名、開始の変更記録の `id` の順で比べる | 先頭以外に `set` で計画中 |
| 1 つしかないものが 2 つ(06:199) | 名前・接頭辞・キー・Issue のリンク・メンバー・接頭辞のないワークスペースの重なり | 06:199 の表のとおりの `set`・`remove` |
| 削除された値を指す設定(06:214) | 既定・初期にした値に `delete` がある | 値の `restore` |
| 完了・中止の初期ステータス(06:220) | 初期ステータスの値の分類が完了・中止 | 初期ステータスの `set` |
| 親が削除された(06:222) | 削除済みの親の下に、削除されていない子がある | 子に `delete`(`op` は親の削除と同じ) |
| 完全な削除と重なった(06:228) | 合わせたあとに、祖先のフォルダがないアイテムがある。`purged.jsonl` にある相手への関連がある | フォルダを消し、`purged.jsonl` に足す。関連の `remove` |
| 別の Store へ移したものと重なった(06:232) | `transfers.jsonl` にある内部 ID のフォルダが、相手の変更で残っている | フォルダを消す(移動の保存が勝つだけ。修復の保存は要らない) |
| 完了したスプリントに入った(06:236) | 完了したスプリントに、未完了のアイテムがある | `set sprint`(バックログ) |

## 削除・復元・完全に削除

- **削除**(論理削除): `delete` の行を書く。下にあるものにも、同じ `op` で `delete` を書く(02:308・03:144)。削除した日時は、その行の `at` である。別の Store へ移しても、行ごと移るので元の日時が残る(02:232)。
- **スプリント・リリースの削除**: 入っていたアイテムに、同じ `op` で `set sprint`(`set release`)を書く(05:153)。
- **復元**: 戻す削除の `op` を持つ `restore` を書く。値は、その `op` の行の `from` から戻す。そのあと別の操作でスプリントに入れたアイテムは、`prev` の木で、その `op` の行が先端でなくなっているので戻さない(08:226)。
- **完全に削除**: エンティティのフォルダを消し、`purged.jsonl` に 1 行足す。中身は残さない。消したものを相手にした関連は、同じ保存で `remove` する(08:275)。

```json
{"id":"01JK…","at":"2026-12-12T00:00:05.000+09:00","by":"hedgehug[bot]","actor":"none","entity":"item","target":"01JF3KQ8W2…","display":"HH-12"}
```

`purged.jsonl` は、旧 ID から辿ったときに「完全に削除されました」と言い分けるため(02:260)と、診断でプロジェクトが分からないことを見分けるため(08:299)に使う。

## 移動・番号・旧 ID

- **同じワークスペースの中**: `set place` と `set rank` を同じ操作で書く(06:143)。
- **別のワークスペース(同じ Store)**: 内部 ID は変わらない。`set place` で番号を振り直し、`transfers.jsonl` に 1 行足す(02:258)。
- **別の Store**: 移動先にフォルダを写し、`moved_in` の行を足す。移動元はフォルダを消し、`transfers.jsonl` に 1 行足す(02:266 の順で、Store ごとに 1 コミット)。

```json
{"id":"01JM…","op":"01JM…","at":"2026-11-12T11:00:00.000+09:00","by":"taro","target":"01JF3KQ8W2…","old":"HH-12","new":"WEB-31","to_store":"01JC9…","to_store_name":"team-b","to_remote":"https://github.com/org/team-b"}
```

- 転送記録の「移動先の Store 名」(02:258)は、移した人のマシンでの名前を `to_store_name` に残す。表示するときは、`to_store` の Store がこのマシンにあればこのマシンでの名前を出し、なければ `to_store_name` を出す。Store の名前はマシンごとのもの(08:99)だからである。
- **使った最大番号**: 番号を振るたびに、ワークスペースの `log.jsonl` に `number` の行を書く。値は行の最大値で決めるので、同時に振っても小さくならない。移したり完全に削除したりしても番号は使い回さない(02:238・02:485)。
- **旧い接頭辞**: ワークスペースの `log.jsonl` に残る、`prefix` の過去の値すべてである。別に記録は持たない(03:104)。

## アクティビティと履歴

- **アクティビティ**: 保存のコミット 1 つが 1 行である(06:389)。行の文・実行者・対象・ワークスペースは、そのコミットで足された変更記録から作る。マージのコミットは出さない。同期の行はコミットではないので、マシン側に記録する(06:401)。
- **人でない実行者の同じ変更**(06:421): `actor` が `user` でなく、対象・項目・`from`・`to` が同じ変更記録を持つコミットが複数あるときは、`at` が最も早いコミットの 1 行だけを出す。
- **移したワークスペースの記録**(06:437): 移動元の Store にないワークスペースの内部 ID を指す行は、ワークスペースの絞り込みの選択肢に出さず、「すべて」でだけ出す。
- **アイテム・プロジェクトの履歴**(02:462): その `log.jsonl` の行から作る。履歴に出さない種類(コメント・関連・リンク・作業時間・ウォッチ・削除。02:477)は除く。
- **レポート**(05): スプリントの出入りの日は `set sprint` の行、ステータスが変わった時刻は `set status` の行、作成の時刻は `create` の行から取る。ポイントなどの量は、いまの値を使う(05:307)。

## このマシンに持つもの

01 の表の右の列は、すべて Store の外に置く。

| 置き場所 | 中身 |
|---|---|
| `~/.config/hedgehug/config.yaml` | ログイン名、同期のタイミング、Store の一覧(名前・clone の場所・remote・アカウント・色・非表示・閲覧のみの印)、アカウント(トークンを除く) |
| OS のキーチェーン(go-keyring) | トークン(デバイスフローで得たものを含む。07:27)と、照合のために最後に確かめたトークンの指紋(07:72) |
| `~/.local/share/hedgehug/stores/<Store ID>/` | Store の clone |
| `~/.local/share/hedgehug/state.db`(SQLite) | 下の 2 種類 |

`state.db` には、作り直せないものと、Store からいつでも作り直せる索引を、テーブルを分けて持つ。

- **作り直せないもの**: 通知と既読、通知を判定したコミット(06:270)、同期の結果と同期の行、保存したビュー(04)、画面の状態、WIP 上限、レポートの選択、GitHub の前回の読み取りの情報(07:229)、GitHub App を入れていない組織(07:97)、時計のずれ(06:132)。
- **索引**: 検索・マイタスク・アクティビティ・履歴・レポートのための、いまの値と変更記録の写し。どの Store のどのコミットまで取り込んだかを覚え、新しいコミットの変わったファイルだけを読み足す。クエリの書き方は暫定(04:162)なので、索引の形は Store の形式に含めない。消しても、次に開いたとき Store から作り直す。

Store をこのマシンから削除したときは、その Store ID の行を `state.db` からすべて消す(06:270)。

## 技術構成

| 部分 | 使うもの |
|---|---|
| サーバー | Go。HTTP の API は huma で書き、OpenAPI を出す |
| git | go-git。go-git にはマージがないので、同期の合わせ方は上の「同期」のとおり自前で行う |
| マシンのデータ | SQLite(modernc.org/sqlite。cgo が要らない) |
| トークン | go-keyring |
| 画面 | Svelte 5、Vite。API の型と呼び出しは orval で OpenAPI から作る |
| 他のタブ・CLI の変更の反映 | サーバーが Store の HEAD の変化を見張り、Server-Sent Events で画面に知らせる |
| CLI | cobra(別の段階で仕様を決める) |

- **同時に書き込むとき**: Store ごとにファイルロックをかけ、1 回の操作のあいだ持つ。画面のサーバーと CLI が同じ Store に書いても、コミットは 1 つずつ順に作られる。
- **1 回の操作の途中で失敗したとき**: 作業ツリーとインデックスを、操作の前のコミットに戻す。1 つも書かなかったことになる(01:106)。

## テスト

- いまの値の決め方: 同じ変更記録の集まりを、どの順で適用しても同じ `*.yaml` になることを、ファジングで確かめる。
- 同期: 06 の各規則と、モックの同期の場面(P1〜P11)を、2 つのクローンを作って再現する場面のテストにする。両方のマシンで同期した結果が、バイト単位で同じになることを確かめる。
- 時計のずれ: 先に書いた側の時計が進んでいても、あとから見て書いた変更が勝つことを確かめる。

## 仕様 01〜08 へ反映する点

1. **後勝ちの最後の決め手**(06:141・05:159・06:195): 「コミットの SHA の辞書順」を「変更記録の ID の辞書順」に替える。変更記録を書いた時点では、自分のコミットの SHA が分からないためである。どのマシンでも同じ結果になる点は変わらない(2026-11-12 承認)。
2. **知らない形式の Store**(08 の「追加」と 06 の「同期のエラー」): `store.yaml` の `format` がこの hedgehug より新しい Store は開かない。追加のときは「{remote} は新しい版の hedgehug で作られています。hedgehug を更新してください」と断る。同期で受け取った remote が新しい形式になっていたときは、同期エラーにし、短い理由を「hedgehug を更新してください」とする。現行の実装と同じ扱いである。
