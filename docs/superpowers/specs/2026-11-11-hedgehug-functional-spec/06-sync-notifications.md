# hedgehug 機能仕様 06: 同期・通知・アクティビティ

複数の人が同じ Store を使うと、同じ項目への変更が重なる。この文書は、同期がいつ動くか、重なった変更で何が残るか、残らなかった人にどう知らせるかを定める。通知は Store に保存せず、各マシンが自分宛てのものだけを作る。

用語、「あなた」、保存の単位、閲覧のみの Store は 01 を参照する。アイテムは 02、自動化の定義は 03、GitHub の PR と Issue の状態の取得は 07、完全な削除と診断は 08 が定める。

## 同期とは

**同期**は、その Store の remote とこのマシンのあいだで、保存を送り、受け取ることである。remote のほかにミラー(08)を持つ Store は、remote への送信が終わったあと、ミラーにも保存を送る。ミラーからは受け取らない。同期が行われても、保存の内容は利用者が気づかないうちに書き換わらない。重なった変更の扱いは「同時に編集したとき」で定める。

remote がない Store は、このマシンの中だけで使うので、同期の対象にならない。

### 手動で同期する

| 操作 | 対象 |
|---|---|
| サイドバーの同期カードにある「すべて同期」ボタン | 表示中で remote がある Store すべて |
| コマンドパレットの「すべての Store を同期」、設定の「一般」にある「すべて同期」ボタン | 同上 |
| キーボードの Shift+Ctrl+S(Shift+Cmd+S) | 同上。サイドバーがある画面ならどこでも、入力中でもダイアログを開いているときでも使える。表示中で remote がある Store が 1 つもないときは、コマンドパレットの「すべての Store を同期」と同じトーストを出す |
| サイドバーの同期カードの要約をクリックして出る「Store ごとの同期状態」から Store を選ぶ | その Store |
| サイドバーの Store メニューの「今すぐ同期」、設定の「Store」にある「今すぐ同期」 | その Store |

Store メニューの「今すぐ同期」は、remote がない Store では無効にし、「remote なし」と添える。設定の「一般」の「すべて同期」ボタンは、表示中で remote がある Store が 1 つもなければ出さない。コマンドパレットの「すべての Store を同期」は、表示中で remote がある Store が 1 つもなくても候補に出し、実行すると、何も同期せず、トースト「同期する Store がありません(remote のある、表示中の Store が要ります)」を表示する。保存にもアクティビティにも残さない。同期カードの「すべて同期」ボタンにポインターを置くと、「Shift+Ctrl+S」(Mac は「Shift+Cmd+S」)と案内を出す。

手動の同期は、条件を待たずにすぐ始まる。閲覧のみの Store も同期できる。非表示の Store は「すべて同期」の対象にならず、設定の「Store」にある「今すぐ同期」でだけ同期できる。同期の途中で Store を非表示にしても、始まった同期は最後まで続け、結果のトーストも出す。受け取った変更からの通知は作るが、非表示のあいだは受信箱に出さず、未読にも数えない(「受信箱」)。

同じ Store の同期がすでに動いているときは、新しく始めずに、動いている同期の結果を使う。

手動の同期でも、編集中の入力欄の内容は書き換えない(「同時に編集したとき」)。

### 自動で同期する

設定の「一般」にある「裏で自動的に同期する」(初期値はオン)と、「同期のタイミング」の次の 3 つで決める。どれもこのマシンだけの設定である。

| 項目 | 選択肢 | 初期値 |
|---|---|---|
| 間隔 | 1・5・15・30・60 分ごと | 5 分ごと |
| 書き込みのあと同期するまで | 10 秒・30 秒・60 秒 | 30 秒 |
| GitHub を読む間隔 | 5・15・30・60 分ごと | 5 分ごと |

「裏で自動的に同期する」をオフにすると、次の契機のすべてが止まり、3 つの項目は選べなくなる。GitHub を自動で読むのも止まる。

GitHub の PR・Issue を読むこと(リンクの取り直し、PR の自動リンクの探索、権限とコラボレーターの読み取り)は、Store の同期とは別に、「GitHub を読む間隔」で行う(07)。

自動で同期する契機は次の 4 つである。

| 契機 | 動き |
|---|---|
| 間隔 | その Store を最後に同期を試みてから(成功・失敗を問わない)、設定した間隔が過ぎたとき |
| アプリを開いたとき | 開いた直後に、対象のすべての Store |
| オンライン復帰 | オフラインからつながったときに、対象のすべての Store |
| 書き込み後 | Store に保存したあと、設定「書き込みのあと同期するまで」の秒数のあいだ次の保存がなければ、その Store。そのあいだに保存が続くあいだは、最後の保存から数え直す。同期エラーの Store は、最後に試みてから選んだ間隔が過ぎるまで同期しない |

自動で同期する対象は、remote があり、非表示ではなく、GitHub に使うアカウントが設定されている Store である。閲覧のみの Store も対象で、受け取りだけを行う(01)。閲覧のみの Store には書き込みがないので、「書き込み後」の契機は起きない。

同期エラーの Store も、アプリを開いたとき、オンライン復帰、手動の同期では、常に試す。成功したら、通常の契機に戻る。例: 間隔が 5 分で、認証エラーの Store を 10:00 に試して失敗したら、次は 10:05 である。10:02 に保存して 30 秒後(10:02:30)になっても、10:05 まで待つ。

自動の同期は、画面に見えているブラウザのタブで、次のあいだは始めずに待つ。条件が解けたら、そのあと続けて同期する。待つのは、入力の途中で画面が書き換わって、入力が失われるのを防ぐためである。画面の反映も、同じ条件で待つ(「画面への反映」)。

- ダイアログ、メニュー、コマンドパレットが開いているとき
- ドラッグしているとき
- 説明やコメントを編集しているとき
- 入力欄にカーソルがあるとき
- 書きかけ(保存していない入力が空でないコメント・説明の入力欄)があるとき

自動の同期は、成功してもトーストを出さず、失敗してもエラーのトーストを出さない。結果は、同期カードと「Store ごとの同期状態」、設定の「Store」で確かめる。失敗した同期はアクティビティに残らない。

### オフライン

このマシンがネットワークにつながっていないとき、ページの上部に「オフラインです。変更はこのマシンにコミットし、つながったら push します。」と表示する。帯は、オフラインで、かつ remote がある表示中の Store が 1 つ以上あるときだけ出す(同期カードと同じ条件)。remote がある Store がなければ、送るものがないので出さない。保存はこれまでどおり行え、未送信の保存として溜まる。つながったら、自動の同期の「オンライン復帰」で送る。

「裏で自動的に同期する」がオフのときは、帯の文を「オフラインです。変更はこのマシンにコミットします。つながったら「すべて同期」で push してください。」にする。つながると帯は消え、自動では送らない。

オフラインのときに手動で同期すると、エラーのトーストで「オフラインのため同期できません。つながったら同期します」と表示する。「すべて同期」では、Store ごとに数えず、このメッセージを 1 つだけ出す。オフラインは Store の同期の状態をエラーにしない。

### 同期のエラー

同期できなかったときは、その Store の状態を「同期エラー」にする。次に同期が成功するまで、この状態が続く。

| 場合 | 手動で同期したときの表示 | 短い理由 | Store の状態 |
|---|---|---|---|
| remote がない | 「{Store 名} には remote がないため、同期するものはありません」 | なし | 変わらない |
| アカウントが設定されていない | 「{Store 名} にアカウントが設定されていないため同期できません」(エラー) | アカウントが設定されていません | 同期エラー |
| 認証に失敗した(トークンが拒否された、トークンの持ち主のログイン名が登録と違う) | 「{Store 名} の同期に失敗しました: 認証に失敗しました」(エラー) | 認証に失敗しました | 同期エラー |
| remote につながらない | 「{Store 名} の同期に失敗しました: remote に接続できません」(エラー) | remote に接続できません | 同期エラー |
| push が拒否された(書き込みの権限がない) | 「{Store 名} の同期に失敗しました: remote への書き込みが許可されていません」(エラー) | remote への書き込みが許可されていません | 同期エラー |
| remote の中身が hedgehug の Store でない | 「{Store 名} の同期に失敗しました: remote が hedgehug の Store ではありません」(エラー) | remote が hedgehug の Store ではありません | 同期エラー |
| remote の履歴が、この Store と共通の履歴を持たない | 「{Store 名} の同期に失敗しました: remote の履歴がこの Store と関係がありません」(エラー) | remote の履歴がこの Store と関係がありません | 同期エラー |
| remote の履歴が書き換えられた(同じ remote から前に受け取った履歴の続きでない) | 「{Store 名} の同期に失敗しました: remote の履歴が書き換えられています」(エラー) | remote の履歴が書き換えられています | 同期エラー |
| 送信が他の人の更新と重なり続けた | 「{Store 名} の同期に失敗しました: 送信が他の人の更新と重なりました。もう一度同期してください」(エラー) | 送信が他の人の更新と重なりました。もう一度同期してください | 同期エラー |

「短い理由」は、「すべて同期」のトーストの行、「Store ごとの同期状態」、設定の「Store」(08)で、同じ文を使う。remote があって、アカウントが設定されていない Store は、手動で同期を試していなくても、同期エラーの状態にする。同期カードの要約の「N 件の Store で同期エラー」にも数える(閲覧のみの Store も同じ)。例: team だけがそうなら、カードは「1 件の Store で同期エラー」になる。

同期は、受信、合わせる、送信の順に行う。途中で切れたときは、その同期を失敗として、Store の状態を「同期エラー」にし、手動のトーストは「{Store 名} の同期に失敗しました: remote に接続できません」とする。受け取った保存は残り、次の同期で続ける。「送信 N 件・受信 M 件」の表示と、アクティビティの同期の行は、成功した同期にだけ出す。送信が他の人の更新と重なって拒否されたときは、自動で「受信、合わせる、送信」を最大 3 回まで繰り返し、それでも送れなければ失敗とする(上の表の最後の行)。git の通信が 60 秒間まったく進まないときは、中断して、「remote に接続できません」と同じ扱いにする。

remote の履歴が、この Store と共通の履歴を持たないときは、合わせずに断る。remote が空のリポジトリのときは、最初の送信として認める。同じ Store の fork やコピーなど、共通の履歴があるものも認める。remote の変更そのものは、そのまま受け入れ(08)、最初の同期で断る。直すには、remote を元に戻すか、Store をこのマシンから削除して clone し直す。このマシンだけで作った Store を既存のチームの Store にまとめたいときは、「別の Store へ移動」(03)を使う。

同じ remote から前に受け取った履歴があるのに、今回受け取った remote の履歴がその続きになっていないときは、remote の履歴が書き換えられたものとして、合わせずに止める。履歴が過去へ巻き戻されたときも同じである。止めたあとも、このマシンの Store は変えない。未送信の保存はそのまま残る。remote が元に戻って、受け取った履歴が前の続きに戻れば、次の同期で、そのまま再開する。hedgehug は remote の履歴を書き換えない(強制 push をしない。ミラーへの送信も同じ)ので、書き換えは、利用者が git で行ったものに限る。直し方は 2 つある。remote を元に戻すか、設定の「Store」の「remote の履歴にそろえる…」で、このマシンの履歴を remote の新しい履歴に置き換える(08)。remote を付け替えたあとの最初の同期と、Store を追加(clone、またはフォルダから探して取り込む)したあとの最初の同期は、前に受け取った履歴の記録を持たないので、この検査ではなく、上の共通の履歴の検査を行う。

ミラー(08)に送れなかったときは、Store の状態を変えない。remote への同期が成功していれば、その同期は成功である。ミラーへの送信には、その Store の「GitHub に使うアカウント」を使う。ミラーごとの結果は、設定の「Store」(08)のミラーの行に出し、手動で 1 つの Store を同期したときは、トーストの結果のあとに警告のトースト「ミラー {K} 件に送れませんでした」を別に出す。ミラーの短い理由は、上の表の「認証に失敗しました」「remote に接続できません」「remote への書き込みが許可されていません」と、「ミラーの履歴がこの Store と関係がありません」(ミラーが空でなく、この Store と共通の履歴を持たない)、「ミラーの履歴が先に進んでいます」(ミラーにだけある保存がある。上書きしないため送らない)である。空のミラーには、最初の送信として送る。

アカウントを設定すると、アカウントが設定されていないことによるエラーの表示は消える。アカウントの削除で同期に使っていた Store が同期できなくなる扱いは 07 を参照する。

### 同期の結果

1 つの Store を同期したときは、トーストで「{Store 名} を同期しました(送信 N 件・受信 M 件)」と表示する。N は送った保存の数、M は受け取った保存の数である。

「すべて同期」では、対象の Store をすべて同期したあとに、結果を 1 つのトーストにまとめる。

| 結果 | 表示 |
|---|---|
| すべて成功 | 「N 件の Store を同期しました」 |
| 失敗がある | 「成功 N 件・失敗 M 件」と、失敗した Store ごとに 1 行、「{Store 名}: {短い理由}」。短い理由は上の表の文言。例: 「team: アカウントが設定されていません」 |

remote がない Store は、「すべて同期」の件数に数えない。

### 同期の状態の表示

サイドバーの下部に、同期カードを置く。表示中で remote がある Store が 1 つもなければ、カードごと出さない。

カードの 1 行目は要約である。

- 同期エラーの Store が 1 つでもあれば、「N 件の Store で同期エラー」とエラーの色で表示する
- そうでなければ、すべての Store の「未送信 X」(X は合計)を表示する。0 なら「すべて最新」と表示する

未送信は、このマシンで保存して、まだ送っていない保存の数である。他の人が remote に送った保存は、カードには出さない。2 行目の最終同期の時刻と、自動で同期する間隔(最長 60 分)で分かる。

2 行目は「最終同期 {相対時間} · Store N 件」である。相対時間は、対象の Store の中で最も新しい、成功した同期の時刻を、01 の書式で表したものである(失敗した試みは数えない)。1 度も同期に成功していない Store は数えず、すべてがそうなら「なし」と表示する。最後に成功した同期からの経過時間が 24 時間以上の Store があるときは(表示の書式とは関係なく、経過時間で判定する)、3 行目に「N 件の Store が 24 時間以上同期されていません」と警告の色で表示する。同期エラーが続いている Store も、最後に成功してから 24 時間以上たっていれば数える。例: team-a が認証エラーで、最後の成功が 2 日前なら、1 行目は「1 件の Store で同期エラー」、3 行目は「1 件の Store が 24 時間以上同期されていません」の両方が出る。時計のずれの警告があるときは、その次の行に「このマシンの時計が {N} 分ずれています」と警告の色で表示する(「時計のずれの警告」)。

要約をクリックすると、メニュー「Store ごとの同期状態」が開く。remote がある表示中の Store を 1 行ずつ並べ、Store 名のあとに「{要約} · {相対時間 または 未同期}」を添える。要約は、同期エラーなら「同期エラー: {短い理由}」(短い理由は「同期のエラー」の表)、そうでなければ「未送信 X」または「最新」である。相対時間は、最後に成功した同期の時刻である。例: 「team-a  同期エラー: 認証に失敗しました · 2 時間前」。最後に成功した同期からの経過時間が 24 時間以上の Store は、相対時間を警告の色にする。項目を選ぶと、その Store を同期する。

同期カードの右端のボタン「すべて同期」で、手動の同期を行う。設定の「Store」にも、Store ごとの同期の状況(未送信件数、最終同期、エラー)を出す(08)。

幅 860px 以下では、ページ見出しのメニューのボタンに、表示中の Store に同期エラーがあるあいだ、エラーの色の点を付ける(ドロワーを開くと同期カードが見える)。閲覧のみの Store の同期エラーも数える。オフラインは同期エラーではないので、点を出さない。非表示の Store の同期エラーは、カードにも点にも数えない。上部に帯は足さない。

### 時計のずれの警告

保存時刻は各マシンの時計で決まり、同期の勝ち負け(後勝ち)と、削除済みを完全に削除する日(08)がそれに頼る。保存時刻は補正せず、時計のずれを利用者に知らせる。

- GitHub に問い合わせるたびに、GitHub の応答に付く日時と、このマシンの時計を比べる。5 分以上ずれたら警告を出し、5 分未満に戻ったら消す。警告の基準の 5 分は、最短の保持日数 7 日に比べて小さいので、削除する日は補正しない
- 設定の「一般」の「同期のタイミング」の上に、警告の色で「このマシンの時計が GitHub の時刻より {N} 分進んでいます。同期で後から届いた変更の勝ち負けと、削除済みを完全に削除する日が、他の人とずれます。OS の日時の設定を確かめてください。」と表示する。遅れているときは「進んで」を「遅れて」にする
- サイドバーの同期カードの警告の行に、「このマシンの時計が {N} 分ずれています」と表示する
- 閲覧のみの Store は書き込まないので、勝ち負けには関わらないが、警告は同じに出す。GitHub に問い合わせたことがない(アカウントも remote もない)マシンには出ない

## 画面への反映

Store に保存された変更は、書き手にかかわらず、開いている画面へ自動で反映する。書き手は、この画面、別のブラウザのタブ・ウィンドウ、このマシンで動く別のプログラム(CLI など)、同期である。CLI そのものは、この仕様で扱わない(01)。反映するのは、Store に保存された変更と、このマシンだけが持つ状態(受信箱の既読、PR のチェックの結果)である。保存されていない作業ツリーの変更は、反映しない。反映は、表示を更新するだけで、保存・通知・自動化は作らない。保存から 1 秒ほどで反映する。

### 反映するもの

| 変わったもの | 更新する画面と部品 |
|---|---|
| アイテムとプロジェクトの作成・値・説明・コメント・作業時間・親・並び・削除・復元・移動 | 開いている一覧(マイタスク、バックログ、検索、保存したビューの結果)、ツリー、カンバン、テーブル、ガント、詳細パネルの値・説明・コメント・履歴、プロジェクトとワークスペースの概要のカードと件数、スプリントとリリースの画面、レポート、アクティビティ、サイドバーの件数 |
| ワークスペースの設定、スプリント、リリース、メンバー、保持日数 | 設定の画面、サイドバーのワークスペースとプロジェクトの名前と並び、値の選択肢が出ている入力欄 |
| このマシンの Store の一覧と設定(追加、削除、名前、色、非表示、remote、ミラー、アカウント、既定、保存先、閲覧のみの印) | サイドバーの Store のバッジと一覧、設定の「Store」の枠、ミラーの行、同期カード、無効だった入力欄 |
| 同期の状態 | 同期カード、「Store ごとの同期状態」、設定の「Store」の同期の状況、幅 860px 以下のメニューのボタンの点 |
| 受信箱の既読と未読 | サイドバーの「受信箱」の未読数、受信箱のタブの未読数と行 |
| このマシンが読んだ GitHub の値(PR のチェックの結果) | PR の行のチェックの表示。読み取りが終わってから 1 秒ほどで、このマシンの全ブラウザのタブに出す |
| 保存したビューの一覧 | サイドバーの「ビュー」の一覧。開いているブラウザのタブの絞り込みとレイアウトは書き換えず、保存した内容との比べ(「変更あり」の表示)だけ更新する |

画面の状態(絞り込み、レイアウト、折りたたみ、スクロール、選択、詳細パネルの開閉と幅)は、ブラウザのタブごとのものなので、他のブラウザのタブの変更では書き換えない。反映のために、ページ全体の再読み込みはしない。

### 反映を待つとき

次のあいだは、この画面の反映を待つ。条件が解けたら、溜まった変更を 1 回でまとめて反映する。待つのは、入力の途中で画面が書き換わって、入力が失われるのを防ぐためである。

- ダイアログ、メニュー、コマンドパレットが開いているとき
- ドラッグしているとき
- 説明やコメントを編集しているとき
- 入力欄にカーソルがあるとき
- 書きかけ(保存していない入力が空でないコメント・説明の入力欄)があるとき

このブラウザのタブの操作の結果は、待たずに、その場で出す。手動の同期の結果は、待たずに反映する。ただし、編集中の入力欄の内容は書き換えない。自動の同期が待つ条件(「自動で同期する」)は、画面に見えているブラウザのタブの条件だけで決める。見えていないブラウザのタブは、見えるようになったときに反映する。

### 反映で変わる画面

- 開いている詳細パネルのアイテムが削除されたら、パネルを閉じる。開いている画面(プロジェクト、ワークスペース、Store)がなくなったときは、マイタスクへ移る(01)。
- 非表示の Store の変更は、画面に出さない。再表示したときに、最新を出す(08)。

### 他の書き手との重なり

このブラウザのタブの操作は、保存の時点の最新の Store に対する保存になる。他の書き手と同じ項目に重なったときは、あとに保存した方が残る。削除と変更が重なったときは、変更を残して削除を取り消し、トースト「{ID} は別の画面で削除されていましたが、変更を保存したため、削除を取り消しました」を出す。説明を保存するときは、編集を始めたときの内容を基準に、保存した時点の内容と行ごとに合わせる(「同時に編集したとき」)。

## 同時に編集したとき

複数の人が、同期の前に同じ値を変えることがある。同期では、2 人が分かれる前の状態(共通の祖先)を基準にして、両方の変更を項目ごとに合わせる(3 方向のマージ)。片方しか変えていない項目は、変えたほうの値を取る。両方が同じ項目を別の値に変えたときは、**その項目を保存した時刻があとの変更が勝つ**。これを後勝ちと呼ぶ。時刻は、アイテム全体の最終更新の時刻ではなく、その項目を最後に保存した時刻で比べる。保存時刻は各マシンの時計で、時計が正しいことを前提にする(補正はせず、ずれは「時計のずれの警告」で知らせる)。保存時刻が同じときは、ログイン名(大文字と小文字を区別しない)が辞書順であとの人の変更が勝つ。ログイン名も同じときは、コミットの SHA が辞書順であとの変更が勝つ。SHA はどのマシンでも同じなので、どのマシンで同期しても、同じ結果になる。

項目は、1 つの値ごとに分ける。タイトル、各プロパティ、スプリント、リリース、場所(親・プロジェクト・ワークスペース・番号)、順位(アイテム・プロジェクト・ワークスペースごと)、種類、プロジェクトのタイトル・ステータス・オーナー・開始日・終了日がそれぞれ 1 つの項目である。同じアイテムでも、別の項目の変更はどちらも残る。移動は、場所と順位を同じ保存で書く(新しい親の末尾、または選んだ位置)。同時に別の場所へ移したときは、保存時刻があとの移動が場所ごと勝つ。同じ 1 件を 2 人が別の位置に動かしたときも、保存時刻があとの位置が勝つ。順位が同じ別のものは、作成の保存が早い方が先、同じなら内部 ID の辞書順に並べるので、全員の画面で同じ並びになる。例: 田中さんの Web と鈴木さんの Docs が同じ順位でも、全員の画面で Web、Docs の順に並ぶ。削除済みのものの順位は比べない。別の Store への移動との重なりは「別の Store へ移動したものと重なったとき」で定める。

アイテムとプロジェクトのほかにも、ワークスペースの設定(名前、接頭辞、プロパティ、値、ワークフローの遷移、テンプレート、自動化、プロジェクト別のルール)、スプリントとリリース、コメント、作業時間、メンバーの表示名、保持日数を、アイテムと同じく項目ごとの後勝ちで合わせる。同じ項目を別の値に変えた負けた人には、「上書き」の通知を作る。編集と削除が重なったときも、アイテムと同じく、編集を残して削除を取り消す(下の表の最後の行)。

次のものは、後勝ちではなく、両方の変更を生かして合わせる。

| もの | 合わせ方 |
|---|---|
| 値を複数持つ項目(関連システム、複数選択のプロパティ、関連、ウォッチ中の人、PR・Issue のリンク、アイテムの解除の記録(07)、プロジェクトのリポジトリ、プロジェクト別のルールの使わないステータス・遷移のチェック(From と To の組ごと)・使うテンプレート・動かさないルールの指定) | 1 つずつの追加と削除を、両方とも生かす。たとえば、一方が「Web」を足し、他方が「API」を足したら、両方が入る。同じ値を一方が足し、他方が外したときは、その値について後勝ちで決め、負けた人に「上書き」の通知を作る。ウォッチ中の人は、各自が自分の入り切りだけを書くので、勝ち負けは起きず、通知しない |
| 説明(アイテムとプロジェクト) | 行ごとに合わせる。別々の行の変更は両方残す。同じ行を両方が変えたときは、両方の版を残し、あいだに「-----」の行をはさむ(保存の古いほうを先にする)。両方の版を残したときは、両方の人に「上書き」の通知を作る |

| 重なり方 | 残るもの |
|---|---|
| 別の項目を変えた | どちらも残る |
| 同じ項目を、同じ値に変えた | その値。通知は作らない |
| 同じ項目を、別の値に変えた | 保存時刻があとの値。負けた人に「上書き」の通知を作る |
| コメント、リンク、関連、作業時間を追加した | どちらも残る |
| アイテムを作成した | どちらも残る(番号の重なりは次節) |
| 一方が削除し、他方が変更した(アイテムの削除、設定・スプリント・リリース・コメント・作業時間などの削除) | 変更が残り、削除は取り消す。削除した人に「同期の修復」の通知を作る(本文は「{ID} は {変更した人} が同時に変更したため、削除を取り消しました」)。もう一度削除するかは、削除した人が決める |

PR のリンクの状態・タイトル・レビューの状態を、2 台が別の値に変えたときは、保存時刻があとの値を残す。通知は作らない。GitHub の値に、次の読み取りで揃う。同じ PR を 2 台が自動でリンクしたときは、1 本にまとめる。

プロジェクト別のルール(03)の変更は、プロジェクトへの変更に数えない。プロジェクトの削除と重なっても、削除は取り消さず、ルールは残る(復元で働く)。ルールを変えた人に通知は作らない。

説明を編集しているあいだに、同期で他の人の変更が届いても、別のブラウザのタブや別のプログラムが保存した変更が届いても、編集中の入力欄の内容は書き換えない。説明を保存するときは、編集を始めたときの内容を共通の祖先として、保存した時点の内容と行ごとに合わせる(上の表と同じ規則)。同じ行を別の人が変えていたら、両方の版を「-----」ではさんで残し、保存した本人にトースト「説明の同じ箇所が同時に編集されたため、両方を残しました」と、同じ文の「上書き」の通知を作る。別の行なら両方が残り、通知は作らない。プロジェクトの説明も同じである。タイトルなど 1 行の入力は、確定した値が通常の後勝ちで決まる。コメントは追加なので、影響しない。

あなたの値が負けたときは、あなたのマシンが、同期で受け取った変更を見て、あなた宛てに「上書き」の通知を作る。勝った人のマシンには、何も作らない。同じ人の別のマシンの変更に負けたときも同じで、負けたマシンが作る。差出人はあなた自身である。例: 太郎さんのノート PC の値がデスクトップ PC に負けたら、ノート PC の受信箱に「あなたの値 X → 残った値 Y」が出る。

### 上書きの通知

通知は、本文「{項目名}が上書きされました」、差出人は上書きした人である。ワークスペースの設定・スプリント・リリース・コメント・作業時間などのときは、{項目名} にその名前を入れる(例: 「ワークスペース名」「Review の名前」)。受信箱では、項目の種類によって表示が分かれる。

| 項目 | 表示 | 「自分の値に戻す」 |
|---|---|---|
| タイトル、プロパティ、スプリント、リリース、プロジェクトのタイトル・ステータス・オーナー・開始日・終了日 | 「あなたの値 X → 残った値 Y」 | 出す |
| 場所、順位、種類 | 本文だけ(「場所が上書きされました」「順位が上書きされました」) | 出さない |
| 関連システム、複数選択のプロパティ | 「あなたの値 X → 残った値 Y」(値は「, 」でつなぎ、空は「なし」)。例: 関連システムが「Web, API」のとき、太郎さんが「Web」にし、田中さんが「API」を足し直したら「あなたの値 Web → 残った値 Web, API」 | 出す |
| 関連、PR・Issue のリンク、プロジェクト別のルール | 本文だけ(「関連が上書きされました」「リンクが上書きされました」。プロジェクト別のルールは、{項目名} を「{プロジェクトの ID} のルール」にする) | 出さない |
| 説明(同じ行を両方が変えて、両方の版を残したとき) | 本文「説明の同じ箇所が同時に編集されたため、両方を残しました」 | 出さない |

場所と種類は、戻すとアイテムの親子の決まり(01)に合わなくなることがあるので、戻すボタンは出さない。順位も出さない。関連とリンクは、関連の向きの扱いと Issue の 1 対 1(07)を戻す側で守る必要があるので、戻すボタンは出さない。プロジェクト別のルールは、複数の値を持つ項目が多く、戻す相手が決まらないので、戻すボタンは出さない。説明は、どちらの版も本文に残っているので、戻すボタンは要らない。

「自分の値に戻す」を押すと、あなたの値を、新しい 1 回の保存として書く。ワークフローの制約は無視する。アクティビティには「{ID} の{プロパティ名}を上書き前の値に戻す」(プロジェクトでは「{タイトル} の{項目名}を上書き前の値に戻す」)と残る。「上書き前の値に戻しました」と表示する。通知は既読になり、ボタンの代わりに「自分の値に戻しました」を表示する。この保存は新しい保存として、あとの時刻で比べられる。時計が進んだ相手には勝てないことがあり、そのときは「上書き」の通知がもう一度届く。「自分の値に戻す」では自動化は動かない(03)。

アイテムが削除済み、または存在しないときは、ボタンを出さない。閲覧のみの Store では、ボタンを無効にして「閲覧のみの Store です」と添える。

### 番号の重なりの修復

2 人が同期の前に、それぞれ同じワークスペースにアイテムを作ると、同じ番号(01 の ID)を取ることがある。プロジェクトの ID(HH-P3)も、同じように重なることがあり、アイテムと同じ規則で直す。同期で重なりが分かったとき、番号を持ち続けるのは、先に remote に届いた方(作成の保存が remote にある方)である。もう一方に、そのワークスペースの次の空き番号を振り直す。両方の作成の保存がすでに remote にあるとき(同期で直しきれずに残った重なりで、診断(08)で見つかる)は、作成が最も古いものが番号を持ち続ける。コメントや説明に書いた ID は、文字のまま変わらない。

振り直しは保存として記録する。アクティビティでは、実行者を「同期」として「{旧 ID} を {新 ID} に振り直し」と表示する。どのマシンが同期しても、同じ番号に振り直す。

振り直されたアイテム(プロジェクト)を作った人のマシンが、同期で振り直しを受け取ったときに、自分宛てに「同期の修復」の通知を作る。他の人宛ての通知を作るマシンはない。本文は「2 台で同時に {旧 ID} が作られたため、あとから届いた方を {新 ID} に振り直しました」である。自分が作ったものを自分の診断(08)で直したときは、通知は 1 件で、本文は「{旧 ID} を {新 ID} に振り直しました。本文中の {旧 ID} は、番号を残した方を指します」である。

### スプリントの実行中が 2 つになったとき

ワークスペースの実行中のスプリントは 1 つだけである(05)。2 人が同期の前に、別のスプリントを開始すると、同期で実行中が 2 つになる。実行中が 2 つ以上のときは、開始日が早い、開始の保存時刻が早い、開始した人のログイン名(大文字と小文字を区別しない)の辞書順が早い、コミットの SHA の辞書順が早い、の順で比べて、先頭の 1 つを実行中のまま残し、他のすべてを計画中に戻す。

計画中に戻した保存は、番号の振り直しと同じく、実行者を「同期」として記録する。戻されたスプリントを開始した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「実行中のスプリントが 2 つになったため、「{スプリント名}」を計画中に戻しました」である。

### 1 つしかないものが 2 つになったとき

1 つしかあってはいけないものが、同期で 2 つになったときは、あとから同期した方(番号の重なりと同じ決め方)を直す。

| もの | 直し方 |
|---|---|
| 名前(ワークスペース、プロジェクト、プロパティ、値、テンプレート、ルール、スプリント、リリース) | 末尾に「 (2)」を付ける。すでにあれば (3)、(4)…とする |
| 接頭辞 | 末尾に数字を付ける(WEB → WEB2)。10 文字を超えるときは、末尾を削って数字を付ける。アイテムの ID は WEB-1 から WEB2-1 に変わるが、番号は変わらない。旧 ID の扱いは接頭辞の変更と同じである(03) |
| プロパティのキー | 末尾に数字を付ける(customer → customer2) |
| Issue のリンク(1 つの Issue に 1 つのアイテム、1 つのアイテムに 1 つの Issue) | あとから同期した方のリンクを外す |
| メンバー(ログイン名で 1 人。大文字と小文字を区別しない) | 行を外して 1 行にする。表示名は残した行のもの。担当・オーナー・コメントの書き手はログイン名で結びつくので、外しても参照は切れない |

どれも「同期の修復」として保存し、アクティビティの実行者は「同期」とする。直したものを作った(リンクした)人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は、名前などでは「2 台で同時に「{名前}」が作られたため、あとから届いた方を「{新しい名前}」に変更しました」、Issue のリンクでは「Issue {リポジトリ}#{番号} は {ID} にリンクされているため、{あなたの ID} からリンクを外しました」である。メンバーの重複を統合したときは、通知を作らない(外した行を作った人にとって、見える結果は何も変わらないため)。

### 削除された値を指す設定

初期ステータス、分類ごとの既定のステータス、初期優先度にした値を、別のマシンが同時に削除していたときは、「同時に編集したとき」の削除と変更の重なりと同じく、削除を取り消して値を残す。同時の削除で、ある分類のステータスが 0 個になるときも、あとから同期した方の削除を取り消す。「同期の修復」として保存し、アクティビティの実行者は「同期」とする。削除した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「「{値の名前}」は {変更した人} が同時に既定にしたため、削除を取り消しました」(分類が 0 個になる場合は「「{値の名前}」は {分類} の最後のステータスのため、削除を取り消しました」)。

### 削除された値を指すプロジェクト別のルール

ワークスペースの値(ステータス・テンプレート)を、別のマシンが同時に削除していたとき、同期で、プロジェクト別のルール(03)が、存在しない値を指すことがある。初期ステータスなどと違い、ルールに入れた値は、外したり絞ったりするためのものなので、削除を取り消さない。受け取ったマシンが、同期の修復として、次のとおり直す。アクティビティの実行者は「同期」とする。

| 指しているもの | 直し方 | 通知 |
|---|---|---|
| 使わないステータスの一覧のステータス | 一覧から外す | 作らない(外した人にとって、見える結果は何も変わらないため) |
| プロジェクトの遷移の制約の From・To のステータス | その行、またはその許可先から外す。許可先がすべてなくなった行は「ワークスペースと同じ」に戻る | そのチェックをした人のマシンに作る |
| プロジェクトの使うテンプレートの限定・種類ごとの既定のテンプレート | 限定・既定から外す。限定が空になったら、限定を外す(すべて使える) | そのテンプレートを入れた人のマシンに作る |
| ワークスペースの種類ごとの既定のテンプレート | 既定から外す(「なし」) | その既定を選んだ人のマシンに作る |
| ルール(ワークスペース全体と専用)のきっかけ・することのステータス | そのルールを無効にする | そのルールを作った(編集した)人のマシンに作る |

通知の本文は次のとおり。

- 遷移・テンプレート: 「プロジェクト「{タイトル}」の{ワークフローの制約|使うテンプレート|{種類}の既定のテンプレート}から、{削除した人} が「{値の名前}」を削除したため、「{値の名前}」を外しました」。ワークスペースの既定は「{種類}の既定のテンプレートから、{削除した人} が「{値の名前}」を削除したため、「なし」に戻しました」
- ルール: 「自動化「{名前}」は、{削除した人} が「{値の名前}」を削除したため、無効にしました」

同じ修復を複数のマシンが行っても、結果は変わらず、通知も 1 台につき 1 件である。

### プロジェクトがなくなったときのルール

プロジェクト別のルールと専用ルール(03)の持ち主のプロジェクトが、ワークスペースにないとき(別のワークスペースへ移された、または完全に削除された)は、そのプロジェクトのルールと専用ルールを、同期の修復として外す。削除済みのプロジェクトは、ワークスペースにあるので、外さない。

完全に削除されたときは、ルールを変えた人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「完全な削除と重なったとき」と同じで、{ID} をプロジェクトの ID にする。別の Store へ移されたときは、「別の Store へ移動したものと重なったとき」の本文で作る。同じ Store の別のワークスペースへ移されたときは、通知を作らない。

### 外された初期ステータス・既定のステータス

プロジェクトが「使わない」にしたステータスを、別の人が初期ステータスや分類の既定のステータスにしたとき(同期で重なったときを含む)は、直さない。そのステータスは、初期ステータスや既定のあいだ、どのプロジェクトでも使うものとして扱う(03)。通知は作らない。

### 完了・中止の分類にされた初期ステータス

初期ステータスに選べるのは、分類が未着手か進行中のステータスだけである(03)。同期で、一方が X を完了・中止の分類にし、他方が X を初期ステータスにして、X が完了・中止の初期ステータスになったときは、初期ステータスを、未着手の既定のステータスに戻す。分類の変更は残す。「同期の修復」として保存し、アクティビティの実行者は「同期」とする。X を初期ステータスにした人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「「{X}」は {変更した人} が{分類}の分類にしたため、初期ステータスを「{未着手の既定}」に戻しました」である。

### 親が循環したとき

親をたどると自分に戻る輪が、同期でできることがある。「種類を変更」と「移動」を 2 人が入れ違うと、2 つのアイテムが互いの親になる(種類と場所は別の項目として合わせるため、それぞれの変更が残る)。このときは、輪の中で番号が最も大きいアイテムを、08 の「親がない」と同じ修復で動かす。番号が同じときは、内部 ID の辞書順があとのアイテムを動かす。輪が複数あるときは、1 つずつ、なくなるまで繰り返す。削除済みのアイテムは輪に数えない(親が削除されたときの規則で、先に子も削除済みになる)。動かす先のプロジェクトが分からないときは、直さない(診断に残す。08)。輪に入っていたアイテムのうち、親が種類の規則(01)に合わないもの(Task の下の Task など)も、同じ修復で動かす。

動かした保存は「同期の修復」として、実行者を「同期」として記録する。動かしたアイテムの親を最後に保存した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「親が循環したため、{ID} を {行き先の ID} の下へ移しました」で、Step を Task にしたときは「。Step は Task になりました」を続ける。

閲覧のみの Store では、この修復を保存しない(「修復の決まり」)。書き込めるマシンの修復が届くまで、輪の中のアイテムは、親がないアイテムとして扱う。

### 親と別のワークスペース・プロジェクトにある子

アイテムを別のワークスペースやプロジェクトへ移す操作と、移動元で他の人が行った、子の追加や親の変更が重なると、同期で、子が親と別のワークスペースまたはプロジェクトに残ることがある。このときは、子を、親のワークスペースとプロジェクトへ移す。子の下のものも、親から順に同じ扱いにする。

- ワークスペースが違うときは、02 の「別のワークスペースと別の Store への移動」と同じ結果にする。ID は、移動先のワークスペースの次の番号に振り直す(旧い番号の小さい順、同じなら内部 ID の辞書順)。プロパティの値は、移動先の定義に合わせて引き直す。ステータスは、確認ダイアログを出せないので、移動先で使えないものを、同じ分類の、移動先の既定のステータスに置き換える。スプリントとリリースは外す。転送記録を残し、旧 ID から辿れる。
- ワークスペースが同じで、プロジェクトだけが違うときは、プロジェクトだけを変える。ID と番号は変えない。
- 親が別の Store へ移ったときは、「別の Store へ移動したものと重なったとき」に従う。

「同期の修復」として保存し、実行者を「同期」とする。子の親(場所)を最後に保存した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「{親の ID} が {移動先} へ移動したため、{旧 ID} を {新 ID} に移動しました」である({移動先} は、ワークスペース名、またはプロジェクト「{名前}」。プロジェクトだけのときは「{新 ID}」を「そのプロジェクト」に読み替えて、「{ID} をそのプロジェクトに移しました」とする)。値が空になった項目があるときは、「。合う値がなく空になった項目: A・B」を続ける。閲覧のみの Store では、保存しない。

### 親が削除されたとき

ある人がアイテム(Epic・作業項目)、プロジェクト、ワークスペースを削除しているあいだに、別の人がその子を変更したり、子を追加したりすると、同期で、削除済みの親の下に、削除されていない子が残る。このときは、子も一緒に削除済みに入れる。アイテムそのものを直接削除して、別の人が変更したときの重なり(「同時に編集したとき」の表の最後の行)は、これとは別で、変更を残す。

子を変更した・追加した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「{親の ID} が削除されたため、{子の ID} も削除済みに入りました」である。

### 完全な削除と重なったとき

削除済みのものの完全な削除(手動、保持日数を過ぎた自動)と、別のマシンでの復元や変更が重なったときは、完全な削除を優先する。復元や変更をした人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「{ID} は完全に削除されたため、あなたの変更は反映されませんでした」である。完全に削除されたものを相手にした関連を付けた変更も同じで、その関連を外し、付けた人に同じ本文の通知を作る。祖先(プロジェクト・ワークスペースを含む)が完全に削除されたアイテムが同期で届いたときも、そのアイテムを完全に削除する。子を作った・変えた人のマシンに、本文「{親の ID} は完全に削除されたため、あなたの変更は反映されませんでした」の通知を作る。

### 別の Store へ移動したものと重なったとき

アイテム・プロジェクト・ワークスペースを別の Store へ移す操作(02、03)と、移動元での他の人の変更が重なったときは、移動を優先する。変更した人の変更は反映されない。変更した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「{旧 ID} は {移動した人} が {移動先の Store 名} へ移動したため、あなたの変更は反映されませんでした。移動先は {新 ID} です」である。例: 「HH-5 は 太郎 が team-b へ移動したため、あなたの変更は反映されませんでした。移動先は WEB-12 です」。移動したアイテムの下に、他の人が子を作っていたときも同じで、子は反映されない。子を作った人への本文は、末尾に「({子の ID}「{タイトル}」)」を足す。例: 「HH-5 は 太郎 が team-b へ移動したため、あなたの変更は反映されませんでした。移動先は WEB-12 です(HH-31「リリースノート」)」。他の人宛ての通知は作らない。修復の保存は要らない(移動の保存が勝つだけである)。同じ Store の別のワークスペースへの移動は、内部 ID が同じなので、この規則ではなく、項目ごとの後勝ち(場所)で合わせる。

### 完了したスプリントにアイテムが入ったとき

完了したスプリントに、同期で未完了のアイテムが入ってきたときは、そのアイテムをバックログへ戻す。スプリントの確定値は変えない。アイテムを入れた人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は「スプリント「{名前}」は完了しているため、{ID} をバックログに戻しました」である。

### 存在しないスプリント・リリースを指すとき

アイテムのスプリントまたはリリースが、次のどれかになっていることがある。完全に削除された。ファイルがない。アイテムのワークスペースのものでない(アイテムを別のワークスペースへ移す操作と、移動元でのスプリントへの追加が重なったとき)。このときは、スプリントを「バックログ」に、リリースを「なし」に戻す。削除済み(論理削除)のスプリント・リリースは、存在するものとして扱い、この修復の対象にしない(復元で戻る。05)。アーカイブのリリースと、削除済みのアイテムも対象にしない。

「同期の修復」として保存し、実行者を「同期」とする。アイテムのスプリント(リリース)の欄を最後に保存した人のマシンが、同期で受け取ったときに、自分宛てに「同期の修復」の通知を作る。本文は、「スプリント「{名前}」は完全に削除されたため、{ID} をバックログに戻しました」「リリース「{名前}」は完全に削除されたため、{ID} のリリースを外しました」「スプリント「{名前}」は {ID} のワークスペースにないため、{ID} をバックログに戻しました」である。名前は共通の祖先から読む。読めないときは「削除されたスプリント」「削除されたリリース」とする。アイテムの履歴には、「スプリントを変更」(リリースなら「リリースを変更」)が残る。

### 修復の決まり

- 修復を保存するのは、Store に書き込めるマシンだけである。閲覧のみの Store の利用者には、同期の修復の通知を作らない(自分が書いたものがないため)
- 上の各節以外のずれは、同期では直さず、診断と修復(08)で見つける。名前・接頭辞・キーの重複、Issue の二重リンク、メンバーの重複、親の循環、親と別のワークスペース・プロジェクトにある子、存在しないスプリント・リリースの参照のように、同期で直しきれずに残った状態も、診断が検出して、同期と同じ直し方で直す
- 同期のあとに、ほかのマシンが同じ修復を行っても、結果は変わらず、通知も増えない
- 人でない実行者の同じ修復が複数のマシンから届いても、アクティビティと履歴に出る行は 1 行である(「アクティビティ」の「対象」)
- 複数の修復が要るときは、次の順に行う。どのマシンが同期しても、同じ結果になる。(1)完全な削除・別の Store への移動との重なり、(2)親が削除されたとき、(3)番号の重なり、(4)親の循環、(5)親と別のワークスペース・プロジェクトにある子、(6)スプリント・リリースの参照、(7)なくなったプロジェクトのプロジェクト別のルール、(8)削除された値を指すプロジェクト別のルール・種類ごとの既定のテンプレート・自動化のルール、(9)そのほか(名前・接頭辞・キー・メンバー・Issue)

## 通知

通知は、あなたに関わる変更を知らせる。各マシンが、このマシンでの自分の操作と、同期で受け取った他の人の変更から、あなた宛てのものだけを作る。他の人宛ての通知は作らない。通知と既読の状態は、このマシンだけで持つ(01)。

通知は 7 種類である。

| 種類 | 受信箱のタブ | 作る条件 | 本文 |
|---|---|---|---|
| 割り当て | 割り当て | 受け取った変更で、アイテムの担当者、またはプロジェクトのオーナーが、あなたになった | 「あなたに割り当てました」、プロジェクトでは「プロジェクト「{タイトル}」のオーナーになりました」 |
| メンション | メンション | 受け取ったコメントと説明(アイテム、プロジェクトとも)の保存で、本文に @ログイン名 として、あなたのログイン名があった | 書かれた本文全体(最新のもの) |
| ウォッチ | ウォッチ | あなたがウォッチしているアイテムを、他の人が変えた | 変更の内容 |
| 上書き | 上書き | あなたの値が、同時に編集した他の人の変更に負けた。説明の同じ箇所を同時に編集して、両方の版を残した | 「{項目名}が上書きされました」 |
| 自動化 | 自動化 | あなたの操作(一括変更では、変えたアイテムごとに 1 件)や、あなたのマシンが取得した GitHub の状態で、自動化が動いた。ステータスの削除で自動化が無効になった、またはきっかけ・することのステータスが書き換わった(03)場合も含む | 「「{ルール名}」で{変更の内容}しました」。無効になったときは 03 の文言。書き換わったときは「自動化「{ルール名}」は、ステータス「{削除した値}」の削除で、{きっかけ または すること}のステータスを「{書き換え先}」に書き換えました」 |
| 自動化が制約で止まった | 自動化 | 自動化が動こうとしたが、ワークフローの制約、またはプロジェクトが使わないステータスのために止まった | 「「{ルール名}」が制約で止まりました」 |
| 同期の修復 | 同期の修復 | 同期での修復(親の循環を切る、親と別のワークスペース・プロジェクトにある子を移す、存在しないスプリント・リリースの参照を外す)が、あなたの作ったもの、またはあなたが変更・追加したものを変えた。あなたの削除が、同時の変更で取り消された。あなたの復元・変更が、完全な削除のために反映されなかった。あなたの変更が、別の Store への移動のために反映されなかった。あなたの未送信の変更が、書き換えられた remote の履歴にないものへの変更だったために、のせ直せなかった(08)。診断での修復(08)も含む | 前節の各文言、診断では「診断で修復しました: {検出した内容}」。診断で番号を振り直したときは前節の文言 |

通知を作らない場合を、まとめて定める。

- 自分の変更では、割り当て、メンション、ウォッチの通知を作らない
- 閲覧のみの Store でも、受け取った変更から作れる通知は作る。作れるのは、割り当て、メンション、ウォッチである(ウォッチ中の人は Store のデータにあるので、閲覧のみでも通知する)。自動化(書き込めず、GitHub の取り直しもしない)、上書き(自分の保存がない)、同期の修復(自分が書いたものがない)は作らない
- Store を追加したときに取得した、それ以前の変更からは、通知を作らない
- 同じ変更で、上書きとウォッチの条件がどちらも合うときは、上書きだけを作る
- メンションの通知は、1 つの本文(アイテムの説明、プロジェクトの説明、1 件のコメント)につき 1 行である。同じ本文が保存し直されたときは、新しい行を作らず、その行を書き換える(次の「メンション」)。書き換えるのは新しい保存(新しい本文)のときだけで、同じ保存を再び受け取ったときは、書き換えも未読に戻すこともしない
- 通知は、受け取った保存(コミット)ごと・通知の種類ごとに 1 回だけ作る。このマシンが判定した保存を、通知と既読と同じく、このマシンだけに覚える。同じ保存を再び受け取っても(remote を入れ直したあとの同期、途中で止まった同期のやり直しなど)作らない。例: 「HH-7 を太郎さんに割り当てた保存」を受け取って「割り当て」の通知を作ったあと、remote を空にして同じリポジトリのアドレスを入れ直して同期しても、「割り当て」は 1 行のままである。閲覧のみの Store、非表示の Store も同じである。Store をこのマシンから削除して追加し直したときは、覚えている保存の情報も Store とともに消すので、過去の変更からは作らない。remote の履歴が書き換えられたあと(08)は、書き換えられた履歴の中で、保存した人・保存した時刻・操作が前の履歴と同じ保存を、同じ保存として扱い、通知を作り直さない

### 通知を判定する単位

判定は、1 回の同期で受け取った、まだ判定していない保存(上で覚えたもの)をまとめて見る。

- 割り当て: アイテムごとに、判定の前の担当者と、判定の後の担当者を比べる。後があなたで、前があなたでなければ、1 行作る。差出人は、あなたにした保存の人である。20 件のアイテムをまとめてあなたにした保存を受け取ったときは、20 行になる(行は 1 つのアイテムを指す)。同じ判定の中で、あなたにしたあとに別の人に変えていたときは、後があなたではないので作らない。別々の同期で受け取ったときは、受け取った時点で作る(あとの同期で別の人になっても、行は残る)
- ウォッチ: アイテムの項目(各プロパティ、タイトル)ごとに、判定の前と後の値を比べ、違えば 1 行作る(本文は「ウォッチ」の文言、差出人は最後に変えた人)。前後が同じ値なら作らない(たとえば、前後とも InProgress)。ステータスが Done で止まったときは「ステータスを Done に変更」の 1 行である。コメントの投稿は、1 件ごとに 1 行作る
- 上書き、同期の修復: 保存ごとに 1 行作る(それぞれ別の出来事のため)。メンションは、「メンション」のとおり本文ごとである
- 自分の保存で終わっている項目は、上のとおり作らない

### 割り当て

担当者をあなた以外の人にする操作は、どの経路でも、新しい担当者に通知を出す。担当者の設定、アイテムの作成と複製、Step の追加、テンプレートでの作成(子・Step を含む)、カンバンのドラッグ、テーブルのセル、一括変更が含まれる。通知は、新しい担当者のマシンが、同期で受け取ったときに、自分宛てに作る。

他の人の操作で動いた自動化が担当者をあなたに変えたときも作る。自分の操作で動いた自動化が担当者を自分にしても、作らない(自分の変更)。差出人は、自動化のときは「hedgehug」、そうでなければ変えた人である。

### メンション

メンション先は、Store のメンバーのログイン名と一致する @ログイン名 で、大文字と小文字を区別しない。`@` の前にどんな文字があっても、一律にメンションとして扱う。

本文が保存されるたびに、その本文にあなたのログイン名があれば、次のようにする。コメントの編集でも、プロジェクトの説明でも同じである。

- その本文の行がまだなければ、行を作る。
- すでにあれば、新しい行は作らない。その行の本文を最新のものに、時刻を保存した時刻に、差出人を保存した人に書き換えて、未読に戻す。受信箱では、新しい時刻の位置に移る。
- 保存した本文からあなたのログイン名が消えたときは、行をそのまま残す(書き換えも未読に戻すこともしない)。

アイテムの複製、作成、テンプレートからの作成でも、説明は新しい本文として同じに扱い、メンションされた人に通知を作る。「あなた」自身がメンションされているときは作らない。

### ウォッチ

ウォッチは、アイテムの詳細パネルのボタンで入り切りする。アイテムを作成または複製した人は、自動でウォッチになる。担当者になった人やメンションされた人は、自動ではウォッチにならない。

ウォッチ中のアイテムで、次の変更を受け取ったときに通知する。

- プロパティの変更。本文は「{プロパティ名}を {値} に変更」
- タイトルの変更。本文は「タイトルを「{新しいタイトル}」に変更」
- コメントの投稿。本文は「コメント: {先頭 40 字}」

説明の変更、リンク(GitHub が取り直した状態・タイトル・レビューの状態と、PR の自動リンクを含む)、関連、作業時間、削除、移動、種類の変更では通知しない。自動化による変更でも通知する。

### 自動化

自動化が動いたマシンの利用者宛てに作る。他のマシンは、受け取った自動化の変更から、自動化の通知を作らない(割り当てやウォッチの条件に合えば、その通知は作る)。例外は、ステータスの削除でルールが変わったとき(無効になった、またはきっかけ・することのステータスが書き換わった)である。この場合は、その Store に書き込める全員のマシンが、受け取った削除の保存から、自動化の通知を 1 件ずつ作る。削除した人のマシンは、自分の操作で作る(1 件)。同じ削除を何台が受け取っても、1 台につき 1 件である。閲覧のみの Store、Store を追加したときに取得した過去の変更、非表示の Store では作らない。自動化の動く条件と連鎖の決まりは 03 を参照する。差出人は「hedgehug」である。

### 同期の修復

差出人は「hedgehug」である。診断での修復の通知も、この種類に含める。

## 受信箱

受信箱は、すべての Store のあなた宛ての通知を 1 つの一覧にする(01)。非表示の Store の通知は出さず、未読数にも数えない。表示に戻せば、また出る。見出しは「受信箱」、補足は「同期で届いた変更、メンション、割り当て、上書きされた値」である。

### タブと未読数

| タブ | 出る通知 |
|---|---|
| すべて | すべての種類 |
| メンション | メンション |
| 割り当て | 割り当て |
| ウォッチ | ウォッチ |
| 上書き | 上書き |
| 自動化 | 自動化、自動化が制約で止まった |
| 同期の修復 | 同期の修復 |

各タブに、未読の通知の数を出す。0 件なら数字を出さない。サイドバーの「受信箱」には、「すべて」の未読数を出す。

### 並びと行の表示

通知を作った時刻の新しい順に並べる。

1 行は、次のものからなる。

- 左端の点。未読のときは目立つ色にする。クリックで既読と未読を切り替える
- 種類を示すピル(メンション・割り当て・ウォッチ・上書き・自動化・同期の修復)
- アイテムの種類のアイコン、ID、Store の点、タイトル。クリックすると、通知を既読にして、詳細パネルを開く。接頭辞は Store の中でしか一意でないため、同じ ID のアイテムの通知が並ぶことがあり、Store の点で見分ける
- 通知を作った時刻の相対時間(01 の書式)。メンションの行は、最後に書き換えた時刻
- 差出人のアバターと名前。差出人がなければ「hedgehug」。差出人がその Store のメンバーにいないときは「不明なユーザー」(01)。続けて本文を Markdown で表示する
- 種類によって、本文の下に操作を出す(後述)

通知がアイテムではなくプロジェクトを指すとき(プロジェクトのオーナーの割り当て、プロジェクトの説明へのメンション、プロジェクトの項目の上書き、プロジェクト別のルールの上書き・修復、プロジェクトの ID の振り直し)は、アイテムの代わりにプロジェクト名を出し、クリックでプロジェクトの概要を開く。対象がアイテムでもプロジェクトでもないとき(スプリント、リリース、ワークスペースの設定など)は、その位置に Store の点とワークスペース名を出し(アイコンと ID は出さない)、クリックで通知を既読にして、対象の画面を開く。例: スプリント「Sprint 25」を戻した通知は「● team-a / Web」と出る。開く先は、スプリントとスプリント名の重複・上書きならワークスペースの「スプリント」タブ、リリースなら「リリース」タブ、自動化の無効化・ルールの名前なら設定の「自動化」、プロパティ・値(ステータス・優先度・関連システム)・ワークフロー・テンプレート・接頭辞・ワークスペース名なら設定の該当するサブタブである。アイテムが削除済みのときは「削除されたアイテム」と表示し、リンクにしない(この表示は、アイテムが削除済みのときだけ使う)。ワークスペースが削除済みのときは「削除されたワークスペース」と表示し、リンクにしない。別の Store へ移動したアイテムの通知(「別の Store へ移動したものと重なったとき」)は、位置に旧 ID を出し、クリックで旧 ID の転送記録の画面(02)を開く。旧 ID のリンクは、02 の転送記録と同じ解決(内部 ID でいまの場所を探す)で開く。完全に削除したアイテム・プロジェクト・ワークスペース(08)の通知は、一覧から消える。完全な削除を同期で受け取ったマシンも、そのものの通知を消す。Store をこのマシンから削除したときは、その Store の通知が消える。

### 操作

- **すべて既読にする**: 見出しの右のボタン。いま表示しているタブの通知だけを既読にする。そのタブに未読がなければ無効にする
- **既読と未読の切り替え**: 左端の点をクリックする
- **上書きの通知**: 「あなたの値 X → 残った値 Y」を表示し、「自分の値に戻す」を出す(「上書きの通知」の節)。戻したあとは「自分の値に戻しました」を表示する
- **自動化が制約で止まった通知**: 本文の下に、止まった理由を表示し、次の 2 つのボタンを出す。どちらかを押すと、通知は既読になり、ボタンの代わりに結果のピルを表示する

| ボタン | 動き | ピル |
|---|---|---|
| 制約を無視して {ステータス名} にする | アイテムのステータスを、制約を無視して変える。1 回の保存で、アクティビティには「「{ルール名}」の変更を制約を無視して適用」と残る。自動化は動かない(03)。「適用しました」と表示する | 適用しました |
| 変更しない | 何も保存しない | このままにしました |

アイテムが削除済みのときは、2 つのボタンを出さない。閲覧のみの Store では、2 つのボタンと「自分の値に戻す」を無効にして「閲覧のみの Store です」と添える。

ボタンの有効と無効は、通知を作ったときの値を覚えておき、いまの値と比べて決める。閲覧のみの Store の無効(上)が先で、アイテムが削除済みまたは存在しないときはボタンを出さない(上)。

- 止まった通知: アイテムのいまのステータスが、止まったときのステータスのままのときだけ、「制約を無視して…にする」を有効にする。違えば無効にして「すでに変更されています(いまは {ステータス名})」を添える。「変更しない」は常に有効にする。例: HH-5 が Cancel に変わっていたら「すでに変更されています(いまは Cancel)」
- 上書きの通知: いまの値が通知の「残った値」のままのときだけ、「自分の値に戻す」を有効にする(複数の値は、集合が一致すること)。違えば無効にして「そのあとさらに変更されています(いまは {値})」を添える。通知の「残った値」は、作ったときのままである
- 戻す先の値が使えないときは、無効にして理由を添える。「「Todo」は削除されています」「スプリント「{名前}」は完了しています」「担当者 {ログイン名} はこの Store のメンバーにいません」
- 押した瞬間に、同期や、別のブラウザのタブ・別のプログラムの保存で値が変わっていたときは、保存せず、エラーのトースト「{ID} は先に変更されたため、適用しませんでした」を出して、行を更新する(押す前に無効にするので、起きるのは保存が重なったときだけである)

既読と未読の切り替え、すべて既読、「変更しない」は、Store を変えないので、保存にもアクティビティにも入らない(01)。

### 件数

一度に出すのは 300 件で、さらにあるときは、末尾に「さらに読み込む」を出し、押すと次の 300 件を足す(アクティビティと同じ)。タブの未読数と「すべて既読にする」は、読み込んだ件数でなく全件が対象である。通知を 1 件ずつ消す操作と、古い既読を自動で消す仕組みは設けない(通知はこのマシンだけに保存し、容量が小さく、既読にすれば目立たないため)。

### 空のとき

| タブ | 表示 |
|---|---|
| 上書き | 「お知らせはありません」、補足は「このマシンで変えた値が、同期であとから届いた変更に負けると、ここに出ます。試すには、値を変えてからサイドバーの同期ボタンを押してください。」 |
| 同期の修復 | 「お知らせはありません」、補足は「同期のときに直したもの(番号の重なり、削除された親、親の循環、移動した親に合わせて移した子など)がここに出ます。」 |
| そのほか | 「お知らせはありません」 |

## アクティビティ

アクティビティは、Store の変更の記録を新しい順に並べる画面である。見出しは「アクティビティ」、補足は「Store の git 履歴。1 つの変更が 1 つのコミットです」である。

### 対象

表示中の Store の記録だけを出す。非表示の Store の記録は出さない。記録になるのは、Store を変える保存と、同期の結果(同期の行)だけである。同期の送信と受信そのものは保存ではない。一覧に入るのは次のものである。

- このマシンでの自分の保存
- 同期で受け取った他の人の保存。保存した人の行として、その人が保存した時刻に並ぶ
- 自動化の変更(「「{ルール名}」で{変更の内容}」)。制約で止まった実行は、何も保存しないので出さない(03)
- 操作した人のいない自動の変更。GitHub からのリンクの取り直しと、PR の自動リンク(07)
- 同期の行と、同期での修復
- remote の履歴にそろえた保存(08)。実行者はあなたで、文は「remote の履歴にそろえ、未送信の保存 {N} 件をのせ直し」である。未送信の保存がなくて、保存を作らなかったときは、行を作らない。種類の絞り込みでは「人の変更だけ」に入る

同期の行は、送った保存か受け取った保存が 1 件以上あった同期だけに作る。実行者は「同期」、本文は「origin と同期 (送信 N 件・受信 M 件)」である。両方が 0 件の同期は残さない。同期の行は、同期の結果の記録で、コミットではないので、SHA を出さず、SHA の欄は空にする。

操作した人のいない変更と、同期での修復は、次の文で残す。

| 変更 | 実行者 | 文 |
|---|---|---|
| GitHub からリンクを取り直して状態が変わった | GitHub | {ID} の {リポジトリ}#{番号} の状態を {状態} に変更 |
| 同期で削除を取り消した(削除と変更の重なり) | 同期 | {ID} の削除を取り消し(設定の値のときは「{値の名前}」の削除を取り消し) |
| 同期で重複した名前・接頭辞・キーを直した | 同期 | {種類}「{旧}」を「{新}」に変更 |
| 同期で Issue の二重リンクを直した | 同期 | {ID} の {リポジトリ}#{番号} のリンクを解除 |
| 同期で、削除された親の子を削除済みに入れた | 同期 | {子の ID} を削除 |
| 同期で、完了したスプリントに入ったアイテムを戻した | 同期 | {ID} をバックログに戻す |
| 同期で、実行中が 2 つになったスプリントを計画中に戻した | 同期 | スプリント「{名前}」を計画中に戻す |
| 同期で、完了・中止の分類になった初期ステータスを戻した | 同期 | 初期ステータスを「{未着手の既定}」に戻し |
| 同期で、メンバーの重複を統合した | 同期 | メンバー {ログイン名} の重複を統合 |
| GitHub からリンクを取り直して、リポジトリ名が書き換わった(07) | GitHub | {ID} のリンクを {旧}#{番号} から {新}#{番号} に更新 |
| 保持日数を過ぎたものを自動で完全に削除した(08) | なし | 保持日数を過ぎた削除済み {M} 件を完全に削除(M は、行の下にあるものを含む件数) |
| GitHub が PR を自動でリンクした(07) | GitHub | {ID} に {リポジトリ}#{番号} を自動でリンク |
| GitHub からリンクを取り直して、レビューの状態が変わった | GitHub | {ID} の {リポジトリ}#{番号} のレビューを {状態} に変更 |
| GitHub からリンクを取り直して、タイトルが変わった | GitHub | {ID} の {リポジトリ}#{番号} のタイトルを「{新しいタイトル}」に変更 |
| 同期で、親の循環を切った | 同期 | {ID} を {行き先の ID} の下へ移動(親の循環) |
| 同期で、親と別のワークスペース・プロジェクトにあった子を移した | 同期 | {旧 ID} を {新 ID} に移動(親に合わせる)。プロジェクトだけのときは「{ID} をプロジェクト「{名前}」に移動(親に合わせる)」 |
| 同期で、存在しないスプリントを外した | 同期 | {ID} をバックログに戻す(スプリントが完全に削除) |
| 同期で、存在しないリリースを外した | 同期 | {ID} のリリースを外す(リリースが完全に削除) |
| 同期で、削除された値を指すプロジェクト別のルールを外した | 同期 | プロジェクト「{タイトル}」のルールから「{値の名前}」を削除(削除された値) |
| 同期で、削除された値を指すワークスペースの種類ごとの既定を外した | 同期 | {種類} の既定のテンプレートを変更(削除された値) |
| 同期で、削除された値を指すルールを無効にした | 同期 | 自動化「{名前}」を無効にする(削除された値) |
| 同期で、なくなったプロジェクトのルールを外した | 同期 | プロジェクト「{タイトル}」のルールを削除(プロジェクトがない) |

実行者のない行は、名前を出さず、アイコンを「hh」にする。種類の絞り込みでは「すべて」にだけ出す。

人でない実行者(GitHub・同期・自動化)の保存が、同じ対象の同じ項目を、同じ変更前の値から同じ変更後の値に変えたものが複数のマシンから届いたときは、最も早い保存の 1 行だけを出す。コミットの短縮 SHA も、最も早い保存のものである。「自動化だけ」「同期だけ」の絞り込みと、300 件の数え方も、その 1 行で数える。例: 2 台が同時に作った「Sprint 25 を計画中に戻す」は 1 行になる。「HH-8 の WEB-core#418 の状態を Merged に変更」と「「PR マージで完了」でステータスを Done に変更」も、2 台分ではなく 1 行ずつになる。人の保存は対象にしない(田中さんと佐藤さんが同時に同じ値にしたら 2 行)。通知は、各人の受信箱に 1 行ずつ作る。

### 絞り込み

| 絞り込み | 選び方 | 出る記録 |
|---|---|---|
| ワークスペース | セレクト。「すべて」と、「{Store 名} / {ワークスペース名}」(表示中の全ワークスペース) | そのワークスペースの記録、そのワークスペースがある Store の同期の行、同じ Store の、ワークスペースに属さない記録(メンバーの追加・変更、保持日数の変更、保持日数を過ぎたものの完全削除) |
| 種類 | 「すべて」「人の変更だけ」「同期だけ」「自動化だけ」 | 下の表のとおり |

| 種類 | 出る記録 |
|---|---|
| すべて | すべて |
| 人の変更だけ | 人が行った保存。自動化、GitHub、同期の記録は除く。同期で受け取った他の人の保存は含む |
| 同期だけ | 同期の行と、同期での修復 |
| 自動化だけ | 自動化の記録と、GitHub からの自動の変更 |

ワークスペースと種類は、組み合わせて使える。アイテムの一括変更など、複数のワークスペースにまたがる 1 件の記録は、関わるどのワークスペースを選んでも出る。別の Store へ移したワークスペースの、移動元に残る記録は、移動先に属するので、移動元の Store のワークスペースの選択肢には出ず、「すべて」でだけ見える。この絞り込みは画面の状態で、Store には保存しない(01)。

### 表示

日付ごとにまとめ、見出しは「今日」「昨日」、それより前は「YYYY/MM/DD」にする(01 の日付の書式とは違い、年を省かない)。日付と時刻は、このマシンの時刻帯で表す(01)。同じ日の中は、時刻の新しい順に並べる。保存時刻が未来(進んだ時計で保存したもの)でも、そのまま保存時刻で並べる。

1 行は、次のものからなる。

- 時刻(HH:MM)
- 実行者のアイコン。同期は同期のアイコン、自動化は「A」、GitHub は GitHub のアイコン、人はアバター
- 実行者の名前(同期は「同期」、自動化は「自動化」、GitHub からの自動の変更は「GitHub」、人がその Store のメンバーにいないときは「不明なユーザー」(01))に続けて、記録の本文
- Store のバッジ、ワークスペース名、対象のアイテムの ID(削除済みでなければリンク)、対象のプロジェクト名(削除済みでなければリンク)
- コミットの短縮した SHA。実際のコミットの SHA の先頭 7 桁を出す(同期の行は空にする)

### 件数

一度に出すのは 300 件で、日付の区切りをまたいで数える。さらに記録があるときは、末尾に「さらに読み込む」を出し、押すと次の 300 件を足す。0 件のときは「この条件のコミットはありません」と表示する。

## 同期のあとの完全な削除

削除済みのものを、保持日数を過ぎたら自動で完全に削除する(08)。同期する Store(remote があり、GitHub に使うアカウントがある Store)では、書き込めるマシンが、同期に成功した直後(手動の「今すぐ同期」の成功後も含む)に行う。同期しない Store(remote がない、または GitHub に使うアカウントが「なし」の Store)では、アプリを開いたとき、日付が変わったとき、保持日数を短くしたあとに行う。同期エラーの Store、閲覧のみの Store、サイドバーで非表示の Store では、自動では行わない(表示に戻したときに、同期しない Store はすぐ、同期する Store は次の同期のあとに行う)。複数のマシンが同じものを削除しても、結果は同じである。同期が失敗したとき、オフラインのときは、行わない。

## モックからの変更点

| 項目 | モック | この仕様 | 理由 |
|---|---|---|---|
| 元に戻す(R1-48、F2) | Ctrl+Z、保存のトーストのボタン、コマンドパレットで元に戻せる。同期すると、元に戻せる履歴がすべて消える | なし。元に戻す・やり直しの仕組みを持たない | ユーザーの指示(2026-11-12)。管理が複雑になる。誤操作で押したとき、何を戻したか分からない |
| 通知の作り方(F1、B20) | ウォッチや割り当ての通知を、操作したマシンが他人宛てに作って積む | 各マシンが、あなた宛てだけを、自分の操作と同期で受け取った変更から作る | 通知はマシンごとに持ち、Store に保存しないため |
