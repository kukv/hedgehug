## 全体の方針

- 記録済みの決定「github.com 以外の remote をなくす」(08「モックからの変更点」、行「remote の形」: 「github.com のリポジトリの URL(SSH 形式と HTTPS 形式)に限る」。理由は「同期は GitHub のアカウントでしか認証できず、GitHub 以外の remote は追加できても同期できないため」)を、勧める案では覆さない。フォルダから探すとミラーだけが、この決定とぶつかる。他の 4 項目は、決定の内側で決まる。
- 現行の作りは写さない。変えた主な点は次のとおり。
  - フォルダから探す: bare リポジトリをそのまま remote にするのをやめ、Store のコピーを見つけて、このマシンの Store として取り込む(コピーする)。
  - ミラー: ミラーから取り込むのをやめ、書き込み先(送信のみ)にする。
  - 自動作成: 「Store を追加」にチェックを足す(現行は remote を入れると作る前提の別ダイアログ)。
  - 既定の Store: 使い道を画面で確かめられる 1 か所(パレットからのワークスペース作成)に絞る。
  - 解除: 現行の 2 段のダイアログをやめ、「このマシンから削除」の確認にチェックを 1 つ足す。

## R11-a: フォルダから探す(A #91)

### 1. 何ができるようになるか

画面: 設定「Store」の上部(「GitHub から検索」の隣)と、初回起動の案内の手順 2。ボタン「フォルダから探す」。

操作の例(解除で残したコピーを取り込み直す)。
1. 設定「Store」で「フォルダから探す」を押す。ダイアログ「フォルダから探す」が開く。
2. 「フォルダ」の欄に `/home/taro/hedgehug-kept` を入れて「探す」を押す。
3. 下の一覧に、見つかった Store のコピーが 1 行ずつ出る。行の内容: パス(等幅)、remote(origin が github.com のリポジトリならその URL。そうでなければ「なし(このマシンだけ)」)、名前の入力欄、「取り込む」。
4. 名前を `team-a` にして「取り込む」を押す。このマシンの Store として追加され、行が「取り込みました」(灰)に変わる。元のフォルダは変わらず、そのまま残る。

別の例(ghq で置いた作業用のコピーを見つける)。フォルダに `/home/taro/ghq` を入れると、その下で Store のコピーを持つものが出る。`github.com/org/tasks` の行は remote が `https://github.com/org/tasks.git` と出る。

### 2. 今の仕様への合わせ方

| 現行 | この案 | 理由 |
|---|---|---|
| bare リポジトリを見つけて、そのパスを remote として Store を追加する | Store のコピーを見つけて、中身をこのマシンの保存先にコピーして取り込む。remote に引き継ぐのは github.com の URL だけ | 08「追加」の検査の表「remote が github.com のリポジトリの URL でない…」→「remote は github.com のリポジトリの URL を入力してください」と、ぶつからないようにするため |

| 名前の初期値は `<owner>-<repo>`、`-2`、`store-1` | 07 の規則(末尾の `-tasks` を除く、`.` を `-` に置き換える、先頭が英数字でないあいだ先頭を削る、空になれば空欄) | 07「GitHub から Store を検索」の名前の初期値と同じにして、入口によって名前の付き方が変わらないようにするため |
| 一覧の段階で、bare の中身を読んで Store かどうかを判定する | 同じ。Store のコピーだけを一覧に出す | 07「Store の検索での判定」の理由は「見えるすべてのリポジトリを clone しなくて済むようにするため」。ローカルのフォルダを読むのは clone ではないので、理由に反しない |

**08「追加」の次に、新しい節「フォルダから探す」を足す(全文)**

> ## フォルダから探す
>
> このマシンのフォルダにある Store のコピーを見つけて、このマシンの Store として取り込む。解除のときにコピーを残した(「このマシンから削除」)Store や、別の場所に置いてあるコピーを使い続けるための入口である。入口は、設定の「Store」の「フォルダから探す」と、初回起動の案内の手順 2 である。
>
> ダイアログ「フォルダから探す」に、「フォルダ」の入力欄(入力例は「/home/taro/ghq」)と「探す」ボタンを置く。欄が空のあいだは「探す」を無効にする。「探す」を押すと、そのフォルダの下から、hedgehug の Store のコピー(hedgehug が保存したデータを持つ git リポジトリ)を探す。見つけたコピーの中は、さらに探さない。探している間は「探しています」と表示する。
>
> 一覧の各行に次を表示する。
>
> | 表示 | 内容 |
> |---|---|
> | パス | 見つかったコピーの場所(等幅) |
> | remote | コピーの origin が github.com のリポジトリの URL ならその URL。origin がない、または github.com でないときは「なし(このマシンだけ)」 |
> | 名前の入力欄と「取り込む」ボタン | まだ取り込んでいないもの。名前の初期値は、フォルダ名から末尾の `.git` と `-tasks` を除き、07 の「GitHub から Store を検索」と同じ規則で整えたもの。このマシンに Store が 1 つもないときは、「ログイン名」の入力欄も出す(07 と同じ。初期値は、このマシンのログイン名が設定済みならそれ、なければ空欄) |
> | 「追加済み」(灰) | remote が、すでに追加した Store の remote と同じもの(08「追加」の比べ方)。「取り込む」は出さない |
> | 「取り込みました」(灰) | このダイアログで取り込んだもの。ダイアログは開いたままにする |
>
> 「取り込む」を押すと、名前を「Store を追加」と同じ順で確かめ(形、重複)、合わなければその行の下に赤字で理由を出す。通ったら、コピーの中身をこのマシンの保存先にコピーして、Store を一覧の末尾に追加する。元のフォルダは変えない。remote は上の表のとおり引き継ぎ、「GitHub に使うアカウント」は「Store を追加」と同じ既定にする。色は 07 の「マウント」と同じ既定にする(選択は設けない)。remote があって、アカウントがあるときは、GitHub に書き込みの権限を問い合わせ、読み取りのみなら閲覧のみの Store にする。問い合わせられないときは、書き込める Store にする。取り込んだ Store に「メイン」は作らない。書き込める Store では、「あなた」がメンバーにいなければ、追加した時点で自動的にメンバーに追加する(01)。
>
> トーストは「{名前} を取り込みました」と、必要なら「{ログイン名} をメンバーに追加しました」を、別々に出す。
>
> 見つからなかったときは「Store は見つかりませんでした」、読めないフォルダがあったときは「読めないフォルダが N 件ありました」を表示する。起点のフォルダが存在しない、または読めないときは「フォルダを開けません」を赤字で表示する。

## R11-b: GitHub 上のリポジトリの自動作成と topic(A #94)

### 1. 何ができるようになるか

画面: 設定「Store」の「Store を追加」のダイアログと、初回起動の案内の「新しい Store を作成」(同じダイアログ)。

操作の例(チームの新しい Store を GitHub に作る)。
1. 「Store を追加」を押す。
2. 名前に `team-b`、remote に `https://github.com/org/team-b.git`、GitHub に使うアカウントに「work (@taro)」を選ぶ。
3. remote を入れたので、チェック「GitHub にリポジトリを作る」が選べるようになる。オンにする。
4. 「追加」を押す。「リポジトリを作っています…」と出る。GitHub に `org/team-b` が private で作られ、topic `hedgehug-store` が付く。このマシンに Store が追加され、ワークスペース「メイン」ができ、最初の送信が行われる。
5. トースト「team-b を追加しました。ワークスペース「メイン」を作りました」。

### 2. 今の仕様への合わせ方

| 現行 | この案 | 理由 |
|---|---|---|
| GUI は「Store を作成」ダイアログ。remote を入れると、なければ作る(確認なし)。CLI は `hh store init --remote` | 「Store を追加」に「GitHub にリポジトリを作る」のチェック(初期オフ)を足す | 08「追加」は、すでに追加と作成を 1 つのダイアログにしている(「remote を入れるかどうかで、新しく作るか、すでにあるものを clone するかが分かれる」)。remote を入れただけで作ると、打ち間違えた URL でリポジトリができてしまう。08「追加」の検査の表に「clone できない(URL が違う…)」を断る行があり、その規則と合わないため、チェックで明示させる |
| 作成は private 固定 | 同じ(選択を足さない) | 公開は GitHub で後から変えられ、誤って公開するほうが取り返しがつかないため |
| topic の失敗で全体が失敗し、作ったローカルの bare を消す | topic を付けられなくても、追加は成功にする | 07「Store の検索での判定」で、検索は topic を使わない。topic がなくても機能に影響しないため |
| 作成後の最初の送信が失敗すると、ローカルの Store も消す | Store は消さず、同期エラーにする | GitHub 上にリポジトリが残るため、巻き戻すと二重に作ろうとして詰まる。空のリポジトリは 08「追加」で「最初の送信として認める」ので、次の同期で送れる |
| 組織のリポジトリを作れないと 403 で、「空のリポジトリを GitHub で作って…」と案内 | 07「GitHub との通信に失敗したとき」の表示を使う。案内は添えない | 文言を 1 か所にそろえるため。チェックを外せば、GitHub で作ったリポジトリを clone して追加できる |

topic と 07 の関係: 07 の決定(「一覧の段階では Store かどうかを判定しない」)は変えない。topic は検索に使わず、GitHub 上でこのリポジトリが hedgehug の Store だと見分けるための印として付ける。付けても検索の結果は変わらない。

### 3. 端の場合

| 場合 | 決め方(よりどころ) |
|---|---|
| C1 チェックが選べる条件 | remote が入力されていて、GitHub に使うアカウントが「なし」でないとき。remote が空のときは無効にして「remote を入れると選べます」、アカウントが「なし」のときは無効にして「アカウントを選ぶと使えます」と添える。07「アカウントを 1 つも登録しないとき」: 「使えない入口は無効にし、理由を添える」と同じ形 |
| C2 作る場所(owner) | remote の URL の owner が、選んだアカウントのログイン名(大文字と小文字を区別しない)と同じなら、そのアカウントの個人のリポジトリとして作る。違えば、その owner の組織のリポジトリとして作る |
| C3 すでに空のリポジトリがある | 作らず、そのまま使う。08「追加」: 「空のリポジトリは、Store でないとは扱わない」、08「remote の変更」: 「remote が空のリポジトリは、最初の送信として認める」 |
| C4 すでにあって、空でない | 断る。「{remote} は空ではありません。「GitHub にリポジトリを作る」をオフにして、clone して追加してください」。何も作らない。clone して追加するのは、チェックなしの経路(08「追加」)で決まる |
| C5 作成に失敗した | 07「GitHub との通信に失敗したとき」の表の行(通信できない、認証エラー、書き込む権限がない、利用上限)。何も作らない |

| コピーを残して解除 | (モックにない。現行は、解除の確認ダイアログで「クローンも消す」を選び、消せないときだけ「残して解除」が出る) | 「このマシンから削除」の確認に「このマシンのコピーを残す」を足す(初期オフ)。オンのときは、コピーを消さず、一覧から外すだけで、警告(失われる)は出さない | ユーザーの指示(2026-11-12)で復活。remote のない Store や未送信のある Store を、失わずに外せるようにするため |

### 5. ユーザーに聞くこと

なし。「取り込み直すとき、元のコピーを移して使い続けるか、複製するか」は、元のフォルダを消さない規則(F1。他のフォルダを消す操作を作らないため)から、複製に決めた。

### 6. 記録済みの決定とぶつかるもの

なし。08「このマシンから削除」の「実行すると、このマシンにある Store のコピーを消す」は、チェックがオフの場合として残る。K3 と取り込み直しの手段は、6-1 の選び方に左右される。

## 6. 記録済みの決定とぶつかって、復活の意味が変わるもの

### 6-1. フォルダから探す(R11-a)

- 画面: 設定「Store」の「フォルダから探す」(現行は、ダイアログ「Store を探す」の下部と、初回起動の案内)。
- ぶつかる決定:
  - 08「モックからの変更点」、行「remote の形」: 「github.com のリポジトリの URL(SSH 形式と HTTPS 形式)に限る。入力例は HTTPS の形」。理由は「同期は GitHub のアカウントでしか認証できず、GitHub 以外の remote は追加できても同期できないため」。
  - 08「追加」の検査の表: 「remote が github.com のリポジトリの URL でない…」→「remote は github.com のリポジトリの URL を入力してください」。
  - 06「同期のエラー」の表: remote があってアカウントがなければ「アカウントが設定されていません」(同期エラー)。ローカルのパスの remote でも、アカウントが「なし」なら必ず同期が止まる。
  - 01「閲覧のみの Store」: 閲覧のみは GitHub の権限だけで決まる(ローカルのフォルダの権限は決まりにない)。
- 具体例: 現行の利用者が、`/srv/git/team.git`(自分のマシンや社内の共有フォルダにある bare リポジトリ)を remote に使っていた。設定「Store」で「フォルダから探す」に `/srv/git` を入れると、現行はこの `team.git` が候補に出て、「マウント」でそのパスを remote として Store が追加され、アカウントなしで同期できた。今の仕様では、そのパスは remote に入れられない。

| 案 | 結果 |
|---|---|
| A 決定を覆す。ローカルのパス(bare リポジトリ)も remote に入れられる | 現行と同じ使い方が戻る。直す文書は多い。08 の「追加」の表・検査・「remote の変更」・「remote の形」の記録とその理由の撤回、06 の同期(アカウントなしでもローカルの remote は同期できる規則、同期のエラーの表)、08 の「同期の状況」の文、01 の閲覧のみ(ファイルシステムの書き込み可否で決める規則)、同じ remote の比べ方(パスの比べ方)、07 の remote の形。GitHub のトークンを使わない同期の経路ができ、認証の規則が 2 本になる |
| B 縮める。remote は github.com のままにして、「フォルダから探す」は、このマシンにある Store のコピーを見つけて、コピーして取り込む入口にする(origin が github.com ならその URL を引き継ぎ、そうでなければ remote なしで取り込む) | 記録済みの決定を覆さない。残したコピーの取り込み直し(R11-f)、別の場所に置いたコピー、ghq で置いたコピーが使える。できなくなるのは、bare リポジトリを remote にして、アカウントなしで共有することだけ。例: `/srv/git/team.git` は、中身を取り込めるが、remote なし(このマシンだけ)になる。08 に節を 1 つ足す(R11-a の 4 に全文) |
| C 復活しない | 決定を何も変えない。GitHub から検索(07)だけが残る。ユーザーの「復活する」という指示と食い違う。R11-f の取り込み直しの手段もなくなり、コピーは利用者が手で扱う |

勧める案: B。理由は、決定の理由(認証は GitHub のアカウントのトークンだけ。同期できない remote を作らない)を保ったまま、「フォルダにある Store を使う」という利用の目的(解除で残したコピーを戻す、別のマシンから持ってきたコピーを使う)を果たせるため。A は、「同期はアカウントでしか認証できない」という記録済みの理由そのものを撤回することになる。

### 6-2. ミラー(R11-c)

- 画面: 設定「Store」の Store の枠(現行は「URL で追加」の複数行の入力欄と、枠の remote の一覧の「ミラー」の印)。
- ぶつかる決定:
  - 01「Store で共有するものと、マシンごとに持つもの」の表: 「Store の一覧と、各 Store の名前・remote・GitHub に使うアカウント・色・非表示」(remote は 1 つ)。
  - 06「同期とは」: 「同期は、その Store の remote とこのマシンのあいだで、保存を送り、受け取ることである」(remote は 1 本)。
  - 08「モックからの変更点」、行「remote の形」(github.com だけ)。現行のミラーはどのホストでもよく、ローカルのパスも入る。
  - 06「同期のエラー」の表: 失敗の種類にミラーがない。現行は、ミラーの履歴が無関係だと同期全体が止まる。
- 具体例: team の Store で、origin は `https://github.com/org/team.git`。バックアップとして `https://github.com/taro/team-backup.git`(個人のリポジトリ)と、会社の NAS の `/mnt/nas/team.git` を足したい。

| 案 | 結果 |
|---|---|
| A 決定を覆す。現行どおり(どのホストでもよく、ミラーからも取り込む) | `/mnt/nas/team.git` も足せる。6-1 の案 A と同じ決定の撤回になる(ローカルのパスの remote、アカウントなしの認証、閲覧のみの判定)。さらに、ミラーから取り込む経路ができ、06 の同期の合わせ方(複数の remote からの取り込み、ミラーだけにある履歴が origin に入る)と、R4(強制 push の修復で、ミラーを保留にする)の規則を足す。6-1 で案 A を選ぶなら、この案にそろえる |
| B github.com の中に縮める。2 本目以降も github.com のリポジトリだけ。ミラーは送信のみ(取り込まない)。失敗は Store の状態を変えず、ミラーの行と手動同期のトーストに出す | `taro/team-backup` は足せる。`/mnt/nas/team.git` は足せない(「remote は github.com のリポジトリの URL を入力してください」)。決定は覆さない。取り込まないので、ミラーにだけある変更は手元に来ない。06 の同期の流れ(受け取る、合わせる、送る)は変えず、送るあとに「ミラーへ送る」を足すだけ。R11-c の 4 に全文を書いた |
| C 復活しない | 何も足さない。バックアップは、利用者が GitHub 側で別の仕組みで取る。ユーザーの「復活する」という指示と食い違う |

勧める案: B。理由は、決定の理由(認証は GitHub のトークンだけ)を保てることと、バックアップという用途には送信のみで足りること。取り込む経路を足すと、同時の変更の規則(06)と R4 の規則が二重になるため。注意: B では、ミラーにだけある保存は手元に来ない。ミラーに直接 push する人がいると、ミラーは「ミラーの履歴が先に進んでいます」と出て、送られなくなる。
