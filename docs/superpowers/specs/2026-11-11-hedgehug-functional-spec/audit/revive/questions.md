# 1. プロジェクト別のルール

## Q1. プロジェクトで「使わない」ステータスを、アイテムの作成ダイアログで選べるようにしますか(記録済みの決定とぶつかる)

関連: Q2 で案 C を選ぶと、この質問は不要。Q2 で案 A か案 B を選んだときだけ答える。

どの画面か。プロジェクト HH-P1 の画面で C キーを押すと開く、アイテムの作成ダイアログ。その中の「ステータス」のセレクト。

ぶつかる決定。02 の仕様は、作成のときは遷移の制約を掛けないので、どのステータスでも選べる、と決めている。この決定は「遷移の制約」についてのもので、「プロジェクトで使わないステータス」は別の仕組み。ただし「どのステータスでも」という言い方とぶつかる。

具体例。ワークスペースのステータスは Todo・InProgress・Review・Done・Pending・Cancel の 6 つ。HH-P1 は、設定タブの「使うステータス」で Pending のチェックをオフにしている。HH-P1 の画面で C キーを押し、作成ダイアログのステータスのセレクトを開く。

- 案 a: Pending を出さない。セレクトは Todo・InProgress・Review・Done・Cancel の 5 つ。作ったアイテムは、必ず使うステータスのどれかになる。ダイアログでプロジェクトを、Pending を使う HH-P2 に変えると、Pending が選べる。
- 案 b: 使わないステータスも出す。セレクトは 6 つのまま。Pending を選ぶと、使わないステータスのアイテムができる。HH-P1 のカンバンには「使わない」の Pending の列が出る。

勧める案: a。理由は 2 つ。
- メニューでは選べないステータスが、作成ダイアログでだけ選べると、「使わない」という決めが入口で崩れる。
- 02 の決定の理由は「作成時には移る元がない」こと。これは遷移の制約を掛けない理由で、使わないステータスを選ばせない理由とは関係がない。

案を選ぶと変わる仕様。
- 案 a: 02「入力の検査」の「どのステータスでも選べる」を「そのプロジェクトで使うどのステータスでも選べる」にする。03「遷移の制約」の「任意の初期ステータスで作れる」を「使うステータスなら任意で作れる」にする。02「モックからの変更点」の「作成時のステータス」の行の理由に「ただし、プロジェクトが使わないステータスは選べない」を足す。
- 案 b: これらの文は変えない。03 の「使わないステータスの扱い」に「作成では、使わないステータスにもなる」を足す。

## Q2. プロジェクトで「使わない」にしたステータスを、どの操作で断りますか

関連: 案 C を選ぶと、Q1 は不要。案 A か案 B を選ぶと、Q1 にも答える。

どの画面か。プロジェクト HH-P1 の設定タブの「使うステータス」。その結果が出る場所は 4 つある。Task のステータスのメニュー、検索のカンバン、作成ダイアログ、設定の「自動化」のルール。

具体例。HH-P1 の設定タブで「Pending」のチェックをオフにする。そのあと、次の 3 つの操作をする。
- (ア)HH-P1 の Task のステータスのメニューを開く。
- (イ)検索のカンバン(`project:HH-P1` で絞る。列はワークスペースのステータスを合わせたものなので Pending の列が出る)で、HH-P1 の HH-5(InProgress)のカードを Pending の列へドラッグする。
- (ウ)ワークスペースのルール「PR を閉じたら Pending」が、HH-P1 の HH-8 に対して動く。

- 案 A: ステータスを選ぶすべての操作で選択肢に出さず、選ぼうとしたら断る。
  - (ア)メニューに Pending が出ない。
  - (イ)「このプロジェクトでは「Pending」を使いません」と出て、何も変わらない。
  - (ウ)実行を止める。受信箱の「自動化」に「このプロジェクトでは「Pending」を使いません」と出る。ボタンは「制約を無視して Pending にする」と「変更しない」。
- 案 B: 画面の選択肢とカンバンの列にだけ出さない(選ぶ操作は断らない)。
  - (ア)メニューに Pending が出ない。
  - (イ)ドラッグは通る。HH-5 は Pending になる。
  - (ウ)ルールは動く。HH-8 は Pending になる。使わないステータスのアイテムは、プロジェクトのカンバンの「使わない」の列に出る。
- 案 C: カンバンの列にだけ出さない(現行の実装)。
  - (ア)メニューに Pending が出る。
  - (イ)ドラッグは通る。
  - (ウ)ルールは動く。作成ダイアログと一括変更にも Pending が出る。

勧める案: A。理由は 3 つ。
- 現行の画面の補足文は「カンバンの列と、ステータスの選択肢に出すもの」と言っている。選択肢から消えると利用者は期待する。
- 使わないと決めたステータスに、ルールが黙ってアイテムを動かすと、プロジェクトのカンバンに列が現れ、決めと食い違う。
- 断る範囲を遷移の制約と合わせられる(移動・同期・値の置き換え・診断の修復では断らない)。新しい規則が少ない。

案を選ぶと直す仕様の範囲。
- 案 A: 02 のステータスのメニュー、04 の一括変更の一覧と理由、04 のドラッグの断り、03 の「制約で止まったとき」、03 の「使うステータス」の節。専用ルールが使っているステータスは「使わない」にできない、という規則も入る。
- 案 B: 02 のステータスのメニューと、04 の一括変更の一覧。専用ルールが使っていても「使わない」にできる。
- 案 C: メニューと一括変更は直さない。カンバンの列の補足文だけ「…カンバンの列に出ません」にする。

# 2. 見積もり時間とレポート

## Q3. 作業時間の見出しで、「見積もり」という言葉を、ポイントと時間の両方を指す総称にしますか(記録済みの決定を覆す)

どの画面か。アイテムの詳細パネルの「作業時間」の見出し。

覆す決定。02「作業時間」の最後の項目に「見積もりは、ポイントのプロパティであり、作業時間とは別のものである」とある。05 の見積もりと実績の定義も、見積もりを「見積もりのポイント」としている。時間型の見積もり(プロパティ「見積もり時間」)を復活すると、この言葉の使い方が変わる。

具体例。HH-5 は、見積もり時間 6、ポイント 3、作業時間 2 時間。詳細パネルを開く。

- 案 A: 「見積もり」を総称にする。ポイントは「ポイント」、時間は「見積もり時間」と呼ぶ。見出しは「2 時間 · 見積もり 6 時間 · 3 pt」。02 の 2 か所(作業時間の見出しと最後の項目)と 05 の列名を書き換える。
- 案 B: 「見積もり」はポイント専用のまま残す。時間の欄に別の名前(例: 「所要見込み」)を付ける。見出しは「2 時間 · 見積もり 3 pt · 所要見込み 6 時間」。02 と 05 の既存の文は変えない。ただし、03 でポイントのプロパティの名前は「ポイント」なのに、見出しだけ「見積もり」と呼ぶ食い違いが残る。

勧める案: A。理由は 2 つ。
- 現行の利用者は、時間の欄を「見積もり」と呼んでいる。
- ポイントの名前の食い違いも解ける。「時間型の見積もり」というご指示とも合う。

## Q4. 見積もりと実績の表を、ポイントと時間で 1 つにしますか(記録済みの決定を広げる)

関連: Q3 と、見積もり時間の復活という話でつながる。

どの画面か。ワークスペース HH の「レポート」タブの最下段にある区画「見積もりと実績」。

広げる決定。05「見積もりと実績」は、対象を「ポイントが設定されている(0 を含む)作業項目のうち、作業時間の記録が 1 件以上あるもの」と決めている。時間の見積もりを足すと、この定義を広げることになる。なお、見積もり時間はプロパティとして復活させるだけで、レポートには出さない案もある。ご指示(「見積もりと実績のレポートを復活」)に反するため、選択肢に入れていない。

具体例。Sprint 24 に 3 件のアイテムがある。
- HH-12: ポイント 3、見積もり時間 2、作業時間 3 時間
- HH-15: ポイント 5、見積もり時間なし、作業時間 8.5 時間
- HH-18: ポイントなし、見積もり時間 0.5、作業時間 0.25 時間

- 案 A: 1 つの表に、ポイントと見積もり時間の両方を載せる。区画は 1 つ。列は「アイテム・ポイント・見積もり時間・作業時間・差・時間/pt」。HH-12・HH-15・HH-18 が 1 行ずつ出る。使っていない側の列は「—」になる。05 の区画の数と並びは変わらない。
- 案 B: 現行の時間の比較を別の区画に分ける。「見積もりと実績(ポイント)」と「見積もりと実績(時間)」の 2 区画になる。ポイントの表には HH-12・HH-15 が、時間の表には HH-12・HH-18 が出る。HH-12 が 2 つの表に出る。05 の区画が 1 つ増える。05 の既存の節は変えない。
- 案 C: ポイントの表をやめて、現行の時間の比較に置き換える。区画は 1 つ。列は「アイテム・見積もり時間・作業時間・差」。HH-15 は出ない。「時間/pt」の列と、「ポイントと作業時間の両方があるアイテムがありません」の案内が消える。ポイントで見積もるチームには使えなくなる。

勧める案: A。理由は 3 つ。
- ポイントで見積もる人、時間で見積もる人、両方付ける人のすべてに、1 つの表で足りる。
- HH-12 を 2 か所で探さなくてよい。
- 案 C は、仕様で決めたポイントの表を消す。案 B は、同じアイテムが 2 回出る。

案 A を選ぶと、ポイントだけのアイテムの行は「見積もり時間」と「差」が「—」になるだけで、既存の行は変わらない。

## Q5. スプリントのボードを、「スプリント」タブのどこに置きますか

どの画面か。ワークスペース HH の「スプリント」タブ。実行中のスプリントのカード。

具体例。実行中の Sprint 24 には、ゴール「ログインを軽くする」、進捗「5 / 12 件 · 18 / 30 pt」、アイテム 12 件がある。朝の確認で、HH-15 を「Doing」から「Review」へ動かしたい。残り日数と、途中で増えた量も見たい。

- 案 A: Sprint 24 のカードの「アイテム 12 件」の欄に、「リスト」と「ボード」の切り替えを置く。最初はボード。カードの中に、進捗、「途中で追加 +3 pt」、小さいバーンダウン、ボードが並ぶ。HH-15 をそのまま「Review」へドラッグできる。「リスト」に切り替えると、今の仕様のリストが出る。計画中と完了のカードは変わらない。
- 案 B: カードは今の仕様のまま(リストだけ)。カードのメニューに「ボードを開く」を足す。押すと、「カンバン」タブが `sprint:"Sprint 24"` の条件で開く。ボードを見るのに画面が移る。小さいバーンダウンと「途中で追加」は出ない。
- 案 C: 現行のとおり、スプリントのタブのカード一覧の上に、帯とボードを置く。実行中のスプリントがあるときだけ出る。カードの下のアイテムのリストと、同じアイテムが 2 か所に出る。

勧める案: A。理由は 2 つ。
- 実行中のスプリントは 1 つ。そのカードを先頭に置き、中にボードを置けば、アイテムを出す場所が 1 か所で済む。画面を移らずに動かせる。
- 案 B は、確認のたびにタブを移る。案 C は、同じアイテムが 2 か所に並ぶ。

# 3. GitHub

## Q6. PR をアイテムに自動でリンクする「印」を、画面からコピーできるようにしますか(記録済みの決定とぶつかる)

どの画面か。アイテム WEB-1 の詳細パネル、GitHub の欄。「PR をリンク」「Issue をリンク」のボタンの横に、新しいボタンを置くかどうか。

用語。「印」は、PR のタイトル・本文・コメントに書く 1 行で、`hedgehug:` の後ろにアイテムの内部の ID を続けたもの(`hh:` でも同じ)。印があると、PR がそのアイテムに自動でリンクされる。

現行の事実。印を作るのはコマンド `hh pr`(CLI。仕様の外)だけ。画面の「PR を作成」は、`hh pr` のコマンドをコピーするだけ。

ぶつかる決定。
- 01「用語と階層」の「内部の ID」: 内部の ID は画面に出ない。
- 02「詳細パネル」: 「ID をコピー」のボタンがコピーするのは、画面の ID(WEB-1 など)。
- 報告書の A #11: 現行の「ULID を表示し、コピーできる」機能の廃止が記録されている。

そのため、画面から内部の ID を取り出す手段が、今の仕様にはない。

具体例。WEB-1 の PR を GitHub で作る。PR の本文に印を書きたい。

- 案 A: 「PR 用の印をコピー」ボタンを足す。押すと `hedgehug:` で始まる 1 行がコピーされ、「コピーしました。PR の説明に貼ってください」と出る。内部の ID は画面に表示しない(貼った先の GitHub では見える)。印を本文に貼ると、WEB の接頭辞を APP に変えても、WEB-1 を別のワークスペースや別の Store へ移しても、印は同じアイテムに付く。本文に「WEB-1」と書いただけの PR は、接頭辞を変えると付かなくなる。変わる決定は、02 の「ID をコピー」の例外(コピーする文字列が画面の ID でない)と、01 の「画面に出ない」(画面には出さないが、コピーでは渡す)。
- 案 B: 印を読むだけにする。画面に印を書く手段は置かない。印を書くのは、仕様の外の道具(`hh pr` など)に任せる。画面だけを使う人は印を書けない。印は CLI を使う人にだけ効く。変わる決定はない。
- 案 C: 印をやめる。ブランチ名と、本文の ID(「WEB-1」の形)だけで結びつける。接頭辞を変えたあと、アイテムを移したあとは、本文の ID もブランチ名も効かなくなる。付け直すには、手でリンクする。

勧める案: A。理由は 2 つ。
- 接頭辞を変えたり、アイテムを移したりしたあとも効き続けるのは印だけ。印の意味はここにある。
- 案 B は、画面の利用者に印を書く手段がなく、読むだけで意味がない。案 C は、復活の範囲を縮める。

案 A の費用は、ボタン 1 つと、01・02 の 2 つの文への例外の追記。

## Q7. マージされずに閉じた PR を、「すべてマージ済み」の条件で数えますか

どの画面か。設定の「自動化」の、ルール作成ダイアログのチェックボックス「リンク中の PR がすべてマージ済みのときだけ」。結果が出るのは、アイテムの詳細パネルの GitHub の欄。

具体例。アイテム WEB-1 に PR を 2 つリンクしている。
- #12 は Merged。
- #13 は Closed。別の PR #14 に作り直したため、マージされずに閉じた。

ルール「全 PR マージで Done」(チェックボックスはオン)がある。#12 がマージされ、GitHub の読み取りが走る。

- 案 a: Closed があると条件は通らない(現行のとおり)。WEB-1 は完了にならない。条件を通すには、詳細パネルの GitHub の欄で #13 のリンクを「×」で解除する。解除した #13 は「解除の記録」に入り、もう自動では付かない。
- 案 b: Closed は数えない。Merged の #12 だけが数えられ、WEB-1 は Done になる。#13 のリンクは残る。
- 案 c: Closed があるときは、ルールを動かさず、通知を出す。「自動化」の通知で、Closed の PR があることを知らせ、利用者が選ぶ。通知の種類と本文が増える。

勧める案: b。理由は 2 つ。
- 取り下げた PR がリンクに残るのは、ふつうに起こる。そのたびに解除させるのは手間。PR の自動リンクも、Closed の PR を新しくリンクしない。考え方がそろう。
- 案 a は現行のとおりだが、取り下げた PR が残るアイテムで、条件が通らないことに気づきにくい。

案 b の文が、案の文書にはすでに書いてある。案 a を選んだときは、03「作成ダイアログの項目」の「(マージされずに閉じたものを除く)」と、R7-18 の「Closed を除いた」を消す。

## Q8. 「計画なし」で閉じた Issue でも、ルール「リンクした Issue が閉じたとき」を動かしますか

どの画面か。設定の「自動化」のルール「Issue 完了で Done」(きっかけ「リンクした Issue が閉じたとき」、すること「ステータスを Done に」)。結果が出るのは、アイテムの詳細パネルの GitHub の欄の Issue の行。

関連: 「Issue が閉じたとき」のルールそのものを復活することは、記録済みの決定とぶつかるが、選ぶ必要はない。末尾の「選んでいただく必要のない決定の変更」に書いた。

具体例。アイテム WEB-5 に Issue(example-org/web#30)をリンクしている。GitHub 上で #30 が「Close as not planned」(計画なし)で閉じられる。

- 案 a: 閉じた理由を区別しない。閉じたら動く。WEB-5 は Done になる。作業をしないと決めたのに、完了として数える。仕様の変更は少ない(Issue の状態は Open と Closed の 2 つのまま)。
- 案 b: 「完了」で閉じたときだけ動く。リンクに閉じた理由(完了・計画なし)を保存し、詳細パネルの Issue の行に「Closed(計画なし)」と出す。WEB-5 は動かない。利用者が手で Cancel にする。07 の Issue の項目に、閉じた理由が足される。
- 案 c: 理由ごとに別のきっかけにする。「Issue が完了で閉じたとき」「Issue が計画なしで閉じたとき」の 2 つ。計画なしのときに Cancel へ動かすルールを作れる。きっかけが 7 つになる。

勧める案: b。理由は 3 つ。
- 「計画なし」の Issue が完了として数えられると、レポート(05)の完了数と速度がずれる。
- 案 a は、間違った Done を利用者が直す手間が出る。案 c は、仕様が増える。
- 案 b は、閉じた理由の保存が 1 項目増えるだけ。現行も閉じた理由を保存している(`StateReason`)。

案 b の文。07「PR・Issue の状態で動く自動化」の「Issue が閉じたとき」の行を、「Issue をリンクして、状態が Closed で、閉じた理由が「完了」のとき。リンク済みの Issue が、Open から、閉じた理由が「完了」の Closed に変わったとき」にする。07「PR と Issue のリンク」の冒頭に「Issue の Closed は、閉じた理由(完了・計画なし)も持つ」を足す。

# 4. 同期

## Q9. 同期で、消えたワークスペースを書き戻す機能を、取り下げますか(復活の依頼を縮める)

どの画面か。設定の「Store」の枠のワークスペースの一覧(復活したワークスペースが出る場所)と、サイドバーのワークスペース。

現行の動き。同期のマージで、ワークスペースに属するアイテムが残っているのに、ワークスペースのファイルが消えているとき、共通の祖先の内容でファイルを書き戻す。

調べた結果。hedgehug の操作でワークスペースのファイルが消えるのは、次の 2 つだけ。どちらも、仕様が「復活させない」と決めている。復活の意味が成り立つ場面がない。
- 完全な削除。06「完全な削除と重なったとき」は「完全な削除を優先する」。
- 別の Store への移動。06「別の Store へ移動したものと重なったとき」は「移動を優先する」。

具体例 1(完全な削除)。太郎さんが、削除済みのワークスペース WEB を、保持日数を過ぎたので完全に削除する。同期の前に、花子さんが WEB に WEB-45 を作っていた。
- 仕様のとおりなら、WEB-45 も完全に削除される。花子さんに「WEB は完全に削除されたため、あなたの変更は反映されませんでした」が届く。
- 書き戻すと、空の WEB が戻り、WEB-45 だけが入った WEB が現れる。完全な削除が取り消される。

具体例 2(別の Store への移動)。太郎さんが、WEB を team-b へ移す。同期の前に、花子さんが team-a の WEB に WEB-45 を作っていた。
- 仕様のとおりなら、WEB-45 は反映されない。
- 書き戻すと、team-a に空の WEB が戻り、team-a と team-b に WEB が並ぶ。

- 案 A: 取り下げる。同期は何もしない。仕様は変えない。
- 案 B: 現行のとおり、共通の祖先から書き戻す。06 の 2 つの節に「ワークスペースだけは、中身が残っていれば書き戻す」という例外を足す。
- 案 C: 共通の祖先から、削除済みの状態で書き戻す。復元するかどうかは、設定の「削除済み」の一覧で選ぶ。完全な削除を優先する決定を弱める。

勧める案: A。理由は、完全な削除を優先する決定と、移動を優先する決定の、両方と矛盾しないのが A だけであること。復元する意味のある場面もない。

## Q10. 同期で、規則に合わない接頭辞を元の値に戻す機能を、縮めた形で残しますか(復活の依頼を縮める)

どの画面か。ワークスペースの設定の「一般」の接頭辞。アイテムの ID の表示。

現行の動き。同期のマージの結果の接頭辞が、現行の有効の定義(英大文字で始まる 2〜10 文字、必須)を満たさず、共通の祖先の接頭辞が有効なとき、祖先の値に戻す。

問題。今の仕様の有効な値は、現行の定義より広い。03「接頭辞」は、空にすること(「空にすると #番号 になります」)を認めている。1 文字の接頭辞も有効。現行の定義のまま戻すと、有効な操作を取り消してしまう。

具体例 1。太郎さんが、ワークスペース WEB の接頭辞を空にして送る。花子さんは、その前の状態から、ワークスペースの名前だけを変えていた。花子さんが同期すると、マージの結果の接頭辞は太郎さんの値(空)になる。現行の定義では空は不正なので、同期が祖先の「WEB」に戻す。太郎さんの操作が、気づかないうちに取り消される。06「同期とは」の「同期が行われても、保存の内容は利用者が気づかないうちに書き換わらない」に反する。

具体例 2。git の操作で、接頭辞の欄が「web-1」に手で書き換えられたものが、同期で届く。03 の検査に合わない値が Store に入る。hedgehug の操作では、仕様の有効な定義に合わない値はできない。起きるのは、このような外部の編集だけ。

- 案 A: 取り下げる。同期は何もしない。
- 案 B: 同期は何もしない。設定の「診断と修復」に、行「接頭辞が規則に合わない」を足す。修復は、接頭辞を「WS」にする(すでにあれば WS2…)。
- 案 C: 縮めた形で、同期で戻す。マージの結果の接頭辞が仕様の定義に合わず、共通の祖先の接頭辞が仕様の定義に合うときだけ、祖先の値に戻す。祖先がないとき、祖先も合わないときは、何もしない。「同期の修復」として保存する(実行者「同期」)。接頭辞を最後に保存した人に、「ワークスペース「{名前}」の接頭辞「{不正な値}」は使えないため、「{祖先の値}」に戻しました」と通知する。アクティビティは「ワークスペース「{名前}」の接頭辞を「{不正な値}」から「{祖先の値}」に戻す」。旧い接頭辞の記録(03)は増やさない。

勧める案: C。理由は 3 つ。
- 仕様の有効の定義を使えば、利用者の操作を取り消さない。
- 外部で壊れた接頭辞を、利用者が最後に使っていた値へ戻せる。
- 何も起きなければ、何もしないので、害がない。

## Q11. 親のアイテムが別の Store へ移ったとき、同期で、その下に作られた子をどう扱いますか(復活の依頼を縮める)

どの画面か。移動元の Store のツリーと、花子さんの受信箱。

ぶつかる決定。06「別の Store へ移動したものと重なったとき」は「移動を優先する。変更した人の変更は反映されない」。理由は、二重のアイテムを作らないため。現行の動きは、この決定に例外を作っている。ご指示の「親が別の Store へ移った場合を含む」を縮める案でもある。

具体例。太郎さんが、Epic HH-5 を team-b へ移す(WEB-12 になる)。同期の前に、花子さんが team-a で、HH-5 の下に Story HH-31「リリースノート」を作っていた。

- 案 A: 06 の規則のとおり、HH-31 は反映されない。花子さんの受信箱に「HH-5 は 太郎 が team-b へ移動したため、あなたの変更は反映されませんでした。移動先は WEB-12 です(HH-31「リリースノート」)」が出る。花子さんは、WEB-12 の下に HH-31 を作り直す。
- 案 B: 現行のとおり、HH-31 を HH-5 の祖先(プロジェクト)の下に残す。花子さんの作ったものは残る。06 の「変更した人の変更は反映されない」に、「子の追加は反映する」という例外ができる。HH-31 は親を失って、team-a のプロジェクトの直下の Epic に並ぶ。
- 案 C: HH-31 を、移動先の Store へ送る。同期の修復は、どのマシンでも同じ結果にならなければならない(06「修復のルール」)。移動先の Store を持たない、書き込めない、非表示にしているマシンがあるので、成り立たない。

勧める案: A。理由は 3 つ。
- 06 の記録済みの決定と矛盾しない。
- HH-31 のタイトルが通知に残るので、作り直せる。
- 案 B は、花子さんが、親が別の Store に移ったことに気づかないまま、HH-31 が別の場所に残る。

## Q12. 親子の輪を切ったあとに残る、種類に合わない親子を、同期でも直しますか

関連: 同期の「親の循環」の修復を復活する案についての質問。Q9〜Q11 とは独立している。

どの画面か。ツリーと、設定の「診断と修復」。

前提。2 人の操作が入れ違うと、親子が輪になることがある。同期の修復は、輪の中で番号が最大のアイテムを、プロジェクトの最初の Epic の下へ動かして、輪を切る(08 の「親がない」の修復と同じ)。このとき、輪の他のアイテムが、種類のルールに合わない親子のまま残る。

具体例。Epic HH-1 の下に Task HH-8 と HH-9、HH-8 の下に Step HH-10、HH-9 の下に Step HH-11 がある。
- 太郎さんが、HH-11 を「種類を変更」で Task にしてから、HH-10 を、いま Task になった HH-11 の下へ「移動…」で移す。
- 花子さんが、HH-10 を「種類を変更」で Task にしてから、HH-11 を、Task になった HH-10 の下へ移す。
- 同期すると、HH-10 と HH-11 が互いの親になる。
- 同期の修復が、番号が大きい HH-11 を HH-1 の下へ動かす。
- HH-10(Task)の親が HH-11(Task)のまま残る。01 の親子の表では、Task の下に置けるのは Step だけ。

- 案 A: 輪に入っていたアイテムの親が、種類のルールに合わないときも、同期で動かす。HH-10 も HH-1 の下へ動く。太郎さんと花子さんの両方に通知が出る。06 の「親が循環したとき」に 1 文足す。
- 案 B: 同期では動かさない。設定の「診断と修復」の「種類に合わない親子」に残す。HH-10 は、診断を実行するまで、Task の下の Task として残る。

勧める案: A。理由は、修復のあとにツリーがルールに合う状態になり、診断を実行しない利用者でも、ルールに合わない親子を見ずに済むこと。

## Q13. 削除済みのスプリント・リリースを指すアイテムを、同期でバックログに戻しますか

どの画面か。スプリントの画面と、アイテムの詳細パネルの「スプリント」欄。設定の「削除済み」の「復元」。

具体例。花子さんが Sprint 25 を削除する。同期の前に、太郎さんが HH-12 を Sprint 25 に入れていた。同期すると、Sprint 25 は削除済みで、HH-12 は Sprint 25 を指している。

- 案 A: 同期の修復が、HH-12 をバックログに戻す(参照を書き換える)。太郎さんの受信箱に「スプリント「Sprint 25」は削除されたため、HH-12 をバックログに戻しました」が出る。花子さんが Sprint 25 を復元しても、HH-12 は戻らない。バックログに戻したのは削除の操作ではなく同期の修復なので、05 と 08 の「同じ削除の操作でスプリントから出たアイテムも戻る」の対象にならない。
- 案 B: バックログに戻さない。HH-12 は参照を残したまま、画面ではバックログに出る(05「存在しないスプリントとリリースの参照」の読み替えを、削除済みにも広げる)。花子さんが Sprint 25 を復元すると、HH-12 は Sprint 25 に入った状態に戻る。保持日数を過ぎて Sprint 25 が完全に削除されたら、その保存で HH-12 の参照も消える(08「完全に削除」に足す)。完全に削除されたあとに届いた参照は、同期の修復が消す。

勧める案: B。理由は 4 つ。
- 08「宙づりの関連」は、削除済みの相手との関連を壊れた状態に数えず、復元で戻す。それと揃う扱いになる。
- 太郎さんの「入れる」操作を、花子さんの復元で取り戻せる。
- 参照を書き換えないので、バーンダウンの「スプリントから出た日」(05)に、同期の修復の日が混ざらない。
- 「同期の修復で子を削除済みにした」ときの復元の扱いは、仕様に書かれていない(08「復元の単位」)。このあいまいさを、スプリントに持ち込まない。

## Q14. 「remote の履歴にそろえる」を押したあと、このマシンの古い履歴を残しますか

どの画面か。設定の「Store」の確認ダイアログ「remote の履歴にそろえる」。強制 push などで remote の履歴が書き換わったときに出る。

具体例。太郎さんが git で、誤って 3 日前の状態へ remote を巻き戻した。花子さんは、巻き戻しの前の履歴をこのマシンに持っている。花子さんが「そろえる」を押す。

- 案 A: 残さない。古い履歴は消える。3 日分の HH-20〜HH-40 が、花子さんのマシンからも消える。押す前なら、古い履歴を使って、git で remote を元に戻せる。押したあとは戻せない。確認ダイアログが「元に戻せません。」と先に言う。のせ直せなかった変更の内容は、受信箱に全文で残る。
- 案 B: のせ直せなかった変更があるときだけ、古い Store を丸ごと別の場所へ残す。場所をトーストに出し、設定の「Store」から削除できる。現行(古い Store を `.kept-{時刻}` に残し、消す操作はない)を、削除できる形にしたもの。秘密を消す目的の書き換えのときは、古い履歴がこのマシンに残る。
- 案 C: そろえるときは、いつも、古い Store を丸ごと残す。設定の「Store」に「退避した Store」の一覧と「削除」ボタンを置く。巻き戻しが誤りだったときの最後の保険になる。画面と保存の置き場が増える。秘密を消す目的の書き換えのときは、古い履歴がこのマシンに残る。

勧める案: A。理由は 3 つ。
- 押すまでは、このマシンの履歴を触らない。誤った書き換えから戻す道は、押す前に残っている。
- 押したあとに残るのは、書き換えた人の意図に反する古い履歴。消すための操作が別に要る。
- のせ直せなかった花子さんの変更は、受信箱に全文で残る。失うのは、remote から消えたほかの人の変更だけ。それは、ほかのマシンと remote を元に戻す道で守る。

# 5. クエリと関連システム

## Q15. 検索の「更新日」を、どの変更で新しくしますか

どの画面か。検索のテーブルの列「更新日」と、絞り込み欄の `sort:-updated`、`updated>-7d`。

前提。詳細パネルの「履歴」には、人の変更のほかに、GitHub が書いた変更(リンクした PR の状態・タイトル。復活でレビューの状態と自動リンクも加わる)と、同期の修復(親の輪を切る、スプリントの参照を消すなど)も、実行者「GitHub」「同期」として残る。コメント・作業時間・関連・ウォッチは履歴に残らない。

具体例。HH-5 は 11/1 に人がタイトルを変えたきり。11/10 に太郎さんがコメントを書いた。11/12 の夜中に、GitHub の読み取りで、リンクした PR のレビューが「承認済み」に変わった。検索のテーブルを `sort:-updated` で並べる。

- 案 A: 履歴のいちばん新しい行の時刻を使う(実行者を問わない)。HH-5 の更新日は 11/12。詳細パネルの履歴の最上段と一致する。PR の多いアイテムは、人が触っていなくても上に来る。
- 案 B: 履歴の行のうち、実行者が人か自動化の行だけを使う(実行者「GitHub」「同期」の行は使わない)。HH-5 の更新日は 11/1。「最近、人が手を入れたもの」の並びになる。列「更新日」の見出しのヒントに「GitHub と同期による変更は含みません」と出す。
- 案 C: コメント・作業時間・関連・GitHub リンクの追加と解除・ウォッチも含める(アクティビティに残る変更すべて)。HH-5 の更新日は 11/12。コメントの多いアイテムが上に来る。

勧める案: B。理由は 3 つ。
- `updated>-7d` で探したいのは、最近人が手を入れたもの。GitHub の読み取りは 5〜60 分ごとに起き、レビューの変化も多いので、案 A・C では人が触っていないアイテムが混ざる。
- 詳細パネルの履歴の行には実行者が出るので、更新日が履歴の最上段とずれる理由は画面で確かめられる。
- 案 C は、コメントのやり取りが多いだけのアイテムが上に来る。

## Q16. テーブルの「グループ」の「関連システム」で、複数の値を持つアイテムを、いくつのグループに入れますか

どの画面か。テーブルのツールバーの「グループ」メニューの「関連システム」(クエリでは `group:system`)。

具体例。関連システムの定義順は Web、API、iOS。HH-5 は「Web, API」、HH-6 は「API」、HH-7 は「iOS, Web」、HH-8 は値なし。

- 案 A: 値の数だけのグループに入る。「Web(2)」に HH-5・HH-7、「API(2)」に HH-5・HH-6、「iOS(1)」に HH-7、「関連システムなし(1)」に HH-8。HH-5 と HH-7 は 2 回出る。見出しの件数の合計は 6、アイテムは 4 件。ツールバーは「4 件」と出る。Web に関わるものを、1 つの見出しで全部見られる。
- 案 B: 最初の値のグループだけに入る(定義順で最初)。「Web(2)」に HH-5・HH-7、「API(1)」に HH-6、「関連システムなし(1)」に HH-8。HH-7 は iOS を持つのに、iOS の見出しがなく、Web の下にだけ出る。見出しの合計は 4 で、アイテムの数と一致する。
- 案 C: 値の組み合わせを 1 つのグループにする。「Web, API(1)」「API(1)」「Web, iOS(1)」「関連システムなし(1)」。見出しが組み合わせの数だけ増え、1 件ずつになりやすい。

勧める案: A。理由は 3 つ。
- 「関連システム別に見る」使い方では、Web と API の両方に関わるアイテムは、どちらの見出しでも見えるべき。
- 案 B は、iOS の見出しがなく、iOS のアイテムが探せない。案 C は、まとまりにならない。
- 案 A の代償は、見出しの件数の合計がアイテム数と合わなくなること。ツールバーの件数と、選択・一括変更をアイテム単位で数えることで、数え間違いを防ぐ。

## Q17. 関連システムの一括変更を、「追加」と「削除」にしますか、「置き換え」にしますか

どの画面か。テーブルで複数のアイテムを選んで開く「一括変更…」ダイアログの、項目のセレクト。

具体例。HH-5 は「Web, API」、HH-6 は「API」、HH-7 は「iOS, Web」。この 3 件を選び、CI を足したい。

- 案 A: 「関連システムを追加」と「関連システムを削除」の 2 つ。「追加」で CI を選ぶと、HH-5 は「Web, API, CI」、HH-6 は「API, CI」、HH-7 は「iOS, Web, CI」になる。「削除」で Web を選ぶと、HH-5 は「API」、HH-7 は「iOS」になる(HH-6 は変わらない)。他の人が同時に足した値は残る。全部を揃えて同じ値にしたいときは、いまの値を「削除」で消してから「追加」する(2 回)。
- 案 B: 「置き換え」だけ。値で CI を選ぶと、3 件とも「CI」だけになる。HH-5 の Web と API が消える。CI を足すだけのつもりでも、各アイテムの元の値を打ち直す方法がない。他の人が同時に足した値も消える(06 の上書きの通知の対象になる)。
- 案 C: 3 つとも。セレクトに「関連システムを追加」「関連システムを削除」「関連システムを置き換える」を並べる。置き換えを選べば、全件を 1 つの値にできる。選択肢が増え、置き換えは取り返しにくい操作。

勧める案: A。理由は 3 つ。
- 一括変更でよくあるのは「この 10 件に API を足す」「この 10 件から iOS を消す」。置き換えを使う場面は少ない。
- 置き換えは、選んだ全アイテムの他の値を消す。確認ダイアログでも気づきにくい。
- 06 の「1 つずつの追加と削除を、両方とも生かす」とも、案 A が合う。全件を 1 つの値にしたい場面は、「削除」と「追加」の 2 回で足りる。

## Q18. ツリーの Tab・Shift+Tab による「字下げ・戻す」を、どうしますか(復活の意味が変わる)

どの画面か。ワークスペースのツリーの行にフォーカスがあるときのキー操作。

現行の動き。Tab を押すと、その行を、直前の兄弟の子にする(字下げ)。Shift+Tab は、親の兄弟にする(戻す)。

ぶつかる決定。01「親子のルール」の表では、Story・Task・Bug の親は Epic、Step の親は Story・Task・Bug、Epic の親はプロジェクトの直下。このため、現行のとおりに動かすと、どの行でも必ず断られる。

具体例。Epic HH-2 の 2 つ目の子 HH-5(Task)の行で、Tab を押す。現行は、直前の兄弟 HH-3(Task)の子にする。仕様では、Task の下に Task は置けない。02 の文言で「Task は Task の下に置けません」と断られる。Shift+Tab も、HH-5 の親の親がプロジェクトなので「プロジェクトの直下には Epic だけを置けます」と断られる。

- 案 A: Tab・Shift+Tab を、ツリーの中でも通常のフォーカス移動にする。親を変える手段は、行のメニューの「移動…」だけにする。復活を縮める。キーだけでは親を変えられない。
- 案 B: Tab・Shift+Tab は通常のフォーカス移動にする。親を変える働きを Alt+Shift+↑↓ に移す。例の HH-5 で Alt+Shift+↓ を押すと、次の Epic HH-8 の子の末尾に入る。字下げ(直前の行の子にする)が、仕様で意味を持つ形(いまの親と違う、置ける親の下へ移す)になる。
- 案 C: Tab・Shift+Tab を残し、押すたびに 02 の断り文言のトーストを出す。動く場面がなく、キーボードだけの利用者が、ツリーから Tab で出られなくなる。

勧める案: B。理由は 3 つ。
- 字下げの目的は、親を素早く変えること。この目的を、仕様のルールの中で達せられる。
- Tab をツリーが取らないので、キーボードだけの利用者がツリーから出られる。
- 親子のルール(01 の表)は変えない。

どの画面か。ワークスペース Web のカンバンを開いたタブのアドレス欄。

# 7. Store の運用

## Q21. 設定の「Store」の「フォルダから探す」を、どの形で復活しますか(記録済みの決定とぶつかる)

関連: Q22 で案 A を選ぶなら、この質問も案 A にそろえる。この質問で案 C を選ぶと、案 B にある取り込み直しの文は、仕様に入れない。

どの画面か。設定の「Store」の上部のボタン「フォルダから探す」(現行は、ダイアログ「Store を探す」の下部と、初回起動の案内)。

ぶつかる決定。
- 08「モックからの変更点」の「remote の形」: remote は github.com のリポジトリの URL(SSH 形式と HTTPS 形式)に限る。理由は、同期は GitHub のアカウントでしか認証できず、GitHub 以外の remote は追加できても同期できないため。
- 08「追加」の検査: 「remote は github.com のリポジトリの URL を入力してください」。
- 06「同期のエラー」: remote があってアカウントがなければ「アカウントが設定されていません」で同期が止まる。
- 01「閲覧のみの Store」: 閲覧のみかどうかは、GitHub の権限だけで決まる。

現行の動き。フォルダの下にある bare リポジトリを探し、そのパスを remote にして Store を追加する。アカウントなしで同期できる。

具体例。利用者が `/srv/git/team.git`(社内の共有フォルダにある bare リポジトリ)を remote に使っていた。設定の「Store」で「フォルダから探す」に `/srv/git` を入れると、現行はこの `team.git` が候補に出て、「マウント」でそのパスを remote として Store が追加される。今の仕様では、そのパスは remote に入れられない。

- 案 A: 決定を覆す。ローカルのパス(bare リポジトリ)も remote に入れられる。現行と同じ使い方が戻る。直す文書は多い。08 の「追加」の表・検査・「remote の変更」・「remote の形」の記録と理由の撤回、06 の同期(アカウントなしでもローカルの remote は同期できる規則、同期のエラーの表)、08 の「同期の状況」、01 の閲覧のみ(ファイルシステムの書き込み可否で決める規則)、remote の比べ方(パスの比べ方)、07 の remote の形。GitHub のトークンを使わない同期の経路ができ、認証の規則が 2 本になる。
- 案 B: 縮める。remote は github.com のままにする。「フォルダから探す」は、このマシンにある Store のコピーを見つけて、コピーして取り込む入口にする。origin が github.com ならその URL を引き継ぎ、そうでなければ remote なし(このマシンだけ)で取り込む。決定は覆さない。解除で残したコピーの取り込み直し、別の場所に置いたコピー、ghq で置いたコピーが使える。できなくなるのは、bare リポジトリを remote にして、アカウントなしで共有すること。例の `/srv/git/team.git` は、中身を取り込めるが、remote なしになる。
- 案 C: 復活しない。決定は何も変えない。GitHub から検索(07)だけが残る。「復活する」というご指示と食い違う。解除で残したコピーの取り込み直しの手段もなくなり、コピーは利用者が手で扱う。

勧める案: B。理由は 2 つ。
- 決定の理由(認証は GitHub のアカウントのトークンだけ。同期できない remote を作らない)を保ったまま、「フォルダにある Store を使う」という目的を果たせる。
- 案 A は、「同期はアカウントでしか認証できない」という記録済みの理由そのものを撤回することになる。

## Q22. 設定の「Store」の「ミラー」(バックアップ用の 2 本目の remote)を、どの形で復活しますか(記録済みの決定とぶつかる)

関連: Q21 で案 A を選ぶなら、この質問も案 A にそろえる。

どの画面か。設定の「Store」の、Store の枠(現行は「URL で追加」の複数行の入力欄と、枠の remote の一覧の「ミラー」の印)。

ぶつかる決定。
- 01「Store で共有するものと、マシンごとに持つもの」: Store ごとの remote は 1 つ。
- 06「同期とは」: 同期は、その Store の remote とこのマシンのあいだで行う(remote は 1 本)。
- 08「モックからの変更点」の「remote の形」: github.com だけ。
- 06「同期のエラー」: 失敗の種類にミラーがない。現行は、ミラーの履歴が無関係だと同期全体が止まる。

現行の動き。2 本目以降の remote として、どのホストでも足せる。ミラーからも取り込む。

具体例。Store「team」の origin は `https://github.com/org/team.git`。バックアップとして、`https://github.com/taro/team-backup.git`(個人のリポジトリ)と、会社の NAS の `/mnt/nas/team.git` を足したい。

- 案 A: 決定を覆す。現行のとおり(どのホストでもよく、ミラーからも取り込む)。`/mnt/nas/team.git` も足せる。Q21 の案 A と同じ決定の撤回になる(ローカルのパスの remote、アカウントなしの認証、閲覧のみの判定)。さらに、ミラーから取り込む経路ができ、06 の同期の合わせ方(複数の remote からの取り込み、ミラーだけにある履歴が origin に入る)と、強制 push の修復でミラーを保留にする規則を足す。
- 案 B: github.com の中に縮める。2 本目以降も github.com のリポジトリだけ。ミラーは送信のみ(取り込まない)。失敗は Store の状態を変えず、ミラーの行と手動同期のトーストに出す。`taro/team-backup` は足せる。`/mnt/nas/team.git` は足せない(「remote は github.com のリポジトリの URL を入力してください」)。決定は覆さない。ミラーにだけある変更は手元に来ない。06 の同期の流れ(受け取る、合わせる、送る)は変えず、送るあとに「ミラーへ送る」を足すだけ。
- 案 C: 復活しない。何も足さない。バックアップは、GitHub 側の別の仕組みで取る。「復活する」というご指示と食い違う。

勧める案: B。理由は 2 つ。
- 決定の理由(認証は GitHub のトークンだけ)を保てる。バックアップの用途には、送信のみで足りる。
- 取り込む経路を足すと、同時の変更の規則(06)と強制 push の規則が二重になる。

案 B の注意。ミラーに直接 push する人がいると、ミラーは「ミラーの履歴が先に進んでいます」と出て、送られなくなる。

## Q24. リリースノート(完了したアイテムの Markdown まとめ)を復活しますか

どの画面か。ワークスペースの「リリース」画面の、リリースのカード。

具体例。リリース v1.0 のカードを開く。「リリースノート」を押すと、完了したアイテムが種類ごとに Markdown で表示される。「Markdown をコピー」を押して、GitHub のリリースの説明欄に貼る。

- 案 a: 復活する。リリースのカードに「リリースノート」と「Markdown をコピー」を足す。05 に、対象・並び・種類ごとの見出しの規則を書く。
- 案 b: 復活しない。リリースのカードは、進捗とアイテムの一覧だけのまま。

勧める案: a。理由は 2 つ。
- 現行で唯一の「ファイルの形に近い出力」。復活しないと、リリースの内容を外へ出す手段がなくなる。
- 表示してコピーするだけで、保存の内容を変えない。同期や決定とのぶつかりが起きない。

(この勧めは、案の文書ではなく、報告書の事実から付けた。)

# 選んでいただく必要のない決定の変更

- p-r3-r7.md「6-R7-1」: 「Issue はアイテムの値を変えない」という記録済みの決定(01・02・06・07 の「モックからの変更点」と 02「GitHub」の同じ語句)と、ルール「Issue が閉じたとき」を復活することは、ぶつからない。決定の理由は「GitHub と双方向に合わせる同期をなくすこと」。このルールは、片方向で、ルールを作った人が動かす値を決める。そのため、文だけを「Issue の状態をアイテムの値に写すことはしない(自動化のルールが動いたときだけ、03 のとおり変える)」に直す。
