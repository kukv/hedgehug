## 目的
ユーザーは、仕様から落ちていた現行の機能を「今の仕様に合わせて復活する」と決めた。決定の内容(変えてはいけない前提):
- R1 プロジェクト単位の上書きを復活(今の仕様に合わせて)。必須項目と「今の違反」は戻さない。
- R2 時間型の見積もりと、見積もりと実績のレポートを復活。
- R3 PR の自動リンクを現行の範囲すべて(ブランチ名、PR のタイトル・本文・コメントの ID、`hedgehug:<ULID>`)で復活。レビュー・チェックの状態の表示も戻す。
- R4 強制 push の検出と修復を復活(「万が一破損したときに困る」ため)。
- R5 他のタブ・別プログラムの変更を開いている画面へ自動で反映する仕組みを復活。
- R6 クエリのキー(`group:`、`mentions:`、関連のキー、`is:invalid`・`is:deleted`・`is:overwritten`、`created`・`updated`)を復活。
- R7 自動化のきっかけ「レビューが依頼されたとき」「リンクした Issue が閉じたとき」と条件「リンク中の PR がすべてマージ済み」を復活。
- R8 関連システムに `sort:`・テーブルのグループ・一括変更を足す。
- R9 同期での自動修復(親の循環、スプリント・リリースの取り外し、親のワークスペースへの追従、ワークスペースの復活、接頭辞の復元)を、診断の手動修復ではなく同期で自動で直す。
- R10 画面の操作(ツリーのキー操作、今すぐ同期のショートカット、パレットの拡張、新しいタブで開く、URL での共有と戻る・進む)を残す。
- R11 Store の運用(フォルダから探す、GitHub 上でのリポジトリの自動作成、ミラー、既定の Store、ローカルのパスの表示、クローンを残して解除)を残す。
- R12 レポートの細部(スプリントのボード、累積フロー図の期間指定とステータス別、P85、「表で見る」)を残す。

## 作るもの: 項目ごとの案
現行の振る舞いをそのまま写さない。今の仕様の構造(設定はワークスペース単位、プロジェクトはアイテムでなく独立、論理削除と復元、元に戻すはない、閲覧のみ、Store ごとのメンバーと「あなた」、github.com だけの remote、保存したビューはマシンに置く、など)に合わせ、**使う人が何をしたいかから最善の形を考えて、理由つきで**決める。仕組みを足す案も、仕様全体と突き合わせて細部まで決めた形なら出してよい。

各項目に次の節を書く:
1. **何ができるようになるか**: どの画面のどの部品で、どう操作すると何が起きるか。具体例(操作の手順と結果)を 1 つ以上。
2. **今の仕様への合わせ方**: 現行との違いと理由。
3. **端の場合**: 0 件・空・閲覧のみの Store・オフライン・複数 Store・同時の変更(同期)・削除済み・移動(別ワークスペース・別 Store)・一括変更・自動化・通知・アクティビティ・保存したビュー・GitHub アカウントのない Store。それぞれ、どの既存の規則で決まるか(よりどころ: ファイル名 + 見出し + 引用した文)を書いて決める。
4. **仕様の変更箇所**: 変える文書・見出し・今の文(引用)→ 新しい文の案。新しく足す節は全文。各文書末尾の「モックからの変更点」の表に足す行も書く。記録済みの決定を覆す箇所は、覆す旨と元の決定(引用)を明記する。
5. **ユーザーに聞くこと**: 次の 2 つを**両方**満たすものだけ。(a) ふつうに使っていて起きる、(b) 既存の規則で片付かない。極端な場合や規則で決まるものは聞かずに 3 で決める。聞くものは、どの画面か・具体例・案 2〜3 個(それぞれの結果)・勧める案 1 つと理由を書き切る。「上の」「同じ」のような前を指す省略をしない。1 項目あたり多くても 3 問。
6. **記録済みの決定とぶつかって、復活の意味が変わるもの**: 例えば「github.com 以外の remote をなくす」決定のもとでの「フォルダから探す」のように、決定を覆すか復活を縮めるかをユーザーが選ばないと進まないものは、5 とは別にここに書く(画面・具体例・案・勧める案)。
