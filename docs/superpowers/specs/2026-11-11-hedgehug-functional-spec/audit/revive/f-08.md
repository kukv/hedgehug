## 0. 全体にかかわる事実(R11 の前提)

### 0-1. 仕様 08 の記録済みの決定: github.com 以外の remote をなくす

- 08「モックからの変更点」の表、行「remote の形」: 「どんな文字列でも入れられる」→「github.com のリポジトリの URL(SSH 形式と HTTPS 形式)に限る。入力例は HTTPS の形」。理由: 「ユーザーの指示(2026-11-12)。同期は GitHub のアカウントでしか認証できず、GitHub 以外の remote は追加できても同期できないため。認証手段がトークンで、HTTPS が実際の通信と合うため」(08:427)。
- 08「追加」の表、行「remote(任意)」: 「入力例は「https://github.com/org/tasks.git」。github.com のリポジトリの URL に限る(後述の検査)。入れると clone する。空にすると、このマシンに新しい Store を作る」(08:65)。
- 08「追加」の検査の表: 「remote が github.com のリポジトリの URL でない(受け付ける形は `git@github.com:owner/name(.git)` と `https://github.com/owner/name(.git)` の 2 つで、末尾の `/` は無視する。clone は試みない。remote が空のときは検査しない)」→ 「remote は github.com のリポジトリの URL を入力してください」(08:78)。
- 08「remote の変更」: 「入れた remote が github.com のリポジトリの URL でないときは、追加のときと同じ検査・同じ文言で断り、入力欄を元の値に戻す」(08:132)。
- 07「GitHub から Store を検索」: 「remote は `https://github.com/{owner}/{name}.git` の形で登録する。どちらの形で入力しても、通信は Store のアカウントのトークンで行い、SSH の鍵は使わない」。

### 0-2. 現行のコードで remote と認証がどう決まるか

- remote が GitHub のホストかどうかは `config.IsGitHubHost`(github.com か、設定の `hosts` に書いたホスト)で決まる(`internal/app/storage/config/hosts.go:96-106`)。つまり現行は GitHub Enterprise のホストも許す。仕様は github.com だけ。
- ローカルのパス(bare リポジトリ)の remote も現行では認められる(`storeops.go:233-241` で、なければ `gitrepo.InitBare` で作る)。
- `StoreAdd` は、remote がローカルのパスだけでもアカウントを必須にする。アカウントが 0 個なら `noAccountChoice`(`account.none`)、2 個以上で未指定なら `choice.required`(`storeops.go:363-369`)。トークンなしのアカウントを登録すれば通る(A #93)。
- `url_rewrites`(設定ファイルの書き換え規則)が、clone・push・fetch の直前に URL を書き換える(`config/hosts.go:108-136`)。フォルダ探しの結果は `Unrewrite` で書き換え前の形に戻して返す(`discover.go:195`)。仕様に `url_rewrites` の記述はない(grep: `rewrite` は 0 件)。

## 1. R11-a: A #91 フォルダから Store を探す

### 1-1. 現行の振る舞い

画面: 設定「Store」の「Store を探す」ボタン(`web/app/settings/SettingsStores.svelte:32`)がダイアログ「Store を探す」を開く(`web/app/stores/StoreDiscoverDialog.svelte`)。初回起動の案内の「次へ: Store を探す」にも同じ部品が出る(`web/app/states/Onboarding.svelte:127-132`)。部品は `web/app/stores/StoreDiscover.svelte`。

探す場所は 2 つ。
1. GitHub(自動)。トークンのあるアカウントが 1 つでもあれば、開いた時点で自動で探す(`StoreDiscover.svelte:104-109`)。トークンのあるアカウントがなく、まだ探していないときは「GitHub で探すにはトークンのあるアカウントが要ります」と出す(`:224`)。サーバーは各アカウントの `UserRepos()` を呼び、`hedgehug-store` の topic が付いたものだけを残す(`discover.go:132-136`)。同じリポジトリが複数のアカウントから見えるときは、push できるアカウントを優先し、同じなら先に挙げたものにする(`discover.go:145-150`)。トークンのあるアカウントがなければ `account.none`(409)(`discover.go:121-125`)。
2. 手元のフォルダ。ダイアログ下部の「フォルダから探す」(`StoreDiscover.svelte:274-300`)。入力欄「フォルダ」(例 `/srv/git`)と「探す」ボタン(空欄のあいだは無効)。サーバー側は `discoverFrom`(`discover.go:162-212`):
   - フォルダの下を `filepath.WalkDir` で全部たどり、bare リポジトリ(`HEAD` ファイル、`objects`、`refs` がある。`isBare`、`:214-223`)を見つけたら、その中へは入らない(`SkipDir`)。
   - bare の `main` ブランチに `.hedgehug/store.yaml` があるものだけを候補にする(HEAD は見ない。`git init --bare` は HEAD が master になるため。`:159-161` の注釈、`:196`)。
   - 読めないディレクトリが 1 つあっても探索は続け、警告 `cannot read <path>: ...` を足す(`:177-185`)。探索の起点そのものが読めなければエラー。
   - フォルダが存在しないときは起点の `WalkDir` がエラーになり、画面は「探す」の失敗として `FormError` とボタン「もう一度探す」を出す(`StoreDiscover.svelte:226-228`)。
   - 権限は、ファイルシステムの書き込み可否(`gitrepo.Writable(p)`)で「write」「read」を決める(`:198-201`)。
   - アカウント: 1 つに決まれば(アカウントが 1 個、または `--account` で指定)候補のアカウントとして付く。決まらず 2 個以上あるときは `choice.required`(`--account`)を返し(`:166-174`)、画面は「どのアカウントで探すかを選んでください。」と選択欄を出す(`StoreDiscover.svelte:290-299`)。アカウントが 0 個でも探索は進み、候補にアカウントは付かない(`ok` が false で、かつ `len(c.Accounts) > 1` でない)。
   - 候補の URL は、パスを `url_rewrites` の逆で書き換え前の形に戻したもの。

候補の共通処理(`StoreDiscover`、`discover.go:49-67`):
- すでにマウント済みのものは候補から除く(repo ID で比べる。ローカルパスは `filepath.Clean` したパスで比べる。`dropMounted`、`:214-236`)。
- 名前の付け方(`nameCandidates`、`:238-300`): リポジトリ名、使われていれば `<owner>-<repo>`、それも使われていれば末尾に `-2`、`-3`。使えない文字は小文字化して `-` に置き換える。何も作れなければ `store-1`、`store-2`。仕様 07 の初期値の規則(末尾 `-tasks` を除く、`.` を `-` に置き換える、先頭の 1 文字を削る、空欄にする)とは違う。
- 結果は owner ごとにまとめて出る。owner が取り出せない(ローカルのパス)ものは「その他」の組に入る(`StoreDiscover.svelte:19,70-75`)。各行: チェックボックス、`owner/repo`、権限(「書き込み可」「閲覧のみ」)、名前の入力欄。0 件のときは「見つかりませんでした」と「探しているチームの Store が見つからないときは、そのリポジトリの権限をチームの管理者に依頼してください。」。
- 説明文は、GitHub のときは「あなたのアカウントと所属する Org から、topic hedgehug-store が付いたリポジトリを探しました。読めないリポジトリはここに出てきません。」、フォルダのときは「フォルダ {looked} の下から、Store を持つ bare リポジトリを探しました。」。
- 下端に CLI の行(`hh store discover --from ...`)と、「マウント」(初回案内では「マウントして次へ」)ボタン(選んだ行がなければ無効)。

マウントの手順(`StoreMount`、`discover.go:79-100`、サーバー `POST /api/stores/mount`):
- 選んだ行を 1 件ずつ、独立に、`StoreAdd(name, [url], "", account)` で追加する(clone、`not_hedgehug` の判定、マージドライバの登録、`SetRemotes`、アクセス判定、必要なら setup 同期、設定への追記、履歴の索引、接頭辞の重複の警告。`storeops.go:347-453`)。1 件が失敗しても残りは続ける。失敗が 1 件でもあれば全体に `store.mount_failed`(400)を付けるが、画面は成功分と失敗分を `MountView` で受け取る(`server/stores.go:197-204`)。
- 画面では、成功した行は「マウントしました」に変わり、失敗した行は赤字で理由を出す(`StoreDiscover.svelte:166-203`)。名前が空の行は「名前を入れてください」で、送らない。

端の場合:
- 閲覧のみ: GitHub 候補で権限が `read` なら、追加後は閲覧のみ(`checkAccessOfNew`、`storeops.go:459-475`)。閲覧のみの Store の setup コミットは手元に残り、「送れない」と数える(`:410-431`)。
- オフライン: GitHub の探索はエラー表示(`failure`)になり、「もう一度探す」を出す。フォルダの探索はオフラインでも動く。
- 同時の変更: 探索中に別の探索を始めると、古い結果は捨てる(`seq` で判定。`StoreDiscover.svelte:111-129`)。
- 複数 Store: すでにマウント済みのものは出ない。同じ名前は自動で別名にする。
- 削除済み(論理削除のアイテムのこと)は、この機能に関係しない。

## 2. R11-b: A #94 GitHub 上のリポジトリの自動作成と topic `hedgehug-store`

### 2-1. 現行の振る舞い

- 入口: 設定「Store」の「Store を作成」ダイアログ(`web/app/create/CreateStore.svelte`)。項目は名前、ID の接頭辞、最初のワークスペース(任意)、remote(任意。入力欄は 1 つ。補足文「あれば最初の push までします。なくてもこのマシンだけで使えます」)、アカウント(アカウントが 2 個以上のときだけ選ぶ)。CLI は `hh store init --remote`(繰り返せる。`storeops.go:34-42`)。
- 順序(`StoreInit`、`storeops.go:58-174`): 名前・接頭辞・ワークスペース名の検査、設定の読み込み、既存の名前の検査、他の Store との接頭辞の重複の検査、アカウントの確定、`prepareRemotes`、ローカルの Store の作成、マージドライバの登録、自動化の書き込み(あれば)、`RunSync` で最初の push(remote があるとき)、設定への追記。
- `prepareRemotes`(`storeops.go:229-286`) の remote ごとの処理:
  - ローカルのパスで、存在しなければ `InitBare` で bare を作る。あれば何もしない。
  - GitHub のホスト(`IsGitHubHost`)でなければ何もしない(すでにあるものとして扱う)。
  - GitHub のホストのとき: アカウントがなければ `noAccountFor`(エラー)。アカウントのホストと remote のホストが違うとエラー `account.host_mismatch`(トークンを別のホストへ送らない)。
  - `CreateRepo(owner, repo, 個人か)` を呼ぶ。作成したリポジトリは private(`:225` の注釈「a private repository」)。結果で分かれる:
    - 422(すでにある): `gitrepo.RemoteEmpty` で中身が空なら、そのまま使う。空でなければ `store.remote_not_empty`(409)と、`hedgehug store add` で使う手順の案内。空かどうかを確かめられないときは別のエラー。
    - 403(権限がない): `github.forbidden`(400)。「空のリポジトリを GitHub で作って、その URL を `hedgehug store init --remote` に渡してください。作成は省かれます」と案内する。
    - その他のエラー: そのエラー。
    - 成功: `made.github` に記録する。
  - 作成したあと、`SetTopics(owner, repo, ["hedgehug-store"])` を呼ぶ。失敗したら全体が失敗し、作った bare は消すが、GitHub 上に作ったリポジトリは残る。
- 失敗したとき: GitHub 上に作ったリポジトリは消さず、エラーに「リポジトリ {URL} は GitHub に作られ、そこに残っています。使うには `hedgehug store add ...` を実行してください」と添える(`note`、`:215-221`)。ローカルの bare とローカルの Store は消す(`undo`)。
- 最初の push: `RunSync(s, opt, true)`。remote が空でない(`ErrRejected` か `ErrUnrelated`)ときは `store.remote_not_empty`。成功すると、設定に追記する。設定への追記が失敗したら、push 済みのコミットは remote に残るので、その旨と `store add` の手順を添える(`:167-171`)。
- topic の使われ方: 作成のときに付けるだけ。付いていることを確かめたり、後から付け直す経路はない。検索では、topic が付いたものだけを一覧に出す(1-1 の GitHub 探索)。つまり、topic を付けずに作った Store(自分で作った空のリポジトリに URL を渡した場合など)は、現行の「Store を探す」に出ない。

端の場合: 閲覧のみのアカウント(GitHub App が入っていない組織など)では作成が 403 になる。オフラインでは `CreateRepo` が失敗し、エラーの文言になる(ローカルの Store は作らない)。アカウントが 0 個のとき、remote が GitHub のホストなら `account.none`、そうでなければ最後にアカウントの選択を求めるエラー(`:103-106`)。

### 2-2. 新仕様との衝突(5 件)
