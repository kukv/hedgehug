## Y1 [聞く] 「更新日」(`updated`)に、GitHub・同期が自動で書いた履歴を含めるか(p-r6-r8 の R6-7・R6-A と p-r3-r7、p-r4-r5-r9)

- p-r3-r7.md「02-items-projects.md (b)」: 仕様の既存の文「例外として、GitHub から取り直したリンクの状態とタイトルの変更は、操作した人のいない自動の変更として、履歴にもアクティビティにも残る(07)」に、レビューの状態の変更と「GitHub が PR を自動でリンクしたこと」を足す。
- p-r4-r5-r9.md「06-Q」: スプリントの取り外しは「アイテムの履歴には、「スプリントを変更」が残る」。同期の修復(循環・追従)も履歴に残る。
- ぶつかるもの: R6 は「GitHub リンクは履歴に出ない」と前提して案 A(履歴に出る変更だけ)を勧める。しかし、GitHub が書く状態・タイトルの変更は、いまの仕様でも履歴に出る。R3 でレビューの状態と自動リンクが増え、R9 の同期の修復も履歴に出る。案 A のままだと、人が触っていないアイテムの更新日が、PR のレビューの変化や同期の修復で進む。
- 画面と具体例: 検索のテーブル。HH-5 は 11/1 に人がタイトルを変えたきり。11/12 の夜中に、GitHub の取り直しで、リンクした PR のレビューが「承認済み」に変わった。`sort:-updated` と列「更新日」を見る。

- 案 C: R6 の元の案 B(コメント・作業時間・関連・GitHub リンクを含む、アクティビティに残るすべて)。コメントの多いアイテムが上に来る。

- 直し方の補足(規則で決まる部分): R6-A の案の説明に、いまの仕様でも GitHub の状態・タイトルの変更は履歴に出ること、R3 でレビュー・自動リンクが増えること、R9 の修復が履歴に残ることを書き足し、案を 3 つに書き直す。R6-7 の「`updated`」の定義は、選んだ案の文にする。

## Y6 ミラー(R11)と、強制 push の修復(R4)(p-r11 の R11-c と p-r4-r5-r9 の R4)

- p-r4-r5-r9.md「R4-20」: 「ミラー(R11)の履歴が書き換えられたときの扱いは、R11 の案がミラーへの送信の失敗として定める。この案が決めるのは、同期の remote(origin)の書き換えだけである。ミラーを戻さないなら、この規則は要らない。」
- p-r11.md「R11-c」3 の M13: 「ミラーは強制 push で書き換えない(R4 の作り直しのあと、ミラーが「先に進んでいます」と出続けても、…)。…R4 の案との整合は、R4 の担当の案で確かめる」。
- ぶつかるもの: 互いに「相手の案で決める」と書き、どちらも決めていない。決めないと、次のことが起きる。R4 の例 1 は、誤って入れたトークンを消すために remote を書き換える場面である。ミラーには、書き換え前の履歴(トークンを含む)がすでに送られている。「そろえる」のあと、ミラーは「ミラーの履歴が先に進んでいます」になり、以後は送られず、トークンはミラーに残る。ミラーの行にだけエラーが出て、同期のエラーの数には入らない(M7)。

## Y7 フォルダから探す・コピーを残す(R11)と、前に受け取った履歴の記録(R4)(p-r11 の R11-a・R11-f と p-r4-r5-r9 の R4)
