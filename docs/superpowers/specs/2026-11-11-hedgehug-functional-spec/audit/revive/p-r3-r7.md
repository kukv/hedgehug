# 共通の前提

## 用語

- **自動リンク**: GitHub 上の PR を、アイテムの ID などから見つけて、アイテムに自動でリンクすること。
- **PR の印**: PR のタイトル・本文・コメントに書く `hedgehug:` に、アイテムの内部の ID(01 の「内部の ID」)を続けた 1 行。`hh:` でも同じ。内部の ID の形は 01 のとおり保存形式の段階で決めるので、この案の仕様の文では形を決めない。
- **解除の記録**: アイテムが持つ「自動でリンクしない PR」の一覧。PR のリンクを解除すると、その PR がここに入る。

## 現行の事実(f-07 と、コードの読みをもとにしたもの)

- PR を探すのは Store の同期の直後(5 分固定)。対象は、アイテムの `repos`(プロジェクトのリポジトリを含む)とリンク先のリポジトリ。Store の remote は探さない。更新が新しい順に 100 件ずつ、前回以降を全部読む。初回は 100 件だけ。
- 見つける場所は、ブランチ名 `hh/<ID>-…`、タイトル・本文・コメントの `WEB-1` の形の ID、`hedgehug:<ULID>`。接頭辞のない ID(`#12`)を読む処理はない。旧 ID でもリンクする。Store ごとに別々に照合する。Issue は自動リンクしない(ガイドには「Issue も」とあるが、コードにはない)。
- 解除は、リンクを消さずに `sync: off` で残す。これが付け直しを防ぐ仕組み。
- レビュー(none / pending / approved / changes_requested)とチェック(success / failure / pending)は、リンクの `gh` に保存している。変わるたびにコミットが作られ、アクティビティに出る。現行は受信箱の通知を出さない。

# R3 PR の自動リンク、レビュー・チェックの表示

## 1. 何ができるようになるか

### 例 1: ブランチ名と ID で、PR が自動でアイテムに付く

前提: Store「team-a」に、ワークスペース「Web」(接頭辞 WEB)がある。プロジェクト「Web リニューアル」に、リポジトリ `example-org/web` を結びつけてある。アイテム WEB-1「ログイン画面を直す」にはリンクがない。

1. 田中さんが `hh/WEB-1-login` というブランチから、PR example-org/web#12 を立てる。
2. あなたが WEB-1 の詳細パネルを開く。GitHub の欄は「リンクはありません」。
3. 最大 5 分(設定「GitHub を読む間隔」の既定)待つと、GitHub の欄に 1 行が足される。「PR」のチップと「Open」のチップ、「example-org/web#12 — ログイン画面を直す」、「レビュー待ち」、「CI 実行中」、行の右端に「ブランチ名から自動リンク」、解除の「×」。
4. アクティビティには、実行者「GitHub」で「WEB-1 に example-org/web#12 を自動でリンク」と 1 行が出る。WEB-1 の履歴にも同じ行が出る。受信箱には何も出ない。
5. 03 の自動化に「PR がリンクされて Open のとき → ステータスを In Progress に」のルールがあれば、このとき WEB-1 が In Progress になる(「自動化」の通知があなた宛てに出る。03)。

PR のタイトルや本文に「WEB-1 を直す」と書いたときも、コメントに「WEB-1 の件です」と書いたときも、同じように付く。右端の文は「タイトル・本文の ID から自動リンク」「コメントの ID から自動リンク」になる。

### 例 2: 間違ってリンクされた PR を外す。外した PR は、もう付かない

1. PR #15 の本文に「WEB-1 とは関係ないが、WEB-1 に似た作業」と書いてあったため、WEB-1 に自動でリンクされた。
2. あなたが WEB-1 の GitHub の欄で、その行の「×」を押す。確認なしでリンクが外れ、トースト「リンクを解除しました」が出る。
3. 次の読み取りで、#15 のコメントが増えても、#15 は WEB-1 に付かない。
4. 気が変わったら、「PR をリンク」から `example-org/web` の 15 を手でリンクし直せる。手でリンクすると、解除の記録から #15 が消え、それ以降は普通のリンクになる。

### 例 3: PR の行で、レビューとチェックが見える

- 詳細パネルの GitHub の欄と、プロジェクトの概要の「PR と Issue」の行で、Open か Draft の PR の行に、レビューの表示(「レビュー待ち」「承認済み」「修正依頼」)とチェックの表示(「CI 成功」「CI 失敗」「CI 実行中」)が出る。どちらも、なしのときは出さない。Merged と Closed の PR には出さない。
- 例: example-org/web#12 が、佐藤さんの承認で「承認済み」になり、CI が通って「CI 成功」になる。あなたは WEB-1 を開くだけで、マージできる状態だと分かる。

### 例 4: PR の印を、PR の説明に貼る(6-R3-1 の案 A を選んだとき)

1. WEB-1 の詳細パネルの GitHub の欄で、「PR 用の印をコピー」を押す。トーストは「コピーしました。PR の説明に貼ってください」。
2. PR の本文に貼る。貼ると `hedgehug:` で始まる 1 行になる。
3. あとで WEB の接頭辞を APP に変えても、WEB-1 を別のワークスペースへ移しても、この印は同じアイテムを指し続ける。「WEB-1」と書いた本文は、03 の規則で旧い ID のためリンクにならない(R3-25)が、印は残る。

### 3-B 設計の点(R3-16〜R3-44)

**探す範囲と時期**

- **R3-16(新規)探すリポジトリ。** その Store の、削除済みでないプロジェクトに結びつけたリポジトリと、その Store のアイテム(削除済みを除く)がリンクしているリポジトリ。Store の remote のリポジトリは探さない。理由: 利用者が書いたものだけを探す。remote のリポジトリは Store のデータで、作業の PR ではない。「リンクしているリポジトリ」を足す理由は、プロジェクトを持たないアイテムでも、1 本手でリンクすれば、同じリポジトリの他の PR が付くため。現行も remote は探さない(f-07 0-1)。
- **R3-17(新規)リンクするアイテム。** その Store の、削除済みでないアイテム(Epic・Story・Task・Bug・Step)。プロジェクトはリンクの対象でない(07 のリンクは「アイテムは PR と Issue をリンクとして持てる」)。ID が `HH-P1` の形のプロジェクトの ID は、読まない(番号が数字だけの形に当たらない)。
- **R3-18(新規)新しくリンクする PR の状態。** Open・Draft・Merged。Closed(マージされずに閉じた)は新しくリンクしない。すでにリンクしてある PR が Closed になったときは、リンクを残して「Closed」と出す。理由: 取り下げた PR は、そのアイテムの作業として数えないほうが、利用者の感覚に合う。「すべてマージ済み」の条件(R7-18)を止めない。
- **R3-19(新規)読む時期。** リンクの取り直しと同じ読み取りで、リポジトリごとに、設定「GitHub を読む間隔」(5・15・30・60 分)が過ぎたとき探す。前回の読み取りのあとに更新された PR をすべて見る。アプリを開いたときとオンライン復帰のときも、前回から間隔が過ぎていれば読む。利用上限と失敗は、07 の「GitHub を読む間隔」のとおり。「裏で自動的に同期する」をオフにすると止まる。自動で読むときは、06 の「自動の同期は、次のあいだは始めずに待つ」と同じ条件のあいだ待つ。
  - よりどころ: 07「GitHub を読む間隔」の全項目。06「自動で同期する」。
  - 07 の現行の文は、アプリを開いたとき・オンライン復帰・入力中の扱いを書いていない。この点の穴も同時に埋める。
- **R3-20(新規)利用者の操作で探す。** プロジェクトにリポジトリを追加したとき(「PR をリンク」の「プロジェクトのリポジトリにも追加する」がオンのときを含む)は、間隔によらず、そのリポジトリをすぐ探す。詳細パネルを開いたときは、開いたアイテムのリンクだけを取り直し、探さない。理由: 07「利用者の操作で読むとき…は、間隔によらずすぐに読む」。リポジトリを足した利用者は、すぐ PR が付くのを期待する。パネルを開くたびに探すと、利用上限を使う。
- **R3-21(新規)初回の読み取り。** このマシンが、その Store のそのリポジトリを初めて読むときは、更新が新しい順に 100 件までを見る。このときの自動リンクは、リンクを足すだけで、自動化のきっかけを起こさない。2 回目以降は、手でリンクしたときと同じにきっかけを起こす。理由: 1 つのプロジェクトにリポジトリを足した直後に、過去の PR が一度に付いて、ルールが一斉に動くと、「元に戻す」がない(01)ため取り返しがつかない。07 の「同期で受け取ったリンクがすでに Merged なら、きっかけは起こさない」と同じ考え方で、すでにあった状態にはきっかけを起こさない。

**ID の形と、見る場所**

- **R3-22(新規)見る場所と形。** 次のとおり。

| 見る場所 | 読む形 |
|---|---|
| ブランチ名 | `hh/` か `hedgehug/` のあとに ID(接頭辞のあるアイテムは `WEB-1`、接頭辞のないアイテムは番号だけ)が続き、そのあとが `-` か名前の終わり。大文字と小文字は区別しない。例: `hh/WEB-1-login`、`hedgehug/WEB-1`、`hh/12-login` |
| タイトル・本文 | PR の印、または接頭辞のある ID(`WEB-1`) |
| コメント | 同じ。古い方から 100 件まで(R3-29) |

  接頭辞のある ID は、英大文字で始まる接頭辞、`-`、番号の並び。ID のすぐ前かあとに `-` があるものは、ID として読まない(「PRE-WEB-7」から「WEB-7」を取らない)。現行の規則と同じ。

- **R3-23(新規)接頭辞のないアイテムのブランチ名。** `hh/12-login` のように、番号だけを書く。その Store の接頭辞のないワークスペースの 12 番に付く。接頭辞のないワークスペースは 1 つの Store に 1 つなので、1 つに決まる。接頭辞は英大文字で始まるので、番号だけの形とは重ならない。
  - よりどころ: 01「用語と階層」「接頭辞のないワークスペースは、1 つの Store に 1 つだけである」、03「接頭辞」の同期の修復の規則。
  - ブランチを作る機能(`hh start`)は仕様の外(01「CLI は扱わない」)。利用者が名前を自分で付ける前提。
- **R3-24(新規)接頭辞のない ID `#12`。** タイトル・本文・コメントの `#12` は読まない。理由: GitHub では同じリポジトリの 12 番の PR・Issue を指す。PR の説明の「#12 を直す」がアイテム #12 にリンクされると、偶然の誤リンクが多発する。接頭辞のないワークスペースのアイテムは、ブランチ名か PR の印(6-R3-1)でリンクする。
  - よりどころ: 01「ID」「ワークスペースに接頭辞があれば `HH-12`、なければ `#12` と表示する」。03 の変更点表「同じ Store に 2 つあると、「#12」がどちらか決まらないため」。
- **R3-25(新規)旧 ID。** 現在の ID だけを読む。旧 ID(接頭辞を変える前、別のワークスペースへ移る前)は読まない。
  - 03「接頭辞」の「リンクにもしない」は、コメントや通知に書かれた古い ID の文字をクリックできるリンクにしない意味で、PR の自動リンクを直接は決めない。だから、この点は規則で決まらず、私が決めた。
  - 理由: 接頭辞 WEB を APP に変えたあと、別のワークスペースが WEB を使い始めると、旧 ID で読むと新しい WEB-1 に誤ってリンクされる。この場合も、現在の ID で読むときに、旧い「WEB-1」と書いた PR が新しい WEB-1 に付く誤りは残る。誤って付いたら、利用者が解除する(R3-32)。印は、この誤りも避けられる。
- **R3-26(新規)同じ ID が複数の Store にあるとき。** Store ごとに、その Store がそのリポジトリを探す対象にしているときだけ、その Store の ID に付ける。複数の Store がそのリポジトリを対象にしていて、両方に WEB-1 があれば、両方に付く。
  - よりどころ: 07「PR は、同じ PR を複数のアイテムにリンクできる」。04 の自由な語の「別の Store に同じ ID のアイテムがあれば、どちらにも一致する」は検索の規則で、リンクを決めない。
  - 理由: 両方の Store がそのリポジトリを作業の場所として登録しているなら、両方に付く利用者の期待が自然で、規則が増えない。誤りは解除できる。
- **R3-27(新規)PR の印の読み方。** `hedgehug:` か `hh:` に続く内部の ID。その Store にその内部の ID のアイテム(削除済みを除く)があれば、そのアイテムに付く。ない Store は飛ばす。印が本文にあるときは、タイトル・本文のほかの ID を読まない。コメントは、印があっても読む。理由: 印は、利用者が「この PR はこのアイテム」と書いたもの。本文に参照として書いた他の ID(「WEB-2 の続き」)を、いっしょに付けないため。現行の `hh pr` の本文の規則と同じ。
- **R3-28(新規)1 つの PR に複数の ID があるとき。** 一致したアイテムのすべてに付ける。1 つの PR の複数のアイテムへのリンクは、07 で許している。
- **R3-29(新規)コメントの範囲。** 古い方から 100 件まで。それより後のコメントの ID は読まない。理由: 現行の上限。1 回の読み取りの重さを抑えるため。仕様に書く(現行の上限を仕様の文にする)。
- **R3-30(新規)Issue は自動リンクしない。** 現行のコードは PR だけ。ガイドの「Issue のタイトル、本文、コメント」の記述は、コードにない経路で、この案は PR だけを戻す。理由: Issue は 1 つのアイテムに 1 つ、1 つの Issue につき 1 つのアイテムに限る(07)。自動で足した Issue のリンクが他のアイテムの Issue と重なったとき、断る場面がなく、同期の修復(06)が外すことになり、利用者に見えない動きが増える。Issue は、手で「Issue をリンク」する。

**リンクの項目と、解除**

- **R3-31(新規)検出元。** 自動でリンクしたとき、リンクに検出元(ブランチ名・PR の印・タイトルか本文の ID・コメントの ID)を保存し、詳細パネルの行の右端に「ブランチ名から自動リンク」「PR の印から自動リンク」「タイトル・本文の ID から自動リンク」「コメントの ID から自動リンク」と出す。手でリンクしたものには出さない。複数の場所で見つかったときは、この順で先に当たったものにする。理由: なぜ付いたかが分かれば、利用者は間違いを解除できる。
- **R3-32(新規)解除の仕組み。** 解除ボタンは、PR のリンクを外し、その PR の「リポジトリ + 番号」(リポジトリは大文字と小文字を区別しない)を、アイテムの解除の記録に足す。1 回の保存。記録のある PR は、自動リンクでそのアイテムに足さない。記録は画面に出さない。理由: 付け直しを防ぐために、無効のリンクを残すと、07 の「もうリンクしています」の検査が無効のリンクを数えるか迷う。記録を別にすれば、検査はリンクだけを数えると書ける。
- **R3-33(新規)記録の消え方。** 手で「PR をリンク」して、同じリポジトリと番号を足したとき、その保存で記録から消す。アイテムの完全な削除で、アイテムと一緒に消える。アイテムの複製には写さない(リンクを複製しない規則と同じ)。
  - よりどころ: 02「複製」の表「コメント・GitHub リンク・作業時間・履歴 | 複製しない」。
  - 「もうリンクしています」の検査(07「追加」)は、記録を数えない。
- **R3-34(新規)同期での合わせ方(足した/外した)。** 解除の記録は、「値を複数持つ項目」として、1 つずつの追加を両方とも生かす。自動で足されたリンクと、同じ PR の解除の記録が両方あるときは、時刻によらず、解除が勝ち、自動で足されたリンクを外す。このとき「リンクが上書きされました」の通知は作らない(足したのが人でない)。アクティビティにも残さない(合わせた結果で、保存ではない)。手で足したリンクは、記録があっても外さない(06 の人どうしの規則で決める)。
  - よりどころ: 06「複数のマシンの変更を合わせる」「値を複数持つ項目…同じ値を一方が足し、他方が外したときは、その値について後勝ちで決め、負けた人に「上書き」の通知を作る」。この規則だと、解除したあとに、まだ受け取っていない別のマシンが自動で足した保存の時刻が新しいとき、自動の足しが勝って、解除が元に戻ってしまう。人の判断を機械の推測が覆さないよう、自動で足したものと人の解除の重なりには、時刻によらない規則を足す。
- **R3-35(新規)同じ PR を 2 台が自動で足したとき。** 1 本にまとめる。検出元は保存の早い方。同じ値を足した場合なので、衝突ではない。

**レビューとチェック**

- **R3-36(新規)レビューは保存し、チェックは保存しない。** PR のリンクが、レビューの状態(なし・レビュー待ち・承認済み・修正依頼)を持つ。変わったときだけ保存する。保存はアクティビティと履歴に実行者「GitHub」で残る(R3-41)。通知は作らない(R3-40)。チェックの結果は Store に保存しない(R3-44)。
  - 理由(レビュー): R7 の「レビューが依頼されたとき」は、前の値と今の値を比べる。比べる前の値を Store に保存しておけば、他のマシンが同じ変更を受け取っても、きっかけが起きるのは保存したマシンだけになる(07「きっかけが起きるのは、そのリンクの更新を実際に保存したマシンだけである」)。変わる回数も、1 つの PR で数回で、アクティビティを埋めない。
  - 状態の決め方(現行どおり): GitHub が承認済み・修正依頼と判定していればそれ。判定がなければ、各レビュアーの最新の意見に修正依頼があれば修正依頼、承認があれば承認済み。意見がなく、レビューの依頼が 1 件以上あればレビュー待ち。それ以外はなし。
- **R3-37(新規)リンクの項目を 2 台が別の値に保存したとき。** 保存時刻があとの値を残す。通知は作らない。次の読み取りで、GitHub の値に揃う。理由: リンクの状態・タイトル・レビューは GitHub が正で、人の編集ではない。複数のマシンが、時間差で別の値を読むのは普通に起きる。
- **R3-38(新規)表示の場所と文言。**
  - 詳細パネルの GitHub の欄と、プロジェクトの概要の「PR と Issue」の行で、Open か Draft の PR の行に、チップのあとにレビューの表示、続けてチェックの表示を出す。
  - レビュー: 「レビュー待ち」「承認済み」「修正依頼」。なしは出さない。現行の「approved」は「承認済み」にする(現行で英語なのはこの 1 つだけ)。「修正依頼」と「レビュー待ち」は現行のまま。
  - チェック: 「CI 成功」「CI 失敗」「CI 実行中」。なしは出さない。現行のまま。
  - Draft の PR にも出す(現行は Draft のレビューを常に「—」にするが、レビューの依頼が Draft に付くと R7 のきっかけが起きるので、表示も合わせる)。
  - Merged と Closed の PR には出さない(それ以上変わらない)。
  - 閲覧のみ・アカウントなし・非表示・オフラインの Store では、レビューは保存した値を出し、チェックはこのマシンが読んだ値があるときだけ出す。
- **R3-39(新規)ブランチ名は保存も表示もしない。** 取り直しで変わる値が増え、書き込みが増える。検出元の表示で、なぜリンクされたかは分かる。R3 の指定(自動リンクの範囲、レビュー・チェックの表示)に、ブランチ名の表示は入っていない。
- **R3-40 通知の矛盾の解き方。** リンクの変更(状態・タイトル・レビュー・自動リンク)は、ウォッチ・割り当ての通知を作らない。
  - 矛盾: 07「表示と更新」は「この保存は、他の人の変更と同じく、ウォッチ・割り当ての通知の対象になり、通知の差出人は「GitHub」とする(06)」と書く。02「操作ごとの記録と通知」は「なし(リンクの変更では通知しない)」、02「ウォッチ」と 06「ウォッチ」は「説明の変更、リンク、関連、作業時間、削除、移動、種類の変更では出ない」と書く。06 のウォッチの対象は、プロパティの変更、タイトルの変更、コメントの投稿の 3 つだけで、リンクの状態は入っていない。
  - 決め方: 3 か所が一致している 02・06 を正とする。07 の文は、記録済みの決定 Q-030(`audit/high-decisions.md`「GitHub 由来の変更は、他の人の変更と同じく通知する(差出人は「GitHub」)」)と B-12(`audit/apply-followups.md`「自分のマシンが GitHub を読んで保存した変更も、通知の対象にする(差出人は「GitHub」)」)から来た。Q-030 の前提は、Issue の mirror が担当者・ステータスを変えることだった(`audit/coverage-report.md` の Q-030(b)「設定の「GitHub Issue」で担当者を mirror にしているとき、…GitHub 側の変更が同期で反映され」)。mirror は 07 で廃止済みで、前提がなくなっている。Q-030 のうち残る部分(GitHub 由来の保存でも、ウォッチ・割り当ての対象になる変更は他の人の変更と同じに通知する)は、守る。ただし GitHub 由来の保存でウォッチ・割り当ての対象になる変更(プロパティ、タイトル、担当者)は、いまは自動化の変更だけで、06「ウォッチ」の「自動化による変更でも通知する」が決めている。
  - 通知が出るのは、自動化が動いたときの「自動化」の通知(あなた宛て。03・06)だけ。

- **R3-42(新規)自動リンクで起きるきっかけ。** 手でリンクしたときと同じ。ただし R3-21 の初回の読み取りでは起きない。PR が Draft で自動リンクされたときは「PR が Open のとき」は起きず、Draft から Open に変わったときに起きる。Merged で自動リンクされたときは「リンクした PR がマージされたとき」が起きる。
- **R3-43(新規)探せなかったときの表示。** プロジェクトの概要の「リポジトリ」の各行に、そのリポジトリの前回の読み取りが失敗していれば、行の下に「PR を探せませんでした: {07「GitHub との通信に失敗したとき」の表示}」を出す。成功したら消す。このマシンだけの表示で、Store には保存しない。リンクの行のある取り直しの失敗は、07 のとおり、リンクの行に出す。理由: リポジトリ名の打ち間違いや、権限がないとき、PR が付かないまま何も出ないと、利用者は理由を知る手段がない。
- **R3-44(新規)チェック結果の持ち方。** チェックの結果は、このマシンだけに持つ(01 の「マシンごとに持つもの」に足す)。他のマシンには共有されない。読んだときに更新する。理由: 1 本の PR で、CI の実行中・成功・失敗が何度も入れ替わる。Store に保存すると、1 回の CI のたびに、各マシンが保存し、アクティビティと履歴(40 件・300 件)を埋める。チェックを使う自動化のきっかけもない。

>
> **解除と付け直し**
>

### 6-R3-1 PR の印 `hedgehug:` を、利用者がどう書くか

**ぶつかる記録済みの決定**

- 01「用語と階層」「内部の ID」: 「ワークスペース・プロジェクト・アイテムは、画面に出ない内部の ID も持つ。…形式(ULID など)は保存形式の段階で決める。」
- 02「詳細パネル」「上から順の構成」: 「ID をコピーするボタン(押すと「コピーしました: {ID}」と表示する。…)」。コピーするのは画面の ID。
- `audit/current-vs-spec.md` A #11: 現行の「ULID を表示し、「ULID をコピー」でコピーできる」は、仕様が廃止を記録している(記録あり: 01:51、02:326)。

**何が問題か**: R3 は「`hedgehug:<ULID>` で PR を結びつける」を戻す決定をしている。印は、利用者が PR の説明に書かないと意味がない。現行で印を作るのは、コマンド `hh pr`(CLI。仕様の外)で、画面の「PR を作成」は `hh pr` のコマンドをコピーするだけ。画面から内部の ID を取り出す手段は、A #11 の廃止で消えている。

**画面と具体例**: アイテム WEB-1 の詳細パネル、GitHub の欄。「PR をリンク」「Issue をリンク」のボタンの横に、新しいボタンを置くかどうか。

**案**

- **案 A: 「PR 用の印をコピー」を足す。** 押すと、`hedgehug:` で始まる 1 行をコピーし、「コピーしました。PR の説明に貼ってください」を出す。内部の ID を画面には表示しない(貼った先の GitHub では見える)。
  - 結果の例: 利用者が印を PR の本文に貼る。WEB の接頭辞を APP に変えても、WEB-1 を別のワークスペースへ移しても、別の Store へ移しても、印は同じアイテムに付く。「WEB-1」と書いた本文は、03 の規則(R3-25)で旧 ID になるため付かなくなる。
  - 変える決定: 02 の「ID をコピー」の例外(コピーする文字列が画面の ID でない)と、01 の「画面に出ない」(画面には出さないが、コピーでは渡す)。A #11 の廃止は、ULID を画面に表示することと、ULID だけをコピーすること。この案は、PR の説明に貼る 1 行を渡すだけで、ULID を表示しない。
- **案 B: 印を読むだけにする。** 画面に書く手段は置かない。印を書くのは、仕様の外の道具(`hh pr` など)に任せる。
  - 結果の例: 画面だけを使う利用者は、印を書けない。印は、CLI を使う人にだけ効く。
  - 変える決定: なし。ただし、R3 の「`hedgehug:<ULID>` で復活」が、画面の利用者には実質なくなる。
- **案 C: 印をやめる。** ブランチ名と ID だけにする。
  - 結果の例: 接頭辞を変えたあと、移動したあとに、本文の ID が効かなくなり、ブランチ名も同様。付け直すには、手でリンクする。
  - 変える決定: R3 の「現行の範囲すべて」から、印を外す。

**勧める案: A。** 理由: 旧 ID を読まない(R3-25)ため、接頭辞を変えたり、アイテムを移したりしたときに、効き続けるのは印だけで、印の意味がここにある。案 B は、画面の利用者に印の手段がなく、読むだけで意味がない。案 C は、R3 の決定を縮める。案 A の費用は、ボタン 1 つと、01・02 の 2 文への例外の追記である。

### 6-R7-1 「Issue はアイテムの値を変えない」と、「Issue が閉じたとき」のルール

**ぶつかる記録済みの決定**(同じ語句が 5 か所)

- 01「モックからの変更点」、06「モックからの変更点」、07「モックからの変更点」、02「モックからの変更点」の「Issue の取り込み・同期・作成」の行と、02「GitHub」(427 行目): 「Issue はリンクして、タイトルと状態(Open・Closed)を GitHub から読んで表示するだけにし、アイテムの値は変えない」(ユーザーの指示、2026-11-12)。理由の欄は「取り込みと同期は、アイテムの値を GitHub と双方向に合わせるため、競合・制約・通知の細かな規則が増え、管理が複雑になるため」。

**何が問題か**: R7 は「リンクした Issue が閉じたとき」のルールを戻す決定をしている。ルールが動くと、Issue の状態でアイテムのステータスが変わる。「アイテムの値は変えない」の文と、文面ではぶつかる。

**どう読むか**: 記録済みの決定の理由は、アイテムの値を GitHub と双方向に合わせる同期をなくすこと。「Issue が閉じたとき」のルールは、片方向で、ルールを作った人が動かす値を決め、03 の制約の検査・通知・「連鎖しない」の規則に乗る。同期の規則(競合・双方向)は増えない。だから、R7 の決定は、同期の廃止の理由を覆さない。

**選ぶ必要はない。** 文を、同期はしないが、ルールは動く、と読める形に直す(4 の 02 のほか、01・06・07 の 4 行の「アイテムの値は変えない」を、「Issue の状態をアイテムの値に写すことはしない(自動化のルールが動いたときだけ、03 のとおり変える)」に変える)。

# R7 自動化のきっかけ 3 つ

R7 の決定は、きっかけ「レビューが依頼されたとき」「リンクした Issue が閉じたとき」と、条件「リンク中の PR がすべてマージ済みのときだけ」の復活。「きっかけ 3 つ」は、この 3 つ。

## 1. 何ができるようになるか

設定の「自動化」(ワークスペースごと。03)の「ルールを作成」ダイアログが、次のようになる。

- きっかけの選択肢が 4 つから 6 つに増える(「PR がリンクされて Open のとき」「レビューが依頼されたとき」「リンクした PR がマージされたとき」「リンクした Issue が閉じたとき」「ステータスが次になったとき」「Step がすべて完了したとき」)。
- きっかけが「リンクした PR がマージされたとき」のときだけ、チェックボックス「リンク中の PR がすべてマージ済みのときだけ」を出す。初期値はオフ。

### 例 1: レビューが依頼されたら、Review へ動かす

1. あなたが設定の「自動化」で「ルールを作成」を押す。名前「レビュー依頼で Review」、きっかけ「レビューが依頼されたとき」、すること「ステータスを変更」、値「Review」にして保存する。ルールの一覧の説明は「レビューが依頼されたとき → ステータスを Review に」。
2. 田中さんが WEB-1 の PR(example-org/web#12)を立てて、佐藤さんをレビュアーに指定する。
3. あなたのマシンが、間隔のあとに読む(最大 5 分)。#12 のレビューの状態が「なし」から「レビュー待ち」に変わった保存の中で、ルールが動き、WEB-1 が Review になる。
4. 受信箱の「自動化」に、あなた宛てで「「レビュー依頼で Review」でステータスを Review に変更しました」が出る。アクティビティに「「レビュー依頼で Review」で …」が出る。
5. 佐藤さんが承認し、そのあと田中さんが再依頼しても、レビューの状態が「なし」に戻らないので、ルールは再び動かない。

### 例 2: Issue が閉じたら、Done へ動かす

1. ルール「Issue 完了で Done」(きっかけ「リンクした Issue が閉じたとき」、すること「ステータスを変更」、値「Done」)がある。
2. WEB-5 に Issue(example-org/web#30)をリンクしてある。
3. 誰かが GitHub で #30 を閉じる。あなたのマシンが読んだとき、WEB-5 が Done になる。
4. すでに閉じた #30 を、WEB-5 に新しくリンクしたときも、リンクの保存の中でルールが動いて Done になる(PR をリンクした時点で Merged のときと同じ)。

### 例 3: すべての PR がマージされたら、Done へ動かす

1. ルール「全 PR マージで Done」(きっかけ「リンクした PR がマージされたとき」、「リンク中の PR がすべてマージ済みのときだけ」にチェック、すること「ステータスを変更」、値「Done」)がある。一覧の説明は「リンクした PR がすべてマージされたとき → ステータスを Done に」。
2. WEB-1 に PR を 2 つ(#12、#13)リンクしてある。
3. #12 だけがマージされる。きっかけは起きるが、#13 が Open なので、ルールは動かない。
4. #13 がマージされる。リンク中の Closed でない PR がすべて Merged になったので、ルールが動き、WEB-1 が Done になる。

| レビューが依頼されたとき(新) | 状態が Open か Draft で、レビューが「レビュー待ち」 | 状態が Open か Draft で、レビューが「なし」から「レビュー待ち」へ | 「なし」に戻ったあとの「レビュー待ち」で、また起きる。承認・修正依頼のあとの再依頼では起きない | アイテムごとに 1 回 | Draft でも起きる |
| リンクした PR がマージされたとき(既存) | 状態が Merged | Merged でない状態から Merged へ | 起きるたび | アイテムごとに 1 回(条件ありは、すべて Merged になった読み取りで 1 回) | 起きない |
| リンクした Issue が閉じたとき(新) | 状態が Closed | Open から Closed へ | 再び開いて、また閉じたら、また起きる | Issue は 1 つのアイテムに 1 つなので、1 回 | なし |

- **R7-17(新規)条件の置き場所。** チェックボックスで、きっかけが「リンクした PR がマージされたとき」のときだけ出す。初期値はオフ。他のきっかけに変えると、チェックの値は保存しない(消える)。ルールの一覧の説明は、条件がオンのとき、きっかけの文を「リンクした PR がすべてマージされたとき」にする。理由: 現行の画面と同じで、現行の使い方を保つ。初期値をオフにするのは、03 の既存の文「リンクした PR がマージされたとき」の意味(1 つでもマージされたら動く)を、ルールを作った人が選ばずに変えないため。
- **R7-18(新規)条件の数え方。** そのアイテムの PR のリンクのうち、Closed(マージされずに閉じた)を除いたものが 1 件以上あり、そのすべてが Merged のときに通る。Issue のリンクは数えない。判定は、きっかけが起きたときに、リンクの保存済みの状態で行う。取り直しに失敗して古い値のままの PR は、保存済みの値で判断する。複数の PR を持つアイテムで、最後の 1 本がマージされた読み取りで 1 回だけ動く。Closed を数えない点は 5-R7-1 で聞く(下の文は案 b)。
- **R7-19(新規)「レビューが依頼されたとき」の定義。** 上の表のとおり。状態が Open か Draft のときだけ起きる。承認済み・修正依頼のあとの再依頼では起きない。理由: レビューの状態の判定は、GitHub の承認・修正依頼の判定が残るあいだ「レビュー待ち」に戻らない(R3-36 の状態の決め方)ため、再依頼は検知できない。Merged と Closed の PR は、依頼が残っていても、アイテムを Review に動かす意味がない。
- **R7-20(新規)Draft の PR とレビュー依頼。** Draft でも起きる。理由: Draft のまま早めにレビューを依頼するチームで、アイテムが Review に動くため。「PR が Open のとき」が Draft で起きない(07)のとは、意味が別。
- **R7-21(新規)「Issue が閉じたとき」の場面。** リンクした時点で Closed でも起きる。Open から Closed に変わったときに起きる。閉じて再び開いて、また閉じたら、また起きる。理由: 「PR をリンクした時点で、すでにマージ済みだったとき」(03)と同じ形にそろえる。再び閉じたときに起きないと、手でステータスを戻したあとのルールが効かない。
- **R7-22(新規)閉じた理由。** 5-R7-2 で聞く。Issue の状態は 07 で Open・Closed の 2 つ。案 a(区別しない)のとき、「計画なし」で閉じた Issue でも、アイテムが「完了」のステータスへ動く。
- **R7-23(新規)同じ読み取りで複数のきっかけ。** 同じアイテムに、同じ読み取りで同じきっかけが複数起きても、そのアイテムのそのきっかけに 1 回だけ起きる。別のきっかけ(PR が新しくリンクされて Open かつレビュー待ちのとき、「PR が Open のとき」と「レビューが依頼されたとき」の両方)は、それぞれのルールを判定する。
- **R7-24(新規)複数のルールの順序と、制約の検査。** ルールは一覧の上から順に実行する(03)。1 つのルールがステータスを変えたら、次のルールは、変えたあとのステータスから遷移の制約を検査する。止められたルールは、その実行を止めて通知し、次のルールへ進む。変更は、リンクの更新と同じ 1 回の保存の中に入る。理由: 現行の挙動(ルールごとに、そのときのステータスから検査し、通ったら次のルールはそのステータスから始める)を、03 の「すること『ステータスを変更』は、遷移の制約を検査する」に載せる。
- **R7-25(新規)動くマシンと保存。** きっかけが起きるのは、そのリンクの更新を保存したマシンだけ。ルールの変更は、そのリンクの更新と同じ保存の中に入る(03「変更は、操作と同じ保存の中に入る」)。
- **R7-26(新規)遅れと、すぐ動く場面。** 読み取りの間隔(5〜60 分)のぶん遅れる。リンクを追加したとき、詳細パネルを開いたときは、すぐ読むので、すぐ動く。「裏で自動的に同期する」をオフにすると、自動では動かない。
  - よりどころ: 07「GitHub を読む間隔」「利用者の操作で読むとき(詳細パネルを開いたとき、リンクを追加したとき、…)は、間隔によらずすぐに読む」。
- **R7-27(新規)同期で受け取った状態と、取得されていないリンク。** 同期で受け取ったリンクの状態では、きっかけは起きない。リンクの追加は GitHub に問い合わせて状態を取得して保存するので(07「追加」)、状態が取得されていないリンクはない。現行の「渡した側が取得していないリンクを、受け取った側の最初の取得で動かす」場面は、なくなる。
- **R7-28(新規)ルールの一覧の説明文。** 「{きっかけ} → {すること}」のきっかけの文は、「レビューが依頼されたとき」「リンクした Issue が閉じたとき」。条件がオンの「リンクした PR がマージされたとき」は「リンクした PR がすべてマージされたとき」。
- **R7-29(新規)「すること」の値。** 03 の「ステータスを変更」(このワークスペースのステータス)だけ。分類の既定を指す選び方は戻さない。新しいきっかけの初期値は、03 の既存の初期値(完了の既定のステータス)のまま。ステータスを変えたり削除したりすると、03 の追従の規則に乗る。理由: R1〜R12 に入っていない。
- **R7-30(新規)削除済みのアイテム。** ルールは動かない。きっかけは捨て、復元してもさかのぼって動かさない。
- **R7-31(新規)PR を自動リンクしたときのきっかけ。** 手でリンクしたときと同じ。ただしそのリポジトリを初めて読むときの自動リンクでは起きない(R3-21、R3-42)。

## 5. ユーザーに聞くこと

### 5-R7-1 マージされずに閉じた PR(Closed)を、「すべてマージ済み」の条件で数えるか

**どの画面か**: 設定の「自動化」のルール作成ダイアログのチェックボックス「リンク中の PR がすべてマージ済みのときだけ」と、アイテムの詳細パネルの GitHub の欄。

**具体例**: アイテム WEB-1 に PR を 2 つリンクしている。#12 は Merged、#13 は Closed(別の PR #14 に作り直したため、マージされずに閉じた)。ルール「全 PR マージで Done」(条件オン)がある。#12 がマージされたあと、または #12 がマージされた状態で、読み取りが走る。

**案**

- **案 a: Closed があると通らない(現行どおり)。** 結果: WEB-1 は完了にならない。利用者は、#13 のリンクを「×」で解除して、条件を通す(解除した #13 は、解除の記録に入り、もう付かない)。
- **案 b: Closed は数えない。** 結果: Merged の #12 だけが数えられ、WEB-1 は Done になる。#13 のリンクは残る。
- **案 c: Closed があるときはルールを動かさず、通知を出す。** 結果: 「自動化」の通知で、Closed の PR があることを知らせ、利用者が選ぶ。通知の種類と本文が増える。

**勧める案: b。** 理由: 取り下げた PR をリンクしたままにするのは普通に起こり、そのたびに解除させるのは手間である。R3 の自動リンクも、Closed を新しくリンクしない(R3-18)ので、同じ考え方になる。案 a は現行どおりだが、取り下げた PR が残るアイテムで、条件が通らないことに気づきにくい。上の 4 の文は案 b で書いてある。案 a を選んだときは、03 の「作成ダイアログの項目」の文の「(マージされずに閉じたものを除く)」と、R7-18 の「Closed を除いた」を消す。

### 5-R7-2 「計画なし」で閉じた Issue でも、「リンクした Issue が閉じたとき」が動くか

**どの画面か**: 設定の「自動化」のルール「Issue 完了で Done」と、アイテムの詳細パネルの GitHub の欄の Issue の行。

**具体例**: アイテム WEB-5 に Issue(example-org/web#30)をリンクしている。ルール「Issue 完了で Done」(きっかけ「リンクした Issue が閉じたとき」、すること「ステータスを Done に」)がある。#30 が、GitHub 上で「Close as not planned」(計画なし)で閉じられる。

**案**

- **案 a: 理由を区別しない。** 閉じたら動く。結果: WEB-5 は Done になる。作業をしないと決めたのに、完了として数える。仕様の変更は少ない(Issue の状態は Open・Closed の 2 つのまま)。
- **案 b: 「完了」で閉じたときだけ動く。** リンクに閉じた理由(完了・計画なし)を保存し、行に「Closed(計画なし)」と出す。結果: WEB-5 は動かない。利用者が手で Cancel にする。07 の Issue の項目に、閉じた理由が足される。
- **案 c: 理由ごとに別のきっかけにする。** 「Issue が完了で閉じたとき」「Issue が計画なしで閉じたとき」の 2 つ。結果: 計画なしのときに Cancel へ動かせる。きっかけが 7 つになる。

**勧める案: b。** 理由: 「計画なし」の Issue が完了として数えられると、レポート(05)の完了数と速度がずれる。案 a は、閉じた理由を見ない代わりに、利用者が間違った Done を直す手間が出る。案 c は、仕様が増える。案 b は、閉じた理由の保存が 1 項目増えるだけで、現行も理由を保存していた(現行の `StateReason`)。

(案 b の文: 07「PR・Issue の状態で動く自動化」の「Issue が閉じたとき」の行を、「Issue をリンクして、状態が Closed で、閉じた理由が「完了」のとき。リンク済みの Issue が、Open から、閉じた理由が「完了」の Closed に変わったとき」にする。07「PR と Issue のリンク」の冒頭に「Issue の Closed は、閉じた理由(完了・計画なし)も持つ」を足す。)
