# R1 プロジェクト単位の上書き

## R1-1 現行の振る舞い

### R1-1-0 構造

- 現行の上書きは、Store の `schema.yaml` の `scoped:` に 1 項目ずつ入る。キーは `where: project:<ULID>`。中身は `statuses`(表示するステータス)、`workflow`(`transitions` と `required`)、`templates`(`only` と `default`)の 3 つ。(`internal/app/domain/schema/schema.go:161-167`、`schema/check.go:212-240`)
- 上書きを置けるのは「グループ」である。種類が project か epic のもの。それ以外は `scoped.not_group` で断る。(`internal/app/usecase/schemas/scoped.go:238-243`。文言は `web/core/messages.ts:373-374`「{id} は {kind} で、プロジェクトでもエピックでもないため、上書きを設定できません」)。画面(`web/app/project/ProjectSettings.svelte`)から開けるのはプロジェクトだけ。エピックへの上書きは CLI の `hh schema scope set <id>` と API の `PUT /api/schema/scoped/{project}` でだけ作れる。
- 効く範囲は、そのグループと、その下のすべてのアイテム。アイテムごとに「いちばん近い祖先で、上書きを持つもの」の上書きが 1 つだけ効く。遠い祖先の上書きとは合成しない。エピックに上書きがあれば、プロジェクトの上書きはそのエピックの下では効かない。(`schema/effective.go:17-46` の `For` と `scopeAmong`、`storage/index/build.go:200-216` の `lineage`。グループ自身が先頭に入る。)
- 現行の「ワークスペース」は Store の中の入れ物で、`schema.yaml` は Store に 1 つ。上書きのキーはプロジェクトの内部 ID だけで、ワークスペースは関係しない。同じ Store の別のワークスペースへプロジェクトを移しても、上書きはそのまま付いていく。

### R1-1-1 画面と操作(プロジェクトの「設定」タブ。`web/app/project/ProjectSettings.svelte`)

見出しの下に「このプロジェクトだけの設定です。ステータスや種類の定義は {Store 名} のまま変わりません。」と出る。区画は上から次のとおり。

1. 「表示するステータス」(`:215-252`)。Store のステータスを 1 つずつチェックボックスで並べる。補足は「カンバンの列と、ステータスの選択肢に出すもの · {表示数} / {全数}」(全部出しているときは末尾に「（Store と同じ）」)。各分類の既定のステータス(`Status.Default` が真のもの)はチェックを外せない(無効)。注記は「カテゴリの既定は外せません（チェックを外せない項目です）。外したステータスのタスクはそのまま表示されます。」。全部出していないときだけ「Store と同じに戻す」ボタンが出る。全部にチェックを入れ直すと、保存時は「空のリスト」(Store と同じ)として送る。(`web/core/scoped.ts` の `setShown`、`putBody`)
2. 「ワークフローの制約」(`:254-277`)。「Store の制約に追加することだけできます（緩めることはできません）」。遷移(From から To)の追加と、必須項目の追加の 2 つの編集部品(`ConstraintEditor.svelte`)。必須項目は仕様が廃止済みなので、復活の対象外(brief のとおり)。
3. 「テンプレート」(`ProjectTemplates.svelte`)。「使うテンプレートを絞ります。1 つも選ばなければ Store のテンプレートをすべて使えます」。種類ごとの既定のテンプレートの選択(Store の既定があるときは「Store の既定（{名前}）」、なければ「なし」を初期表示)。
4. 「自動化」(`ProjectAutomations.svelte`)。R1-1-6 に書く。
5. 「今の違反」(`ProjectViolations.svelte`、`is:invalid project:<id>` で引く)。仕様で廃止済みなので、復活の対象外。
6. 末尾に「保存」(変更があるときだけ有効)と「すべて Store の値に戻す…」(上書きがあるときだけ有効)、CLI の等価コマンドの行。

保存は `PUT /api/schema/scoped/{project}`。送るのは変更した部分だけで、各部分は丸ごと置き換え。送らない部分は元のまま残る。空の部分は「Store の値に戻す」意味になる。(`internal/app/server/scoped.go:26-33,59-83`、`domain/schema/scoped.go:40-100`)。上書きが空になる(ステータスもワークフローもテンプレートもない)と、項目ごと消える。「すべて Store の値に戻す…」は確認ダイアログ「プロジェクトの設定を Store の値に戻す」を開き、本文は「このプロジェクトのステータス・遷移の制約・必須の項目の上書きをすべて外し、{Store 名} の値に戻します。テンプレートの上書きもあれば一緒に外れます（1 コミット）。」。確定後のトーストは「プロジェクトの設定を Store の値に戻しました」、保存後は「プロジェクトの設定を保存しました」。(`DELETE` は `ScopedRemove`、`usecase/schemas/scoped.go:186-198`)

保存の検査(`usecase/schemas/scoped.go:115-138,200-227`):
- 対象は、削除済みでないグループでなければならない。削除済みなら `task.deleted`(「{id} is deleted; restore {id} first」)で断る。
- テンプレートは Store に存在するものだけ。なければ `template.not_found`。
- 書き込んだ結果が、`schema.yaml` に今までなかった問題を持つときは `scoped.invalid` で断る(「上書きがスキーマに合いません: …」)。検査の項目: 不明なステータス名、各分類の既定を隠すこと(`schema.default_hidden`、「{名前} is the default of {分類} and cannot be hidden」)、`where` の形式・重複、不明なステータスを指す遷移、存在しない必須項目、存在しないテンプレート。
- 保存は 1 コミット(op `schema`)。
- 閲覧のみの Store では、各ボタンとチェックボックスが無効になり、理由が添えられる(`useReadOnlySentence`)。
- 他の人がその間に同じ上書きを変えたときは、「ほかで変更されました。編集中の内容はそのままです。」の帯と「もう一度読み込む」が出る(`:204-213`)。
- スキーマを読み込めないときは「スキーマを読み込めません · {理由}」と「もう一度読み込む」。
- オフラインの扱いは画面にない。保存はローカルの Store への書き込みで、同期は別。

### R1-1-3 アイテムの移動

- 同じ Store の中で、アイテムを別のプロジェクトへ移すと、効く上書きは移動先のものに変わる。移動の検査は新しい違反だけを断り、ステータスが変わらない移動では遷移の検査が走らない。アイテムのステータスが移動先の上書きで「隠れている」ステータスでも、そのまま残る(カンバンでは、列が残る)。
- 別の Store へ移すとき(`hh mv --store`、GUI は `StoreMove`)、移すアイテムの集まりに含まれるプロジェクト(エピックを含む)に上書きか自動化の項目があると、「プロジェクトの設定(表示と自動化)」を「持っていく」か「持っていかない」かを必ず選ばせる(`--scoped carry|drop`。指定がないと `choice.required`、CLI は聞き返す)。「持っていく」は、移動先のスキーマに合わせて切り詰める: 移動先にないステータス、それを指す遷移、存在しない必須項目、移動先にない種類の既定テンプレート、移動先にないテンプレートを外し、外したものを一覧で見せる(「scoped: dropped status "review" (not in org-b)」など)。切り詰めても移動先のスキーマの検査に通らないときは `move.invalid`(「use --scoped drop」)で断る。元の Store からは、持っていったときも持っていかなかったときも、その上書きは外れる。(`usecase/stores/movestore.go:438-540,763-835`、`domain/schema/carry.go`、`web/app/stores/MoveScopedChoice.svelte`)
- 同じ Store の別のワークスペースへ移すときは、上書きの扱いに関する処理が一切ない(ワークスペースがスキーマの単位でないため)。

### R1-1-4 削除済みのプロジェクトと上書き

- プロジェクトを論理削除しても、上書きは残る。削除済みのプロジェクトに対する `schema scope set` は断る。`schema scope rm` は削除済みにも、存在しない ULID にも使える(上書きがその ULID で残っているときだけ)。
- 診断(`doctor`)は、存在しない・削除済みのプロジェクトを指す上書きを `override.not_project`(「…is not a project of this store, or is deleted」、ヒント「restore the project, or remove the override」)で報告する。(`usecase/schema_findings.go:76-93`)
- 設定「スキーマ」の「プロジェクトごとの上書き」の一覧(A #22)は、上書きのあるプロジェクトを「ID タイトル」と、「ステータス N 件を表示 · 遷移の制約 N 件 · 必須の項目 N 件」の 1 行で並べ、行からそのプロジェクトの設定タブへ移る。プロジェクトが見つからない行は ULID だけを出す。(`web/app/settings/SettingsSchema.svelte:115-147,222-247`)

### R1-1-5 同期で、上書きとスキーマが同時に変わったとき

- `schema.yaml` は、同期でキーごとの 3 方向のマージ(`merge.kindYAML`)になる。`scoped` のリストは `where` をキーにして項目ごとに合わせ、各項目の中もキーごとに、両側が変えたときは保存時刻があとのほうが勝つ。(`internal/app/domain/merge/yaml.go:365-375`、`merge.go:100-120`)
- マージの結果は検査されない。検査は、あとでその Store に新しい `schema.yaml` を書くとき(`storage/store/tx.go:548-553`)と、診断(`schema_findings.go:39-58`)で行う。したがって、一方がステータスを削除し、他方がそのステータスを上書きの `statuses` か遷移に加えると、マージ後の `schema.yaml` には存在しないステータス名が残る。読み取りでは、`Effective.Statuses()` は存在するものだけを返し、遷移の判定は名前を比べるだけなので、実害は出ないが、診断には「unknown_status」として出る。上書きの検査項目(`schema.default_hidden` など)に当たる状態は、マージ後も診断が拾う。同期の側に自動修復はない(同期のマージのコードに、上書きを直す処理を見つけられなかった)。

### R1-1-6 自動化の上書き

- `automations.yaml` に 2 種類の項目がある。(1)`rules[].where: project:<ULID>`(そのプロジェクト専用のルール)。(2)`scoped: [{where: project:<ULID>, disable: [ルール id]}]`(そのプロジェクトとその下で、ルールを無効にする)。(`internal/app/domain/automation/file.go:55-61,100-105`)
- `where` を持てるのは種類が project のものだけ(`automation.not_project`、`usecase/automations/automations.go:249-263`)。スキーマの上書き(project と epic)より狭い。
- 効く範囲は「アイテムの祖先に、その project が含まれる」こと。Store のルール → プロジェクト専用のルールの順に、ファイルの順で実行する。そのアイテムの祖先のどれかのプロジェクトで無効にされた id のルールは動かない。(`automation/eval.go:128-161`)
- 画面(プロジェクトの設定 > 「自動化」)。見出し脇に「{Store 名} のルールをこのプロジェクトで無効にする・このプロジェクトだけのルールを追加する」。ルールごとの行に、ルールの要約、id、出どころ(「このプロジェクトだけ」「{親プロジェクトのタイトル}」「{Store 名}」)、状態のスイッチ、専用ルールだけに「削除」。スイッチの表示は、「このプロジェクトで無効」「このプロジェクトで有効」「親のプロジェクトで無効」「{Store 名} で無効」(この 2 つは操作できない)、専用ルールは「有効」「無効」。スイッチと削除は、押した時点で保存する(下書きとは別)。「このプロジェクトだけのルールを追加」はダイアログ「このプロジェクトだけのルールを追加」(id、イベント、`pr.merged` のときだけ「リンク中の PR がすべてマージ済みのときだけ」のチェック、遷移先(ステータスかカテゴリの既定))。(`web/app/project/ProjectAutomations.svelte`、`web/core/automations.ts:79-111`、`web/app/settings/RuleDialog.svelte`)
- ルールの検査(`automation/check.go`): 専用ルールが「ステータスを設定」するとき、そのプロジェクトの上書きが隠しているステータスなら `automation.unknown_status`「status … does not exist, or the project hides it」。Store 全体のルール(`where` なし)は、上書きでは検査されない。したがって、Store のルールが、あるプロジェクトで隠されたステータスへアイテムを動かすことは、実行時にも検査にも止められない。
- ステータスの削除・改名で、ルール側(`rules[].set.status`)は別経路で追従する(`schema/migrate.go` の対象外。`automation` 側の処理)。ここは詳しく追っていない。
- 別の Store へ移すときは、R1-1-3 の carry / drop の対象に自動化の項目も入る。

### R1-3-B 規則で決まらない点(13 件)

具体例は、ワークスペース「WEB」のプロジェクト WEB-P1(Store の初期設定。Todo・InProgress・Done・Pending・Cancel の 5 つ)で、「表示するステータス」から Pending を外す設定を持つ、としている。

1. **上書きをどこに置くか(持ち主と画面)**
   - 案 a: ワークスペースの設定の一部にして、プロジェクトの設定タブに「表示するステータス」「遷移の制約」「テンプレート」「自動化」の区画を足す(現行の画面と同じ置き場)。03 のサブタブ(8 つ)は変えず、A #22 の一覧は置かないか、03 のサブタブ「ワークフロー」などの下に出す。

   - 案 c: 案 a と案 b の両方(現行と同じ。プロジェクトの設定タブで編集し、ワークスペースの設定に一覧を出す)。

2. **分類の既定と「初期ステータス」を隠せるか**
   - 現行は「各分類の既定のステータス」を隠せない。仕様には別に「初期ステータス」がある。

# R7 自動化のきっかけ 3 つ(03 の自動化の節の側)

## R7-1 現行の振る舞い

### R7-1-0 きっかけを決める仕組み

- ルールのきっかけ(`on`)は 4 つ: `pr.opened`、`pr.review_requested`、`pr.merged`、`issue.closed`。条件(`when`)は 1 つ: `all_linked_prs_merged`。(`internal/app/domain/automation/file.go:20-30`、`automation/check.go:67-72`)
- 画面の表記: 「PR が開かれた」「レビューを依頼された」「PR がマージされた」「Issue が閉じられた」(`web/core/github.ts:157-163`)、条件は「リンク中の PR がすべてマージ済み」(`web/core/automations.ts:20-21`)。ルール作成ダイアログのイベントの選択肢はこの 4 つ。条件のチェックは、イベントが `pr.merged` のときだけ表示する(`web/app/settings/RuleDialog.svelte:40-41,89-95`)。ファイルと CLI には、どのイベントにも `when` を付けられる(`hh automation add --when …`。`check.go` は `on` との組み合わせを制限していない)。
- 既定のルール(`hh store init --template dev`): `pr-opened`(→ in_progress)、`pr-review`(`pr.review_requested` → review)、`pr-merged`(`pr.merged` + `all_linked_prs_merged` → カテゴリ done の既定)、`issue-closed`(`issue.closed` → カテゴリ done の既定)。(`file.go:DevRules`、`docs/guide/ja/github.md:49-55`)

### R7-1-1 いつ動くか(1 つのアイテムの前後の GitHub の状態を比べる)

- 動くのは、同期のあとに、GitHub を読んで、アイテムの `gh`(PR ごとの状態・レビュー・チェック、Issue ごとの状態。タスクのファイルに保存され、同期で共有される)が**書き換わったとき**だけ。書き換わらなければ(`apply` が `Changed=false`)、ルールは判定されない。(`internal/app/usecase/github_fetch.go:218-263` の `if !a.Changed { continue }`、`usecase/github_apply.go:34-93`、`usecase/github_rules.go:21-46`)
- 比べるのは、アイテムが保存していた `gh`(古い値)と、今回の取得で作った `gh`(新しい値)。古い値に載っていない PR・Issue は「状態なし」から始まる。(`automation/eval.go:26-60` の `EventsOf`)。`EventsOf` の式と、テスト `TestEventsOf`(`eval_test.go:21-82`)から出る結果は次のとおり(「pending → none → pending」の行だけはテストになく、式から読んだ)。

| 古い → 新しい | 起こるきっかけ |
|---|---|
| PR がまだない → Open の PR | `pr.opened` |
| PR がまだない → Draft の PR | `pr.opened`(Draft でも起こる) |
| PR がまだない → Closed の PR | なし |
| PR がまだない → Merged の PR | `pr.merged` |
| PR がまだない → Open でレビュー依頼中(pending) | `pr.opened` と `pr.review_requested` |
| Draft → Open | なし |
| レビューなし(none)→ 依頼中(pending) | `pr.review_requested` |
| 承認済み(approved)→ pending | なし |
| 変更依頼(changes_requested)→ pending | なし |
| pending → none → pending | none → pending の取得のたびに `pr.review_requested`(2 回目) |
| Open → Merged | `pr.merged` |
| Merged のまま | なし |
| Open → Closed | なし |
| 2 つの PR が同時に Open(新規) | `pr.opened` が 1 回(アイテムごとに、きっかけの名前ごとに 1 回) |
| 2 つの PR が同時に Merged | `pr.merged` が 1 回 |
| Issue がまだない → Open | なし |
| Issue がまだない → Closed | `issue.closed` |
| Issue Open → Closed | `issue.closed` |
| Issue Closed のまま | なし |

- 同じ取得で複数のきっかけが起こると、`pr.opened` → `pr.review_requested` → `pr.merged` → `issue.closed` の順に、各きっかけのルールをファイルの順に判定する。ルールごとに、そのときのステータスからの遷移を検査し(上書きの制約も含む)、通ったら次のルールはそのステータスから始める。止められたルールは、その取得のコミットに拒否として残し(`Hedgehug-Automation-Rejected`)、次のルールへ進む。最後に決まったステータスを、取得のコミットとは別の 1 コミット(op `set`)で書く。(`eval.go:92-130`、`usecase/github_rules.go:48-76`)
- 削除済みのアイテムには動かない(`eval.go:93-96`)。

### R7-1-2 3 つの個別の挙動

**`pr.review_requested`(`レビューを依頼された`)**
- レビューの状態は、GraphQL の応答から決める(`internal/lib/github/graphql.go:143-166`)。`reviewDecision` が APPROVED か CHANGES_REQUESTED ならそれ。そうでなければ、各レビュアーの最新の意見のうち CHANGES_REQUESTED があればそれ、APPROVED があれば approved。意見がなく、レビュー依頼が 1 件以上あれば `pending`。それ以外は `none`。
- きっかけが起こるのは、新しい取得で `pending` になり、古い値が「なし」か `none` のとき。Draft の PR も対象になる(`state` を見ない)。マージ済みの PR を初めて見たときに、まだレビュー依頼が残っていれば、`pr.review_requested` も起こる(`state` を見ない)。(`eval.go:42-44`)
- 「別の人にさらに依頼した」「承認のあとで再依頼した」では起こらない(古い値が `none` でないため)。
- 画面表示: アイテムの詳細パネルの GitHub の欄の各 PR に、レビューのラベルを出す(`web/app/detail/GitHubSection.svelte:104`)。これは R3 の対象。

**`issue.closed`(`Issue が閉じられた`)**
- 対象は、アイテムのリンクのうち、`Sync` が `off` でない Issue(`link` モードでも `mirror`・`push` でも)。`gh.issues` の状態が `closed` になり、古い値が `closed` でないとき。初めて見た Issue が最初から Closed でも起こる。再び開かれて閉じられれば、また起こる。(`eval.go:50-57`)
- 例外: リンクが `mirror` モードで、同期する項目に `status` が含まれ、Issue が「not_planned」で閉じられたときは、この判定から外す(`usecase/github_issues.go:324-347` の `closedHere`)。理由はコードのコメントに「中止にされ、`issue.closed` のルールの対象にならない。さもないと完了に動かされ、次のミラーで、人が編集したかのように戻される」とある。仕様は Issue の同期(mirror・push)をなくしたので、この例外の前提がなくなる。
- Issue の `StateReason`(completed / not_planned)は `gh` に保存されている(`withIssue`、`github_apply.go:99-105`)。

**`all_linked_prs_merged`(`リンク中の PR がすべてマージ済み`)**
- ルールを判定する時点で、アイテムの `gh` を見る。リンクのうち種類が PR で `Sync` が `off` でないものが 1 件以上あり、そのすべてが `gh.prs` で `merged` のときだけ通る。1 件でも `Open`・`Draft`・`Closed`、または `gh` にまだ載っていない(取得できていない)ものがあれば通らない。リンクが 0 件(Issue のリンクだけ)も通らない。大文字小文字は区別しない。(`automation/eval.go:185-205`、`eval_test.go:184-214`)
- `Closed`(マージされずに閉じた PR)がリンクに残っていると、そのアイテムではこの条件が通らない。外す方法は PR のリンクの解除(`Sync=off`)。
- 条件は、きっかけが起こった取得のときだけ判定される。つまり、2 つの PR のうち 1 つを先にマージしても、きっかけ `pr.merged` は起こるが条件が通らず、ルールは動かない。もう 1 つをマージしたとき、`pr.merged` がまた起こり、条件が通ってルールが動く。

### R7-1-3 GitHub を読む間隔、初回のリンク、同期で受け取ったリンク

- GitHub を読むのは、Store の同期の直後(`replication/sync.go:134-146` が `fetchGitHub` を呼ぶ)。リポジトリごとに、前回から 5 分(定数 `ghstate.Interval = 5 * time.Minute`)たっていれば読む。利用上限の残りが 10% 未満なら 3 倍。失敗したときも、次は 5 分あと。設定で変えられない。(`internal/app/storage/ghstate/ghstate.go:18-84`、`usecase/github_fetch.go:99-117`)。同期の周期自体は設定(既定 2 分、書き込み後 30 秒の遅延、`storage/config/config.go:76-83`)。
- 読む対象は、アイテムのリポジトリ(`repos`)と、リンクの `Sync` が `off` でない PR・Issue の番号。Merged の PR も読み続ける。(`github_fetch.go:289-318`)。PR の一覧は更新日時が前回以降のもの。
- 手動で読み直す入口は `hh pr` の直後だけ(`integration/pr.go:245` が、そのリポジトリを期限に関係なく読む)。
- 初回のリンク: `hh link` でリンクを足しても、その場では GitHub を読まない。リンクのタスクの `gh` に、その PR の状態がないので、次の取得で「状態なし」からの比較になり、Open なら `pr.opened`、Merged なら `pr.merged`、レビュー依頼中なら `pr.review_requested`(あれば)が起こる。PR をリンクして解除し、また同じ PR をリンクしたときも、解除で `gh` から消える(`apply` が使用中のリンクだけ残す)ので、また起こる(`github_rules_test.go:442-468`)。
- 自動のリンク: ブランチ名 `hh/<ID>-…`、PR のタイトル・本文・コメントの ID、`hedgehug:<ULID>` で PR をアイテムに結びつける(R3 の対象)と、同じ取得の中で `gh` が新しくでき、同じ流れで `pr.opened` などが起こる。
- 同期で受け取ったリンク: 他のマシンが PR をリンクして、すでに取得して `gh` を書いていれば、受け取ったマシンが取得しても `gh` に差がないので、きっかけは起こらない(`github_rules_test.go:561-598` の `TestRuleDoesNotFireOnWhatAnotherCloneWrote`)。他のマシンが取得する前にリンクだけを渡したとき(取得できないマシン、GitHub のアカウントがないマシンなど)は、受け取ったマシンの最初の取得で、「状態なし」からの比較になり、きっかけが起こる。同じアイテムを 2 台が同時に取得すると、同じ変更を 2 台が書く(マージで同じ内容になる)。
- 閲覧のみの Store は取得しない(`fetchStore` が `CheckWritable` で終わる)。
- ルールの変更は、Store のアイテムごとに、取得のコミットのあとの別コミットとして書かれ、作者は `hedgehug-automation`(`docs/guide/ja/github.md:57`)。

## R7-2 新仕様との衝突(10 件)

1. **03 ワークスペースの設定 > 自動化 > きっかけとすること**(03:`きっかけは次の 4 つから選ぶ。`):

2. **03 > 自動化 > きっかけとすること(作成ダイアログ)**: 「作成ダイアログの項目は、名前、きっかけ、(きっかけが「ステータス」なら)ステータス、すること、値である。初期値は、きっかけが「リンクした PR がマージされたとき」、すること「ステータスを変更」、値が完了の既定のステータスである。」。条件「リンク中の PR がすべてマージ済みのときだけ」を選ぶ項目がない。

7. **07 > PR と Issue のリンク**(07:175): 「1 つのリンクは、種別(PR か Issue)、リポジトリ、番号、タイトル、状態からなる。状態は、PR が Open・Draft・Merged・Closed、Issue が Open・Closed である。」。リンクは「レビューの状態」を持たない(`01`〜`08` を `レビュー`・`review` で検索して 0 件)。`pr.review_requested` を動かすには、レビューの状態を読み、保存する必要がある(R3 が戻す)。Issue も、Open・Closed の 2 状態だけで、閉じた理由(完了 / 計画なし)は持たない。

10. **03 > 自動化 > 実行の規則と、モックからの変更点**(03:`変更は、操作と同じ保存の中に入る。`、`| 自動化の動く範囲 | 同期で受け取った変更でも動く | このマシンで利用者が値を変える操作(一括変更はアイテムごと)だけ。同期、診断の修復、値の削除の置き換え、…では動かない。…`): 現行は、取得のコミットのあとの別コミット(op `set`)。仕様は「操作と同じ保存の中に入る」。また、仕様の「動かないのは、…同期で受け取った変更」は、現行の「他のマシンが取得せずに渡したリンクは、受け取ったマシンの最初の取得で動く」と区別する必要がある(取得して保存するのは「このマシンが GitHub から取り直して保存した変更」なので、仕様の文でも動く側に入る)。

隣接する差異(今回の復活の対象外だが、同じ表を直すときに触れる): 03・07 のきっかけ「PR が Open のとき」は、現行の `pr.opened`(初めて見た Open か Draft の PR で起こり、Draft から Open、Closed から再び開くでは**起こらない**)と意味が違う。仕様は Draft では起こさず、Open でない状態から Open に変わったとき(Draft から、Closed から再び開いたとき)に起こす。

### R7-3-B 規則で決まらない点(9 件)

具体例は、アイテム HH-5 に PR(example-org/web#12)と Issue(example-org/web#30)をリンクしている、としている。

1. **「レビューが依頼されたとき」の定義(R3 とつながる)**
   - 現行は、レビューの状態が「なし」から「依頼中」に変わったとき(最初に見たときを含む)。承認・変更依頼のあとの再依頼では起こらない。
   - 案 a: 現行の定義を戻す。PR のリンクに、レビューの状態(なし・依頼中・承認済み・変更依頼)を持たせる(R3 と同時)。
   - 案 b: 「レビュー依頼の件数が 0 から 1 以上になったとき」とし、承認や変更依頼のあとの再依頼でも起こす(例: 承認済みの #12 に再びレビューを依頼したとき)。
   - 案 c: Draft の PR の依頼では起こさない(Draft から Open に変わったときに、依頼が残っていれば起こす)。
   - 影響: R3 でレビューの状態を保存しないと動かせない。案 b・c は、PR のリンクが持つレビューの値を増やす(依頼の件数、Draft かどうかの組み合わせ)。例として、HH-5 を `review` に動かすルールが、承認済みの #12 の再依頼で再び動くかが変わる。
2. **「リンクした Issue が閉じたとき」の「閉じた」の範囲**
   - 現行は、Closed になった(最初に見たときが Closed でも)のすべて。閉じた理由(完了 / 計画なし)は見るが、例外は Issue 同期の mirror モードのときだけ。
   - 案 a: Closed になったらすべて(閉じた理由を見ない)。仕様の Issue の状態は Open・Closed の 2 つなので、これが最小。
   - 案 b: 閉じた理由が「完了」のときだけ起こす。「計画なし」では起こさない。リンクに閉じた理由を持たせる。
   - 影響: ルールが「完了」へ動かす設定(現行の既定ルール)のとき、案 a では、計画なしで閉じた Issue(#30)でも HH-5 が完了になる。
3. **Issue をリンクした時点で、すでに Closed のとき**
   - 現行は動く(最初に見たときが Closed)。仕様の PR は「PR をリンクして、状態が Open(Merged)のとき」で、リンク時に起こす。
   - 案 a: PR と同じく、リンク時に Closed なら起こす(例: すでに閉じた #30 をリンクした瞬間に、HH-5 が完了へ動く)。
   - 案 b: リンクしたあとに、Open から Closed に変わったときだけ起こす。
   - 影響: 案 a は、閉じた Issue を参照用にリンクしただけでアイテムが動く。案 b は、リンクの追加時に、GitHub から読んだ状態を保存する際に「前の状態」が必要になる(Open だったか)。
4. **Issue が再び開かれて、また閉じられたとき**
   - 現行は、閉じるたびに起こる。
   - 案 a: 閉じるたびに起こす。案 b: 1 つの Issue につき 1 回だけ。
   - 影響: 案 a では、HH-5 を手で Todo に戻したあと、#30 を再度閉じるとまた完了になる。
5. **`all_linked_prs_merged` の数え方**
   - 現行は、PR のリンクが 1 件以上あり、すべて Merged のとき。Closed(マージなし)の PR が 1 件でもあると、そのアイテムでは通らない。解除したリンクは数えない。Issue のリンクは数えない。`gh` にまだない PR(取得前)があると通らない。きっかけが起こった取得でしか判定しない。ファイルと CLI は、どのきっかけにも付けられるが、画面は `pr.merged` のときだけ選べる。
   - 案 a: 現行のとおり(Closed が混ざると通らない)。
   - 案 b: Closed の PR は数えない(Open と Draft がなく、Merged が 1 件以上)。
   - 案 c: 画面でも、どのきっかけにも条件を付けられるようにする(例: `issue.closed` かつ「すべての PR がマージ済み」)。
   - 影響: HH-5 に PR を 2 つ(#12 は Merged、#13 は Closed)リンクしているとき、案 a では完了にならず、案 b では完了になる。仕様の「リンクした PR がマージされたとき」(03:458)は条件なしで、1 つでもマージされたら動くので、条件つきと条件なしの 2 つを選べるように 03 の表をどう書くかも決める。
6. **画面(作成ダイアログ・一覧)での出し方**
   - 案 a: きっかけの選択肢を 6 つにし(PR が Open、レビューが依頼された、PR がマージされた、Issue が閉じた、ステータスが次、Step がすべて完了)、条件のチェックは「リンクした PR がマージされたとき」のときだけ出す(現行どおり)。
   - 案 b: 条件を、独立した欄にする(きっかけと別の選択)。
   - 案 c: 「リンクした PR がすべてマージされたとき」を、7 つ目のきっかけとして足す(条件を持たない)。
   - 影響: 03 の作成ダイアログの項目(衝突 2)、一覧の説明文(衝突 3、「{きっかけ} → {すること}」に条件を足す)、ステータスの削除で書き換える規則(「きっかけまたはすること(ステータスを変更)がそのステータスだったルール」)に、新しいきっかけは関係しない(ステータスを持たない)。
7. **「すること」の値**
   - 現行の既定ルールは、`set: {category: done}`(分類の既定のステータスへ)。仕様の「すること」は「ステータスを変更 | このワークスペースのステータス」のみで、値の初期値は「完了の既定のステータス」。
   - 案 a: 仕様の「ステータスを変更」だけにする。`issue.closed` の既定の値も、完了の既定のステータスという具体的なステータスの名前で持つ。ステータスの名前を変えたり削除したりすると、03 の追従の規則に乗る。
   - 案 b: 「分類の既定へ」の選び方を足す(ステータスの名前を変えても追従する)。
   - 影響: 例として、完了の既定を Done から Shipped に変えたとき、案 a のルールは Done のまま、案 b は Shipped へ動く。
8. **Draft の PR とレビュー依頼・取得の遅れ**
   - 現行の `pr.opened` は Draft でも起こすが、仕様は Draft では起こさない。レビュー依頼が Draft の PR に付いたときの扱いは、仕様にない(1 番の案 c と同じ問題)。
   - 取得の遅れ: 仕様の間隔(5〜60 分)のとき、PR が Open から Merged に変わってから動くまで最大でその間隔。リンク追加時は A7 により即時に動く。
   - 案 a: Draft かどうかを `pr.review_requested` の条件に含めない(現行どおり)。案 b: 含める(Draft では起こさない)。
   - 影響: Draft の PR にレビューを依頼するチームで、HH-5 が review に動くかが変わる。
9. **同期で受け取ったレビュー・Issue の状態**
   - A5 で、同期で受け取った状態では動かない。ただし、現行は「渡した側が取得していない(アカウントがない、取得できない)リンク」を、受け取った側の最初の取得で動かす。
   - 案 a: 仕様どおり、リンクを保存したマシン(`hh link` した側)でだけ、そのマシンの取得(リンク時と、読む間隔ごと)で動かす。アカウントのないマシンで足したリンクは、他のマシンでは動かない。
