# 復活の案 p-r1: R1 プロジェクト単位の上書き

仕様 01〜08 と現行のコードは変更していない。この文書は案である。引用は「ファイル名 + 見出し + 文(そのまま)」で書く。

## 件数の表

| 項目 | 規則で決めた点の件数 | ユーザーに聞く数 | 決定とぶつかる数 |
|---|---|---|---|
| R1 プロジェクト単位の上書き | 40(3 章の D1〜D40) | 1(Q1: 使わないステータスをどの操作で断るか) | 1(6 章: 作成ダイアログのステータスのセレクトと、02 の決定「どのステータスでも作れる」) |

## 用語の決め

- 「上書き」は、同期で負けた人への通知(06 の「上書きの通知」)と、R6 の `is:overwritten` が使う語である。紛れるので、この案では **プロジェクト別のルール** と呼ぶ。03 の冒頭が使う「アイテムの決まり」の、プロジェクトごとの版である。
- 「表示するステータス」は **使うステータス** と呼ぶ。外したものは **使わないステータス** である。「表示するだけ」でなく、選ぶ操作から外すことを名前で示すためである(Q1)。
- 「Store の値に戻す」は **ワークスペースの決まりに戻す** と呼ぶ。設定の持ち主が Store でなくワークスペースだからである(03)。
- プロジェクト自身のステータス(Todo・InProgress・Done・Pending・Cancel の 5 つ固定)と、アイテムのステータスは別である。画面の語は、プロジェクト自身には「プロジェクトのステータス」、決まりの側は「アイテムのステータス」と書き分ける。

## 案の要約

1. プロジェクト別のルールは、**ワークスペースの設定の一部**として持つ。プロジェクトの内部 ID で結びつく。置けるのは**プロジェクトだけ**で、Epic には置けない。
2. 編集は、プロジェクトの「設定」タブに 4 つの区画を足して行う。03 のサブタブは 8 つのまま変えない。
3. 変えられるのは 4 つ。(a)使うステータス、(b)遷移の制約の追加、(c)使うテンプレートと種類ごとの既定、(d)自動化(ワークスペースのルールを動かさない指定と、このプロジェクトだけのルール)。
4. 必須の項目と「今の違反」は戻さない(03 の「ワークフロー」の冒頭と、モックからの変更点の行で廃止済み)。
5. 初期ステータスと、分類ごとの既定のステータスは、どのプロジェクトでも**常に使う**。外した印が残っていても、読むときに使うものとして扱う。これで、後から初期ステータスが変わったときも、同期で重なったときも、修復の行が要らない。
6. 改名は追従の処理が要らない(03 の「アイテムは値そのものを指していて、名前の文字ではない」と同じ)。削除と、テンプレートの種類変更だけ追従する。
7. プロジェクトを別のワークスペース・別の Store へ移すと、決まりは「名前が同じ値に合わせる」で一緒に移る(02 の値の引き直しと同じ)。移動先にないものは外れ、確認ダイアログで先に一覧を見せる。
8. 同期では、複数の値を持つ項目は両方を生かし、消えた値・消えたプロジェクトを指す決まりは同期の修復で外す。診断にも同じ行を足す(R9 の「同期で自動修復」と同じ考え方)。

# 1. 何ができるようになるか

## 1-0 画面の全体

プロジェクト HH-P1「Web リニューアル」を開き、見出しの下の「設定」タブを押す。区画は上から次の 7 つになる(今は 3 つ)。

| 区画 | 内容 |
|---|---|
| 名前 | 今のとおり |
| 使うステータス | このプロジェクトで使うステータスをチェックで選ぶ |
| ワークフローの制約 | ワークスペースの制約に、このプロジェクトだけの制約を足す |
| テンプレート | 使うテンプレートを絞り、種類ごとの既定を変える |
| 自動化 | ワークスペースのルールをこのプロジェクトで動かさない指定と、このプロジェクトだけのルール |
| 別のワークスペースへ移動 | 今のとおり。確認ダイアログに、決まりの移り方を足す |
| 削除 | 今のとおり |

見出しの直下(名前の区画の上)に「このプロジェクトだけの決まりです。ステータスや種類の定義は {ワークスペース名} のままです。」と出す。4 つの区画は、チェックや選択のたびに保存する(03 の「チェックのたびに保存」と同じ)。各区画の右上に「ワークスペースの決まりに戻す…」を置く。

ワークスペースの設定側には、サブタブを足さない。「ステータス」「ワークフロー」「テンプレート」「自動化」の 4 つのサブタブの上に、決まりを持つプロジェクトがあるときだけ 1 行を出す。「プロジェクト別のルールがあるプロジェクト: HH-P1 Web リニューアル・HH-P3 …(2 件)」。各名前を押すと、そのプロジェクトの設定タブの、その区画へ移る。

## 1-1 使うステータス(例: 使わないものを外してカンバンを軽くする)

手順と結果。

1. HH-P1 の設定タブの「使うステータス」を開く。ワークスペース WEB のステータス Todo・InProgress・Review・Done・Pending・Cancel が、チェックボックスつきで並ぶ。全部にチェックが付いている。「6 / 6」。
2. 「Pending」のチェックを外す。保存され、「5 / 6」になる。Pending のアイテムが HH-P1 に 2 件あるので、行に「2 件が使用中」と添える。アイテムは変わらない。
3. HH-P1 のカンバン(プロジェクトの画面)を開く。Pending の列は、2 件あるあいだだけ出る。見出しに「使わない」の印が付き、ここへカードをドロップすると「このプロジェクトでは「Pending」を使いません」と出て、何も変わらない。2 件を別の列へ動かせば、列は消える。
4. HH-P1 の Task のステータスのボタンを押すと、メニューに Pending が出ない。作成ダイアログでプロジェクトに HH-P1 を選んでも、ステータスのセレクトに Pending が出ない。
5. 検索 `status:Pending project:HH-P1` は、今までどおり 2 件を返す。バーンダウンやベロシティも変わらない(分類で数えるため)。

初期ステータス Todo、未着手の既定 Todo、進行中の既定 InProgress、完了の既定 Done、中止の既定 Cancel の行は、チェックが付いて無効で、「初期ステータスで、未着手の既定でもあるため外せません」のように理由を添える。

## 1-2 ワークフローの制約(例: HH-P1 は Review を必ず通す)

1. 「ワークフローの制約」を開く。行が今のステータス(From)、列が次のステータス(To)の表が出る。ワークスペースが許さない遷移のセル(WEB では InProgress から Done は許可、Todo から Done は禁止、など)は、チェックなしで無効になり、ホバーで「ワークスペースの制約で変更できません」と出る。
2. 行 InProgress の To で、Review にだけチェックを付ける。右に「制限あり」と出る。
3. HH-P1 の Task を InProgress から Done にしようとすると、メニューの Done が無効になり、ヒントに「ワークフローの制約: InProgress から Done には変更できません(Review のみ)」と出る。ワークスペースの他のプロジェクトでは、今までどおり Done に変えられる。

プロジェクトの制約は、ワークスペースの制約に**足して絞る**だけで、緩められない。2 つの許可先が重ならないときは、文言を「ワークフローの制約: A から B には変更できません(変更できる先がありません)」にする。

## 1-3 テンプレート(例: HH-P1 は 3 つだけ使い、Task の既定を変える)

1. 「テンプレート」を開く。ワークスペースのテンプレートが、種類のアイコンと名前でチェックボックスつきで並ぶ。1 つもチェックしないあいだは「すべて使えます」と出す。
2. 「Bug 報告」「週次タスク」「リリース作業」の 3 つにチェックを付ける。
3. 下の「種類ごとの既定」の Task のセレクトで「週次タスク」を選ぶ。選択肢は、「ワークスペースと同じ(なし)」「なし」と、使うテンプレートのうち種類が Task のもの。
4. 作成ダイアログでプロジェクトに HH-P1 を選び、種類を Task にすると、テンプレートのセレクトには「なし」「週次タスク」だけが並び、「週次タスク」が当たっている。プロジェクトを HH-P2 に変える。HH-P2 が使うテンプレートを「Bug 報告」だけに限定しているなら、「週次タスク」は HH-P2 で使えないので、テンプレートが「なし」に戻り、HH-P2 の Task の既定があればそれが当たる。HH-P2 に限定がなければ、「週次タスク」は使えるので、そのまま残る。

## 1-4 自動化(例: HH-P1 だけ、PR のマージで完了にしない)

1. 「自動化」を開く。ワークスペースのルールが、出どころ「ワークスペース」で並ぶ。各行にスイッチがあり、ON は「このプロジェクトで動く」。
2. ルール「PR マージで完了」のスイッチを OFF にする。HH-P1 とその下のアイテムでは、このルールが動かない。ほかのプロジェクトでは動く。ワークスペース側でそのルールが無効なときは、スイッチを無効にして「ワークスペースで無効」と添える。
3. 「このプロジェクトだけのルールを追加」を押す。ダイアログは、ワークスペースの「ルールを作成」と同じ項目(名前・きっかけ・ステータス・すること・値)で、ステータスの選択肢は使うステータスだけ。名前は「HH-P1 レビュー完了」とし、きっかけ「ステータスが Review になったとき」、すること「担当者を 田中 に」で作る。このルールは HH-P1 の下のアイテムにだけ動く。
4. ワークスペースの「自動化」サブタブには、このルールが「HH-P1」の印つきで並ぶ。編集と削除もそこでできる。

## 1-5 戻す

各区画の「ワークスペースの決まりに戻す…」で確認ダイアログを出し、「戻す」を押すと、その区画のこのプロジェクトの決まりをすべて外す。例: 「使うステータス」では、外してあったチェックがすべて付く。「自動化」では、動かさない指定がすべて外れ、このプロジェクトだけのルールが削除される(ダイアログの本文にルールの件数を出す)。

# 3. 端の場合(規則で決めた点)

引用は「ファイル名 + 見出し + 文」。以降 D1〜D40 を、規則で決めた点として数える。

## 持ち主・置き場

**D1 持ち主はワークスペース。** 01「Store で共有するものと、マシンごとに持つもの」の表「ワークスペースとその設定(プロパティ、値、ワークフロー、テンプレート、自動化、スプリント、リリース)」。決まりは設定の一部として Store で共有する。結果: プロジェクトを開く全員に同じ決まりが効く。保存したビューやマシンごとの設定には置かない。

**D2 置けるのはプロジェクトだけ。** 01「用語と階層」「**プロジェクト**: Epic をまとめる単位。」と 03 冒頭「「アイテムの決まり」を、ワークスペースごとに持つ」。Epic はアイテムで、設定の単位でない。現行のデータの取り込み・移行を定めた節は 01〜08 にない(「移行」の語は 02 のメッセージの「移行先」にだけ現れる)。現行で Epic に置かれた上書きは、この仕様の対象に含めない。

**D3 変更は 1 回の保存で、アクティビティに残る。** 03「範囲と画面の構成」「1 回の変更が 1 回の保存になり、アクティビティに残る。」。文は 4 章 C14 の表のとおり。履歴・通知は出さない。根拠: 02「リポジトリの追加と削除」「追加も削除も、プロジェクトの履歴には残らず、通知も出ない。」。

**D4 閲覧のみの Store では編集できない。** 03「範囲と画面の構成」「閲覧のみの Store のワークスペースでは、設定の Store に書く入力欄とボタンをすべて無効にし、「閲覧のみの Store です」と添える。」。4 つの区画のチェック・スイッチ・追加・戻すを無効にして添える。決まりの効き目(列・メニューの絞り込み)は、閲覧のみの Store でも出る(保存済みのデータを読むだけ)。

**D5 保存の方式は即時保存。** 03「遷移の制約」「チェックのたびに保存する。」。下書きと「保存」ボタンは持たない。「ワークスペースの決まりに戻す…」は、03「ルールの一覧」の「削除は、確認ダイアログ「ルールを削除」…で…確認する」に合わせて確認ダイアログを出す(ボタン「戻す」)。元に戻す仕組みは持たない(01)ので、戻したあとの再設定は手で行う。

**D6 ワークスペースの設定側の 1 行。** 03「範囲と画面の構成」のサブタブ 8 つは変えない。「ステータス」「ワークフロー」「テンプレート」「自動化」の上に、決まりのあるプロジェクトを 1 行で知らせる。削除済みのプロジェクトは数えない(03「名前の重複は…重複の数に、削除済みのワークスペースとプロジェクトは入れない」と同じ扱い)。閲覧のみでも出す(押して開くだけ)。

## 使うステータス

**D7 初期ステータスと分類の既定のステータスは常に使う。** 03「分類ごとの既定のステータス」「既定のステータスは、分類を変えることも削除することもできない。」、同「初期ステータス」「新しく作るアイテムの最初のステータスを、**初期ステータス**として 1 つ指定する。」。両方とも作成・複製・Step・分類の列・置き換え先で自動で書かれる値なので、使わないステータスになると、使わないはずのステータスが自動で入る。チェックを外せなくする(無効の行)。そのうえで、あとから別の人が初期ステータスや既定を、外してあるステータスに変えたときや、同期で一方が外し、他方が初期ステータスにしたときは、外した印を消さず、**読むときに使うものとして扱う**。そのステータスが初期・既定でなくなれば、印がまた働く。結果: 修復の行も、断る文言も要らず、どのマシンでも同じ結果になる(06「同時に編集したとき」の「どのマシンで同期しても、同じ結果になる」と同じ性質)。

**D8 使わないステータスのアイテムは、そのまま残る。** 03「分類」「分類を変えても、アイテムは変わらない。」と同じ考え方で、使わなくしてもアイテムは変えない。アイテムの値が使わないステータスになる経路は、移動・同期・値の置き換え・診断の修復・受信箱の「制約を無視して…」と、使わないことにした時点で既にそのステータスにいたもの(作成は 6 章)。作成ダイアログの「一緒に作るもの」の子と Step は初期ステータスで作るので、使わないステータスにならない。見え方は D9・D10。

**D9 カンバンの列。** 04 カンバン「列」「対象のワークスペースにあるステータスの名前ごとに 1 列」。プロジェクトの画面だけ、使わないステータスの列を出さない。そのステータスのアイテムが 1 件でもあれば、元の位置に出し、見出しに「使わない」の印を付ける。件数と WIP 制限は他の列と同じ(04「(削除された値)」の列の「件数と WIP 制限は他の列と同じ」に倣う)。「ステータスの分類」の分け方は 4 列のままで影響しない。

**D10 使わないステータスの列・メニューへの変更は断る。** メニューは項目から外す(2-2 の表)。ドラッグでドロップしたときは、何も変えずに「このプロジェクトでは「{ステータス}」を使いません」と表示する。根拠: 04「ドラッグ」「そのカードのワークスペースに同じ名前のステータスがないときは、何も変えずに「{ワークスペース名} にはこのステータスがありません」と表示する。」と同じ見せ方。検索・ビューのカンバンで、列が出ていても、カードのプロジェクトが使わないステータスの列へのドロップは、同じ文言で断る。Q1 の案 A のときだけ有効。

**D11 ステータスのメニューの現在値。** 02「ステータスの変更」「いまのステータスにはチェックを付ける。」と、「いまのステータスがワークスペースの一覧にないとき(削除された値のまま残っているとき)は、遷移の制約を検査しない。」。現在値が使わないステータスのときは、チェックつきで 1 項目だけ残し、「このプロジェクトでは使わない」と添える。その項目を選び直しても何も変わらない(同じ値)。ほかの項目は、遷移の制約を通常どおり検査する。

**D12 使うステータスを外すとき、専用ルールが使っていれば断る。** 検査は入口(外す操作)に置く。03「自動化」は、きっかけと同じステータスのルールを「検査は、スイッチと保存の 2 つの入口だけに置く」と定めており、同じ形にそろえる。トースト「「{ステータス}」はこのプロジェクトだけのルール「{ルール名}」が使っているため、使わないことにできません。先にルールを変えてください」を出し、チェックは外れない。ワークスペース全体のルールが使っている場合は断らない(ほかのプロジェクトでは使うため)。実行時は D26 のとおり止まる。

**D13 改名は追従の処理がない。** 03「名前」「名前を変えても、アイテムの値は変わらない(アイテムは値そのものを指していて、名前の文字ではないため)。」。決まりも値そのものを指すので、名前を変えても何も書き換えない。分類の変更も、決まりに影響しない(03「ステータスの分類の変更 | 影響なし」)。

**D14 ステータスを削除したときの追従。** 03「削除」「ステータスのとき、さらに次の変更をする。 ワークフロー: そのステータスの行と、ほかの行の許可先から外す。許可先がすべてなくなった行は、「どこへでも」に戻る。」。同じ規則を、使わないステータスの一覧、プロジェクトの制約の行と許可先、プロジェクト専用ルールのきっかけ・することに適用する(専用ルールはワークスペースのルールの一覧に入るので、既存の「代わりのステータスに書き換える/同じなら無効にして通知する」がそのまま働く)。確認ダイアログの添え書きに「プロジェクト別のルールを含む」を足す。専用ルールの書き換え先(代わりのステータス)が、そのプロジェクトで使わないステータスのときは、そのまま書き換えて残す(入口の検査は D12 の外す操作と、保存の 2 か所だけで、書き換えには掛けない。03 が同期で届いたきっかけと同じステータスのルールを「直さずにそのままにする」のと同じ)。実行のときは D26 で止まる。

## 遷移の制約

**D15 合成は積集合で、文言の X・Y も積集合。** 03「遷移の制約」「文言は「ワークフローの制約: A から B には変更できません(X・Y のみ)」で、X・Y は許可している To である。」。ワークスペースの許可先と、プロジェクトの許可先(行にチェックがなければ全部)の重なりから、使わないステータスを除いたものを X・Y とする。重なりが空のときは「ワークフローの制約: A から B には変更できません(変更できる先がありません)」とする。重なりが空になる行は、プロジェクトの表で「変更できる先がありません」と添える。ワークスペースの表を編集したあとに空になることは防げない(防ぐ検査は入れない。診断にも出さない)。理由: 空の重なりは「止まったまま」でなく、設定を見直せば直る状態で、アイテムは壊れていない。

**D16 使わないステータスに関するプロジェクトの制約は、使わないあいだ無視する。** プロジェクトの表には、使うステータスだけを出す。保存した制約のうち、使わないステータスを From または To とするものは、使わないあいだ数えない。使うステータスに戻せば、再び働く。行のチェックが使わないステータスだけのときは、その行を「ワークスペースと同じ」として扱う。理由: 03 のモックからの変更点の行「ステータスの削除で空になった遷移の行」の「許可先がなくなった行は「どこへでも」に戻る」と同じ考え方で、閉じ込められる行を作らない。

**D17 制約を適用しない変更に、プロジェクトの制約も含める。** 03「遷移の制約」「次の変更には、遷移の制約を適用しない。アイテムの作成(…)、アイテムの移動(…)、種類の変更、同期で受け取った変更、値の削除による置き換え、診断の修復、受信箱の「制約を無視して…」と「自分の値に戻す」。」。プロジェクトの制約も同じ。例: 太郎さんが同期で届けた、HH-P1 の制約に反するステータスの変更は、そのまま受け入れる。

**D18 一括変更は、残して続ける。** 04 一括変更「ワークフローの制約に合わないアイテムは変えずに残し、件数を知らせます。」。プロジェクトの制約に反するアイテムも同じ。例: 10 件を Done にして、うち 2 件が HH-P1 の制約で Done に行けないとき、8 件を変え、「8 件を変えました。2 件はそのままです: HH-4・HH-7(ワークフローの制約: …)」。使わないステータスのアイテムは、理由「{ID}(このプロジェクトでは使わないステータス)」で残す。一括変更の一覧から、選んだアイテムのどのプロジェクトでも使わない名前は除く。

## テンプレート

**D19 使えるテンプレートの決め方。** 03「種類ごとの既定」「候補は、その種類のテンプレートだけである。」と 02「ダイアログの項目」「その種類に使えるテンプレートがあるときだけ出す。「なし」を含む」。使えるテンプレート = ワークスペースのテンプレートのうち、種類が合い、プロジェクトの限定(1 つも選んでいなければ全部)に入るもの。種類ごとの既定は、プロジェクトの既定があればそれ、なければワークスペースの既定。ただし、どちらも使えるテンプレートに入らないときは「なし」とする(警告は出さない)。理由: 限定を変えたあとに既定が食い違っても、保存したデータは矛盾せず、決め方が 1 つで済む。

**D20 テンプレートの削除・種類変更。** 03「種類ごとの既定」「テンプレートの種類を変えて既定の種類と合わなくなったとき、またはテンプレートを削除したときは、既定から外す。」と、「削除すると、種類ごとの既定からも外れる。」。同じ規則を、プロジェクトの限定と既定に適用する。限定が空になったときは、限定を外した(すべて使える)状態になる。確認ダイアログ「テンプレートを削除」に、決まりが変わるときだけ「N 件のプロジェクトの決まりからも外れます。」を足す(限定が空になるプロジェクトがあれば「「X」を使うよう限定していた HH-P1 は、すべてのテンプレートを使えるようになります」を続ける)。改名は D13 と同じで何もしない。

**D21 作成ダイアログの連動。** 02「ダイアログの中での連動」「**プロジェクトを変えたとき**: 親を選び直す。」。ステータスのセレクトの選択が新しいプロジェクトで使わないなら、初期ステータスに戻す。選んでいるテンプレートが新しいプロジェクトで使えないなら、「なし」に戻し(説明がテンプレート由来なら空に戻し)、新しいプロジェクトの、いまの種類の既定のテンプレートを当てはめる。使えるなら、そのまま残す。ダイアログを開いた時点とワークスペースを変えた時点は、そのときのプロジェクトの既定で当てはめる。例: HH-P1 の Task の既定「週次タスク」を当てた状態で HH-P2(限定なし、既定なし)に変えると、「週次タスク」は HH-P2 でも使えるので残る。

## 自動化

**D22 専用ルールはワークスペースのルールの一覧に入る。** 03「名前の重複は、…ルール(それぞれワークスペース内)で認めない。」。専用ルールの名前も、ワークスペースの中で重複できない(同じ名前なら「同じ名前のルールがあります」)。新しいルールが一覧のどこに入るかは 03 に定めがない(既存の抜け)。専用ルールを含め、作ったルールは一覧の末尾に入る、と定める(4 章 C18)。03「実行の規則」「有効なルールのうち、きっかけに合うものを、一覧の上から順に実行する。」。専用ルールも同じ順で判定する。ワークスペースの「最近の実行」(03「このワークスペースで、自動化が変えたアクティビティを、新しい順に最大 8 件」)には、専用ルールの実行も入る。

**D23 効く範囲。** 判定するアイテムの属するプロジェクトが、専用ルールの持ち主のとき動く。ルールを動かさない指定があるプロジェクトでは、そのルールを判定しない。「Step がすべて完了したとき」は親に対して動くので、親のプロジェクトで判定する(03「親に対して動く」)。アイテムを別のプロジェクトへ移すと、次の判定から移動先の決まりが効く(D29)。

**D24 専用ルールの作成の入口。** プロジェクトの設定タブの「自動化」からだけ作る。ワークスペースの「自動化」サブタブの「ルールを作成」は、今までどおりワークスペース全体のルールだけを作る。専用ルールの編集と削除は、どちらのタブからもできる。ダイアログの項目と検査(03「きっかけとすること」の表、保存の条件)は同じで、ステータスの選択肢だけ使うステータスに絞る。

**D25 ワークスペースで無効のルールの表示。** 03「ルールの一覧」「一覧の各行は、有効・無効のスイッチ、名前、説明…」。ワークスペースでルールが無効のときは、プロジェクトの「自動化」の該当行のスイッチを無効にして「ワークスペースで無効」と添える(プロジェクトの指定は変えられない)。専用ルールのスイッチは、そのルール自身の有効・無効で、03 の「スイッチを ON にするときも、上の表の最後の条件と同じ検査をする」がそのまま働く。

**D26 使わないステータスへの自動化は止める。** 03「制約で止まったとき」「すること「ステータスを変更」は、遷移の制約を検査する。反するときは、実行を止め、アイテムを変えない。」。これに、「アイテムのプロジェクトが使わないステータスへは変更しない」を加える。止まったとき、保存もアクティビティも残さず、あなた宛ての受信箱「自動化」に、理由「このプロジェクトでは「{ステータス}」を使いません」つきの通知を出す。ボタンは 03 のとおり(「制約を無視して {ステータス名} にする」「変更しない」)。専用ルールのきっかけが使わないステータスのときは、きっかけに合う変更が起きないので動かない。Q1 の案 A のときだけ有効。

**D27 ステータスの削除でルールが変わったときの通知。** 03「削除」「ルールが変わったとき…受信箱の「自動化」へ通知を 1 件ずつ作る」。専用ルールも同じ通知文を使い、ルール名にプロジェクトは添えない。

## 検索・保存したビュー・レポート

**D28 検索・ビュー・テーブル・ガント・レポートに効かない。** 04 の検索のキーの表「`status` | ステータスの名前 | アイテムのステータスの名前が一致する。」、03「値の編集」「保存したビューの検索条件は書き換えない」、05「数え方の共通ルール」「**分類**: ステータスが属する未着手・進行中・完了・中止の 4 つ(03)。」。例: HH-P1 で Pending を使わなくしても、`status:Pending project:HH-P1` は一致する。保存したビューは、決まりの変更で書き換えない。WIP 制限も列の名前で持つので消えない(04「WIP 制限」「上限は、列の分け方ごとに、列の名前で持つ。」)。プロジェクトのカンバンで使わないステータスの列が出ないあいだも、上限は残る。

## 移動

**D29 アイテム(Epic・Story・Task・Bug・Step)の移動。** 02「同じワークスペースの中での移動」「ワークフローの制約の検査はしない。」と、「値の引き直し」の「移動先のワークフローの制約は検査しない。」。移動先のプロジェクトの決まりも検査しない。ステータスが移動先で使わないものでも、そのまま残る。別のワークスペースへ移すときは、名前が一致するステータスに引き直す(使うかどうかは見ない)。例: HH-6 の Task が、Pending を使わない HH-P1 から HH-P2 へ移るとき、ステータスが Pending のままでも移れる。

**D30 プロジェクトの移動(別のワークスペース・別の Store)。** 02 プロジェクト「移動」「各アイテムの扱いは、アイテムを別のワークスペースへ移すときと同じである。」。決まりは、プロジェクトのデータとして一緒に移し、次のように名前で合わせる。移動元の決まりは、同じ保存で外す。

| 決まり | 移るもの | 外れるもの(確認ダイアログで先に一覧にする) |
|---|---|---|
| 使わないステータス | 移動先に、同じ名前のステータスがあるもの | 同じ名前がないもの |
| 遷移の制約 | From と To の両方が、移動先に同じ名前であるもの | どちらかがないもの |
| 使うテンプレートの限定 | 同じ名前・同じ種類のテンプレートがあるもの。残ったものが 0 件なら、限定を外す(すべて使える) | ないもの |
| 種類ごとの既定 | 同じ名前・同じ種類のテンプレートがあるもの | ないもの(「ワークスペースと同じ」になる) |
| ルールを動かさない指定 | 移さない(ルールは移動先のものと別物のため) | すべて |
| 専用ルール | きっかけ・することのステータスが、移動先に同じ名前であるもの | ステータスがないもの(ルールごと削除される) |

専用ルールの担当者は、別の Store へ移すとき、ログイン名が一致する移動先のメンバーに置き換え、いなければ移動先のメンバーに加える(02「値の引き直し」「担当者・ユーザー・ウォッチ中の人」と、プロジェクト「移動」のメンバーを加える規則)。移動先に同じ名前のルールがあるときは、「{移動先} には同じ名前のルールがあります: {名前}。先にルールの名前を変えてください」と表示して断る(02「移動先に同じ名前のプロジェクトがあるときは…断る」と同じ扱い)。別の Store への移動の保存の順(02「保存」)と、どれかが失敗したときに何も変えない規則は、そのまま使う。転送の記録に、決まりは含めない。

**D31 ワークスペースの別の Store への移動・削除・復元。** 03「別の Store へ移動」「ワークスペースの設定、プロジェクト、アイテム、コメント、作業時間、スプリント、リリースが、そのまま移動先へ移る。」と、「削除」「ワークスペース、その中のプロジェクト、アイテム、スプリント、リリース、設定は、まとめて「削除済み」に入り」。決まりは設定の一部なので、一緒に移り、一緒に削除済みに入り、一緒に戻る。専用ルールの担当者も、03 の「移動先のメンバーに載せる人」(設定の…自動化ルールの担当者の値)に既に入っている。変更なし。

**D32 プロジェクトの論理削除と復元。** 08「復元の単位」「戻るものは、削除する前の値で、元の場所に戻る。」。プロジェクトを削除しても、決まりと専用ルールは残り、働かない(下のアイテムが削除済みのため)。復元で、決まりも働く。削除済みのプロジェクトの決まりは、設定タブを開けないので編集できない。専用ルールは、ワークスペースの「自動化」に「(削除済み)」の印つきで残る。名前の重複には数える(03「名前の重複は…」の「重複の数に、削除済みのワークスペースとプロジェクトは入れない」は、ワークスペースとプロジェクトの名前だけの規則)。

**D33 プロジェクトの完全な削除。** 08「完全に削除」「取り除くのは Store の現在の中身だけで」。完全に削除する行の保存の中で、決まりと専用ルールも外す。確認ダイアログの本文に、専用ルールがあるときだけ「専用のルール {M} 件も削除します。」を足す。保持日数を過ぎた自動の完全削除も同じ。

## 同期

**D34 同時に変えたときの項目の合わせ方。** 06「同時に編集したとき」「項目は、1 つの値ごとに分ける。」。決まりの項目は次のとおり。複数の値を持つもの(使わないステータス、遷移のチェック(From と To の組ごと)、使うテンプレートの限定、このプロジェクトで動かさないルール)は、1 つずつの追加と削除を両方生かす(06 の表「値を複数持つ項目」)。単一のもの(種類ごとの既定のテンプレート)は後勝ち。専用ルールは、ワークスペースのルールと同じ扱い(ルールごとの後勝ち)。「同じ値を一方が足し、他方が外したとき」は後勝ちで、負けた人に「上書き」の通知を作る。

**D35 「上書き」の通知。** 06「上書きの通知」の表に、1 行を足す。本文は「{項目名}が上書きされました」で、項目名は「{プロジェクトの ID} の使うステータス」「… のワークフローの制約」「… の使うテンプレート」「… の{種類}の既定のテンプレート」「… のルール「{名前}」の指定」とする。表示は本文だけで、「自分の値に戻す」は出さない(関連・リンクと同じ。複数の値で、戻す相手が決まらないため)。

**D36 削除された値を指す決まりは、同期で外す。** 06「削除された値を指す設定」「初期ステータス…にした値を、別のマシンが同時に削除していたときは…削除を取り消して値を残す。」は、初期ステータスと既定のための規則で、決まりには当てはめない(外したいステータスを、外す人が決まりに入れたからといって、削除を取り消すのは筋が通らない)。受け取ったマシンは、同期の修復として、存在しないステータス・テンプレートを指す決まりを外す。使わないステータスの一覧からは黙って外す(通知なし)。遷移のチェック、使うテンプレートと既定は、外して、そのチェック(指定)を作った人のマシンが通知を作る。ルールは無効にして通知する(03「自動化がきっかけと同じステータスになる」の、無効にして通知する扱いと同じ)。同じ修復を複数のマシンが行っても 1 行(06「修復の決まり」)。ワークスペースの種類ごとの既定のテンプレートと、ワークスペース全体のルールが、同期で削除済みの値を指したときにも、同じ修復を行う(06・03 にこの場合の決めがなかったため、同じ行に含める)。

**D37 持ち主のプロジェクトがなくなったとき。** 06「別の Store へ移動したものと重なったとき」「移動を優先する。」、「完全な削除と重なったとき」「完全な削除を優先する。」。決まりの変更をした人の変更は反映されず、そのプロジェクトの決まりと専用ルールは、同期の修復で外す。通知は、決まりを変えた人のマシンが作る。完全に削除のときは既存の本文「{ID} は完全に削除されたため、あなたの変更は反映されませんでした」の {ID} をプロジェクトの ID にして使う。同じ Store の別のワークスペースへ移したときは、新しい本文を使う(4 章 C11)。別の Store への移動には既存の本文を使う。

**D38 プロジェクトの削除と、決まりの変更が重なったとき。** 06「同時に編集したとき」の表の最後の行「一方が削除し、他方が変更した…| 変更が残り、削除は取り消す。」。決まりの変更は、**プロジェクトへの変更に数えない**。プロジェクトの削除は取り消さず、決まりは残る(D32)。理由: 決まりはワークスペースの設定で、プロジェクトの項目(06「プロジェクトのタイトル・ステータス・オーナー・開始日・終了日」)ではないため。決まりを変えた人には通知を出さない(決まりは消えずに残るので、失われるものがない)。

## 診断・通知・そのほか

**D39 診断に 2 行を足す。** 08「検出する項目」の表と注意書き。「設定が存在しない値を指す」と「決まりの持ち主がない」。直し方は D36・D37 の同期の修復と同じで、通知は出さない。08「結果の表示と修復」は「直したアイテムごとに」通知を出し、アイテムでないメンバーの重複には「アイテムではないので、通知を出さない」と定めているので、アイテムでない設定の修復も同じ扱いにする。閲覧のみの Store の分は、08 のとおり無効にして「閲覧のみの Store です」と添える。

**D40 そのほかの端の場合(まとめ)。**
- 0 件: 決まりがなければ、4 つのサブタブの上の 1 行は出さない。プロジェクトに専用ルールがなければ「自動化」の区画はワークスペースのルールだけを並べる(ルールがなければ、03「ルールはありません」と同じ文)。テンプレートがないときは「テンプレートはありません」(03「一覧と編集」)と出す。
- 空: 使わないステータスが 0 件、制約のチェックが 0 件、限定が 0 件は、ワークスペースの決まりと同じ(保存データは空になる)。
- オフライン: 保存はこのマシンへの書き込みで、同期は別(06「オフライン」「保存はこれまでどおり行え、未送信の保存として溜まる。」)。
- 複数の Store: ワークスペースごとの設定なので、Store をまたぐ影響はない。一括変更・検索・ビューで複数の Store のアイテムを選んでも、アイテムごとに自分のワークスペースのプロジェクトの決まりを引く。
- GitHub アカウントのない Store: 決まりの編集は Store への保存だけで、GitHub のアカウントを使わない(03 の設定の保存に、アカウントを求める記述はない)。効き目も同じで、GitHub を読まない。
- 一括変更: D18。
- 保存したビュー: D28。
- 通知: 決まりの変更は通知を作らない(D3)。「自動化」の通知は D26・D27。「同期の修復」の通知は D36・D37。
- アクティビティ: 4 章 C14 の文。同期の修復の実行者は「同期」。
- 履歴: プロジェクトの履歴は「作成・項目の変更・移動・復元」だけ(02「履歴」)。決まりの変更は残さない。
- 複製と種類の変更: 02「複製」「ステータス | ワークスペースの初期ステータス。ワークフローの遷移の制約は検査しない」、「種類の変更」「ステータスは変わらず、ワークフローの制約も検査しない。」。初期ステータスは常に使うので、複製した結果が使わないステータスになることはない。種類の変更は決まりに影響しない。

## Q1. プロジェクトで「使わない」にしたステータスを、どの操作で断りますか

## 6-1. 作成ダイアログのステータスのセレクトに、使わないステータスを出しますか

ぶつかる記録済みの決定。02 のモックからの変更点の行: 「| 作成時のステータス | 初期ステータス以外を選ぶと、遷移の制約まで検査する | 遷移の制約を適用せず、どのステータスでも作れる | 遷移の制約は「いまのステータスから次へ」の決まりで、作成時には移る元がないため |」。同じ趣旨の文が、02「入力の検査」の「作成時にはワークフローの遷移の制約を適用しないので、どのステータスでも選べる。」と、03「遷移の制約」の「アイテムの作成(Step の追加、テンプレートでの作成、複製を含む。任意の初期ステータスで作れる)」にある。この決定は「遷移の制約を作成に掛けない」ことを決めたもので、「使わないステータス」は別の仕組みだが、「どのステータスでも」の言い方とぶつかる。

画面は、プロジェクト HH-P1(Pending を使わない)を選んだ作成ダイアログのステータスのセレクト。

具体例。HH-P1 の画面で C キーを押し、プロジェクトが HH-P1 の作成ダイアログを開く。ステータスのセレクトを開く。

- **案 a(推奨)**: Pending を出さない。セレクトは Todo・InProgress・Review・Done・Cancel の 5 つ。作ったアイテムは、使うステータスのどれかになる。プロジェクトを HH-P2(Pending を使う)に変えると、Pending が選べる。
- **案 b**: 使わないステータスも出す。セレクトは 6 つのままで、Pending を選ぶと、使わないステータスのアイテムができ、HH-P1 のカンバンに「使わない」の Pending の列が出る。

勧める案: a。理由は 2 つ。(1)メニューでは選べないステータスが、作成ダイアログでだけ選べると、使わないという決めが作成の入口で崩れる。(2)02 の決定の理由は「作成時には移る元がない」で、遷移の制約を掛けない理由であり、使わないステータスを選ばせない理由とは関係がない。

案を選んだときに変わる仕様の箇所。

| 変わる箇所 | 案 a | 案 b |
|---|---|---|
| 02 入力の検査の「どのステータスでも選べる」(下の C6 の 5 つ目) | 「そのプロジェクトで使うどのステータスでも選べる」にする | 変えない |
| 02 の作成ダイアログのステータスのセレクト(C6 の 3 つ目)と連動(C6 の 4 つ目の、ステータスを戻す文) | 入れる | 入れない |
| 03 遷移の制約の「任意の初期ステータスで作れる」(下の C6 の 6 つ目) | 「使うステータスなら任意で作れる」にする | 変えない |
| 02 モックからの変更点の「作成時のステータス」の行(下の C6 の 7 つ目) | 「理由」の末尾に「ただし、プロジェクトが使わないステータスは選べない」を足す | 変えない |
| 03 の新しい節の「使わないステータスは、次のように扱う」(C19) | 「作成ダイアログのステータスのセレクトに出さない」を足す | 「作成では、使わないステータスにもなる」を足す |

## 6 章の補足: 書き換える既存の文(決定でないもの)

次の既存の文は書き換えるが、決定の行ではない(02・03・04 のモックからの変更点の表と audit/*-decisions.md に、これらを決めた行は見つからなかった)。

| 書き換える文 | どこ | 理由 |
|---|---|---|
