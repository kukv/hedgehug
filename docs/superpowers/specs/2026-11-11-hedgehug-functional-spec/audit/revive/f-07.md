## 0. 現行の振る舞い(事実)

### 0-1. どのリポジトリの、どの PR を、いつ探すか

出所は `internal/app/usecase/github_fetch.go`(以下 fetch)、`github_autolink.go`(autolink)、`github_apply.go`(apply)、`internal/app/storage/ghstate/ghstate.go`、`internal/lib/github/graphql.go`。

- いつ: Store の同期(`hh sync`、GUI の裏の自動同期)が終わった直後に 1 回、その Store について `FetchGitHub` が呼ばれる(`internal/app/usecase/replication/sync.go:164`、`fetchGitHub`)。remote のない Store も、GitHub のリポジトリを指すアイテムがあれば同じ形で読む(`replication/sync.go:296` の `fetchOnly`、`HasGitHubTargets`)。GUI に「いま読む」導線はない(`hh pr` のあと `integration/pr.go:245` が `FetchGitHubRepo` を呼ぶだけ)。
- 間隔: 固定 5 分(`ghstate.go:19` `Interval = 5 * time.Minute`)。設定はない。リポジトリごとに数え、最後に読んだ時刻と最後に試した時刻の遅い方から 5 分たつまで読まない(`ghstate.go:64-84` `NextAt`)。利用上限の残りが 10% 未満のあいだは 3 倍の 15 分(`ghstate.go:21,92-94`)。上限を使い切って断られたら、GitHub が返した解除時刻まで読まない(`fetch.go:144-147`、`ghstate.go:87-89`)。失敗したら `LastTry` を記録し、次の間隔まで読み直さず、そのあいだは前回の警告を出し直す(`fetch.go:112-125`)。
- どのリポジトリか: `targetsOf`(`fetch.go:305-340`)。その Store の、削除済みでも壊れてもいないアイテムの `repos` に書かれたリポジトリ(プロジェクトに結び付けたリポジトリを含む。現行ではプロジェクトも種類 `project` のアイテム)と、無効でないリンクが指すリポジトリ。Store の remote のリポジトリは対象に入らない(`targetsOf` は remote を見ない)。どのアイテムも名指ししなくなったリポジトリは、読み取りの記録ごと捨てる(`fetch.go:88`、`dropGone`)。
- どの PR か: 対象のリポジトリごとに 2 種類を読む。
  1. 走査 `ScanPulls`(`graphql.go:254-286`): 更新日時の新しい順に 100 件ずつ。前回の走査で GitHub が返した最新の更新日時(`Since`)以降に更新された PR をすべて読む。初回(`Since` が空)は最新の 100 件だけ。状態の絞り込みはなく、Open・Draft・Merged・Closed のすべてを読む。1 件ごとに、タイトル、本文、ブランチ名、最新のコミットのチェック結果、レビューの情報、コメントの先頭 100 件を取る(`graphql.go:55-59`)。
  2. リンク済みの番号の取得 `LinkedItems`(`graphql.go:293-`): リンクが指す PR・Issue を番号で 100 件ずつ。状態に関わらず、無効でないリンクはすべて毎回読む(Merged も読む)。
- どのアカウントか: `ss.GitHubForRepo`(`conn.go:160-193`)。config の `repo_accounts` の規則があればそのアカウント、なければ Store に割り当てたアカウント、それもなくアカウントが 1 つだけならそれ。アカウントがなければ、リポジトリごとに警告「no account can read {repo}; set repo_accounts in config.yaml」(`conn.go:171`)を出し、間隔まで再試行しない。仕様 07 は `repo_accounts` の規則を廃止している(07「モックからの変更点」の「リポジトリごとのアカウントのルール」)ので、この点は現行と違う。
- 書き込める Store だけ: 閲覧のみの Store は読まない(`fetch.go:59-61`)。非表示の Store は、現行では読む(`Hidden` は GUI の一覧にだけ効き、`FetchGitHub` は見ない。`config.go:32`「the CLI is not affected」。`fetch.go`・`replication/sync.go` に `.Hidden` の参照はない)。

### 0-2. 自動リンクの探し方

`mentioned`(`autolink.go:59-89`)と `autoLinks`(`autolink.go:115-135`)。走査で読んだ PR だけが対象で、リンク済みの番号の取得で読んだ PR は対象にならない(`fetch.go:181` は `scanned` だけを渡す)。

- ブランチ名: `^(?:hh|hedgehug)/([A-Za-z][A-Za-z0-9]*-[0-9]+)(?:-|$)`(`autolink.go:14`)。`hh/WEB-1-login` も `hh/WEB-1` も `hedgehug/WEB-1-x` も一致。大文字小文字は問わず、アイテムの照合のときに大文字小文字を区別しない(`resolve.go:32`)。
- 本文・タイトル・コメント: `hedgehug:<26 文字の ULID>` または `hh:<ULID>`(`autolink.go:15`)と、`WEB-1` の形のアイテム ID(`autolink.go:16`)。ID の形は大文字の接頭辞だけで、その Store の接頭辞(ワークスペースの接頭辞と、アイテムが持っていた ID・旧 ID の接頭辞。`prefixesOf`、`autolink.go:93-111`)のどれかに一致したものだけを拾う。ハイフンに隣り合う一致は捨てる(`PRE-WEB-7` は `WEB-7` ではない。`autolink.go:25-34`)。
- `hh pr` が作った PR の本文は最終行が `hedgehug:<ULID>` で、その行がある本文は、その ULID のアイテムだけを指す。本文の残りとタイトルは読まない(`autolink.go:79-84`、`markOf`)。コメントは最終行の規則に関係なく読む(`autolink.go:85-87`)。コメントは先頭 100 件。
- 接頭辞のない ID: 現行には「接頭辞なし」のワークスペースがない(接頭辞は必須で 2〜10 文字。`model/taskid.go:13`、`audit/current-vs-spec.md` C4)。`#12` の形を読む処理はない。
- 照合: `ix.Resolve(名前)`(`autolink.go:122`、`resolve.go:26-55`)。その Store 1 つの中で、現在の ID、旧 ID(`former_ids`)、ULID の順に探し、段階ごとに 1 件に決まれば採用する。同じ段階で 2 件以上なら曖昧で、黙って飛ばす(`autolink.go:123-125`)。見つからないものも飛ばす。削除済みのアイテムと壊れたファイルのアイテムにはリンクしない(`autolink.go:126-128`)。
- Store をまたぐとき: 照合は Store ごとに別々(Store ごとに `FetchGitHub` が走り、`ix` は Store の索引)。同じ ID(たとえば `WEB-1`)が 2 つの Store にあって、両方の Store のアイテムがそのリポジトリを指していれば、同じ PR が両方の Store の `WEB-1` に別々にリンクされる。そのリポジトリを指すアイテムがない Store には、リンクされない。
- 同じ PR を複数のアイテムにリンクしてよい(`autolink.go:129`、アイテムごとに 1 件ずつ)。1 つの PR が複数の ID を指していれば、ID の数だけアイテムにリンクされる。
- Issue は自動リンクしない。走査は PR だけ(`ScanPulls`)。ガイド(`docs/guide/ja/github.md:21-24`)は「pull request や Issue のタイトル、本文、コメントにある `hedgehug:<ULID>`」と書くが、コードにその経路はない。ガイドと実装が食い違っている。

### 0-3. リンクの作り方と解除

- 作る: `apply`(`apply.go:34-45`)。アイテムに、同じ参照のリンクが無効なものも含めて 1 つもなければ、種別 PR、同期モード `mirror`、由来 `via`(`branch`・`mark`・`id`・`comment`。`model/github.go:24-27`)付きでリンクを足す。
- 解除: `Unlink`(`integration/link.go:153-163`)。リンクを消さず、`sync: off` にして残し、`gh` に保存した状態は捨てる。無効のリンクは、読み取りの対象からも自動リンクの対象からも外れ(`fetch.go:323`、`apply.go:48`)、自動リンクは同じ参照のリンクが 1 つでもあれば足さない(`apply.go:35-36` の `CanonRef` 比較は `Live()` を見ない)。これが「解除したリンクを次の読み取りで付け直さない」仕組み。
- 手動で付け直す: `link`(`integration/link.go:106-129`)。無効のリンクがあれば、モードを入れ直して有効に戻し、`via` を空にする(「this link is of a person now」)。有効なリンクがあれば `link.exists`「{リポジトリ}#{番号} is linked already」で断る。
- Issue のリンクの数: 現行は 1 つのアイテムに何本でも、同じ Issue を複数のアイテムにもリンクできる(`link.go` に制約はない)。仕様の「1 つのアイテムに 1 つ」とは違う。自動リンクは PR だけなので、この制約とぶつからない。

### 0-4. 表示

- 詳細パネルの GitHub 欄の PR の行(`web/app/detail/GitHubSection.svelte:95-120`): `{リポジトリ}#{番号}`、タイトル、状態のチップ、レビュー(`reviewLabel`: 「レビュー待ち」「approved」「修正依頼」。none は「—」、Draft は常に「—」。`web/core/github.ts:90-96`)、チェック(`checksLabel`: 「CI 成功」「CI 失敗」「CI 実行中」。チェックなしは出さない。`github.ts:98-105`)、右端に「ブランチ名 · 検出元」(検出元は `viaLabel`: 「ブランチ名から自動リンク」「本文の hedgehug:<ULID> から自動リンク」「ID から自動リンク」「コメントから自動リンク」。手でリンクしたものは出さない。`github.ts:107-115`)。
- プロジェクト概要の「PR」表(`web/app/project/ProjectOverview.svelte:133-158`): 列は PR、タイトル、状態、レビュー、CI、タスク。
- 「PR を作成」ボタンは、PR 作成用の文字列(本文の末尾に `hedgehug:<ULID>` を入れる。`integration/pr.go:135`、`model.MarkedBody`)をコピーする。

### 0-5. レビュー・チェックの保存、保存と通知

- 保存している。`withPull`(`apply.go:90-94`)が、タイトル、ブランチ、状態、レビュー、チェック、マージ日時を、アイテムのファイルの `gh.prs[]` に書く(`model/github.go:81-89`)。`apply` は取得した値で書き直し、変わっていれば(`sameState` が YAML を比べる。`apply.go:114-126`)保存する。つまり、レビューやチェックが 1 つ変わるたびに保存が起きる。取得のたびに読むだけではない。
- 1 回の読み取りで変わったアイテムをまとめて 1 つのコミット(操作名 `gh-fetch`、`Automated: true`)にする(`fetch.go:231-281`)。そのあと、自動化のルールが動けばアイテムごとに別のコミット(ステータスの変更)を作る(`fetch.go:288-289`、`github_rules.go:48-66`)。
- アクティビティ: `gh-fetch` のコミットは「自動」として絞り込める(`usecase/github_status.go:18-24` の `AutomatedCommit`、`server/activity.go:104-110`)。元に戻す(undo)の対象外(`tasks/undo.go:77`)。
- 通知: 現行の受信箱の「ウォッチ」の通知は、ステータスと担当者の変更だけを見る(`storage/inbox/collect.go:435-447`)。`gh` の変更(レビュー・チェックを含む)では通知は出ない。確かめたのは `collect.go` の `changes()` の比較項目で、`gh` は入っていない。
- 取得に失敗したとき: 保存した値のまま残す(`apply.go:60-62` の `case i >= 0`)。失敗は読み取りの警告として同期のレポートに載り、`github.json`(このマシンだけの記録、Store には保存しない)に警告が残って間隔のあいだ出し直される。
- アカウントのない Store: 警告を出して読まない。すでにリンクされた PR の保存した値はそのまま残り、表示される。
- 閲覧のみの Store: 読まない(`fetch.go:59-61`)。保存した値を表示。
- 利用上限: 0-1 のとおり。

### 0-6. 自動化(R7 の現行の側)

`automation/eval.go:26-60` の `EventsOf`。前回の `gh` と今回の `gh` を比べる。

- `pr.opened`: 前回なかった PR(新しくリンクされた PR を含む)が Open または Draft のとき。
- `pr.review_requested`: 今回のレビューが `pending` で、前回が `none` か空のとき。`pending` は、レビューの意見がまだなく、レビュー依頼が 1 件以上あること(`graphql.go:160-163`)。一度でも承認・修正依頼があれば `pending` に戻らない(戻る遷移では起きない)。
- `pr.merged`: 今回 Merged で前回が Merged でないとき。初めて見た PR が Merged だったときも起きる(コメント「a PR seen for the first time as merged is a pr.merged」)。
- `issue.closed`: リンクした Issue が今回 closed で、前回が closed でないとき。初めて見た Issue が closed のときも起きる。
- 条件 `all_linked_prs_merged`(`eval.go:186-208` の `allMerged`): 無効でない PR のリンクが 1 つ以上あり、その保存済みの状態がすべて Merged のとき。リンクのないアイテム、取得できていない PR がある(保存した状態がない)アイテムは偽になる。
- 動くのは、そのリンクの更新を保存したマシンだけ(コミットを書いたのがそのマシン)。

## 1. 仕様との衝突

### 3-B. 規則で決まらない点(24 件)

**探す範囲と読み取り**

N1. 自動リンクのために PR を探すリポジトリ。
- 案 a: 現行どおり、アイテムの `repos`(プロジェクトのリポジトリを含む)とリンク先のリポジトリ。影響: プロジェクト概要で「PR はありません」のプロジェクトでも、そのリポジトリの PR が `WEB-1` を本文に書けば、詳細パネルの GitHub 欄に PR が現れる。02:534 の「使い道は、PR・Issue のリンク先の候補」を「自動リンクの探す範囲」に広げる文が要る。
- 案 b: すでにリンクのあるリポジトリだけ。影響: アイテム `WEB-1` に PR を 1 本も手でリンクしていないリポジトリの PR は、いつまでも自動リンクされない。最初の 1 本は手で付けるしかない。仕様の取り直し(07)の範囲と一致する。
- 案 c: 案 a に Store の remote のリポジトリも足す。影響: Store のリポジトリ(例 team/hedgehug-store)の PR(Store のデータを変える PR)も走査され、設定「Store」のアカウントの利用上限を使う。現行は remote を探さない。

N2. 走査のコストと間隔。
- 案 a: リンクの取り直しと同じ「GitHub を読む間隔」と同じ読み取り(1 回で走査もする)。影響: 利用上限の消費が増える(現行も 1 回の読み取りで両方読む)。初回は最新 100 件までなので、それより古い PR は更新されるまでリンクされない。
- 案 b: 走査は別の間隔(たとえば長め)。影響: 設定「一般」の選択肢が増える(08:32 は 4 つの選択で固定)。
- 案 c: 走査をやめ、詳細パネルを開いたとき、そのアイテムの ID でそのリポジトリの PR を検索する。影響: 開くまでリンクされない。ブランチ名・本文・コメントの検索は GitHub の検索の対象によって結果が違う。
- 補足: 初回に最新 100 件だけ読む現行の上限(`graphql.go:254`)を、仕様で書くか。

N3. 自動リンクを探す PR の状態。現行は Open・Draft・Merged・Closed のすべて。
- 案 a: すべて(現行)。影響: 3 年前にマージされた PR が、更新(コメントなど)されたときに今のアイテムへリンクされることがある。
- 案 b: Open と Draft だけ。影響: マージ済みの PR を見落とす。「Merged は取り直さない」(07)と整合する。
- 案 c: すべて探すが、Merged・Closed は新しくリンクしない(すでにリンク済みなら読む)。

**ID の書き方**

N4. 接頭辞のない ID(`#12`)。GitHub 上では、PR の本文の `#12` は同じリポジトリの 12 番の PR・Issue への参照で、チャットでも同じ形。
- 案 a: 読まない(現行と同じ。接頭辞のある ID の形だけ)。影響: 接頭辞のないワークスペースのアイテム(例: メイン、`#12`)は、本文の ID では自動リンクされない。ブランチ名か、手でリンクするしかない。
- 案 b: 読む。影響: PR の本文「#12 を直す」は、GitHub では 12 番の PR・Issue を指すのに、アイテム `#12` にリンクされる(Store の `#12` と GitHub の `#12` は別物)。リポジトリごとにたまたま同じ番号になる偶然のリンクが多発する。
- 案 c: `hh/<番号>-…`(ブランチ名)と `hedgehug:` 印だけ、接頭辞のないワークスペースを許す。影響: 本文に書く手段が印しかなくなる。

N5. ブランチ名の形 `hh/<ID>-<slug>`。接頭辞のないワークスペースのアイテムのブランチ名の形は仕様にない。ブランチを作る機能(`hh start`)も仕様の外(01:7 CLI は扱わない)。
- 案 a: 接頭辞のあるアイテムだけ現行の形。接頭辞なしのアイテムはブランチ名ではリンクされない。
- 案 b: `hh/12-slug` のように番号だけの形を足す。影響: 接頭辞のある `hh/WEB-1-x` との見分けは、先頭が数字かで付く。別の Store の `#12` と区別できない(N6)。
- 案 c: ブランチ名での自動リンクをやめる(R3 の「現行の範囲すべて」と食い違う)。

N6. Store をまたぐ同じ ID。仕様 04(183・417 行)の検索は Store をまたぐすべてに一致する。現行の自動リンクは Store ごとに独立。
- 案 a: 現行どおり、Store ごとに、その Store がそのリポジトリを指しているとき(アイテムの `repos` かリンク)だけ。影響: 同じ PR が `team-a` の `WEB-1` と `team-b` の `WEB-1` の両方にリンクされることがある(両方の Store がそのリポジトリを持つとき)。
