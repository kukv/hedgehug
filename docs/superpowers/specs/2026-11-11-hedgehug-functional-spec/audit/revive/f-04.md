# R6 クエリのキー(A #33〜#37)

## R6-1 `group:`(A #33)

### 現行の振る舞い
- 書き方: `group:status`。1 つの語に値は 1 つだけ(`group:status,kind` は「group: takes one field」で断る)。`-group:` と `group>x` も断る。`group:` を 2 つ書くと「a query takes one group:」で断る(`internal/app/storage/query/sort.go:36-60`)。`sort:` を 2 つ書いた場合も同じく「a query takes one sort:」で断る(同 `:55-58`)。
- 指せる項目(`sort.go:67-135`): status、kind、title、created、updated、label、assignee、スキーマの追加プロパティ(`PropOrBuiltin`。priority・start・due・estimate・points・parent などの組み込みも含む)。知らない名前は「cannot sort or group by "x"」(未知として扱う)。
- 結果: 値ごとに 1 つのグループ。値がないものは最後の 1 グループ(キー空)。グループの並びは項目の並び(status はスキーマの定義順、kind は Project・Epic・…、enum は選択肢の定義順、日付・数値は値の大小、テキストは小文字化した五十音・辞書順)。グループの中の並びは `sort:`、なければ rank(`sort.go:216-258`)。
- 複数の値を持つ項目(label、assignee、複数選択のプロパティ)では、1 件が値の数だけのグループに入る。単一値の項目で値が複数あれば最初だけ(`sort.go:222-225`)。
- 日付(created・updated)では、グループのキーが RFC3339 の秒までの文字列なので、ほぼ 1 件ずつのグループになる(日付単位にはまとめない)。
- ウェブ画面: 上の「大きな事実」1。ツリー・ガントでは `withoutOrder`(`web/app/tree/filter.ts:48-62`)が `group:`・`sort:` を API に送る前に外す。保存したビューのツリー・ガントは `treeOrderProblem`(`web/app/views/draft.ts:66`)の理由「ツリーとガントのビューは rank の順に並ぶため、group: と sort: は使えません」で保存を断る(`web/app/views/ViewSave.test.ts:164`)。
- CLI: `hh ls group:status` でグループごとに出す。API は、クエリに `group:` があるときだけ `groups` を返す(`internal/app/usecase/browse/read.go:136-148`)。
- 端の場合: 0 件ならグループなし(空の 1 グループ)。削除済みは対象外(`is:deleted` を書かない限り)。複数 Store を一度に問い合わせるときのグループは `mount.Query` が Store をまたいで合わせる(確かめた範囲では、キーの文字列が同じものを 1 つにする。`sortkey.go` は並べ替えの比較のみで、グループの合流の実装は読んでいない)。閲覧のみの Store: 読むだけなので変わらない。オフライン: 変わらない(Store のローカルの索引を読む)。

### 新仕様との衝突
1. 04 クエリ言語の「キー」の表: 「`sort` | 並べ替えのキー | 一致の判定には使わず、並べ替えにだけ使う(後述)」。`group` の行がない。表は固定の列挙で、`group` を足すと表と、04 の検索ヘルプの表(「`sort:-priority` | 並び順(- で降順。テーブルとカンバンで使われる)」)の両方を変えることになる。
2. 04 テーブルのグループの節: 「「グループ」の設定で、行をグループに分ける。初めは「なし」である。」と、7 値の表(ステータス・担当者・プロジェクト・親・種類・優先度・スプリント)。グループの手段が設定だけで、クエリのキーはない。現行 `group:` の指せる項目(追加プロパティ、created、updated など)は、この表にない。
3. 04 テーブルのグループの節: 「グループの並びは、並べ替えたあとの行に最初に現れた順である。ステータスの定義順や優先度の順位では並べない。」現行の `group:` は項目の並び(定義順・値の大小)で並べる。
4. 04 並べ替えの節: 「`sort:` が効くのは、テーブルの行の並びと、カンバンの列(レーン)の中のカードの並びだけである。ツリーとガントは、階層と並び順のまま動かさない。」と、audit/mid-low-decisions.md の Q-097(ツリー・ガントを開いているとき欄の下に灰色で「ツリー・ガントでは sort: は使われず、並び順のままです」)。`group:` については書かれていない。現行はツリー・ガントで `group:`・`sort:` をエラーにするので、`sort:` の扱いと反対になる。
5. 04 保存したビューの節「ビューが持つもの」の表: 「テーブルの設定 | 表示する列、グループ、列見出しの並べ替え」「カンバンの設定 | 列の分け方、スイムレーン、列ごとの WIP 制限」。グループとスイムレーンはビューの設定として持つので、クエリの `group:` が同じ役目を持つと二重になる。04 モックからの変更点の表にも「「未保存の変更」の対象 | … | 保存したビューが持つものすべて(スイムレーン、ガントの目盛り、ロードマップを含む)」とある(`group:` は絞り込みの一部として比べられる)。
6. 04 モックからの変更点の表: 「グループの名前 | ステータス・優先度は名前、そのほかは ID。大文字小文字を区別する | ステータス・優先度は名前(区別しない) | 比較の規則をそろえるため」。現行 `group:` の status は名前、優先度などの組み込みは値の文字列そのままで、テキストの比較は小文字化。

### 決めなければならない点
規則で決まる:
- 削除済みは対象外。よりどころ: 04 組み立て方「対象になるのは、削除済みでないアイテムである。」
- 値のないものの置き場所は最後。よりどころ: 04 並べ替え「値がないアイテムは、昇順でも降順でも最後に置く。」(並べ替えの文。グループの見出しの語は表ごとに決まる(スプリントは「スプリントなし」など)ので、新しい項目の見出しは決まらない側)。

規則で決まらない:
1. **`group:` とテーブルの「グループ」の設定の優先。** 04 は `sort:` と列見出しのときだけ「列見出しの並べ替えは、クエリの `sort:` より優先する」と定める。例: 絞り込み欄に `group:kind` を書き、「グループ」を「ステータス」にしたとき。案 A: 設定が優先(`sort:` と同じ)。`group:` は設定が「なし」のときだけ効く。案 B: `group:` が優先し、設定のメニューは `group:` の値を表示して無効にする。案 C: `group:` は書けないが、書いたら設定に読み替える(絞り込み欄が設定のもう 1 つの入口になる)。
2. **指せる項目。** 案 A: テーブルの 7 値だけ(「`group:` の候補」を 04 の候補の表に足す)。案 B: 現行どおり、追加プロパティ・created・updated・関連システムなども可。案 C: キーを廃止して、設定だけにする(R6 の「復活」の趣旨に反するので、ユーザーの確認が要る)。
3. **ツリー・ガント・カンバンでの扱い。** 現行のウェブではテーブルも含めてどの画面も `group:` を描かない。案 A: テーブルだけが `group:` を見て、ほかは無視(灰色の注記は Q-097 と同じ形)。案 B: 現行どおりツリー・ガントではエラー(Q-097 の `sort:` と食い違う)。案 C: カンバンでは列の分け方・スイムレーンの代わりに読む。例: カンバンで `group:priority` を書いたとき、スイムレーンの「優先度」と同じ見た目にするか、無視するか。
4. **グループの並び。** 仕様のテーブルは「最初に現れた順」。現行 `group:` は項目の並び。案 A: 最初に現れた順に統一(`group:status` でも定義順にならない)。案 B: 項目の並び(定義順・値の大小)。案 C: 名前の五十音(スイムレーンと同じ。04 スイムレーン「レーンは名前の五十音順に並べ、「なし」に当たるレーンは最後に置く」)。
5. **複数の値を持つ項目(関連システム・複数選択)で 1 件が複数のグループに入るか。** R8-2 と同じ。仕様の担当者は単一値(04 テーブルのセル「担当者、ユーザー | セレクト」)なので、現行の「担当者が複数ならそれぞれのグループ」は残らない。
6. **`group:` を 2 つ以上書いたとき。** 現行はエラー。仕様の `sort:` は「`sort:` が複数あるときは、最初のものだけを使う」でエラーにしない。案 A: 最初のものだけ使う。案 B: 現行どおりエラー(04 のエラーは 2 種類だけと書かれているので、足す)。

## R6-2 `mentions:`(A #34)

### 現行の振る舞い
- `mentions:tanaka`、`mentions:@me`、`mentions:none` は書けない(現行は none を matchBy で受ける: 本文・コメントにメンションがないもの)。値のログイン名は大文字小文字を区別せず、ホストなしの値は、どのホストのそのログイン名にも一致する(`internal/app/storage/index/refs.go:95-105` `MentionNames`)。
- 対象: アイテムの本文と、削除されていないコメントの本文の `@login`・`@host/login`(`internal/app/storage/index/comments.go:112-125`)。コードブロックとインラインコードは対象外(`refs.go:21-34` `Mentions` は `prose` を通す)。`@` の前が英数字・`_`・`.`・`@`・`/`・`-` なら対象外(メールアドレスやパスを除く。`refs.go:12-15` の正規表現)。
- `@me` は `Options.Me`(このマシンに登録した GitHub アカウントのログイン名すべて。`internal/app/usecase/session.go:735`)。アカウントがないと「@me needs an account to be set up」。
- Store のメンバーかどうかは見ない。メンバーにいないログイン名でも一致する。
- 受信箱は同じ `Mentions` を使って「メンション」の通知を作る(コメントに "as the inbox does" と書かれている)。
- ウェブ画面に、このキーを案内する場所(検索ヘルプの表、候補)はない(`rg "mentions:" web/` に該当なし。あるのは Go の `eval.go` のみ)。

### 新仕様との衝突
1. 04 クエリ言語の「キー」の表と検索ヘルプの表に `mentions` がない(固定の列挙)。`watching`(「その人がウォッチしている」)の隣に足す形になる。
2. 02 メンション: 「説明とコメントの中の `@ログイン名` が、その Store のメンバーのログイン名と一致したとき、そのメンバーに通知が出る。ログイン名は、大文字と小文字を区別せずに比べる。`@` の前にどんな文字があっても、一律にメンションとして扱う。」現行の抽出は `@` の前の文字(英数字・`.`・`@`・`/`・`-` など)とコードを除くので、`a@b.com` の `@b` は現行では対象外、仕様では対象。同じ文は 06 通知の「メンション」の節にもある(「`@` の前にどんな文字があっても、一律にメンションとして扱う。」)。
3. 02 メンション: 「保存した本文からメンションが消えた人の行は、そのまま残す。」通知の行は消えないが、`mentions:` は今の本文で判定するので、本文から消えたメンションにはもう一致しない。通知の一覧と検索結果がずれる。
4. 04 `assignee` の行: 「ログイン名(`@` を付けてもよい)、`@me`、`none`。表示名では書けない」「`@me` は、そのアイテムの Store での「あなた」」。現行の `mentions:@me` は Store ごとの「あなた」ではなく、マシンの全アカウントのログイン名。01 の「あなた」は Store ごとに決まる(「Store のアカウントのログイン名、なければこのマシンの「ログイン名」でメンバーと照合する」)。

### 決めなければならない点
規則で決まる:
- ログイン名の比較は大文字小文字を区別しない。よりどころ: 04 組み立て方「名前、ログイン名、ID の比較は、大文字と小文字を区別しない。」
- 値のないアイテムは、否定のクエリで一致する側に入る。よりどころ: 04 組み立て方「値のないアイテムは、否定では一致する側に入る。」
- `none` は「値がない」の意味(メンションがない)。よりどころ: 04 のキー表で `none` を取るキー(`assignee`・`watching` など)の書き方に合わせる。ただし `mentions` に `none` を許すかは仕様に書かれていない(下の決まらない点 5 に重ねる)。

規則で決まらない:
1. **`@me` の意味。** 案 A: `assignee:` と同じ「そのアイテムの Store での「あなた」」。例: Store A のあなたが taro、Store B のあなたが taro2 なら、`mentions:@me` は A では `@taro`、B では `@taro2` を探す。案 B: 現行どおり、マシンの全アカウントのログイン名。
2. **抽出の規則。** 案 A: 02 のとおり `@` の前の文字を問わない(`a@b.com` の `@b`、コードの中も対象)。通知と同じ集合になる。案 B: 現行どおり、メールアドレス・パス・コードを除く。通知とは別の集合になる。
3. **Store のメンバーにいないログイン名。** 02 の通知は「その Store のメンバーのログイン名と一致したとき」。検索で `mentions:xyz`(メンバーにいない)を書いたとき、案 A: 一致を返す(現行)。案 B: 04 のエラー「「xyz」というキーはありません」に近い扱いは仕様になく、候補にも出さないので、結果は 0 件にする(Store ごとのメンバーだけに照合)。
4. **削除済みのコメントのメンション。** 現行は含めない。仕様には、コメントの削除でメンションの通知の行がどうなるかの記述が見つからなかった(「メンション」の節に削除の語なし。`rg "コメント.*削除"` は 02 のコメント節の削除の説明のみ)。案 A: 含めない(現行)。案 B: 通知の行が残るので含める。
5. **`mentions:none` と `host/login` の書き方。** 仕様のログイン名はホストなし(01 メンバー「表示名とログイン名」)。案 A: `none` を許す、`host/login` はやめる。案 B: `none` を許さない(`priority:none` のようにエラー。04 モックからの変更点「`priority:none` はエラーにする」の前例)。

## R6-3 関連のキー(A #35)

### 現行の振る舞い
- 10 個のキー: `blocked_by:` `blocks:` `causes:` `caused_by:` `relates:` `related_by:` `duplicates:` `duplicated_by:` `clones:` `cloned_by:`(`internal/app/domain/schema/relations.go:17-38`、`eval.go:209-216`)。
- 向きのある 4 種(blocked_by/blocks、causes/caused_by、duplicates/duplicated_by、clones/cloned_by)は、キーが「そのアイテムから見た自分の側の名前」、値が相手。例: `blocks:HH-3` は「HH-3 をブロックしているアイテム」(HH-3 の `blocked_by` に入っているもの。`eval.go:545-562` `inverse`)。`blocked_by:HH-3` は「HH-3 にブロックされているアイテム」(自分の `blocked_by` に HH-3 を持つもの)。
- **現行の `relates` は向きがある**(`relates` は自分から相手へ。`related_by` は逆)。`docs/guide/ja/planning.md:46` が明記: 「`relates` にも向きがあるので、`relates:WEB-2` は `WEB-2` を指しているタスクだけを探します。`WEB-2` に関係のあるものをすべて探すときは、`hh ls relates:WEB-2` と `hh ls related_by:WEB-2` の 2 回で求めます。クエリに OR はありません。」
- 値: ID、ULID、`<store>:<ID>`、`none`(`none` は、その関連を 1 つも持たない/その関連の相手に指されていない。`eval.go:476-493,545-562`)。Store をまたぐ問い合わせで、その Store にない ID は一致なし(`MissingIDs`)。同じ ID が 2 つの Store にあれば「task.ambiguous」で断る(`internal/app/usecase/mount_ops.go:17-21`)。ただし `mount.Query` は `MissingIDs` を有効にするので、確かめた範囲では Store をまたぐクエリでは曖昧な ID はエラーにならず、各 Store の中で解決される(`eval.go:445-470` は 1 つの Store の索引だけを見る)。
- `.inverse` の旧い書き方(`causes.inverse:`)はエラーで逆方向のキー名を案内する(`eval.go:244-248`)。

## R6-7 `created`・`updated`(A #37)

### 現行の振る舞い

3. **記録の持ち方。** 現行はブラウザの localStorage。案 A: 現行どおり(01 の「マシンごと」の表に 1 行足す)。案 B: このマシンの画面の状態として、ブラウザによらない保存先にする。
4. **削除済み・完全に削除・旧 ID の扱い。** 例: 最近開いた HH-12 が削除された、または別のワークスペースへ移って HH-12 でなくなった。案 A: 一覧から外す(削除済み)。移動したものは新しい ID で出す。案 B: 残して、押したら 02 の「見つからないとき」のトーストを出す。

## R10-7 新しいタブで開く(A #7)

### 現行の振る舞い
- 画面内のリンク(`onLinkClick`。`web/app/router.ts:239-249`)を、左クリックで Ctrl・Cmd・Shift を押しながらクリックすると、`window.open(絶対 URL, "_blank")` で新しいタブを開く。「noopener」を付けないので、新しいタブは sessionStorage のコピーを受け取り、トークンを引き継ぐ(コメント: 「The token is in sessionStorage, which is per tab. A tab the browser opens from a link starts without it ("open it from hh ui" screen)」)。Alt が付くと何もしない(ブラウザの既定)。
- パレットの候補を Ctrl/Cmd+Enter で選ぶと、`href` を持つ候補を同じ方法で新しいタブに開き、パレットを閉じる(`web/app/palette/CommandPalette.svelte:306-312,338-341`)。`href` のない候補(コマンドの `run` だけのもの)は、Ctrl+Enter でも普通に実行する。
- 中クリック・右クリックの「新しいタブで開く」は、`e.button !== 0` で処理を抜けるので、ブラウザの標準動作になる。標準動作で開いたタブは、トークンを引き継がない(コードのコメントのとおり)。そのタブには 08 の「トークンのない URL」の画面が出る(確かめたのはコードの読みまで。実際のブラウザで試していない)。
- 新しいタブは、アプリを最初から読み込み、同じ `hh ui` のサーバーに接続する。タブごとにトークンの入れ物(sessionStorage)があり、閉じたタブの URL を開き直すとトークンがない(08 の画面)。

### 新仕様との衝突
1. 08 サーバーに接続できない画面とトークンのない画面: 「hedgehug の画面は、端末で `hh ui` を実行すると開く URL からだけ使える。」「トークンのない URL | `hh ui` が開いた URL でない(URL にトークンが付いていない、または一致しない。`hh ui` を再起動したあとの、古い URL を含む。サーバーにつながって再読み込みした古い URL は、トークンが一致しないので、この画面に変わる)」。現行はアドレス欄からトークンを消し、sessionStorage に持つので、同じタブの再読み込みでは画面が続く(仕様の「サーバーにつながって再読み込みした古い URL は…この画面に変わる」は、`hh ui` の再起動などでトークンが変わった場合の話)。新しいタブがトークンを引き継ぐのは、仕様のどこにも書かれていない。
2. 01 キーボードの表: 「Enter | 1 行の入力欄で確定する。…」。パレットの Ctrl+Enter(新しいタブ)は表にない。同じ表の「Ctrl+Enter(Cmd+Enter)」は「複数行の入力欄で確定する」。
3. 02 コマンドパレットの候補を実行したときの動作の表(「操作 | 動作」「アイテム | 詳細パネルを開く」「プロジェクト・ワークスペース | それぞれの概要を開く」)には、新しいタブの記述がない。詳細はパネルで、アドレスがない(R10-8)ので、「新しいタブで開く」の対象がパネルのアイテムにない。
4. 02 の「アイテムのメニュー」の「ID をコピー」「詳細を開く」(「詳細を開く」と「ID をコピー」は閲覧のみの Store でも使える)。リンクのコピー・新しいタブで開くはメニューにない。

### 決めなければならない点
規則で決まる:
- 新しいタブでも、`hh ui` のトークンのない URL では何も使えず、08 の画面になる。よりどころ: 08「hedgehug の画面は、端末で `hh ui` を実行すると開く URL からだけ使える。」
- 画面の状態(最後に開いていた画面・絞り込みなど)は、マシンごとに持つ。よりどころ: 01 の表の「画面の状態」。新しいタブで開いた画面の状態は、同じマシンの状態と共有される(ただし 04 は「ワークスペースの画面とプロジェクトの画面は、ワークスペースごと、プロジェクトごと、タブごとに別の状態を持つ」と書く。ここでの「タブ」は画面内のタブ(ツリー・カンバンなど)で、ブラウザのタブではない)。
- 閲覧のみの Store のアイテムを新しいタブで開くのは、見るだけなので使える。よりどころ: 01 閲覧のみの Store「次は無効にしない。画面の移動とタブの切り替え。中身を見るために開くもの」。

規則で決まらない:
1. **新しいタブがトークンを引き継ぐ仕組みを仕様に書くか。** 引き継がないと、新しいタブはいつも 08 のトークンのない画面になる。案 A: 引き継ぐ(現行。「新しいタブで開く」の操作を仕様に足す。引き継ぎの方法は技術なので仕様には書かず、「新しいタブも同じように使える」とだけ書く)。案 B: 引き継がず、この機能をやめる(トークンのない画面になる操作は仕様にしない)。
2. **対象の画面と、どの操作が新しいタブで開けるか。** 現行は、画面内のリンク(関連の相手、子の行、親、パンくず、通知のリンクなど `onLinkClick` を使うもの)とパレットの候補。案 A: 現行の範囲どおり。案 B: 画面の URL を持つ画面(ワークスペース・プロジェクト・検索・設定のページ・受信箱・アクティビティ)のリンクだけにして、アイテムの詳細は含めない(詳細パネルは URL を持たない)。
3. **中クリックと右クリックの「新しいタブで開く」。** 現行はトークンを引き継がず、08 の画面になる。案 A: 左クリック + 修飾キーと同じにそろえる(中クリックも引き継ぐ。ブラウザの動作による)。案 B: 何もせず(現行)。利用者には壊れて見える。
4. **キーの案内。** パレットの下端の「↑↓ で選択 ・ Enter で開く ・ Esc で閉じる」(02)に「Ctrl+Enter で新しいタブ」を足すか。

## R10-8 URL での画面の共有とブラウザの戻る・進む(A #8)

### 現行の振る舞い
`web/app/router.ts:88-160,195-215`。History API(`pushState`、`replaceState`、`popstate`)で画面を切り替える。
- アドレスの形:

| 画面 | アドレス |
|---|---|
| マイタスク(ホーム) | `/`・`/my`(ワークスペースがあるとき。なければ「ワークスペースなし」の案内) |
| ワークスペース | `/workspaces/<Store 名>/<ULID>`(概要)、`…/<ULID>/<tab>`(tree・kanban・table・backlog・sprints・releases・gantt・reports・settings) |
| プロジェクト | `/projects/<ULID>`(ツリー)、`/projects/<ULID>/<tab>`(overview・tree・kanban・table・gantt・settings) |
| アイテムの詳細 | `/tasks/<ULID>`(全画面のページ。ID でも引ける: `/tasks/HH-5`) |
| 保存したビュー | `/views/<Store 名>/<ビューの名前>` |
| 検索 | `/query/<layout>?q=<クエリ>`(絞り込みの入力は `replace` で書き換え、履歴を増やさない。`QueryPage.svelte:43-60`) |
| 受信箱・アクティビティ | `/inbox?tab=…`、`/activity?workspace=<ULID,…>&sync=…` |
| 設定 | `/settings/general`、`/accounts`、`/stores`、`/workspaces/<Store>`、`/automations/<Store>`、`/schema/<Store>?tab=…` |

- 知らない path は `/` になる。クエリ文字列とハッシュは、上の `?q=` などを除いて捨てる(`router.go`)。
- 戻る・進むは `popstate` で画面を切り替える。トークンは URL の `#token=` から sessionStorage に移して、アドレス欄から消す(`web/core/token.ts`)ので、アドレスをコピーしても、別のタブ・別のブラウザではトークンがなく、08 のトークンのない画面になる。同じタブの再読み込み・戻る・進むは、トークンが残るので続けて使える。
- 画面の中の状態(ツリーの折りたたみ、カンバンの設定、テーブルの列など)は、このアドレスに含まれない。
- 「ID が Store をまたいで重なる」: アドレスは ULID(と、Store 名つきの形)で作るので、重ならない。ただし ID(`/tasks/HH-5`)で開くと、複数の Store に同じ ID があれば「task.ambiguous」になる(`internal/app/usecase/mount_ops.go:17-21`)。同じ ULID が 2 つの Store にある場合(同じ Store の fork を 2 つ追加したときなど)も同じ曖昧のエラーになる(`ResolveIn` は Store ごとに引いて、複数の Store に当たれば曖昧)。
- 存在しないもの: `/tasks/<ULID>` が見つからなければ読み込みエラーの表示(`TaskDetail.svelte` の `loadError`)。

### 新仕様との衝突
1. 01 画面の移り方と、共通の表示: 「アプリを開き直すと、最後に開いていた画面を開く。…詳細パネルは閉じた状態で開き、開いていたアイテムは覚えない。例: HH-12 の詳細パネルを開いたまま再読み込みすると、同じ画面が詳細パネルなしで開く。」現行は `/tasks/<ULID>` で再読み込みすると、同じアイテムの全画面ページが開く。アイテムの詳細がアドレスを持つ形(ページ)と、パネル(アドレスを持たない)の食い違い。
2. 01 同じ節: 「アプリを開き直すと、最後に開いていた画面を開く。その画面がもうないとき(…)と、初めて開いたときは、マイタスクを開く。」現行の「最後の画面」は、ブラウザのアドレス(開き直したときのアドレスは `hh ui` が開く URL であり、パスがない)で決まり、記録していない。`hh ui` の URL のパス部分を変えて開くか、保存しておくかが決まらない。01 の表では「画面の状態(最後に開いていた画面、…)」はマシンごと。
3. 02 の旧 ID の節: 「旧い画面のアドレスは、新しいアイテムを開く。」「見つからないとき: 画面は開かず、…トーストで出す。」と 03 のワークスペースの移動: 「旧い画面のアドレスを開くと「このワークスペースは {日時} に {Store 名} へ移動しました」と表示して、移動先へのリンクを出す。…旧い画面のアドレスは、記録の内部 ID で、表示中のすべての Store から探し、いまある場所を開く」。仕様は「旧い画面のアドレス」があることを前提にするが、体系は定めない(モックでは「画面のアドレスがないので…」(audit/mock-v17-decisions.md の 03-05 24)とある)。現行のアドレス(`/workspaces/<Store>/<ULID>`)は、移動後に移動元の Store では見つからない。
4. 01 の範囲: 「データの保存形式、同期の実装方法、技術構成、CLI は扱わない。それらは次の段階で決める。画面を開く `hh ui` コマンドの引数と動作は、CLI の仕様で定める。」アドレスの体系は技術構成に近い。
5. 08 トークンのない URL(上記 R10-7)。URL の「共有」は、トークンのない URL を別の人・別のマシンへ渡すことになり、相手には 08 の画面が出る。「共有」ができるのは、同じタブの中の戻る・進む、同じ `hh ui` から開いた別タブ(R10-7)だけ。
6. 04 検索「絞り込みとレイアウトの設定は、このマシンに残す(01 の画面の状態)。」と 04 画面の状態「ワークスペースの画面とプロジェクトの画面は、ワークスペースごと、プロジェクトごと、タブごとに別の状態を持つ。」現行の検索の絞り込みはアドレスの `?q=` が持つ(再読み込みで残る)。仕様は「このマシンに残す」。アドレスにクエリを持たせると、画面の状態の持ち主が 2 つ(アドレスとマシン)になる。
7. 04 保存したビューの節: 「このマシンに保存したビュー」「Store を変えない」。現行のアドレス `/views/<Store 名>/<ビュー名>` は Store 名を含む(ビューを Store に保存するため)。仕様はビューを Store に属させない(04 モックからの変更点「保存したビュー | Store に保存して共有する | このマシンに置く自分だけのもの」)ので、アドレスの形が成り立たない。

### 決めなければならない点
規則で決まる:
- 画面を開いたとき、見つからない画面(削除・非表示)ならマイタスクを開く。よりどころ: 01「その画面がもうないとき(削除された、Store を非表示にしたなど)と、初めて開いたときは、マイタスクを開く。開いている画面が操作や同期でなくなったときも、マイタスクに移る。」
- アドレスは `hh ui` が開いた URL からだけ使える。よりどころ: 08(上記)。URL の共有は、別の人には使えない。

規則で決まらない:
1. **アドレスで共有できる範囲。** 案 A: 同じタブの戻る・進む、同じ `hh ui` のタブ間だけを仕様にし、「人へ渡す」ことは仕様にしない(08 と整合)。案 B: アドレスにトークンを含めて共有できるようにする(トークンの漏れる方向で、08 の「トークンのない URL」の意味が変わる)。案 C: ブラウザの戻る・進むだけにして、アドレスの体系を仕様にしない。
2. **アイテムの詳細のアドレス。** 仕様は詳細パネル(アドレスなし)で、再読み込みでは覚えない(01)。案 A: アドレスを持たない(`/tasks/<ULID>` をやめ、旧 ID のリンクの扱いは 02・03 の文のとおり別の導線にする)。案 B: パネルにもアドレスを持たせ(`?item=<ULID>` など)、戻る・進むで開閉するが、01 の「覚えない」を変える。案 C: 現行どおり `/tasks/<ULID>` のページを残し、パネルは別の見せ方にする(01 のパネルの規則とずれる)。
3. **「最後に開いていた画面」の記録。** 現行は記録がなく、ブラウザのアドレスで決まる。案 A: このマシンの画面の状態として、画面のパスを記録し、`hh ui` の URL(パスなし)で開いたときに復元する。案 B: アドレスを正とし、`hh ui` が最後のパスを付けて開く(CLI の仕様の話になる)。
4. **検索の絞り込みの持ち主。** 案 A: アドレスの `?q=` が正(再読み込み・戻る・進む・タブ複製で残る)。仕様の「このマシンに残す」はアドレスがないときの値として併用する。案 B: マシンの画面の状態だけ(アドレスは `/query/<layout>`、クエリは持たない)。
5. **保存したビューのアドレス。** 案 A: Store 名を持たないアドレス(`/views/<ビューの名前>`)。ビューの名前はこのマシンで重複できない(04)ので成り立つ。名前を変えたら旧アドレスは使えなくなる。案 B: ビューに内部の ID を振って `/views/<ID>`(名前の変更でアドレスが変わらない)。
6. **ID が Store をまたいで重なるとき。** 現行のアドレスは ULID なので重ならない。`/tasks/HH-5` のような ID のアドレスを許すか。案 A: ULID のみ許す(ID のアドレスは曖昧のエラーを出さない)。案 B: ID も許し、複数の Store に当たれば 04 の「同じ ID のすべてに一致」に合わせて選択画面を出す(現行は「task.ambiguous」のエラー)。
