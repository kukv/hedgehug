## 先に読む: 仕様を読み直して分かったこと

1. **f-06 の R5-R3 は読み違いである。** f-06 は「画面の状態(絞り込み・レイアウト・折りたたみ)はタブごと」を、ブラウザの別タブどうしは影響しない根拠にしていた。04-search-layouts.md「画面ごとの状態」の文は「ワークスペースの画面とプロジェクトの画面は、ワークスペースごと、プロジェクトごと、タブごとに別の状態を持つ。たとえば、あるワークスペースのカンバンで絞り込んでも、同じワークスペースのテーブルや別のワークスペースのカンバンには影響しない。」である。ここでの「タブ」は、画面の中のタブ(カンバン・テーブルなど)であって、ブラウザのタブではない。状態は「このマシンに残す」(04「モックからの変更点」の「画面の状態の保存」)。したがって、ブラウザの別タブどうしで画面の状態が及び合うかは、仕様に規則がない。R5 の 3 で決める。
2. **親の循環は、ふつうの操作では作れない。** 01 の親子の表は、Epic はプロジェクトの直下、Story・Task・Bug は Epic の下、Step は Story・Task・Bug の下とし、Step の下には何も置けない。この表を守る限り、輪はできない。できるのは、2 人が「種類を変更」と「移動」を入れ違えたときだけである(R9 の 1 に、操作の手順を書いた)。起きる頻度は極めて低い。R4 と同じ「万が一」の備えとして扱う。
3. **ワークスペースが消える場面は、完全な削除と別の Store への移動の 2 つだけで、どちらにも「復活させない」規則がある。** 接頭辞は、2 人の有効な値のどちらかが後勝ちで残るだけで、無効な値は hedgehug の操作ではできない。この 2 つは、規則に合う形では成り立たない。R9 の 6 に出す。
4. **「親が別の Store へ移った」場合の子は、同期の修復では移動先へ送れない。** 修復はどのマシンでも同じ結果にならなければならず(06「修復の決まり」)、移動先の Store を持たないマシンがあるためである。R9 の 6 に出す。
5. **スプリント・リリースの取り外しは、論理削除のもとでは、削除済みを含めると復元で戻らなくなる。** 関連(08「宙づりの関連」)は「削除済みは宙づりに含めない。復元すれば関連も戻る」と決めている。同じ扱いにするかを R9 の 5 で聞く。

# R4 強制 push の検出と修復

## 1. 何ができるようになるか

remote の履歴が git で書き換えられたとき、同期は合わせずに止まり、原因が画面に出る。利用者は、remote を元に戻すか、このマシンの履歴を remote の新しい履歴にそろえるかを選べる。

**例 1: 履歴が書き換えられた(花子さんの操作)**
1. 太郎さんが、誤って入れたトークンを消すため、git で GitHub の remote(github.com/org/tasks)の履歴を書き換えて push -f する。
2. 花子さんのマシンの Store「team」には、まだ送っていない保存が 3 件ある。10:05 の自動の同期が、受け取った履歴を見て止まる。花子さんの画面は何も動かない。
3. サイドバーの同期カードが「1 件の Store で同期エラー」になる。「Store ごとの同期状態」には「team  同期エラー: remote の履歴が書き換えられています」と出る。
4. 設定の「Store」の枠の同期の状況に、「同期エラー: remote の履歴が書き換えられています」が出て、その下に「remote を元に戻すか、このマシンの履歴を remote の新しい履歴にそろえてください。」と、ボタン「remote の履歴にそろえる…」が出る。
5. 「remote の履歴にそろえる…」を押すと、確認ダイアログ「remote の履歴にそろえる」が開く。本文は次のとおり。
   - 「team の remote の履歴が書き換えられています。このマシンの履歴を、remote の新しい履歴に置き換えます。」
   - 「まだ送っていない保存 3 件は、新しい履歴の上に 1 回の保存としてのせ直します。」
   - 「remote の新しい履歴にない 0 件のアイテムが、このマシンからも消えます。」(0 件のときは、この行を出さない)
   - 「remote が誤って書き換えられたときは、先に remote を元に戻してください。戻れば、そろえずに同期が再開します。」
   - 「元に戻せません。」
6. 「そろえる」を押すと、トースト「remote の履歴にそろえました」が出て、続けて同期が行われ、のせ直した 1 件が remote へ送られる。アクティビティに「remote の履歴にそろえ、未送信の保存 3 件をのせ直し」が、実行者あなたで 1 行残る。

**例 2: 戻せない保存がある(花子さんの操作)**
1. 例 1 の書き換えで、HH-30 が remote の履歴から消えた。花子さんは、書き換えの前に、HH-30 へコメント「リリース前に確認」を書いて、まだ送っていなかった。
2. 確認ダイアログには、「remote の新しい履歴にない 1 件のアイテムが、このマシンからも消えます。そのアイテムへの未送信の変更は、のせ直せません。内容は受信箱の「同期の修復」に残します。」が出る。
3. 「そろえる」を押すと、トースト「remote の履歴にそろえました。戻せなかった変更が 1 件あります。受信箱の「同期の修復」を見てください」が出る。
4. 受信箱の「同期の修復」に、「HH-30 は remote の新しい履歴にないため、あなたの変更は反映されませんでした: コメント: リリース前に確認」が出る。コメントの本文は、全文を出す。

**例 3: remote を別の Store に付け替えた(強制 push と取り違えない)**
1. 太郎さんが、設定の「Store」で「team」の remote を、別のチームのリポジトリ(github.com/org2/tasks)に付け替える。「remote を設定しました」と出る(08「remote の変更」)。
2. 次の同期は、前に受け取った履歴の記録を持たないので、書き換えの検査をせず、共通の履歴の検査だけを行う。共通の履歴がないので、「team の同期に失敗しました: remote の履歴がこの Store と関係がありません」で止まる(06「同期のエラー」)。「remote の履歴にそろえる…」は出ない。直すには、remote を元に戻す。

**例 4: 同じアドレスのリポジトリが、別の Store に作り直された**
1. GitHub 上で org/tasks が削除され、同じ名前で、別の hedgehug の Store が作られた。remote のアドレスは変わっていない。
2. 次の同期は、書き換えとして止まる。ただし、新しい履歴に、前に受け取った履歴のワークスペースが 1 つも残っていないので、「remote の履歴にそろえる…」は押せない。説明は「remote は、この Store とは別の Store になっています。remote を元に戻すか、Store をこのマシンから削除して clone し直してください。」になる。

## 2. 今の仕様への合わせ方

### 現行との違いと理由

| 論点 | 現行(f-06 が確かめたもの) | 案 | 理由 |
|---|---|---|---|
| 検出の条件 | 取得した origin の先頭が、前に追っていた先頭の子孫でないとき止める。共通の履歴の有無は見ない(`forcepush.go:57-80`) | 同じ remote から前に受け取った履歴があり、今回受け取った履歴がその続きでないとき止める。remote を付け替えたあとの最初の同期は、受け取った履歴の記録を持たないので、書き換えの検査をせず、06 の共通の履歴の検査だけを行う | 06「同期のエラー」の「共通の履歴を持たないときは、合わせずに断る」と、書き換えを別の事象にするため |
| remote の付け替え | 付け替えても追跡の記録は残るので、無関係なリポジトリへ付け替えると、書き換えとして止まるはずである(コードの読み取りによる推論。実行して確かめていない) | 付け替えたら、前に受け取った履歴の記録を捨てる | 無関係な履歴の上へ、未送信の保存をのせ直さないため(08「モックからの変更点」の「remote の履歴が共通でない」の理由) |
| 止まったときの表示 | 英語の原文がカードに出る可能性がある。日本語の文はあるが、カードで使われるか未確認 | 06 の同期のエラーの表に行を足す。短い理由は「remote の履歴が書き換えられています」 | 同じ Store の状態を画面ごとに別の言い方にしないため(06「モックからの変更点」の「同期の失敗の表示」) |
| 直す入口 | 設定の「診断と修復」を開くと自動で診断が走り、「想定外の force push」が出る | 設定の「Store」の同期の状況に、エラーの説明とボタンを出す。診断には載せない | 診断は「自動では動かない」(08「診断と修復」)。同期の状態は、データの検査ではない |
| 閲覧のみの Store | GUI の修復は無効。CLI は作り直す(コードの読み取りによる。未確認) | ボタンを使える | 閲覧のみの Store は、このマシンのコピーを remote にそろえるだけで、保存を作らない。R4-9 で理由を書く |
| のせ直せなかった保存 | 古い Store を丸ごと `.kept-{時刻}` にコピーして残す。消す操作はない | のせ直せなかった変更の内容を、受信箱の通知に全文で残す。古い Store のコピーは、Q-R4-1 の答えで決まる | 履歴を消す目的(秘密の削除)を、コピーが損なうため。05 の同じ種類の通知(06「完全な削除と重なったとき」)に合わせる |
| 手元の履歴 | 古い履歴を、このマシンから消す | 同じ | そろえるとは、置き換えるという意味のため |
| 記録 | 受信箱に「履歴の書き換えを取り込んだ」を 1 件、戻せなかったタスクごとに 1 件 | 受信箱は、戻せなかったアイテムごとに 1 件だけ。アクティビティに 1 行 | 「書き換えを取り込んだ」は、利用者が自分で押した操作の結果で、知らせる必要がないため |

| 08 の枠組み | この案での扱い |
|---|---|

| 「修復は、あなたが行った変更として記録する。アクティビティに「診断で修復: …」と残り」(08「結果の表示と修復」) | 保存を作るのは、未送信の保存があるときののせ直しだけである。実行者はあなた。文は「remote の履歴にそろえ、未送信の保存 {N} 件をのせ直し」。「診断で修復」の文言は使わない |
| 「取り除くのは Store の現在の中身だけで、git の履歴は書き換えない」(08「完全に削除」) | この文は、完全に削除の操作の話である。hedgehug は remote の履歴を書き換えない(強制 push をしない)。置き換えるのは、このマシンのコピーだけである |

## 3. 端の場合と、規則で決めた点

### 設計の決定

- R4-1 検出の条件。同じ remote から前に受け取った履歴があり、今回受け取った履歴がその続きでないときだけ、書き換えとして止める。巻き戻し(履歴が過去へ戻された)も止める。よりどころ: 06-sync-notifications.md「同期のエラー」: 「同期は、受信、合わせる、送信の順に行う。」。止める理由は、書き換えが秘密の削除などの意図である場合に、合わせて送り直すと、削除した内容を remote へ戻してしまうためである。
- R4-2 remote が空のリポジトリのときは、書き換えとして止めず、最初の送信として認める。よりどころ: 06-sync-notifications.md「同期のエラー」: 「remote が空のリポジトリのときは、最初の送信として認める。」
- R4-3 remote を付け替えたとき(08 の「remote の同じ・違うは、ホスト名、owner、リポジトリ名を取り出して比べる」で、違うものになったとき)は、前に受け取った履歴の記録を捨てる。同じ remote の別の書き方(SSH と HTTPS、大文字と小文字、末尾の「.git」)への書き換えでは捨てない。remote を空にしたときも捨てる。よりどころ: 08-stores-maintenance.md「追加」: 「SSH の形式(`git@github.com:org/tasks.git`)と HTTPS の形式(`https://github.com/org/tasks`)は、同じ remote として扱う。remote を変えるとき(後述)にも同じ比べ方を使う。」
- R4-4 付け替えのあとの最初の同期は、06 の共通の履歴の検査だけを行う。共通の履歴があれば(同じ Store の fork やコピーを含む)認め、なければ「remote の履歴がこの Store と関係がありません」で止める。よりどころ: 06「同期のエラー」: 「同じ Store の fork やコピーなど、共通の履歴があるものも認める。remote の変更そのものは、そのまま受け入れ(08)、最初の同期で断る。」
- R4-5 書き換えの検出と、共通の履歴の検査は、同じ同期で両方は起きない。前に受け取った履歴の記録があれば書き換え、なければ共通の履歴。よりどころ: R4-3(付け替えると記録を捨てる)。
- R4-6 止まったときの表示は、06 の表に 1 行足す。手動の同期のトースト「{Store 名} の同期に失敗しました: remote の履歴が書き換えられています」、短い理由「remote の履歴が書き換えられています」、Store の状態は同期エラー。短い理由は、「すべて同期」のトーストの行、「Store ごとの同期状態」、設定の「Store」で使う。よりどころ: 06「同期のエラー」: 「「短い理由」は、「すべて同期」のトーストの行、「Store ごとの同期状態」、設定の「Store」(08)で、同じ文を使う。」
- R4-7 止まっているあいだ、このマシンの Store は変えない。未送信の保存はそのまま残る(同期カードの「未送信」に数える)。remote が元に戻って、受け取った履歴が前の続きに戻れば、次の同期で、そろえずにそのまま再開する。よりどころ: 06「同期のエラー」: 「次に同期が成功するまで、この状態が続く。」
- R4-8 止まった Store も、自動の同期は、間隔が過ぎるたびに試す。よりどころ: 06「自動で同期する」の表の「書き込み後」の行: 「同期エラーの Store は、最後に試みてから選んだ間隔が過ぎるまで同期しない」と、「同期エラーの Store も、アプリを開いたとき、オンライン復帰、手動の同期では、常に試す。」
- R4-9 閲覧のみの Store でも「そろえる」を使える。閲覧のみの Store は書き込めず(未送信の保存がなく)、そろえるはこのマシンのコピーを置き換えるだけである。よりどころ: 08-stores-maintenance.md「一覧」: 「名前・色・非表示・remote・アカウント・このマシンから削除は、このマシンだけの設定なので、閲覧のみの Store でも操作できる。」と、06「自動で同期する」: 「閲覧のみの Store も対象で、受け取りだけを行う(01)。」。閲覧のみの Store でそろえなければ、同期が永久に止まる。確認ダイアログは、「まだ送っていない保存」の行を出さない。
- R4-10 「そろえる」は、新しい履歴の中に、前に受け取った履歴のワークスペース(画面に出ない内部の ID が同じもの)が 1 つも残っていないときは、押せなくする。理由は「別の Store になっています」。よりどころ: 08-stores-maintenance.md「モックからの変更点」の「remote の履歴が共通でない」: 「無関係な履歴を合わせると、同じ番号が大量に重なるため」。同じ番号が大量に重なる状態を、そろえる操作が作らないため。
- R4-11 のせ直しは、06「同時に編集したとき」の合わせ方で行う。基準は、前に受け取った履歴(書き換えの前)で、項目ごとの保存時刻は元のままにする。そのため、花子さんの古い値が、太郎さんの新しい値に勝つことはない。よりどころ: 06「同時に編集したとき」: 「時刻は、アイテム全体の最終更新の時刻ではなく、その項目を最後に保存した時刻で比べる。」。のせ直しで負けた値の「上書き」の通知は、06「同時に編集したとき」の規則に従い、負けたマシンが作る。
- R4-12 のせ直せないものは、remote の新しい履歴にないものである。新しい履歴にないものを、完全に削除されたものと同じに扱う。そのものへの未送信の変更は、のせ直さない。そのものの下に作った未送信のアイテムも、のせ直さない。よりどころ: 06-sync-notifications.md「完全な削除と重なったとき」: 「削除済みのものの完全な削除(手動、保持日数を過ぎた自動)と、別のマシンでの復元や変更が重なったときは、完全な削除を優先する。」と「祖先が完全に削除されたアイテムが同期で届いたときも、そのアイテムを完全に削除する。」。ただし「祖先」にプロジェクト・ワークスペースが含まれると読めるように、この文に書き足す(4 の 06-J)。
- R4-13 のせ直せなかった変更は、アイテムごとに 1 件、受信箱の「同期の修復」に出す。本文は「{ID} は remote の新しい履歴にないため、あなたの変更は反映されませんでした: {変更の内容}」。{変更の内容} は、プロパティなら「{プロパティ名}を {値} に変更」、コメントなら「コメント: {本文全体}」、説明なら「説明: {本文全体}」、下に作ったアイテムなら「「{タイトル}」を作成」を、1 行ずつ並べる。プロジェクト・ワークスペースのときは、{ID} のかわりに「プロジェクト「{名前}」」「ワークスペース「{名前}」」と書く。本文を全文にするのは、メンションの通知が本文全体を出す(06「メンション」)のと同じ理由で、内容を失わないためである。
- R4-14 remote の新しい履歴にないものの、受信箱の通知は消す。よりどころ: 06-sync-notifications.md「モックからの変更点」の「通知の寿命」: 「完全に削除したアイテム・プロジェクト・ワークスペースの通知を消す(同期で完全な削除を受け取ったマシンも消す)。」
- R4-15 書き換えられた履歴の中に、保存した人・保存した時刻・操作が、前の履歴と同じ保存があれば、同じ保存として扱い、通知を作り直さない。そろえたあとに受け取る、新しい保存からは、通常どおり通知を作る。よりどころ: 06-sync-notifications.md「通知」: 「通知は、受け取った保存(コミット)ごと・通知の種類ごとに 1 回だけ作る。このマシンが判定した保存を、通知と既読と同じく、このマシンだけに覚える。」。書き換えると保存の識別子(SHA)が変わるので、識別子だけで判定すると、割り当てやメンションの通知が全部もう一度出る。

> ### remote の履歴が書き換えられたとき
>
> 同期が「remote の履歴が書き換えられています」で止まったとき(06)、設定の「Store」の同期の状況に、説明とボタン「remote の履歴にそろえる…」を出す。診断(「診断と修復」)には載せない。閲覧のみの Store でも使える。同期が動いているあいだは無効にし、「同期しています」を添える。オフラインでも使える。
>
> 押すと、確認ダイアログ「remote の履歴にそろえる」を出す。本文は次の順に並べる。行は、当てはまるものだけを出す。
>
> | 行 | 出す条件 |
> |---|---|
> | 「{Store 名} の remote の履歴が書き換えられています。このマシンの履歴を、remote の新しい履歴に置き換えます。」 | いつも |
> | 「まだ送っていない保存 {N} 件は、新しい履歴の上に 1 回の保存としてのせ直します。」 | 書き込める Store で、N が 1 以上 |
> | 「まだ送っていない保存はありません。」 | 書き込める Store で、N が 0 |
> | 「remote の新しい履歴にない {M} 件のアイテム(削除済みを含む)が、このマシンからも消えます。」 | M が 1 以上。プロジェクト・ワークスペースがあれば「{P} 件のプロジェクト」「{W} 件のワークスペース」も並べる |
> | 「そのものへの未送信の変更は、のせ直せません。内容は受信箱の「同期の修復」に残します。」 | M が 1 以上で、のせ直せない変更がある |
> | 「remote が誤って書き換えられたときは、先に remote を元に戻してください。戻れば、そろえずに同期が再開します。」 | いつも |
> | 「元に戻せません。」 | いつも |
>
> ボタンは「そろえる」(警告色)と「キャンセル」。N は、同期カードの「未送信」と同じ数え方である。キャンセルすると何も変えない。
>
> 実行すると、次の順に行う。
> 1. 同期で受け取った、書き換えられた remote の履歴を、このマシンの履歴にする。
> 2. 未送信の保存を、06「同時に編集したとき」の合わせ方で、新しい履歴の上にのせ直す。基準は、書き換えの前に受け取っていた履歴で、項目ごとの保存時刻は元のままにする。remote の新しい履歴にないもの(アイテム・プロジェクト・ワークスペース)は、完全に削除されたものと同じに扱う(06「完全な削除と重なったとき」)。そのものへの未送信の変更と、そのものの下に作った未送信のアイテムは、のせ直さない。
> 3. 受信箱の、消えたものの通知を消す。のせ直せなかった変更を、アイテム(プロジェクト・ワークスペース)ごとに 1 件、受信箱の「同期の修復」に出す。本文は「{ID} は remote の新しい履歴にないため、あなたの変更は反映されませんでした: {変更の内容}」である。{変更の内容} は、プロパティなら「{プロパティ名}を {値} に変更」、コメントなら「コメント: {本文全体}」、説明なら「説明: {本文全体}」、下に作ったアイテムなら「「{タイトル}」を作成」を、1 行ずつ並べる。プロジェクト・ワークスペースのときは、{ID} のかわりに「プロジェクト「{名前}」」「ワークスペース「{名前}」」と書く。
> 4. このマシンの古い履歴は残さない(Q-R4-1 で A 以外が選ばれたときは、そちらの文に差し替える)。
> 5. 続けて、通常の同期を行う。のせ直した保存が remote へ送られる。
>
> 途中で止まったときは、元のままになる。のせ直した保存は、書き込める Store にだけできる。閲覧のみの Store では、保存を作らず、履歴だけを置き換える。
>
> トーストは「remote の履歴にそろえました」。のせ直せなかった変更があるときは、「remote の履歴にそろえました。戻せなかった変更が {K} 件あります。受信箱の「同期の修復」を見てください」(K はアイテム・プロジェクト・ワークスペースの数)。アクティビティには、のせ直した保存があるときだけ、実行者あなたで「remote の履歴にそろえ、未送信の保存 {N} 件をのせ直し」と残る。
>
> 次の場合は、ボタンを押せなくし、説明を出す。

> | 場合 | 出す説明 |

> | 書き換えられた remote の履歴に、前に受け取った履歴のワークスペースが 1 つも残っていない(別の Store になっている) | 「remote は、この Store とは別の Store になっています。remote を元に戻すか、Store をこのマシンから削除して clone し直してください。」 |

### Q-R4-1 「remote の履歴にそろえる」で、古い履歴をこのマシンに残すか

- どの画面か: 設定の「Store」の確認ダイアログ「remote の履歴にそろえる」。押したあとに、このマシンの古い履歴をどうするか。
- 具体例: 太郎さんが git で、誤って 3 日前の状態へ remote を巻き戻した。花子さんは、その巻き戻しの前の履歴をこのマシンに持っている。花子さんが「そろえる」を押すと、3 日分の HH-20〜HH-40 が、このマシンからも消える。
- 案 A: 残さない。そろえると、古い履歴は消える。花子さんが、押す前に remote を元に戻したいときは、古い履歴を使って git で戻せる。押したあとは、戻せない。確認ダイアログが「元に戻せません。」と先に言う。のせ直せなかった変更の内容は、受信箱に全文で残る。
- 案 B: のせ直せなかった変更があるときだけ、古い Store を丸ごと別の場所へ残す。場所をトーストに出し、設定の「Store」から削除できる。現行(古い Store を `.kept-{時刻}` に残し、消す操作はない)を、削除できる形にしたもの。秘密の削除が目的の書き換えのとき、古い履歴が、このマシンに残る。
- 案 C: そろえるときは、いつも、古い Store を丸ごと残す。設定の「Store」に「退避した Store」の一覧と「削除」ボタンを置く。巻き戻しが誤りだったときの最後の保険になる。画面と保存の置き場が増える。秘密の削除が目的の書き換えのとき、古い履歴が、このマシンに残る。
- 勧める案: A。理由は、(1) 押すまでは、このマシンの履歴を触らないので、誤りの書き換えから戻す道は、押す前に残っている。(2) 押したあとに残るのは、書き換えた人の意図に反する古い履歴で、消すための操作が別に要る。(3) のせ直せなかった利用者の変更は、受信箱に全文で残るので、失うのは、remote から消えたほかの人のものだけである。それらは、ほかのマシンと remote を元に戻す道で守る。

# R5 他のタブ・ウィンドウや同じマシンの別プログラムが Store に書いた変更の、開いている画面への反映

## 1. 何ができるようになるか

Store に保存された変更は、書き手にかかわらず、開いている画面に自動で出る。書き手は、別のタブ・ウィンドウ、このマシンで動く別のプログラム(CLI など)、同期のどれでもよい。CLI そのものの仕様は、これまでどおり扱わない(01「この仕様の範囲」)。

**例 1: 別のタブの変更(田中さんの操作)**
1. 田中さんが、同じ Store を 2 つのタブで開いている。タブ A は HH のツリー、タブ B は HH のテーブルである。
2. タブ B で HH-12 のステータスを Done に変える。保存から 1 秒ほどで、タブ A のツリーの HH-12 の行が Done になる。行は 10 秒、薄く強調される。
3. タブ A のスクロール位置、開いている詳細パネル、絞り込みは、そのままである。

**例 2: 書きかけがあるとき(田中さんの操作)**
1. タブ A で、HH-12 の詳細パネルを開き、コメント欄に「確認します」と書きかけている(まだ投稿していない)。
2. このマシンの別のプログラムが、HH-30 のタイトルを変える。タブ A の画面は変わらない。
3. 田中さんがコメントを投稿すると、書きかけがなくなる。そのとき、タブ A は、HH-30 のタイトルの変更をまとめて反映する。

**例 3: 別のタブで Store の設定を変えた(田中さんの操作)**
1. タブ B で、設定の「Store」の「team」を非表示にする。
2. タブ A のサイドバーから、team のワークスペースが消える。開いていたのが team のワークスペースなら、マイタスクへ移る(01「画面の移り方と、共通の表示」)。

**例 4: 受信箱の既読(田中さんの操作)**
1. タブ B で、受信箱の通知を既読にする。タブ A のサイドバーの「受信箱」の未読数が、1 秒ほどで減る。

## 3. 端の場合と、規則で決めた点

### 設計の決定

- R5-1 反映するのは、Store に保存された変更(コミットされたもの)だけである。保存されていない作業ツリーの手書きの変更は、反映しない。よりどころ: 01-overview.md「書き込みの単位」: 「保存は、利用者の操作のほか、同期の修復(実行者「同期」)、…でも作る。どれも Store を変えるときだけである。」。保存でないものは、Store の内容ではない。
- R5-2 反映するのは、次のものである。変わった内容によって、更新する画面と部品を決める(4 の 06-G の表)。アイテム、プロジェクト、ワークスペースとその設定、スプリント、リリース、メンバー、保持日数、同期の状態、このマシンの Store の一覧と設定(名前・色・非表示・remote・アカウント)、保存したビューの一覧、受信箱の既読と未読数。
- R5-3 反映しないのは、画面の状態(絞り込み、レイアウト、折りたたみ、スクロール、選択、詳細パネルの幅)と、入力途中の内容である。別のタブで変えた画面の状態は、開いているタブには及ばず、次に画面を開いたときに読む。よりどころ: 04-search-layouts.md「画面ごとの状態」: 「画面ごとの状態として、絞り込みと、レイアウトの設定を持つ。このマシンに残す(01 の画面の状態)。保存にもアクティビティにも残らない。」。画面の状態は、いま見ている人の画面のものなので、他のタブが書き換えると、見ている内容が変わってしまうためである。
- R5-4 保存したビューは、一覧(サイドバーの「ビュー」)だけを更新する。開いているタブの絞り込みとレイアウトは書き換えない。保存した内容と画面の状態の比べ(「変更あり」の表示)だけを、新しい定義で更新する。よりどころ: 04「保存したビュー」: 「画面の状態が保存された内容と比べられる」と、「自分だけのもので、Store には書かず」。
- R5-5 反映までの目安は、保存から 1 秒である。
- R5-6 反映を待つ条件は、06 が自動の同期を待たせる 5 つと同じである。ダイアログ・メニュー・コマンドパレットが開いているとき、ドラッグしているとき、説明やコメントを編集しているとき、入力欄にカーソルがあるとき、書きかけがあるとき。待つ範囲は、そのタブの画面の反映である。待っているあいだに届いた変更は、条件が解けたとき、1 回でまとめて反映する。よりどころ: 06-sync-notifications.md「自動で同期する」: 「自動の同期は、次のあいだは始めずに待つ。条件が解けたら、そのあと続けて同期する。待つのは、入力の途中で画面が書き換わって、入力が失われるのを防ぐためである。」
- R5-7 複数のタブがあるとき、自動の同期が待つ条件は、画面に見えているタブの条件だけで決める。見えていないタブの、開いたままのダイアログは、同期を待たせない。見えていないタブは、見えるようになったとき、溜まった変更を反映する。よりどころ: 06「自動で同期する」の理由(入力の途中で画面が書き換わるのを防ぐ)は、見えている画面だけに当てはまる。見えないタブのために、同期を無期限に止めないため。
- R5-8 手動の同期の結果は、待たずに反映する。ただし、編集中の入力欄の内容は書き換えない。よりどころ: 06-sync-notifications.md「手動で同期する」: 「手動の同期は、条件を待たずにすぐ始まる。」と「手動の同期でも、編集中の入力欄の内容は書き換えない(「同時に編集したとき」)。」
- R5-9 このタブの操作の結果は、待たずに、その場で画面に出す。反映を待っているのは、ほかの書き手の変更だけである。
- R5-10 反映は、表示を更新するだけである。保存・通知・自動化は作らない。別のタブや別のプログラムの操作は、このマシンでのあなたの操作なので、割り当て・メンション・ウォッチの通知は作らない。よりどころ: 06-sync-notifications.md「通知」: 「自分の変更では、割り当て、メンション、ウォッチの通知を作らない」。
- R5-11 編集中のアイテムが、他の書き手に変えられたときは、編集が終わるまで、画面を書き換えない(R5-6)。説明を保存するときは、06 の説明の合わせ方で、編集を始めたときの内容を基準に、保存した時点の内容と行ごとに合わせる。よりどころ: 06-sync-notifications.md「同時に編集したとき」: 「説明を保存するときは、編集を始めたときの内容を共通の祖先として、保存した時点の内容と行ごとに合わせる(上の表と同じ規則)。」。この文は同期の文だが、保存した時点の Store を相手にするので、他の書き手にも当たる。
- R5-12 画面が見ているアイテムが、他の書き手に削除されたら、反映のときに、詳細パネルを閉じる。確認は出さない。書きかけがあるあいだは、反映を待つので、書きかけを失わない。よりどころ: 02-items-projects.md「アイテムの詳細パネル」: 「開いているアイテムが削除されたら、パネルを閉じる。同期でそうなったときは、確認を出せないので、そのまま閉じる。」
- R5-13 開いている画面(プロジェクト・ワークスペース・Store)が、他の書き手の変更でなくなったとき(削除、完全な削除、別の Store への移動、Store の非表示)は、反映のときに、マイタスクへ移る。よりどころ: 01-overview.md「画面の移り方と、共通の表示」: 「開いている画面が操作や同期でなくなったときも、マイタスクに移る。」。他の書き手の変更を足す(4 の 01-B)。
- R5-14 別のタブとこのタブの操作が、同じ項目に重なったときは、あとに保存した方が残る。このタブの操作は、保存の時点の最新の Store に対する保存になる。削除と変更が重なったときは、06 と同じく、変更を残して削除を取り消す。取り消したときは、トースト「{ID} は別の画面で削除されていましたが、変更を保存したため、削除を取り消しました」を出す。よりどころ: 06-sync-notifications.md「同時に編集したとき」の表の最後の行: 「一方が削除し、他方が変更した(アイテムの削除、…) | 変更が残り、削除は取り消す。」。作業中の人が気づかないうちにアイテムが消えるのを防ぐ理由は、他のタブにも当たる。
- R5-15 ページ全体の再読み込みは、サーバーに接続できない画面からつながったときと、利用者がブラウザで読み直したときだけである。反映のために、ページ全体を再読み込みしない。よりどころ: 08-stores-maintenance.md「サーバーに接続できない画面とトークンのない画面」: 「つながったら重ねた画面を閉じ、書きかけ(…)がなければ元の画面を再読み込みする。あるときは、投稿・保存・キャンセルのあとで再読み込みする。」

### 端の場合

- R5-16 0 件・空。Store が 0 件でも、Store の一覧の変更(別のタブで Store を追加した)は反映する。最初の Store ができたら、初回起動の案内(08)が消えて、通常の画面になる。
- R5-17 閲覧のみの Store。別のタブの書き込みは起きない(閲覧のみは書き込めない)。同期で受け取った変更と、remote・アカウントの変更による「閲覧のみ」の印の見直し(08「remote の変更」)は、反映する。印が外れたら、無効だった入力欄が使えるようになる。
- R5-18 オフライン。同じマシンの中の書き込みなので、ネットワークに関係しない。`hh ui` が止まったときだけ、反映は止まる。止まったあとの画面は 08 の「サーバーに接続できない」に従う。つながったあとは、ページ全体を再読み込みするので、止まっているあいだの変更も出る(R5-15)。
- R5-19 複数 Store。Store ごとに独立して反映する。
- R5-20 同時の変更(同期)。待っているあいだに複数の変更が届いたときは、1 回の反映にまとめる(R5-6)。反映のあいだに、さらに変更が届いたときは、続けて反映する。
- R5-21 削除済み。論理削除されたアイテムは、一覧から消え、削除済みの一覧(08)に出る。開いている詳細パネルは閉じる(R5-12)。復元されたものは、一覧に戻る。
- R5-22 移動(別ワークスペース・別の Store)。別のワークスペースへ移されたアイテムを、このタブが開いているときは、アイテムの新しい ID の詳細パネルに移さず、パネルを閉じる(旧 ID のリンクからは辿れる。02「関連・転送記録・旧 ID」)。別の Store へ移されたときも同じ。
- R5-23 一括変更。一括変更の結果は、1 回の保存なので、1 回で反映する(04「一括変更」)。
- R5-24 自動化。自動化が書いた変更も、他の書き手の変更として反映する。反映は自動化を動かさない(R5-10)。
- R5-25 通知。受信箱の既読と未読数は、このマシンの全タブで同じにする。よりどころ: 06-sync-notifications.md「通知」: 「通知と既読の状態は、このマシンだけで持つ(01)。」。別のタブで既読にしたら、開いているタブの未読数も 1 秒ほどで変わる。
- R5-26 アクティビティ。別の書き手の保存は、保存した人の行として並ぶ(06「アクティビティ」の「このマシンでの自分の保存」)。反映のとき、一覧の先頭に足す。
- R5-27 保存したビュー。R5-4。
- R5-28 GitHub アカウントのない Store。Store のデータの反映は、同期と関係がないので、同じである。
- R5-29 非表示の Store。画面の反映は、Store のデータを出していないので、何も更新しない。再表示したときに、最新を出す。設定の「Store」の同期の状況は、非表示の Store も更新する。よりどころ: 08「非表示と再表示」: 「「非表示」を押すと、その Store はないものとして扱う。サイドバー、マイタスク、検索、受信箱、アクティビティには出ず」、「データは消えず、設定の Store の一覧と、「今すぐ同期」は使える。」
- R5-30 入力途中のコメントとダイアログの扱い。ダイアログが開いているあいだは、ダイアログの下の画面を書き換えない(R5-6)。ダイアログの中の選択肢(移動先の候補など)は、閉じるまで変えない。
- R5-31 日付の更新との関係。日付が変わったときの自動更新は、「入力中の欄と開いているダイアログは動かさない」(01「日付と時刻」)。反映も同じ考え方で、同じ結果になる。

## 4. 仕様の変更箇所

**06-G 新しい節「画面への反映」**(06-sync-notifications.md の「時計のずれの警告」の次、「同時に編集したとき」の前に置く。全文)

> ## 画面への反映
>
> Store に保存された変更は、書き手にかかわらず、開いている画面へ自動で反映する。書き手は、この画面、別のタブ・ウィンドウ、このマシンで動く別のプログラム(CLI など)、同期である。CLI そのものは、この仕様で扱わない(01)。保存されていない作業ツリーの変更は、反映しない。反映は、表示を更新するだけで、保存・通知・自動化は作らない。保存から 1 秒ほどで反映する。
>
> ### 反映するもの
>
> | 変わったもの | 更新する画面と部品 |
> |---|---|
> | アイテムとプロジェクトの作成・値・説明・コメント・作業時間・親・並び・削除・復元・移動 | 開いている一覧(マイタスク、バックログ、検索、保存したビューの結果)、ツリー、カンバン、テーブル、ガント、詳細パネルの値・説明・コメント・履歴、プロジェクトとワークスペースの概要のカードと件数、スプリントとリリースの画面、レポート、アクティビティ、サイドバーの件数 |
> | ワークスペースの設定、スプリント、リリース、メンバー、保持日数 | 設定の画面、サイドバーのワークスペースとプロジェクトの名前と並び、値の選択肢が出ている入力欄 |
> | このマシンの Store の一覧と設定(追加、削除、名前、色、非表示、remote、アカウント、閲覧のみの印) | サイドバーの Store のバッジと一覧、設定の「Store」、同期カード、無効だった入力欄 |
> | 同期の状態 | 同期カード、「Store ごとの同期状態」、設定の「Store」の同期の状況、幅 860px 以下のメニューのボタンの点 |
> | 受信箱の既読と未読 | サイドバーの「受信箱」の未読数、受信箱のタブの未読数と行 |
> | 保存したビューの一覧 | サイドバーの「ビュー」の一覧。開いているタブの絞り込みとレイアウトは書き換えず、保存した内容との比べ(「変更あり」の表示)だけ更新する |
>
> 画面の状態(絞り込み、レイアウト、折りたたみ、スクロール、選択、詳細パネルの開閉と幅)は、タブごとのものなので、他のタブの変更では書き換えない。反映のために、ページ全体の再読み込みはしない。
>
> ### 反映を待つとき
>
> 次のあいだは、この画面の反映を待つ。条件が解けたら、溜まった変更を 1 回でまとめて反映する。待つのは、入力の途中で画面が書き換わって、入力が失われるのを防ぐためである。
>
> - ダイアログ、メニュー、コマンドパレットが開いているとき
> - ドラッグしているとき
> - 説明やコメントを編集しているとき
> - 入力欄にカーソルがあるとき
> - 書きかけ(保存していない入力が空でないコメント・説明の入力欄)があるとき
>

# R9 同期での自動修復 5 種

## 1. 何ができるようになるか

5 種のうち、同期の自動修復として成り立つのは 3 種(親の循環、スプリント・リリースの取り外し、親のワークスペースへの追従)である。ワークスペースの復活は、成り立たない。接頭辞の復元は、仕様の操作では起きず、縮めた形でだけ成り立つ。この 2 つと、親が別の Store へ移った場合の子を、6 に出す。

| 種類 | 判定 | 同期での直し方 |
|---|---|---|
| 親の循環 | 成り立つ(起きる頻度は極めて低い) | 輪の中で番号が最大のアイテムを、08 の「親がない」と同じ修復で動かす |
| スプリント・リリースの取り外し | 成り立つ(範囲は Q-R9-1 の答えで決まる) | 完全に削除された・ファイルがない・別のワークスペースのものを指す参照を外す |
| 親のワークスペースへの追従 | 成り立つ(別の Store へ移った場合は 6 の X-R9-3) | 子を、親のワークスペースとプロジェクトへ移す。ワークスペースが違うときは、02 の移動と同じ結果にする |
| ワークスペースの復活 | 成り立たない(6 の X-R9-1) | 同期では何もしない |
| 接頭辞の復元 | 起きない(6 の X-R9-2) | 縮めた形で復元する案を 6 に出す |

**例 1: 親の循環(2 人の操作が入れ違う)**
HH に Epic HH-1、その下に Task HH-8 と Task HH-9、HH-8 の下に Step HH-10、HH-9 の下に Step HH-11 がある。
1. 太郎さんが、Step HH-11 を「種類を変更」で Task にする(10:00。親が HH-1 の下に移る)。続けて、Step HH-10 を、メニューの「移動…」で、いま Task になった HH-11 の下へ移す(10:03)。
2. 花子さんが、Step HH-10 を「種類を変更」で Task にする(10:01。親が HH-1 の下に移る)。続けて、Step HH-11 を、Task になった HH-10 の下へ移す(10:04)。
3. 同期すると、06 の項目ごとの後勝ちで、HH-10 の場所は太郎さんの 10:03(HH-11 の下)、HH-11 の場所は花子さんの 10:04(HH-10 の下)が残り、種類は両方 Task になる。HH-10 と HH-11 が、互いの親になる。
4. 同期の修復が、番号が大きい HH-11 を、プロジェクトの最初の Epic(HH-1)の下へ動かす。HH-11 の場所を最後に保存したのは花子さんなので、花子さんの受信箱に「親が循環したため、HH-11 を HH-1 の下へ移しました」が出る。アクティビティに、実行者「同期」で「HH-11 を HH-1 の下へ移動(親の循環)」が 1 行残る。
5. HH-10(Task)の親が HH-11(Task)のまま残る。この「種類に合わない親子」は、6 の X-R9-4 で扱う。

**例 2: 子が親と別のワークスペースにある(太郎さんと花子さんの操作)**
1. 太郎さんが、Epic HH-5 を、別のワークスペース WEB へ移す。HH-5 は WEB-12 になる。
2. 同期する前に、花子さんが、HH ワークスペースで、HH-5 の下に Story HH-31 を作る。HH-31 は「作業項目」で、親は HH-5(内部 ID は同じ)、ワークスペースは HH である。
3. 同期すると、HH-31 の親は WEB-12 で、HH-31 はまだ HH にある。同期の修復が、HH-31 を、WEB のプロジェクト(WEB-12 のプロジェクト)へ移し、WEB の次の番号 WEB-13 にする。値は WEB の定義に合わせて引き直し、スプリントとリリースは外す。転送記録が残り、HH-31 で探しても WEB-13 が見つかる。
4. 花子さんの受信箱に「WEB-12 が WEB へ移動したため、HH-31 を WEB-13 に移動しました。合う値がなく空になった項目: 優先度」が出る。アクティビティに、実行者「同期」で「HH-31 を WEB-13 に移動(親に合わせる)」が 1 行残る。

**例 3: スプリントの取り外し(花子さんと太郎さんの操作)**
1. 花子さんが、Sprint 25 を削除する。同期の前に、太郎さんが、HH-12 を Sprint 25 に入れていた。
2. 同期すると、Sprint 25 は削除済みで、HH-12 は Sprint 25 を指す。Q-R9-1 の答えが B なら、HH-12 は参照を残したまま、画面ではバックログに出る。花子さんが Sprint 25 を復元すると、HH-12 が Sprint 25 に入った状態に戻る。答えが A なら、同期の修復が HH-12 を外し、復元しても戻らない(太郎さんには「スプリント「Sprint 25」は削除されたため、HH-12 をバックログに戻しました」が届く)。
3. 保持日数を過ぎて Sprint 25 が完全に削除されたあとに、HH-12 がまだ Sprint 25 を指しているときは、どちらの答えでも、同期の修復が HH-12 をバックログに戻す。

## 3. 端の場合と、規則で決めた点

### 設計の決定

- R9-1 修復の順序。複数の修復が要るときは、(1) 完全な削除・別の Store への移動との重なり、(2) 親が削除されたとき、(3) 番号の重なり、(4) 親の循環、(5) 親のワークスペース・プロジェクトへの追従、(6) スプリント・リリース、(7) そのほか(名前・接頭辞・キー・メンバー・Issue)、の順に行う。どのマシンが同期しても、同じ結果になるため。よりどころ: 06-sync-notifications.md「番号の重なりの修復」: 「どのマシンが同期しても、同じ番号に振り直す。」
- R9-2 親の循環で動かすのは、輪の中で番号が最も大きいアイテムである。番号が同じとき(別のワークスペースのもの)は、内部 ID の辞書順があとのものを動かす。輪が複数あるときは、1 つずつ、なくなるまで繰り返す。よりどころ: 08-stores-maintenance.md「検出する項目」: 「親の循環 | 親をたどると自分に戻る | 循環の中で番号が最も大きいアイテムを、親がないときと同じ修復で動かす」。同点の決め方は、06「同時に編集したとき」の「SHA は…どのマシンで同期しても、同じ結果になる」の考え方で足す。
- R9-3 動かす先は、08 の「親がない」の修復と同じである(プロジェクトの最初の Epic の下。輪に入っていない Epic のうち、ツリーの並び順で先頭のもの。Step は Task にして移す。Epic がなければ「修復で作った Epic」を作る。プロジェクトが分からないときは直さず、診断に残す)。「修復で作った Epic」は、どのマシンが作っても同じものになる。よりどころ: 08「検出する項目」の「親がない」の修復内容。
- R9-4 削除済みのアイテムは、輪に数えない。輪に削除済みのアイテムが入っているときは、先に、親が削除されたときの規則で、削除されていない子が削除済みになる。よりどころ: 06「親が削除されたとき」: 「このときは、子も一緒に削除済みに入れる。」と 08「検出する項目」: 「調べるのは、削除済みでないアイテムと、ワークスペースの設定と、Store のメンバーである。」
- R9-5 循環の通知の宛先は、動かしたアイテムの親(場所)を最後に保存した人のマシンである。本文は「親が循環したため、{ID} を {行き先の ID} の下へ移しました」(Step を Task にしたときは「。Step は Task になりました」を続ける)。よりどころ: 06「モックからの変更点」: 「修復の通知先 | 受信した側が自分宛てに作る | 修復で変わったものを作った人のマシンが、同期で受け取ったときに自分宛てに作る。保存は書き込めるマシンだけが行う」
- R9-6 追従で動かすのは、子(と、子の下のすべて)である。子を、親のワークスペースとプロジェクトへ移す。ワークスペースが違うときは、02 の移動と同じ結果にする(移動先の次の番号、値の引き直し、スプリントとリリースを外す、転送記録)。同じワークスペースの別のプロジェクトのときは、プロジェクトだけを変え、ID と番号は変えない。よりどころ: 02-items-projects.md「別のワークスペースと別の Store への移動」: 「同じ Store を含め、ID が変わるすべての移動で、移した日時を含む転送記録を残し、旧 ID から辿れる。」(「モックからの変更点」の「別のワークスペースへの移動」)と、「値の引き直し」の節。08「検出する項目」の「親が別のワークスペースにある」: 「子をその親のワークスペースへ移す(新しい番号になり、旧 ID から辿れる)」

## 5. ユーザーに聞くこと

### Q-R9-1 削除済み(論理削除)のスプリント・リリースを指すアイテムを、同期で外すか

- どの画面か: スプリントの画面と、アイテムの詳細パネルの「スプリント」欄。設定の「削除済み」の「復元」。
- 具体例: 花子さんが Sprint 25 を削除する。同期の前に、太郎さんが HH-12 を Sprint 25 に入れていた。同期すると、Sprint 25 は削除済みで、HH-12 は Sprint 25 を指す。
- 案 A: 同期の修復が、HH-12 をバックログに戻す(参照を書き換える)。太郎さんの受信箱に「スプリント「Sprint 25」は削除されたため、HH-12 をバックログに戻しました」が出る。花子さんが Sprint 25 を復元しても、HH-12 は戻らない(外したのは、削除の操作ではなく、同期の修復のため。05 と 08 の「同じ削除操作で外れたアイテムも戻る」の外)。
- 案 B: 外さない。HH-12 は、参照を残したまま、画面ではバックログに出る(05「存在しないスプリントとリリースの参照」の読み替えを、削除済みにも広げる)。花子さんが Sprint 25 を復元すると、HH-12 は Sprint 25 に入った状態に戻る。保持日数を過ぎて Sprint 25 が完全に削除されたら、その保存で HH-12 の参照も外れる(08「完全に削除」に足す)。完全に削除されたあとに届いた参照は、同期の修復が外す。
- 勧める案: B。理由は、(1) 08「宙づりの関連」が、削除済みの相手との関連を壊れた状態に数えず、復元で戻すのと同じ扱いになる。(2) 太郎さんの「入れる」操作を、花子さんの復元で取り戻せる。(3) 参照を書き換えないので、バーンダウンの「外れた日」(05)に、同期の修復の日が混ざらない。(4) 「同期の修復で子を削除済みにした」ときの復元の扱いが、仕様に書かれていない(08「復元の単位」)ので、同じ曖昧さを、スプリントに持ち込まない。

## 6. 記録済みの決定とぶつかって、復活の意味が変わるもの

### X-R9-1 ワークスペースの復活

- どの画面か: 設定の「Store」の枠のワークスペースの一覧(復活したワークスペースが出る場所)と、サイドバーのワークスペース。
- 現行の動き: 同期のマージで、そのワークスペースに属するアイテムが残っているのに、ワークスペースのファイルが消えていて、共通の祖先にそのファイルがあるとき、祖先の内容で書き戻す。
- 具体例 1(完全な削除): 太郎さんが、削除済みのワークスペース WEB を、保持日数を過ぎたので完全に削除する。同期の前に、花子さんが WEB に WEB-45 を作っていた。仕様の規則では、06「完全な削除と重なったとき」の「完全な削除を優先する」で、WEB-45 は完全に削除され、花子さんに「WEB は完全に削除されたため、あなたの変更は反映されませんでした」が届く。復活は、空の WEB を書き戻し、WEB-45 だけが入った WEB が現れる。完全な削除が、取り消される。
- 具体例 2(別の Store への移動): 太郎さんが、WEB を team-b へ移す。同期の前に、花子さんが team-a の WEB に WEB-45 を作っていた。仕様の規則では、06「別の Store へ移動したものと重なったとき」の「移動を優先する。変更した人の変更は反映されない」で、WEB-45 は反映されない。復活は、team-a に空の WEB を書き戻し、team-a と team-b に同じ WEB が並ぶ。
- 具体例 3(論理削除): 太郎さんが WEB を削除する(削除済み)。花子さんが WEB-45 を作っていた。ファイルは残っているので、復活の対象にならない。06「親が削除されたとき」で、WEB-45 も削除済みに入る。
- 具体例 4(ファイルが手で消えた): git の操作で、WEB のファイルだけが消えた。hedgehug の操作では起きない状態で、仕様の範囲外(01「この仕様の範囲」)。
- 結論: hedgehug の操作でワークスペースのファイルが消えるのは、完全な削除と別の Store への移動の 2 つだけで、どちらも、仕様が「復活させない」と決めている。復活の意味が成り立つ場面がない。
- 案 A: 取り下げる。同期は何もしない。仕様は変えない。
- 案 B: 現行どおり、基準から書き戻す。06「完全な削除と重なったとき」「別の Store へ移動したものと重なったとき」に、「ワークスペースだけは、中身が残っていれば書き戻す」という例外を足す。
- 案 C: 基準から、削除済みの状態で書き戻す。復元するかどうかを、削除済みの一覧で選ぶ。完全な削除を優先する決定を弱める。
- 勧める案: A。理由は、完全な削除を優先する決定(06)と移動を優先する決定(06)の、両方と矛盾しないのは A だけであり、復元する意味のある場面がないため。

### X-R9-2 接頭辞の復元

- どの画面か: ワークスペースの設定の「一般」の接頭辞。アイテムの ID の表示。
- 現行の動き: マージの結果の接頭辞が、有効の定義(英大文字で始まる 2〜10 文字、必須)を満たさず、共通の祖先の接頭辞が有効なとき、祖先の値に戻す。
- 具体例 1(仕様の有効な値が、現行の定義では不正になる): 太郎さんが、WEB の接頭辞を空にして(03「接頭辞」の「空にすると #番号 になります」)送信する。花子さんは、その前の状態から、ワークスペースの名前だけを変えていた。花子さんが同期すると、マージの結果の接頭辞は、太郎さんの値(空)である。現行の定義では、空は不正なので、同期は、祖先の WEB に戻す。太郎さんの操作が、気づかないうちに取り消される。06「同期とは」の「同期が行われても、保存の内容は利用者が気づかないうちに書き換わらない」に反する。1 文字の接頭辞(W)も同じである。
- 具体例 2(仕様の定義で、操作では起きない): 2 人が別々に接頭辞を変えると、後勝ちで、2 つの有効な値のどちらかが残る。同じ接頭辞が 2 つのワークスペースにできると、06「1 つしかないものが 2 つになったとき」で WEB2 のようになる(有効)。接頭辞のないワークスペースが 2 つになると WS が付く(有効)。仕様の定義(空、または英大文字で始まる 10 文字以内の英大文字と数字)に合わない値は、hedgehug の操作ではできない。
- 具体例 3(外部の編集): git で、接頭辞の欄が「web-1」に手で書き換えられたものが同期で届く。03 の検査に合わない値が、Store に入る。
- 結論: 現行の有効の定義を当てはめてはいけない(具体例 1)。仕様の定義で見ると、不正な値が現れるのは、外部の編集だけ(具体例 3)である。
- 案 A: 取り下げる。同期は何もしない。
- 案 B: 同期は何もしないが、診断に行「接頭辞が規則に合わない」を足し、修復は、接頭辞を「WS」(すでにあれば WS2…)にする。
- 案 C: 縮めた形で、同期で復元する。マージの結果の接頭辞が仕様の定義に合わず、共通の祖先の接頭辞が仕様の定義に合うときだけ、祖先の値に戻す。祖先がないとき、祖先も合わないときは、何もしない。「同期の修復」として保存し(実行者「同期」)、接頭辞を最後に保存した人に、「ワークスペース「{名前}」の接頭辞「{不正な値}」は使えないため、「{祖先の値}」に戻しました」を通知する。アクティビティは「ワークスペース「{名前}」の接頭辞を「{不正な値}」から「{祖先の値}」に戻す」。旧い接頭辞の記録(03)は増やさない(不正な値は、使われた接頭辞ではないため)。
- 勧める案: C。理由は、(1) 仕様の有効の定義を使えば、利用者の操作を取り消さない。(2) 外部で壊れた接頭辞を、祖先の値という、利用者が最後に使っていた値へ戻せる。(3) 起きなければ、何もしないので、害がない。

### X-R9-3 親が別の Store へ移った場合の子

- どの画面か: 移動元の Store のツリーと、花子さんの受信箱。
- 具体例: 太郎さんが、Epic HH-5 を team-b へ移す(WEB-12 になる)。同期の前に、花子さんが team-a で、HH-5 の下に Story HH-31「リリースノート」を作っていた。
- 現行の動き: HH-31 を、HH-5 の祖先(プロジェクト)の下へ移して残す。
- 規則: 06「別の Store へ移動したものと重なったとき」: 「移動を優先する。変更した人の変更は反映されない。」。理由は、「二重のアイテムを作らないため」(06「モックからの変更点」の「別の Store への移動との重なり」)。
- 修復が、移動先の Store に子を送ることはできない。修復は、どのマシンでも同じ結果にならなければならない(06「修復の決まり」)が、移動先の Store を持たない・書き込めない・非表示のマシンがある。
- 案 A: 06 の規則どおり、HH-31 は反映されない。花子さんの受信箱に「HH-5 は 太郎 が team-b へ移動したため、あなたの変更は反映されませんでした。移動先は WEB-12 です(HH-31「リリースノート」)」が出る。花子さんは、WEB-12 の下に、HH-31 を作り直す。
- 案 B: HH-31 を、HH-5 の祖先(プロジェクト)の下に残す(現行)。花子さんの作ったものは残るが、06 の「変更した人の変更は反映されない」に、「子の追加は反映する」という例外ができる。HH-31 は、親を失って、team-a のプロジェクトの直下の Epic に並ぶ。
- 案 C: HH-31 を、移動先の Store へ送る。移動先を持たないマシンがあるので、同期の修復としては成り立たない。
- 勧める案: A。理由は、(1) 06 の記録済みの決定と矛盾しない。(2) HH-31 のタイトルが通知に残るので、作り直せる。(3) 案 B は、花子さんが、親が別の Store に移ったことに気づかないまま、HH-31 が別の場所に残る。
- ユーザーの決定「親が別の Store へ移った場合を含む」を、縮める案である。

### X-R9-4 輪を切ったあとに残る「種類に合わない親子」

- どの画面か: ツリーと、診断(設定の「診断と修復」)。
- 具体例: R9 の 1 の例 1 で、HH-11 を HH-1 の下へ動かしたあと、HH-10(Task)の親が HH-11(Task)のまま残る。01 の親子の表では、Task の下に置けるのは Step だけである。
- 規則: 08「検出する項目」の「種類に合わない親子」は診断が直す。06「修復の決まり」は、同期の各節以外は診断で直すとする。
- この問いは、依頼された 5 種の外にある。輪を切る同期の修復が、輪の他のアイテムを、決まりに合わない親子のまま残すため、挙げる。
- 案 A: 輪に入っていたアイテムの親が、種類の決まりに合わないときも、同期で同じ修復(「親がない」と同じ)で動かす。06-N の「親が循環したとき」に 1 文足す(「輪に入っていたアイテムのうち、親が種類の決まりに合わないものも、同じ修復で動かす」)。例 1 では、HH-10 も HH-1 の下へ動き、花子さんと太郎さんの両方に通知が出る。
- 案 B: 同期では動かさず、診断に残す(08 の「種類に合わない親子」)。HH-10 は、利用者が診断を実行するまで、Task の下の Task として残る。
- 勧める案: A。理由は、修復のあとに、ツリーが決まりに合う状態になり、診断を実行しない利用者でも、決まりに合わない親子を見ずに済むため。
- この案を採るときの文は、06-N の「動かす先のプロジェクトが分からないときは、直さない(診断に残す。08)。」の次に、「輪に入っていたアイテムのうち、親が種類の決まりに合わないもの(Task の下の Task など)も、同じ修復で動かす。」を足す。
