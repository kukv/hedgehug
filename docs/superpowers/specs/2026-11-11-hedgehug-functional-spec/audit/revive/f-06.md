# R4 強制 push(履歴が書き換えられた remote)の検出と、同期を止めて作り直す修復(A #68)

## 1. 現行の振る舞い

### 1-1 検出

- 検出は同期の受信の直後に 1 回だけ行う。`internal/app/remote/replicate/sync.go:205`(`beginFetch` で、取得の前の origin の先頭を `tracked` として控える)、`:226`(`checkOrigin(s, tracked, opt)`)。
- 条件: 取得した origin の先頭 `head` が `tracked` の子孫でないこと。`internal/app/remote/replicate/forcepush.go:57-80` の `checkOrigin` が `r.IsAncestor(tracked, head)` を呼ぶ(`forcepush.go:65`)。`tracked` が空(その Store がまだ origin から何も受け取っていない)または `head` が空(origin が空のリポジトリ)のときは「子孫である」と数える(`internal/lib/gitrepo/merge.go:64-70` の `IsAncestor`)。
- この条件は「共通の履歴があるか」ではない。履歴が共通でも、origin が過去へ巻き戻された(`git reset --hard` して push -f した)ときは `head` が `tracked` の祖先になり、子孫ではないので止まる。テスト `TestRunStopsOnARewriteThatDropsNothing`(`forcepush_test.go:107`)は「何も落とさない書き換え」でも止まることを確かめている。
- 止めるときの処理(`forcepush.go:74-80`): origin の追跡 ref(`refs/remotes/origin/main`)を取得前の値へ戻す。手元の Store は変えない。`.hedgehug/local/force-push.json`(`origin`=新しい先頭、`tracked`=追っていた先頭、`checked`=時刻)を書く。`ErrForcePush` を返す。
- 検出は origin だけである。ミラー(`i > 0` の remote)には `checkOrigin` を呼ばない(`sync.go:204-232`)。
- 次の同期で origin が再び子孫に戻っていれば、`checkOrigin` は `force-push.json` を消して通常どおり進む(`forcepush.go:66-71`)。

### 1-2 止まったときの画面の表示

- 同期は失敗として終わり、`sync.json` の `last_error` に `err.Error()` の英語の文が入る(`internal/app/usecase/session.go:818`)。文は `the history of origin differs from this store's; check origin, then run hedgehug doctor --fix to rebuild the store on it`(`forcepush.go:19`)。
- サイドバーの同期カードは、`last_error` をそのまま `errors[].message` に入れる(`web/app/sidebar/sync-summary.ts:50`)。状態は「エラー」(オフラインより弱く、保留より強い、`sync-summary.ts:56-58`)。画面に出る文は、コードの読み取りでは英語の原文である(未確認: 実際の表示は実行していない)。
- 「今すぐ同期」のトーストは `同期に失敗しました: {Store 名}: {error}`(`sync-summary.ts:69-74`)。`error` は `usecase.Describe(err)`(`internal/app/usecase/errors.go:172-180`)で、`err.Error()` の英語のままである。
- 日本語の文 `sync.force_push`(「remote の履歴が手元と食い違っています。確認してから、hh doctor --fix で origin の新しい履歴にそろえてください」、`web/core/messages.ts:265-266`)は、API が 409 の problem `sync.force_push` を返したときだけ使われる(`errors.go:112-113`)。同期カードとトーストの経路が、この日本語の文を使うかは確かめられなかった(`SyncReport.Error` を作る `internal/app/server/syncapi.go:54` は `Describe` を使っている)。
- 自動の同期は止まった Store を、設定の間隔ごとに試し続け、そのたびに失敗する。サーバーのログには `sync {Store 名}: ...` が出る(`internal/app/server/loop.go:250-252`)。

### 1-3 修復の入口と画面

- 入口は設定の「診断と修復」(`web/app/settings/DoctorSection.svelte`)。この部品は Store の設定を開くと、ボタンを押さなくても自動で診断を実行する(`DoctorSection.svelte:86-92` の `$effect` が `load(s)` を呼ぶ)。
- `force-push.json` が残っていると、検出の項目「想定外の force push」が出る(`web/core/doctor.ts:26`、`internal/app/usecase/maintenance/maintain.go:209-218` の `forcePushFinding`)。文は「前回の同期で、origin の履歴が手元と食い違っていました(想定外の force push)」、ヒントは「hh doctor --fix で、origin の履歴の上に Store を作り直し、未 push の変更を再適用します。再適用できない変更があれば、古い Store を残します」(`doctor.ts:255-256`、`:330-331`)。
- 検出が 1 件以上あると、ボタン「修復…」が出る。押すとダイアログ「doctor で修復する」(`DoctorSection.svelte:281-296`)。本文は「次の問題を、1 コミットで直します。」に、親の循環・削除済みの親の子・親と違うワークスペースにあるタスク・重複した ID を並べ、続けて「force push の後は、Store を origin の新しい履歴にそろえ、未 push の変更を再適用します。ほかの問題は直せないので、診断に残ります。」。ボタンは「修復する」(danger)と「キャンセル」。
- 閲覧のみの Store では「修復…」を無効にする(`off`、`DoctorSection.svelte:35`、`:187`)。サーバー側の `rebuildStore`(`internal/app/usecase/maintenance/rebuild.go`)には `CheckWritable` がなく、閲覧のみかどうかを見ない(`fixStore` の `maintain.go:239` には `CheckWritable` がある)。CLI の `hh doctor --fix` が閲覧のみの Store を作り直すかは、コードの読み取りでは作り直す(未確認)。
- 修復を実行した後、トースト「Store を origin の新しい履歴にそろえました」(ほかに修復がなければ。`DoctorSection.svelte:125-132`)。「修復の結果」の欄に、「origin の新しい履歴にそろえました」「未 push の {N} コミットを再適用しました」「戻せなかったタスク: {ID, ID…}」「古い Store は {パス} にあります」を出す(`DoctorSection.svelte:205-221`)。

### 1-4 修復(「origin の新しい履歴にそろえる」)で手元の未送信の保存がどうなるか

実装: `internal/app/remote/replicate/rebuild.go` の `RebuildStore`(`:116`)、`prepare`(`:156`)、`replay`(`:389`)、`findDropped`(`:444`)、`apply`(`:306`)。

1. 前提(`prepare`): 作業ツリーに未コミットの変更があれば `ErrDirtyRebuild`(「the store has uncommitted changes, which the rebuild would drop; commit or restore them, then run hedgehug doctor --fix」、`rebuild.go:37-47`)で断る。HEAD が main の上にないときも断る。
2. origin を取得し直す。origin が空なら「origin is empty」で断る。origin が再び子孫になっていたら、`force-push.json` を消すだけで終える。
3. 手元の未送信のコミット(古い HEAD から、追っていた origin の先頭までの間にないもの)を `replay` で集め、新しい origin の先頭の上に「1 つのコミット」(操作名 `replay`、説明「N unpushed commit」)として載せる。マージは通常の同期と同じ規則(`mergeTrees`、基準=古い履歴の共通の祖先)で行う。新しい履歴がすでに持っている内容は変更に数えない。
4. 新しい履歴にそのタスクのファイルがない場合(origin 側で消された。基準にはあり、新しい先頭にない)は、そのタスクへの未送信の変更を載せない(`findDropped`)。載せなかったタスクは「戻せなかったタスク」になる(`Rebuild.Purged`)。タスクのコメント・作業時間の変更も、そのタスクの分として載せない。手元だけで作ったタスク(基準にない)は戻せなかったものに数えず、そのまま載る。
5. 戻せなかったタスクが 1 件でもあれば、古い Store の丸ごとのコピーを `{Store のフォルダー}.kept-{UTC 時刻}`(例: `team-a.kept-20261112T031500.000000000`)に作る。Store のフォルダーの隣である(`rebuild.go:357-367` の `keepOldStore`)。コピーは作業ツリーと `.git` を含み、ロックと一時ファイルを除く。`rebuild.go:23-26` のコメント「Nothing removes it」のとおり、この古い Store を消す処理はコード中に見つからなかった(`keptPrefix` を使う箇所は `rebuild.go` だけ。「このマシンから削除」の処理も触れていない)。
6. 点の打ち方: `rebuild.json` を書いた後は、途中で止まっても続きから終える(`finish`)。HEAD と main を新しい履歴へ動かし(`MoveMain`)、追跡 ref を新しい origin の先頭にし、受信箱に項目を足し、履歴の索引のキャッシュを消し、`force-push.json` を消す。古い履歴のオブジェクトは掃除する(失敗しても警告で済ます)。
7. 受信箱に入る項目(`rewriteItems`、`rebuild.go:490-510`): 「履歴の書き換えを取り込んだ」(`rewrite_applied`)を 1 件、戻せなかったタスクごとに「未 push の変更を捨てた」(`purged_change`)を 1 件。GUI の通知の本文は、前者「履歴の書き換え(purge)を取り込みました」、後者「完全に削除されたタスクへの、未 push の変更を捨てました」、ラベルはどちらも「同期の修復」(`web/core/notifications.ts:275-281`)。
8. 修復は送信しない(コードのコメント「It does not push」、`rebuild.go` の `maintenance/rebuild.go:22`)。載せた 1 コミットは次の同期で送る。
9. ミラー: 古い履歴を持つミラーは `mirrors-held.json` に控え、そのミラーへの送信は、ミラーが新しい履歴に変わるまで保留する(`internal/app/remote/replicate/mirrors.go:56-71` の `holdMirrors`)。
10. その他の修復も同じ操作の中で行う(`doctor --fix` は作り直しの後に、同期と同じ修復を 1 コミットで行う、`maintain.go:55-110`)。

### 1-5 端の場合

- 0 件・空: origin が空のときは検出しない(最初の送信として通る)。作り直しは「origin is empty」で断る。
- 未コミットの変更: 作り直しを断る(上記 1)。
- 同時の変更: 同期ロック `sync.lock` と Store のロックを取る。作り直しの間、サーバーの監視(`Watcher`)はその Store を手放し、作り直した後の最初の見直しで、画面に「その Store のアイテムが変わった」(ULID の空の `tasks.changed`)を送って全部取り直させる(`internal/app/usecase/watch/watch.go:150-200`、`:276-300`)。
- 複数 Store: Store ごとに独立して検出・作り直す。1 つ失敗しても、ほかの Store は続ける(`maintain.go:75-90`)。失敗した Store は、その Store の項目に「origin の履歴が手元と食い違っていますが、Store を作り直せません: {理由}」(`force_push.rebuild_failed`)が出る。
- 閲覧のみ: 検出する(受信はするため)。GUI の修復は無効。コードの読み取りでは、閲覧のみの Store は未送信がないはずなので、作り直しても戻せなかったものは出ない(未確認)。
- remote の付け替え: `SetRemotes`(`internal/lib/gitrepo/remote.go:66-84`)は origin の URL を書き換えるだけで、追跡 ref を消さない。コードの読み取りでは、一度でも origin と同期した Store の remote を、履歴が無関係な別のリポジトリへ付け替えると、次の同期は `ErrUnrelated`(「the remote holds a history of its own」)ではなく `ErrForcePush` で止まる(`tracked` が古い origin の先頭で、新しい origin の先頭の子孫ではないため)。`ErrUnrelated` が出るのは、追跡 ref がまだない Store(一度も同期していない、または remote を足したばかりの、ローカルだけで作った Store)が、共通の履歴のない remote に同期したときだけである(`sync.go:459`、テスト `TestUnrelatedHistories`、`sync_test.go:382`)。この付け替えのときの動作は、コードを読んだ推論で、実行して確かめていない。
- 履歴の書き換えの原因: 現行の「完全に削除」(`hh purge`)は Store の現在の中身を消すだけで、履歴を書き換えない(`docs/guide/ja/maintenance.md:60`「hedgehug には、履歴から内容を消すコマンドがありません」)。強制 push が起きるのは、利用者が `git filter-repo` などで手で書き換えて `git push --force` したときだけである(同ガイドの「履歴から内容を消す」)。ガイドは「同期が自動で直さないのは、誤った force push があったときに、全員がそれに揃ってしまわないようにするためです」と書く。

### 1-6 古い Store の場所

`{Store のフォルダー}.kept-{UTC の年月日 T 時分秒.ナノ秒}`(Store のフォルダーと同じ親の下)。例: Store のフォルダーが `~/.local/share/hedgehug/stores/team-a` なら、`~/.local/share/hedgehug/stores/team-a.kept-20261112T031500.000000000`。画面にはこのパスが「古い Store は {パス} にあります」と出る。画面でも CLI でも、消す操作はない。複数回の作り直しでコピーは増える。次の作り直しの開始時に、作りかけの `.kept-new` だけは消す(`rebuild.go:26-29`、`prepare` の `osfs.RemoveAll(dir + keptNew)`)。

## 2. 新仕様との衝突

### R4-C1 検出する条件が違う(共通の履歴の有無 / 追っていた履歴の子孫か)

- 06-sync-notifications.md「同期のエラー」: 「remote の履歴が、この Store と共通の履歴を持たないときは、合わせずに断る。remote が空のリポジトリのときは、最初の送信として認める。同じ Store の fork やコピーなど、共通の履歴があるものも認める。」(06:94)
- 06-sync-notifications.md「同期のエラー」の表: 「remote の履歴が、この Store と共通の履歴を持たない」→「{Store 名} の同期に失敗しました: remote の履歴がこの Store と関係がありません」(06:87)
- 現行との差: 現行が止めるのは「前回追っていた origin の先頭の子孫でない」ときで、共通の履歴を持つ書き換え(巻き戻し)も止まる。逆に、`git filter-repo --invert-paths` のような全コミットが作り直される書き換えは、古い Store とは共通の履歴を持たなくなる。現行はこれを `force_push` で止めるが、仕様の文だけを当てはめると「関係がありません」の断りになり、診断も修復もない。巻き戻しの方は、共通の履歴があるので仕様では「認める」側に入り、手元にある巻き戻された分が次の同期で origin へ送り直される(未確認: 仕様にこの場合の文がない)。

### R4-C2 直し方が違う

- 06-sync-notifications.md「同期のエラー」: 「直すには、remote を元に戻すか、Store をこのマシンから削除して clone し直す。」(06:94)。08-stores-maintenance.md「remote の変更」にも同じ文(08:139)。
- 現行は「origin の新しい履歴にそろえる」(未送信を再適用)で、Store を削除せずに直す。仕様の直し方には、未送信の保存を持ち越す手段がない(「このマシンから削除」の確認は「未送信の変更が N 件あります。」と警告するだけ。08「このマシンから削除」)。

### R4-C4 「共通の履歴があるものは認める」と、現行の止め方

- 06-sync-notifications.md「同期のエラー」: 「同じ Store の fork やコピーなど、共通の履歴があるものも認める。」(06:94)

## 1. 現行の振る舞い

### 1-1 サーバー側

- サーバー(`hh ui`)は 300ms ごとに、すべての Store(remote の有無・非表示にかかわらず、`SyncTargets(c, true)`、`internal/app/usecase/watch/watch.go:231-260`)を見る(`pollInterval`、`internal/app/server/poll.go:14`)。
- 見るもの(`watch.go` の `pollLocked`):
  - Store の HEAD。前回と違えば、新しいコミットごとに `tasks.changed`(`store`、`ulids`、`removed`、`commit`、`op`、`author`、`automated`)を送る。HEAD の第 1 親をたどれて 50 件以内ならコミットごと、そうでなければ 1 件にまとめる(`watch.go:400-431` の `splitMax`、`headMoved`、`publishDiff`)。タスクのファイルと、コメント・作業時間のファイルの変更を `ulids` に、消えたもの・移動した記録になったものを `removed` に入れる。

  - 受信箱の変更(ファイルの印と HEAD の移動)。変われば、全 Store の未読数を数え直して `notifications.unread` を送る。
  - `config.yaml`(Store の一覧・アカウント・既定の Store)。変われば `stores.changed` を送る。
  - 最初に見た Store は記録するだけで、何も送らない。作り直された Store と、最初の見直しの後に現れた Store は、ULID の空の `tasks.changed` を送り、画面に全部取り直させる(`watch.go:200-225`)。

### 1-2 画面側

- `web/core/connection.ts`: 接続が切れたら 1・2・4・5 秒(以降 5 秒)の間隔で再接続を試みる(`:13`、`loop`)。`hello` で各 Store の HEAD が前回と違うか、初めての接続なら `resync` を出す(`onHello`)。
- `web/core/cache.ts:470-488` の `onTasksChanged`: 自分のタブが保存したコミット(`own`)でなければ、変わったアイテムに印(`CLI で更新 · 今`、`同期で更新 · 今`(操作名が `merge`・`repair`)、`自動化で更新 · 今`。`cache.ts:6`、`:16-18`)を 10 秒つけ、ツリーの行にその文字を出す(`web/app/tree/TreeRow.svelte:133-134`)。続けて、画面に出ている一覧・詳細を取り直す(`queueRefresh`)。消えたものは捨てる。`resync` と `schema.changed` では全部取り直す。

- 画面ごとの購読: 一覧・ツリー・カンバン・ガント・テーブルは `cache.ts`、受信箱・アクティビティ・レポート・スプリント・設定の整合の画面は、それぞれ `tasks.changed` と `resync` で取り直す(`web/app/*` の `c.conn.on(...)`)。Store の一覧・色・非表示は `stores.changed`。
- 切れたとき: `Disconnected.svelte`(`web/app/states/Disconnected.svelte`)が画面全体を覆う。文は「Hedgehug のサーバーに接続できません」「端末で hh ui を実行してください。表示中の内容は {HH:MM} 時点のもので、編集はできません。」「5 秒ごとに再接続しています」。ボタンはない。つながったら覆いを外し、切れている間に HEAD が動いていれば `resync`(データの取り直し)をする。ページは再読み込みしない。
- 自分の同期: サーバーの同期ループ(`loop.go`)は、ダイアログやメニューが開いていることを知らない(`presence` は「画面が見えているか」だけ。`internal/app/server/presence.go`)。つまり、現行は「入力の途中は自動の同期を待つ」を実装していない(06:57-63 に対して)。

### 1-3 端の場合

- 0 件・空: Store が 0 件でも見直しは動く。最初の Store ができたときは、全部取り直しの印を出す。
- 閲覧のみ・remote なし: すべての Store を見るので、このマシンだけの Store への別タブの書き込みも届く。
- オフライン: ネットワークと関係がない(ファイルを見るだけ)。サーバーに接続できない(`hh ui` が止まった)ときだけ止まる。
- 複数 Store: Store ごとの HEAD で別々に見る。
- 同時の変更: 取り直しの間に別の変更が来たら、1 回の取り直しにまとめ(同じターンの `queueRefresh`)、取り直し中の行には新しい行を優先する(`cache.ts` の `lastChange`)。
- 削除済み: 論理削除は `removed` ではなく `ulids` に入る(ファイルは残るため)。

- 他のタブ・CLI の書き込みは、すでにコミットされた後に届くので、待たせられない。待つ規則の理由「入力の途中で画面が書き換わって、入力が失われるのを防ぐ」を満たすには、届いた後に画面の側で「書き換えを遅らせる」規則が別に要る。現行は待たず、欄ごとの保護(フォーカスと保存待ち)だけで済ませている。

### R5-C3 「入力欄は書き換えない」が同期だけの文で、保護の範囲が現行と違う

### R5-C4 「再読み込み」という語の意味

- 08-stores-maintenance.md「サーバーに接続できない画面とトークンのない画面」: 「つながったら重ねた画面を閉じ、書きかけ(保存していない入力が空でないコメント・説明の入力欄)がなければ元の画面を再読み込みする。あるときは、投稿・保存・キャンセルのあとで再読み込みする。」(08:353)

# R9 同期での自動修復 5 種(A #73、#74、#76)

対象: 親の循環(`parent_cycle`)、存在しないスプリント・リリースの取り外し(`sprint_detached`・`release_detached`)、親のワークスペースへの追従(`workspace_mismatch`)と親が別の Store へ移った場合(`parent_moved`)、消えたワークスペースの復活(`workspace_revived`)、不正な接頭辞の復元(`id_prefix`)。

## 1. 現行の振る舞い

### 1-0 全体

- 修復は `merge.Repair`(`internal/app/domain/merge/repair.go:55`)が行う。呼ばれる場所は 2 つ。(a)同期のマージ(`internal/app/remote/replicate/sync.go:615`)。マージの結果のファイル一式に対して、基準(共通の祖先)つきで呼ぶ。(b)同期の最後と `hh doctor --fix` の `repairHead`(`sync.go:865-925`、`:893`)。HEAD のファイルに対して、基準なしで呼ぶ。`repairHead` は、索引が修復の対象の問題(重複 ID、ID なし、接頭辞の食い違い、ワークスペースの食い違い、親の循環・存在しない親・削除済みの親)を見つけたときだけ全ファイルを読む(`sync.go:937-966` の `needsRepair`)。
- 修復の順序(`repair.go:55-70`): ワークスペースの復活 → 接頭辞の復元 → 親の循環 → 削除済み・消えた・別の Store へ移った親の子 → 別の Store へ移ったものへの関連の除去 → 親のワークスペースへの追従 → ID の振り直し → 重複の報告 → 移動記録の下のコメントの除去。
- 保存: 修復は 1 つのコミット(操作名 `repair`、または `merge` コミットの中)として保存され、トレーラー `repaired` に種類を残す。同じ入力は同じ出力になる(`repair.go:35-37` のコメント)。時刻 `updated` は修復を行った時刻(`r.in.Now`)に書く(`repair.go:820-840` の `files`)。
- 通知(`web/core/notifications.ts:109-161`): 通知の宛先は、`Repaired.Author`(修復したファイルを最後に書いた人。`repair.go:178-181` の `tell`)。GUI の文は種類ごとに作る。`parent_cycle`・`parent_deleted`・`parent_moved`・`ref_moved`・`sprint_detached`・`release_detached` は日本語の文が決まっている。`workspace_revived`・`workspace_mismatch`・`id_prefix` は文が決まっておらず、一般の文「同期の修復: {種類}(元の値: {値})」(`notifications.ts:165-175` の `repairedText`)になる。つまり画面には `同期の修復: workspace_revived(元の値: null)` のような種類名がそのまま出る。診断の結果の欄(`doctor.ts:81-86`)には、これら 3 つの日本語の文がある(「削除されていたワークスペースを復元しました」、「ID の接頭辞がワークスペースと違っていたため、振り直しました」、「親と違うワークスペースにあったため、親のワークスペースに合わせました」)。
- 閲覧のみの Store: `Repair` と `repairHead` の呼び出しに、閲覧のみかどうかの分岐はない。`acc.ReadOnly` の分岐は修復の後(`sync.go:252`)にあり、そこで送信を止める(`sync.go:243-258`)。コードの読み取りでは、閲覧のみの Store でもマージのコミットと修復のコミットがローカルに作られ、送信できない件数(`Unpushable`)に数えられる(未確認: 実行していない)。

### 1-1 親の循環(`parent_cycle`)

- 条件: 親をたどると自分に戻るアイテムの輪(`findCycle`、`repair.go:268-290`)。削除済みのアイテムも輪に入る(アイテムの一覧に削除済みも載る)。

- 行き先: 優先順位で最初に置ける所へ(`reparent`、`repair.go:353-381`)。(1)基準でそのアイテムが持っていた親(置ける種類で、輪の下でなく、削除済みでないとき)(2)今の親の祖先(近い順。基準から読めるものも使う)(3)ルート(プロジェクトだけが置ける)(4)そのワークスペースの「未分類」プロジェクト(なければ、ワークスペースから決まる ULID で作る。`repair.go:394-424`)。Step を Epic・プロジェクトの下に置くときは Task になる。ワークスペースが読めず「未分類」が作れないときは、親を外してルートへ置く(輪を切るため)。位置は新しい親の末尾。

- 通知の文: 「スプリント {名前} から外しました(移動先のワークスペースにはありません)」(リリースは「リリース」。`notifications.ts:149-158`)。名前が読めないときは ULID。

### 1-3 親のワークスペースへの追従(`workspace_mismatch`)と、親が別の Store へ移ったとき(`parent_moved`)

- `workspace_mismatch`(`followParents`、`repair.go:594-625`): ルートから順に、子のワークスペースが親のワークスペースと違えば、子を親のワークスペースへ移す(子の下も順に追従する)。移ったアイテムは `moved` として数え、`renumber` で移動先の接頭辞の新しい番号を振る(`id_renumbered` の通知は出さない。移ったことの通知 `workspace_mismatch` だけ。`repair.go:735-760`)。古い ID はアイテムの `FormerIDs` に残る(`repair.go:741-743`)。続けて、移動先のワークスペースにないスプリント・リリースを外す(1-2)。プロパティの値の引き直し(ステータス・優先度・関連システム等)はしない。ワークスペースと、親・位置・ID・スプリント・リリース以外は変えない。移動先で値が合わなければ、診断の「ステータスがない」「存在しない値」の対象として残る(確認: `repair.go` に値の引き直しの処理がない)。
- `parent_moved`(`detachFromDeleted`、`repair.go:508-530`): 親のファイルが、別の Store へ移った記録(forward)になっているとき、削除済みの親の子と同じ扱いで、親の祖先の近い順に置ける所へ(1-1 の `reparent` と同じ優先順)。通知の文: 「親{元の親}が別の Store へ移ったため、{行き先}の下に移しました」。
- 関連: 別の Store へ移った記録を指す関連は除く(`ref_moved`、`repair.go:537-571`)。記録の下のコメント・作業時間は、ファイルごと除く(`dropUnderForwards`)。
- 同じ関数の仲間 `parent_deleted`(削除済み・消えた親の子): 親が削除済み(論理削除)または消えたとき、削除されていない子を、祖先の近い順に置ける所へ移す(`repair.go:508-535`)。通知の文: 「親{元の親}が削除されたため、{行き先}の下に移しました」(`notifications.ts:126-141`)。R9 の 5 種には入っていないが、同じ仕組みで、仕様の承認済みの規則とぶつかる(R9-C6)。
- 通知の宛先: 子のファイルを最後に書いた人(`tell(c, ..., model.TaskPath(c))`)。

### 1-4 消えたワークスペースの復活(`workspace_revived`)

- 条件(`reviveWorkspaces`、`repair.go:176-198`): マージの結果に、そのワークスペースに属するアイテムが残っているのに、ワークスペースのファイルが消えているとき、基準(共通の祖先)にそのファイルがあれば、基準の内容でファイルを書き戻す。基準にもなければ復活せず、診断の `no_workspace` に任せる(`repair.go:187` のコメント)。基準なしの呼び出し(`repairHead`、`hh doctor --fix`)では、復活は起きない(`readBase` が nil を返す)。
- 結果: 基準の時点のワークスペースの内容(名前・接頭辞・設定)がそのまま戻る。ワークスペースの設定ファイル(スキーマ)は別のファイルで、復活の対象は `workspaces/{ULID}.md` だけである。復活後のワークスペースは通常の状態(現行にワークスペースの論理削除はない)。
- 通知: 宛先はワークスペースのファイルを最後に書いた人。文は一般の文(1-0)。
- 現行でワークスペースが消える場面: 一方がワークスペースを物理的に削除し、もう一方が同じワークスペースにアイテムを作った(現行の「ワークスペースの削除」は、ゴミ箱を経由しない物理削除。audit/current-vs-spec.md の C 表の記述に一致)。

### 1-5 不正な接頭辞の復元(`id_prefix`)

- 条件(`restorePrefixes`、`repair.go:200-224`): ワークスペースの接頭辞が `ValidIDPrefix` を満たさず、基準のそのワークスペースの接頭辞が有効なとき。有効の定義は `^[A-Z][A-Z0-9]{1,9}$`(英大文字で始まる 2〜10 文字、`internal/app/domain/model/taskid.go:12`、`:18-25`)。空の接頭辞は不正である。1 文字も不正である。
- 結果: 基準の接頭辞と、その設定日時 `prefix_set` に戻す。アイテムの ID は変えない(ID は接頭辞が戻れば合うため)。基準にない、基準の接頭辞も不正のときは、何もしない。基準なしの呼び出しでも、何もしない。
- 現行の接頭辞は必須である(空にする操作がない)。仕様では空が有効(R9-C8)。
- 通知: 宛先はワークスペースのファイルの最後の書き手。文は一般の文(1-0)。値は不正だった接頭辞(JSON の 1 行)。
- 古い接頭辞の記録: 現行はアイテムごとに `FormerIDs` を持つだけで、仕様の 03:104 の「ワークスペースごとの旧い接頭辞の記録」に当たるものは、`restorePrefixes` が触らない。

### R9-C10 通知の本文と宛先

- 06-sync-notifications.md「通知」の「同期の修復」の行(06:261)と、「同期の修復」の節: 「同期の修復 | 同期の修復 | 同期での修復が、あなたの作ったもの、またはあなたが変更・追加したものを変えた。…」。各修復の節が本文を 1 つずつ定め、5 種の本文はない。06 の「モックからの変更点」: 「修復の通知先 | 受信した側が自分宛てに作る | 修復で変わったものを作った人のマシンが、同期で受け取ったときに自分宛てに作る。保存は書き込めるマシンだけが行う」(06:488)。
