# 画面からスキーマを編集する 設計

- 日付: 2026-11-08
- 置き換える部分: `docs/superpowers/specs/2026-11-01-phase4-gui-design.md` の画面の表で、SettingsSchema を「スキーマの閲覧、schema check、migrate」としている行

## 目的

いまのスキーマ画面でできるのは、閲覧と、名前の変更・マージ（migrate）だけです。それ以外の変更は `.hedgehug/schema.yaml` を直接編集するしかありません。これを画面からもできるようにします。対象はステータス・種類・プロパティ・関連・enum の値で、それぞれ追加・削除・属性の変更・並べ替えができるようにします。

親設計は「各ステータスは名前・表示名・カテゴリ・色・並び順を持つ」と決めていますが、編集の手段は決めていません。CLI ではこれまでどおり YAML を編集します。

## 決定の一覧（2026-11-08、利用者の決定）

| # | 対象 | 決定 |
|---|---|---|
| 1 | 範囲 | ステータス・種類・プロパティ（関連を含む）・enum の値の追加・削除・並べ替えと、型以外の属性の変更。名前は今までどおり「名前…」（migrate）で変える |
| 2 | 使用中の削除 | タスクが使っている定義は削除できない。「マージ…」で移すよう案内する |
| 3 | 属性の変更 | 型以外はすべて変えられる。既存のタスクが規則に合わなくなる変更は、何も書かずに、違反するタスクを一覧して拒否する（Store 間の移動と同じ扱い） |
| 4 | 色 | 決まった色から選ぶ。YAML に書かれた別の値（`#3451D1` など）は「カスタム」として表示し、そのまま残す |
| 5 | CLI | 足さない。画面と API だけ |

## 編集できるもの

| 定義 | 追加のとき決めるもの | あとから変えられるもの |
|---|---|---|
| ステータス | 名前・表示名・カテゴリ・色 | 表示名・カテゴリ・色・既定 |
| 種類 | 名前・表示名・役割・置ける親・アイコン・既定のテンプレート | 表示名・役割・置ける親・アイコン・既定のテンプレート・既定 |
| プロパティ（関連以外） | 名前・表示名・型、enum と multi_enum は値 | 表示名 |
| 関連（`task_ref`） | 名前・表示名・複数・逆方向の表示名・双方向 | 表示名・複数・逆方向の表示名・双方向 |
| enum の値 | 値 | （名前は「名前…」で変える） |

- 追加したものは一覧の末尾に入ります。位置は並べ替えで変えます。
- 名前の規則は migrate の新しい名前と同じです。空の名前と重複は `Check()` が拒否し、プロパティは組み込みのフィールド名も拒否します。ほかの規則は足しません。
- 既定は「既定にする」だけができます。同じカテゴリ（種類なら work の役割）で既定だったものは、同じ書き込みで既定でなくなります。既定を外すだけの操作はありません。種類で既定にできるのは work の役割の種類だけです（既定を使うのは work の役割だけのため）。各カテゴリに既定がちょうど 1 つ必要という `Check()` の規則があるためです。
- 既定のステータスのカテゴリと、既定の種類の役割は変えられません。変えると元のカテゴリ（役割）から既定がなくなるためです。画面ではその欄を無効にし、理由を出します。
- `blocked_by` は組み込みの関連なので、これまでどおり編集の対象外です。
- ワークフロー、プロジェクトごとの上書き、テンプレートの編集は、この変更に含めません。上書きは今までどおりプロジェクトの設定で編集します。

## 削除

- 削除できるのは、タスクが 1 件も使っていない定義だけです。数えるのは Store にあるすべてのタスクで、削除済みのタスクも含みます。削除済みのタスクは復元できるので、その定義が消えると復元したときに規則に合わなくなるからです。migrate も削除済みのタスクを書き換えています。
- 使っているタスクがあるときは 422 `schema.in_use` で拒否します。応答には件数（うち削除済みの件数）を入れます。画面の削除ボタンは、件数が 0 のときだけ有効にします。件数が 1 以上のときは「マージ… で別の定義へ移してから削除してください」と理由を出します。画面の件数には削除済みのタスクが入っていないため、件数 0 でもサーバーが拒否することがあります。その場合はサーバーの文をそのまま出します。
- 既定のステータスと、work の役割で既定の種類は削除できません（`Check()` の規則）。画面では削除ボタンを無効にし、「別のものを既定にしてから削除してください」と理由を出します。
- 削除した定義を参照している箇所は、同じ書き込みで外します。削除の確認ダイアログには、外れる箇所を一覧します。

| 削除するもの | 外す参照 |
|---|---|
| ステータス | Store と各上書きのワークフロー（遷移の制約のキーと移動先、必須の項目のキー）、上書きの `statuses` |
| 種類 | ほかの種類の置ける親、上書きの `templates.default` のキー |
| プロパティ | Store と各上書きの必須の項目 |
| enum の値 | なし |

- 遷移の制約の移動先がすべてなくなったキーは、キーごと外します。必須の項目が空になったキーも外します。Store 間の移動で上書きを持ち込むとき（`Carry`）と同じ扱いで、何かを求めていた制約が何も求めなくなったら残さない、という考え方です。
- 置ける親が削除する種類だけの種類があるときは、削除を 422 `schema.parents_empty` で拒否し、その種類を名前で示します。置ける親を空にすると YAML では省略され、「どこにでも置ける」という逆の意味になってしまうためです。
- 上書きの `statuses` は既定のステータスを必ず含む（`Check()` の規則）ので、ステータスの削除で空になることはありません。
- 保存済みビューの列が、削除したプロパティを指していることがあります。これは今までどおり表示で飛ばし、doctor が警告します。

## 属性の変更とタスクの検証

役割・置ける親・関連の「複数」を変えると、既存のタスクが規則に合わなくなることがあります。書き込みの前に、Store にあるすべてのタスク（削除済みを含む）を変更後のスキーマで検査します。変更前にはなかった違反が出るタスクがあれば、何も書かずに 422 `schema.tasks_invalid` で拒否し、タスクの ID と違反の一覧を返します。もとからあった違反は数えません。`ValidateWrite` と同じ考え方で、同期で壊れたタスクがあっても、ほかの変更を止めないためです。

## 並べ替え

- ステータス・種類・プロパティ・関連・enum の値の、それぞれの一覧の中で並べ替えます。プロパティと関連は YAML の `props` という 1 つのマッピングに入っていますが、画面ではそれぞれのタブの中だけで並べ替えます。サーバーは、タブに出ていないプロパティの位置を変えません。
- 要求は並べ替えたあとの名前の全体です。今の名前の集合と一致しなければ 409 `schema.order_stale` で拒否します。画面は読み込み直して、もう一度並べ替えてもらいます。ほかの書き込みと重なって、黙って誰かの追加を落とすのを防ぐためです。
- 画面では、行のつまみをドラッグして並べ替えます（カンバンで使っている pragmatic-drag-and-drop）。キーボードでは、つまみにフォーカスして ⌥↑ / ⌥↓（Windows と Linux は Alt）で 1 つずつ動かします。ツリーの並べ替えと同じキーです。
- プロパティと関連の並びは、スキーマ画面だけでなく、プロパティを並べるすべての画面（タスク詳細、テーブルの列の候補、ガント、上書きの必須の候補）に使います。いまは名前の順に並べていますが、それでは並べ替えた結果が見えないためです（2026-11-08、利用者の決定）。
- 並びを持たせるため、`GET /api/schema` の応答に `prop_order`（`props` のキーを YAML の順に並べたもの）を足します。`props` は JSON のオブジェクトなので、Go の `encoding/json` がキーを名前の順に並べ替えてしまい、並びが伝わらないためです。

## 色とアイコン

色とアイコンは、いまは画面のどこにも出ていません。`StatusIcon` は色を受け取れますが渡している呼び出し元がなく、`KindIcon` は `icon` を見ずに名前で形を決めています。編集できるようにするのに合わせて、ステータスと種類を表示するすべての箇所（ツリー・カンバン・テーブル・リスト・詳細・ガント・パレットなど、`StatusIcon` と `KindIcon` を使う箇所）で、スキーマの色とアイコンを使います。

- 色の候補は 12 色です: グレー・ブルー・グリーン・アンバー・レッド・ティール・オレンジ・パープル・スカイ・ピンク・オリーブ・ブラウン。YAML にはこの英語の名前（`gray`・`blue`・`green`・`amber`・`red`・`teal`・`orange`・`purple`・`sky`・`pink`・`olive`・`brown`）を書きます。画面は名前をテーマのトークン（`--muted`・`--accent`・`--success`・`--amber`・`--danger`・`--store-*-dot`）に置き換えるので、ライトとダークの両方で読めます。選択肢には「自動」もあり、選ぶと `color` を消して、今のカテゴリの色に戻します。
- 候補にない値が YAML に書かれていれば、これまでどおり `safeColor` を通った値をそのまま使います。編集ダイアログでは「カスタム（値）」として選択中に表示し、ほかの色を選ばない限り書き換えません。`safeColor` を通らない値は今までどおり無視し、カテゴリの色で描きます。
- 種類のアイコンは、組み込みの形から選びます: project・epic・story・task・bug の形と、「自動」（今までどおり、名前が組み込みならその形、そうでなければ役割の形）。YAML には形の名前を書きます。候補にない値は無視し、「自動」と同じに描きます。ダイアログでは「カスタム（値）」と表示し、ほかを選ばない限り書き換えません。
- bug の赤は、今は種類の名前で決めています。これを、bug の形で描くときの色に変えます。

## API

どの書き込みも、ほかのスキーマの書き込み（プロジェクトの上書き）と同じく 1 操作 1 コミットです。Store のロックの中で今のスキーマを読み直して変更を当て、`NewProblems(cur.Check())` が空でなければ 422 `schema.invalid` で拒否します。応答は変更後の `SchemaView` とコミットです。読み取り専用の Store への書き込みは、ほかの書き込みと同じ誤りになります。

| 操作 | エンドポイント |
|---|---|
| ステータスの追加・変更・削除・並べ替え | `POST /api/schema/statuses`、`PATCH /api/schema/statuses/{name}`、`DELETE /api/schema/statuses/{name}`、`PUT /api/schema/statuses/order` |
| 種類 | `POST /api/schema/kinds`、`PATCH /api/schema/kinds/{name}`、`DELETE /api/schema/kinds/{name}`、`PUT /api/schema/kinds/order` |
| プロパティと関連 | `POST /api/schema/props`、`PATCH /api/schema/props/{name}`、`DELETE /api/schema/props/{name}`、`PUT /api/schema/props/order` |
| enum の値 | `POST /api/schema/props/{name}/values`、`DELETE /api/schema/props/{name}/values/{value}`、`PUT /api/schema/props/{name}/values/order` |

- `PATCH` は送ったフィールドだけを変えます。表示名・色・アイコン・既定のテンプレート・逆方向の表示名は、空文字列で消します。`default` は `true` だけを受けます。
- `PUT …/order` の本文は `{"names": [...]}` です。`props/order` は、プロパティか関連のどちらか一方の名前の全体を受けます。
- `?store=` の扱いは、ほかのスキーマの API と同じです。
- 書き込みのあと、サーバーは今までどおり `schema.changed` を出します。画面のスキーマのキャッシュは、それで読み直します。
- 元に戻す（Undo）は対象外です。migrate と同じく、変更は git の履歴に 1 コミットずつ残ります。

## 画面

- 各タブ（ステータス・種類・プロパティ・関連）の表の上に「追加…」ボタンを置きます。行には「編集…」「名前…」「マージ…」「削除…」と、並べ替えのつまみを置きます。enum の値の行には「名前…」「マージ…」「削除…」とつまみを置き、プロパティの行に「値を追加…」を置きます。
- 追加と編集は 1 つのダイアログでします。追加のときだけ、名前・型など、あとから変えられない欄を出します。
- 書き込めない Store では、どのボタンも今の「名前…」と同じく無効にし、理由を出します。
- 種類のタブの「置ける親」は、ルートとほかの種類のチェックボックスで選びます。「どこにでも」を選ぶと、親の指定を消します（YAML で `parents` を書かない状態）。「どこにでも」でもなく、どの親も選ばない状態では保存できません。
- 拒否されたときは、ダイアログの中にサーバーの文を出します。`schema.tasks_invalid` はタスクの ID を一覧し、各行からタスクを開けるようにします。
- `SettingsSchema.svelte` は 622 行あるので、タブごとのコンポーネントに分けてから足します。
- 画面上部の「追加・削除・色や並びの変更は YAML（.hedgehug/schema.yaml）を編集してください」は、「この Store で使う共通の定義です。ここで追加・編集・並べ替えができます。」に変えます。

### F1・F6 の API

- `PATCH /api/schema/statuses/{name}`・`/kinds/{name}`・`/props/{name}` は `name`（新しい名前）を受ける。名前が変わるときは、定義とそれを参照する箇所、それを使うタスクを、ほかの属性の変更と同じ 1 コミットで書き換える。新しい名前がすでにある定義なら 409 `schema.name_taken`（マージはマージのボタンでする）。
- `PATCH /api/schema/props/{name}` は enum と multi_enum のとき `values` を受ける。`values` は保存後の値の全体で、順に `{"name": "<値>", "from": ["<今の値>", …]}` を並べる。
  - `from` がない値は追加。`from` が 1 つで名前が違えば名前の変更。`from` が 2 つ以上ならマージ（タスクの値を `name` に書き換える）。
  - 今の値のうち、どの `from` にも出てこない値は削除。使っているタスクがあれば 422 `schema.in_use`（値と件数を付ける）。
  - 同じ今の値が 2 つの `from` に出る、空の値、重複した値は 422 `schema.value_invalid`。
- 値の個別の操作（`POST`・`DELETE …/values…`・`PUT …/values/order`）はなくす。
- 「名前…」ボタンがなくなるので、画面から migrate の API を名前の変更に使うのをやめる。マージは今までどおり migrate を使う。

### F8: 関連の逆方向の検索（2026-11-08、利用者の決定）

逆方向の表示名を英語にすると空白を含み、クエリのキーにできなくなる。そこで、クエリは表示名ではなく名前で検索する。

- 関連（`task_ref` のプロパティ）の逆方向は `<名前>.inverse:<ID>` と書く（例: `duplicates.inverse:WEB-1` は WEB-1 と重複しているタスク側から見た相手）。組み込みの `blocks` はそのまま使え、`blocked_by.inverse` も同じ意味にする。
- 逆方向の表示名（`inverse`）をキーにする検索はやめる。表示名は画面の表示だけに使う。
