# 種類・関連・組み込みのプロパティを固定する 設計

- 日付: 2026-11-08
- 置き換える部分: 親設計（Hedgehug 設計ドキュメント）の、種類・関連・プロパティ・クエリの関連のキーの記述。`docs/superpowers/specs/2026-10-30-phase1a-model-format-design.md` の `kinds` と `props` の記述。`docs/superpowers/specs/2026-11-08-schema-gui-edit-design.md` のうち、種類・関連・プロパティのマージの編集

## 目的

種類と関連は、追加・変更・階層の組み替えが自由にできる。しかし実際にはカスタマイズして使う場面がほとんどなく、機能が過剰になっている。そこで、種類・関連・よく使うプロパティを固定の概念にし、使い方を Jira の標準に近い形でそろえる。あわせて、GitHub と同期する項目にコメントを足す。

ステータスは今までどおり Store ごとに自由に定義できる（この変更に含めない）。

## 決定の一覧（2026-11-08、利用者の決定）

| # | 対象 | 決定 |
|---|---|---|
| 1 | 種類 | Project・Epic・Story・Task・Bug・Step の 6 つに固定する。追加・変更・プロジェクトごとの上書きはできない |
| 2 | 階層 | ワークスペースの直下はプロジェクトだけ。エピックはプロジェクトの下だけ。ストーリー・タスク・バグはプロジェクトかエピックの下。ステップはストーリー・タスク・バグの下だけで、子を持てない |
| 3 | 関連 | blocked_by・causes・relates・duplicates・clones の 5 つに固定する。どれも向きがある。追加・変更はできない |
| 4 | プロパティ | priority・start・due・estimate・points・labels を組み込みにする。プロパティ一覧に出さず、値のリストを持つ priority と labels だけ専用の欄で値を編集する |
| 5 | 独自のプロパティ | 今までどおり追加・変更できる。ただし task_ref 型はなくし、プロパティのマージはなくす。ステータスと値のマージは残す |
| 6 | 進捗 | ストーリー・タスク・バグを数える。ステップは数えず、親の行に内訳を出す |
| 7 | GitHub | 同期する項目にコメントを足す |
| 8 | 既存のデータ | 変換コマンドを用意する |

## 種類と階層

| 名前 | 表示名 | 役割 | 置ける場所 | 子に置ける種類 |
|---|---|---|---|---|
| project | Project | グループ | ワークスペースの直下 | epic・story・task・bug |
| epic | Epic | グループ | project の下 | story・task・bug |
| story | Story | アイテム | project・epic の下 | step |
| task | Task | アイテム | project・epic の下 | step |
| bug | Bug | アイテム | project・epic の下 | step |
| step | Step | アイテム | story・task・bug の下 | なし |

- ストーリー・タスク・バグは同じ階層の兄弟。「ストーリーの下にタスク」は置けない。
- プロジェクトは階層の一部というより、全体の入れ物として扱う。プロジェクトの下にプロジェクトは置けない。
- schema.yaml の `kinds` はなくす。種類の名前・表示名・役割・置ける場所・アイコン・色はコードに固定する。アイコンは今の 5 つの形に、ステップの形を 1 つ足す。色は今の既定（バグは赤、ほかは既定のアイコンの色）。
- 種類を指定せずにタスクを作ると、親に合わせて決める（2026-11-08、利用者の決定）: 親がなければ project、親が project か epic なら task、親が story・task・bug なら step。CLI の `hh add`、画面での作成、テンプレートの中の種類を省いた子のどれも同じ。schema.yaml の `default` はなくなる。親が step のときは、step には子を置けないので、種類は step になり、配置の検査が「a step cannot be placed under step」で拒否する（2026-11-09、利用者の決定。`hh gh import --parent <step>` も同じ。Go と画面の既定の種類は同じ）。
- 親を指定せずにプロジェクト以外の種類を指定して作る要求は、今の配置の誤りと同じく拒否する。CLI で `hh use` のプロジェクトがあれば、今までどおりそれが親になる。
- `hh gh import` は取り込み先の親が必須（2026-11-08、利用者の決定）。`--parent` がなければ `hh use` のプロジェクトを使い、それもなければ 422 `import.parent_required`（「--parent で取り込み先を指定してください」）で止める。取り込んだタスクの種類は親に合わせて決まる。
- 種類ごとの既定のテンプレート（今の `kinds[].template`）は、schema.yaml の `templates.default`（種類 → テンプレート）へ移す。形はプロジェクトの上書きの `templates.default` と同じ。
- （2026-11-09、利用者の決定）Store 全体の `templates.only` は、検査はされていたが効いたことがない。schema.yaml にあれば、検査で 422 `schema.invalid`（書き込みを拒否）、doctor の指摘（`schema.templates_only_on_store`）にする。`templates.only` はプロジェクトの上書き（`scoped[].templates.only`）にだけ使える。画面のスキーマ編集は書かない。
- プロジェクトの上書き（`scoped`）は、今までどおりプロジェクトかエピック（グループの役割）に付けられる。上書きできるのはステータス・ワークフロー・テンプレートだけ（今と同じ）。

### 親子の修復（同期の自動修復と hh doctor --fix）

親子の関係が壊れたタスク（親が削除された、親が別の Store へ移った、同時の編集で親子が循環した）は、今はワークスペースの直下へ移している。直下にはプロジェクトしか置けないので、次のように変える（2026-11-08、利用者の決定）。

- いちばん近い、置ける祖先の下へ移す。祖先は、循環なら共通の祖先の版（base）での親、それ以外は元の親の祖先を近い順にたどる。
- 見つかった祖先の下に今の種類のままでは置けず、種類がステップで、祖先がプロジェクトかエピックなら、種類を task に変えて置く。
- 置ける祖先がなければ、そのワークスペースの「未分類」プロジェクト（なければ作る）の下へ移す。ステップなら task に変える。
- 移したこと（種類を変えたならそれも）は、今と同じく通知（inbox）に出す。

## 関連

| 名前（タスクの項目） | 表示名 | 逆方向の名前 | 逆方向の表示名 | 表すもの |
|---|---|---|---|---|
| blocked_by | Blocked by | blocks | Blocks | 作業の順番・依存（これから先の話） |
| causes | Causes | caused_by | Caused by | 問題の原因と結果（すでに起きた問題） |
| relates | Relates to | related_by | Related by | 関係がある |
| duplicates | Duplicates | duplicated_by | Duplicated by | 同じ内容の重複。片方を閉じるときに使う |
| clones | Clones | cloned_by | Cloned by | 複製として作った元と先 |

- 5 つとも、今の `blocked_by` と同じくタスクの組み込みの項目（ULID のリスト）として保存する。`props:` には入れない。参照できるのは今までどおり同じ Store のタスクだけ。
- どれも向きがある。付けた側に表示名、付けられた側に逆方向の表示名で出す。今の relates は向きのない双方向だったが、向きを持たせる。
- 循環の検査は、今の blocked_by と同じく blocked_by だけにする。
- クエリのキーは上の表の「名前」と「逆方向の名前」（例: `causes:WEB-1`、`caused_by:WEB-1`）。`<名前>.inverse` の書き方（2026-11-08 の F8）はなくす。
- task_ref 型のプロパティは作れなくなる。
- workflow.required には 5 つの関連の名前を書ける（今の blocked_by と同じ）。
- 自分自身を指す関連は、5 つとも新しく付けるときに拒否する（422 `ref.self`、「自分自身は指せません」）。blocked_by の自己参照は今までどおり循環として拒否する。変換で来た自己参照は、書き込みを止めない規則（もとからある違反は通す）で残る（2026-11-09、利用者の決定）。
- 向きを持たせた relates では、X に関係あるものすべてを 1 つのクエリで書けない。`relates:X` と `related_by:X` の 2 回で求める。ガイドに 1 行書く。クエリに OR は足さない（2026-11-09、利用者の決定）。
- `<関連の名前>.inverse`（名前が 5 つの関連のどれか）をキーにしたときだけ、未知のキーの文を「逆方向は caused_by: で書きます」のように、逆方向の名前で案内する。ほかの未知のキーは今までどおり（2026-11-09、利用者の決定）。
- 関連（blocked_by を含む）は、並べ替え・グループ化・表の列の対象にしない（今の blocked_by と同じ。2026-11-09、利用者の決定）。
- 別の Store へ動かすときに切る参照の名前は、トレーラー・`hh mv` の出力・修復 `ref_moved`・API の `MoveUnlinkView.field` のどれも、`props.` を付けずに関連の名前（`causes`・`relates` など。blocked_by と同じ）にする。過去のコミットの `props.relates` は履歴に残るだけで、読み返さない（2026-11-09、利用者の決定）。
- 詳細の逆方向の表示（`hh show`・画面・API の `reverse`）は、キーを逆方向の名前（blocks・caused_by・related_by・duplicated_by・cloned_by）、ラベルを表の表示名（Blocks・Caused by など）にする。行は値があるときだけ出す。blocked_by の行は今までどおり常に出す（2026-11-09、利用者の決定）。
- 関連は、タスクの作成の本文（`POST /api/tasks`）には足さない（blocked_by と同じ）。作成のあとに PATCH で付ける。`props` に関連の名前を入れた作成は 400 で、「関連は作成後に付けます」と案内する（2026-11-09、利用者の決定）。
- `hh dep add|rm <id> [--blocked-by <id>…] [--causes <id>…] [--relates <id>…] [--duplicates <id>…] [--clones <id>…]` は、1 回に複数のフラグを渡せ、フラグごとに複数の相手を渡せる。1 コミットで書く。フラグが 1 つもなければ使い方のエラー。同じ組を 2 回付けようとしたら、今の `dep.invalid` を相手ごとに出す（2026-11-09、利用者の決定）。逆方向を付けるフラグ（`--blocks` など）は作らない。
- 独自のプロパティの `multi` は残す（task_ref 型の廃止だけが決定で、`multi` の廃止は含まない）。task_ref 型を作ろうとしたら、422 `schema.unknown_type` で「関連は固定です。hh dep か詳細の関連の欄で付けます」と案内する（2026-11-09、利用者の決定）。
- 関連の表示名は、すべて上の表の英語にする。画面側にも固定の表（`web/core/relations.ts`）を置き、Go の表と一致することをテストする。カンバンの必須項目のダイアログも、Blocked by・Causes などの表示名で出す（2026-11-09、利用者の決定）。
- 5 つの関連は、blocked_by と同じ集合の項目としてマージする。同じ相手を複数の関連に付けられる。参照の検査（同じ Store のタスクだけ、存在しない・別 Store は書き込みで拒否、削除済みは通す）、同期の修復、別の Store へ動かすときに切る参照も、5 つに広げる。
- 逆方向は付けた側の項目にだけ保存し、逆方向の項目は持たない。`hh set` に逆方向のキーを書くと読み取り専用として拒否する。詳細の「関連を追加」も順方向の 5 つだけで、逆方向のグループは取り外せない。
- 4 つの関連に副作用はない（duplicates で相手を閉じる、clones で複製を作る、といった機能は持たない）。
- クエリのキーは Store ごとのスキーマに依らず、全 Store で使える。`is:blocked`、ガントの矢印、ツリーの印は blocked_by のまま。クエリのキーの一覧（Go の `queryKeys` と画面の `QUERY_KEYS`）に足すのは 8 つ（blocks は今もある）。
- 索引のキャッシュの形式を上げる。

## 組み込みのプロパティ

| 名前 | 表示名 | 型 | 値のリスト |
|---|---|---|---|
| priority | 優先度 | enum | 編集できる。既定は low・mid・high・urgent |
| start | 開始日 | date | なし |
| due | 期限 | date | なし |
| estimate | 見積もり | duration | なし |
| points | ポイント | number | なし |
| labels | ラベル | multi_enum | 編集できる。既定は空 |

- 6 つともタスクの組み込みの項目として、`props:` の外のトップレベルのキーに保存する（labels は今もトップレベル）。
- labels は今は自由入力だが、値のリストにある値だけを付けられるようにする。
- 値のリストは schema.yaml のトップレベルの `priorities:` と `labels:` に書く。値の追加・名前の変更・削除・並べ替え・マージは、独自の enum の値と同じ規則で行う（使用中の値はマージせずに消せない）。
- schema.yaml の `props` に、組み込みと同じ名前のプロパティは定義できない（今の組み込みのフィールドと同じ扱い）。
- workflow.required には 6 つの名前を書ける。
- 値の照合（2026-11-09、利用者の決定）: ラベルと優先度は、大文字小文字を無視して照合し、保存はリストの綴りに直す（リストに `bug` があれば、`hh set labels+=Bug` は `bug` を付ける）。リストの重複の判定も、大文字小文字を無視する。ラベルのリストが空のときは、ラベルを付けようとすると「設定の「ラベル」で足してください」と案内する。違反のコードは、タスクの違反の `bad_value`。
- クエリの `label:` は、今までどおり値を検査しない（`priority:` は今のままリストにない値で止める）。ラベルを消したり名前を変えたりしても、保存済みビューの `query` は書き換えない（2026-11-09、利用者の決定）。
- priorities は 1 つ以上必須で、labels は空でよい。キーがなければ priorities は既定、labels は空。`priorities: []` は `schema.values_empty`。画面は優先度の最後の 1 つを消せない（2026-11-09、利用者の決定）。
- 同期のマージ（2026-11-09、利用者の決定）: `labels:` は集合としてマージする（base と比べて、追加と削除を両方反映する）。同時に別のラベルを足しても、両方残る。`priorities:` は順序に意味があるので、リスト全体が後勝ちのまま。上の「独自の enum の値と同じ規則」は、このマージには当てない。
- トップレベルの型つきの値（start・due・estimate・points）が読めないとき（`due: next week` など）は、そのキーだけ知らないキーとして退避し、`bad_value` の違反にする。タスクは壊れた扱いにせず、`hh set due=…` で直せる（2026-11-09、利用者の決定）。
- CLI（2026-11-09、利用者の決定）: `hh schema migrate priority <旧> <新>`・`hh schema migrate label <旧> <新>`（名前の変更とマージ）と、`hh schema labels add <名前>…`・`hh schema labels rm <名前>…`（追加と、使われていないラベルの削除）。優先度の追加・削除・並べ替えと、ラベルの並べ替えは画面で行う。大文字小文字だけの名前の変更（`bug` → `Bug`）は、CLI でも画面でも綴りの変更として受け付け、リストとタスクの値を書き換える。完全に同じ名前だけを「同じ」として断る（2026-11-09、利用者の決定）。
- 別の Store へ動かすとき、priority と labels は移動先のリストで検査し、リストにない値があれば 422 `move.invalid` で断る（今の priority と同じ規則）。先に移動先のリストに足す（2026-11-09、利用者の決定）。
- 画面のラベルの入力（詳細・表のその場編集・カンバンの必須項目のダイアログ・一括変更・作成の 5 か所）は、リストから選ぶだけで、同じ選択の部品を使う。リストが空なら「設定の「ラベル」で足してください」のリンクを出す（2026-11-09、利用者の決定）。
- 画面の置き方（2026-11-09、利用者の決定）: 表の列名は今の名前（ラベルは `label`）。詳細は、ステータスの下に優先度・開始日・期限・見積もり・ポイント・ラベルの固定の順で出す。作成ダイアログに出すのは優先度・期限・ラベル（プロジェクトの作成ダイアログは、これに今の開始日を足した優先度・開始日・期限・ラベル。2026-11-09、利用者の決定）。ガントの開始と終了は、組み込みの start・due と独自の日付プロパティから選べる。
- クエリのキーは今のまま（`priority:`・`start:`・`due<`・`estimate:`・`points:`、ラベルは単数の `label:`）。priority の並べ替え・グループ化は `priorities:` の並び順。空の priority は値なし（`hh set priority=` で消える）で、既定値は付けない。
- 独自のプロパティを組み込みと同じ名前で作る要求と、組み込みと同名への名前の変更は、422 `schema.invalid`。日付・期間・数の書式は、独自のプロパティの date・duration・number と同じ（points の小数は許し、NaN・Inf は拒否する）。
- タスク内のマージは、priority・start・due・estimate・points がスカラーの項目（後勝ちで、負けた値は inbox に出る）、labels が今の集合のマージ。リストにない値が同期で入ってきたときは、書き込みは拒否だが、同期の結果は警告にして doctor の `task.bad_value` に出す。
- priority や due で動く通知はない。`hh gh import --label` は残す。索引とレポートのキャッシュの形式を上げる。

## 独自のプロパティ

- 型は text・number・bool・date・datetime・duration・enum・multi_enum・user・url（task_ref をなくす）。
- 追加・名前の変更・表示名・値の編集・削除・並べ替えは今までどおり。
- プロジェクトごとの上書きの対象には、今までどおりプロパティを含めない（組み込みも独自も）。
- プロパティどうしのマージをなくす。画面のボタンと API、CLI の `hh schema migrate` のプロパティのマージ（マージ先が既存のプロパティの場合）をなくし、422 で拒否する。名前の変更は残す。

## API・JSON の形（2026-11-09、利用者の決定）

- タスクの JSON は、組み込みの項目を blocked_by・labels と同じくトップレベルに、型つきで持つ。GET・一覧の行（`hh ls --json`、`GET /api/tasks`）・PATCH・POST が同じ形。`props` の中には出さない。
- 関連 4 つは blocked_by と同じ形にする。GET は Ref オブジェクト（ULID・ID・タイトルなど）の配列、PATCH は ID の配列で受ける（`relations:` の入れ子は作らない。2026-11-09、利用者の決定）。
- priority・start・due・estimate・points は、points が数、日付が `YYYY-MM-DD`、期間が `1h30m`。値がなければ `null`。PATCH で消すのは `null`。
- `props` に組み込みの名前を入れた要求は、今までどおり 400。

## スキーマ画面

- 「種類」タブと「関連」タブをなくす。
- 「プロパティ」タブは独自のプロパティだけを出す。型の候補から task_ref を外し、「マージ」ボタンをなくす。
- 「優先度」タブと「ラベル」タブを足す。どちらも値のリストを、プロパティの編集ダイアログと同じ値の編集欄で編集する。値ごとに使っているタスクの件数で削除の可否を決める。
- ステータスのタブは今のまま。
- （2026-11-09、利用者の決定）Store の種類ごとの既定のテンプレート（`templates.default`）は、設定の「テンプレート」画面で、プロジェクトのテンプレート画面と同じ「<種類> の既定」の欄で選ぶ。

## 進捗

- プロジェクト・エピックの進捗は、子孫のストーリー・タスク・バグを数える。ステップは数えない。
- ストーリー・タスク・バグの行には、子のステップの内訳（例: 2/3）を出す。

## GitHub のラベルの同期をやめる（2026-11-08、利用者の決定）

- タスクのラベルと GitHub の issue のラベルの同期をやめる。同期する項目（`hh automation fields`）から `labels` をなくし、push・mirror・issue の作成のどれでもラベルを送らず、取り込まない。
- 理由: ラベルの使い方はリポジトリごと、Organization ごとに違い、hedgehug の値のリストとそのまま対応づけられない。GitHub のラベルとの対応づけは別に検討する。
- `hh gh import --label` の絞り込み（取り込む issue を GitHub のラベルで選ぶ）は同期ではないので残す。
- 既存の automations の `labels` の項目は、変換の段 3→4 で取り除く。

## GitHub のコメント同期

- 同期する項目（`hh automation fields`）に `comments` を足す。既定では push・mirror のどちらにも含めない（利用者が足す）。
- push モード: hedgehug のコメントを issue のコメントとして作る。編集・削除も反映する。GitHub 側で編集されたコメントは、次の push で上書きし、今の push と同じく上書きを `hh inbox` に知らせる。
- mirror モード: issue のコメントを hedgehug のコメントとして取り込む。編集・削除も反映する（削除は hedgehug のコメントの削除と同じ扱い）。取り込んだコメントは hedgehug で編集・削除できない（422）。作者は `github:<login>` とする。
- どのコメントがどの GitHub のコメントに当たるかは、コメントのファイルの `gh` に、リンクごとの GitHub のコメントの ID を持って対応づける。
- 同期の時機・レート制限・失敗の扱いは、今の issue の同期と同じ。
- 取り込むコメントの ULID は、GitHub の投稿時刻とコメントの ID から決める（`DerivedULID`）。2 つのクローンが同じコメントを別々に取り込んでも、同じファイルになり、マージで 1 件に畳まれる。並びは GitHub の時系列になる（2026-11-09、利用者の決定）。
- 1 つのタスクに複数の issue のリンクがあるとき（2026-11-09、利用者の決定）: mirror は、今のフィールドの規則どおり先頭の mirror のリンクの issue だけ取り込む。push は push のリンクすべてに送るが、送るのは hedgehug のコメントだけで、作者が `github:` のコメントは送らない。同じ issue の `gh` の ID があるコメントは、モードを変えても同じコメントとみなし、作らず、取り込まない。
- push するのは、作者が自分（`me`）のコメントだけで、そのクローンが送る。GitHub 上の作者は書いた本人になる。作者が空のコメントは送らない。削除済みで一度も push していないコメントも送らない（2026-11-09、利用者の決定）。
- 本文は、今の本文の push と同じく、そのまま送る。`@login` は GitHub でも本物のメンションとして通知になる。`@host/login` は GitHub では `@host` への通知になりうるので、ガイドに 1 行書く（2026-11-09、利用者の決定）。
- 初回（`comments` を同期する項目に足した直後）は、push が 1 回の同期で GitHub に作るコメントを 30 件までにして、残りは次の同期へ回す。mirror の取り込みには上限を置かず、通知も抑えない（2026-11-09、利用者の決定）。
- push が GitHub に送る本文の末尾に、見えないマーカー `<!-- hedgehug:<コメントの ULID> -->` を入れる（2026-11-09、利用者の決定）。コメントを作る前に issue のコメントを調べ、同じマーカーのものがあれば、`gh` の ID を戻して作らない。マーカーがなければ、本文が同じでも書き直す。`gh` の ID を失ったコメント（LWW で負けた、GitHub に作ったあと記録の前に落ちた）の重複を防ぐ最後の手がかり。
- `gh` の要素は `ref`・`id`・`body_synced` を持つ。`body_synced` は、最後に同期した本文を正規化した全文で、GitHub 側で編集されたかの基準（phase5 の `synced` と同じ）。
- push は、タスクごとの 1 コミットで `gh` を書く。`gh` だけを書くときは、コメントの `Updated` を進めない（ストアの層に `Updated` を保つ書き込みを足す）。本文の編集が `gh` の記録に負けず、`gh` の ID が編集に負けない（2026-11-09、利用者の決定）。コメントの同期のマージは `Updated` が新しい側のファイルを採るが、勝った側にない `ref` の `gh` の要素は負けた側から足す（2026-11-09、利用者の決定）。
- GitHub 側でコメントが消えていたとき、push は作り直して `gh` の ID を更新する（PATCH が 404 のとき。push は hedgehug を正本とする）。mirror は、issue のコメントを全ページ読めたときだけ削除を反映する。読みきれなければ警告して何も変えない。コメントの取得は REST で、レート制限の記録（`ghstate`）は GraphQL の分だけ（2026-11-09、利用者の決定）。
- 取り込んだコメントは、作者が `github:` で始まるもの。作者は `github:<login>`（bot は `dependabot[bot]`、消えたユーザーは `ghost`）。リンクを外しても、モードを変えても、ずっと編集・削除できない（422 `comment.mirrored`。検査の順は、削除済み → 取り込み → 作者）。API の `CommentView` に `github`（真偽）を足し、画面の印に使う（2026-11-09、利用者の決定）。
- push で GitHub 側の編集を上書きした通知は、field を `comments:<コメントの ULID>` にし、画面は「コメント（先頭の数文字）」と出す（2026-11-09、利用者の決定）。先頭の数文字は、上書きした手元の本文（その push のときのコメントの本文）から取り、通知のデータに持たせて画面と CLI に出す（2026-11-09、利用者の決定）。
- push 済み（`gh` のあるコメント）の追加の `hh undo` は断る（422 `undo.comment_pushed`）。消したいときは `hh comment rm` を使う（GitHub からも消える。2026-11-09、利用者の決定）。
- 取り込んだコメントの `Created` は GitHub の created_at、取り込み・編集の反映の `Updated` は GitHub の updated_at にする。削除の反映の `DeletedAt` と `Updated` は、削除前のファイルから決まる値にする（削除前の `Updated` より後）。2 つのクローンが同時に取り込んでも同じファイルになり、inbox の「上書き」にならない。片方だけが削除済みのように中身が本当に違うときは、今までどおり知らせる（2026-11-09、利用者の決定）。
- コメントの取り込みのコミットは、同期を実行した本人の書き込みでも、新しいコメントとメンションを本人にも知らせる。issue のフィールドの mirror は変えない（2026-11-09、利用者の決定）。
- mirror が、`gh` で対応づけたコメント（push で作った自分のコメントなど）の手元の編集を GitHub の本文に戻したときは、issue のフィールドの mirror と同じく、失われた本文をつけて `hh inbox` に知らせる（2026-11-09、利用者の決定）。
- push が issue のコメントの一覧で同じマーカーのコメントを 2 件以上見つけたら（同じアカウントの 2 つのクローンが同時に作った場合など）、`gh` が指す 1 件を残し、余分を DELETE する（2026-11-09、利用者の決定）。
- 取り込みは、コメントの作者や本文の `@login` を watcher に足さない。索引と inbox は、本文にあるメンション・参照をそのまま読む。
- mirror が更新・削除するのは、`gh` の ID で対応づけたコメントだけ。手元で書いて `gh` のないコメントは消さない。mirror の削除は論理削除（`DeletedAt`）で、hedgehug のコメントの削除と同じ。issue が GitHub で読めないときは、コメントの削除を反映しない。
- push は、コメントを ULID の順に作る。hedgehug で削除したコメントは GitHub で DELETE し、404 は成功とみなして `gh` を消す。`hh issue` は issue の作成でコメントを送らず、次の同期が `comments` を push する。対象は issue のコメントだけで、PR のリンクのコメントは対象にしない。閲覧のみの Store は取り込まず、push もしない。

## 形式の番号と変換コマンド

### 形式の番号

- Store の形式の番号（`.hedgehug/store.yaml` の `format`、`model.StoreFormat`）を、形式を変える PR ごとに 1 つ上げる。今は 1。種類と階層で 2、関連で 3、組み込みのプロパティで 4 にする（GitHub のコメント同期は上げない。コメントのファイルに `gh` を足すだけで、古い hedgehug も知らないキーとして保つ。ただし `comments` を同期する項目に足すと、古い hedgehug は `automations.yaml` を読めず、ルールと issue の同期が止まる。影響は足したチームだけなので、ガイドに「足す前にその Store を使うすべてのクローンを更新する」と書く。2026-11-09、利用者の決定）。
- 新しい形式の Store は、今までどおり開かずに「hedgehug を更新してください」と出す。
- 古い形式（`format` が最新より小さい）の Store は、変換するまで開かない（2026-11-08、利用者の決定）。`hh store convert` と `hh doctor` だけを通し、ほかの操作は 422 `store.old_format`（「hh store convert で新しい形式にしてください」）で止める。画面も同じ文を出す。古い形を読むコードは、変換の段の関数の中にだけ持つ。履歴の読み取りも、同期のマージの base も、その関数を通す（下の「古い形を読む入口」。2026-11-09、利用者の決定）。

### 変換コマンド

- `hh store convert [--dry-run] [--kind <今の種類>=<新しい種類>]…`。
- 変換は「1→2」「2→3」のように 1 段ずつの手順として持ち、今の番号から最新まで順に当てる。2 つ以上前の形式でも 1 回のコマンドで変換できる。段を足すときは、前の段に手を入れず、新しい段を 1 つ足す。
- `--dry-run` は、段ごとに変わる内容を一覧するだけで、何も書かない。実行は全段を 1 コミットで書き換え、`format` を最新にする。
- 同期している Store では、変換したあとそのまま push する。リモートも同じ古い形式で、取り込んでいないリモートのコミットか push していないローカルのコミットがあるときは、`hh store convert` が先に古い形式のまま同期（取り込み・マージ・push）してから変換して push する。1 回のコマンドでする（2026-11-09、利用者の決定）。409 `store.convert_unsynced` は、この同期が失敗したとき（push が拒否された、マージで止まったなど）に出し、文は実際の原因を示す。`--dry-run` は同期も書き込みもせず、先に同期する旨を出す。この同期のマージの修復は、変換の `--kind` を通らず、固定の表で動く（親が消えた独自の種類の子は「未分類」へ移る）。
- ほかのクローンで、push していないコミットを残したまま、新しい形式に変換されたリモートを取り込む場合、そのクローンは古い形式なので、利用者の `hh sync` は 422 `store.old_format` で止まり、`hh store convert` を案内する。`hh store convert` は、ローカルのまだ push していない変更を新しい形式に変換してから、同期で合わせる。409 `sync.format_diverged` は、この変換の中で使う検査（リモートが新しい形式で、ローカルに push していない変更がある）として残る。向きが逆の場合（次の項）には、変換のあとの `hh sync` が利用者に返す。
- push していないコミットがなく、リモートが新しい形式に変換済みなら、`hh store convert` は変換せずにリモートへ fast-forward する（2026-11-09、利用者の決定）。古い形式の Store は `hh sync` を通さないので、取り込みはこのコマンドでする。
- リモートが最新でない途中の形式なら、ローカルをリモートの形式まで変換して同期で合わせ（push していないコミットがなければ fast-forward）、そのあと残りの段を当てて push する（2026-11-09、利用者の決定）。
- 逆向きの食い違い（2026-11-09、利用者の決定）: 手元が最新の形式で、リモートがそれより古い形式のまま、手元にないコミットを持つとき（あるクローンが変換している間に、別のクローンが古い形式のコミットを push した）、`hh sync` は 409 `sync.format_diverged` で止まる。このときの文は向きに従い、リモートが古い側なら「`hh store convert` でリモートの変更を変換する」よう案内し、新しい側ならこれまでの文にする（args の `remote_older` で画面も出し分ける）。`hh store convert` は、リモートの先頭のファイルに変換の段を（リモートの形式から手元の形式まで）当て、そのコミットを親がリモートの先頭の 1 コミット（op convert）として push し（リモートの fast-forward）、そのあと通常の同期で手元とマージして push する。1 回のコマンドでする。最新の形式の Store でも、リモートがあればこの状態を調べる（なければ何もしない）。`--dry-run` は何も書かず、リモートの変更を変換する旨と段ごとの内容を一覧する。push が拒否されたとき（また別のクローンが push した）は 409 `store.convert_unsynced` で、もう一度実行するよう案内する。
- 変換より前の hedgehug のクローン（形式の検査を持たない古い版）は、変換済みのリモートへ未 push のコミットごと同期でき、独自の種類やルート直下のタスクを形式 2 のリモートへ push してしまう。古い版のコードは直せないので、利用者の決定でガイドだけで扱う（2026-11-09、利用者の決定）。変換の前にその Store を使うすべてのクローンの hedgehug を更新するよう案内し、起きたときの戻し方として、`hh doctor` の指摘（未定義の種類・置けない場所）を `hh edit` で直す手順をガイドに書く。
- doctor は古い形式を見つけたら、このコマンドを案内する。画面は doctor の指摘を出す（変換は CLI でする）。

### 古い形を読む入口

- 変換の段は、Store 全体の書き換えのほかに、タスク 1 件のファイルを次の形式の形に書き換える関数を持つ（2026-11-09、利用者の決定）。この関数には、タスク 1 件で決まる変換（キーの移動、種類の名前の対応、値の型の直しなど）だけを入れる。木全体の関係で決まるもの（配置の繰り上げ、「未分類」への移動）は入れない。その版のスキーマが要る段は、その版のコミットの `schema.yaml` を読む。この関数は `updated` を動かさない。
- 過去のコミットのタスクファイルを読む入口は、そのコミットの `store.yaml` の `format` を読み、最新まで段の関数を順に当ててから使う（2026-11-09、利用者の決定）。入口は `hh restore --at`、`hh show --at`、`hh undo`、`hh inbox` の取り消し、レポート（バーンダウン・ベロシティ）、履歴の差分。Part 1 の段 1→2 も同じ入口に乗せる。段を足すと、入口はそのまま新しい段を当てる。`hh inbox` の上書きの取り消しで、変換より前に記録された関連の項目（`props.duplicates`・`props.causes`・`props.relates`・`props.clones` と独自の task_ref）は、「関連は固定になったため取り消せない」と案内して何も変えない（戻したい値は `hh dep` で足す。2026-11-09、利用者の決定）。`hh undo` が変換前のコミットのテンプレートを読むときも段の関数を当てる。変換前の版の schema.yaml とビュー（`views/*.yaml`）を戻す取り消しは断る。その版の `store.yaml` がない・読めないときは、最新の形式とみなさずにエラーにする（黙って変換前のまま読まない）。変換のコミット（op convert）は `hh undo` の対象にしない（2026-11-09、利用者の決定）。過去の版の関連の値に ULID の形でない値（当時から不正だった値）があれば、正しい ULID だけを関連へ動かし、不正な値は `props` の元の名前のまま残す（黙って捨てない。duplicates・causes・relates・clones なら doctor の `task.legacy_field` が指摘し、利用者が `hh edit` で直す。2026-11-09、利用者の決定）。
- 段 3→4 を過去の版に当てるとき、ラベルは、その版の schema.yaml ではなく今（HEAD）の `labels:` で照合し、綴りもそれに合わせる（形式 3 の版にはふつう `labels:` がなく、その版のリストで照合するとラベルが全部消えるため。変換で残したラベルは戻り、残さなかったラベルは変換と同じく外れる。2026-11-09、利用者の決定）。
- 同期のマージは、base（共通の祖先）の形式がマージする側より古いとき、base のタスクにも同じ段の関数を当ててからマージする（2026-11-09、利用者の決定）。変換後どうしと同じ条件でマージされるので、片方が変換後に外した関連が、もう一方の変換で戻ることはない。
- `hh doctor` は、古い hedgehug のクローンが push してきた古い形を見つける（2026-11-09、利用者の決定）。`props` に、今の形式で組み込みの名前になっているもの（形式 3 なら duplicates・causes・relates・clones、形式 4 ならさらに priority・start・due・estimate・points）が残っていれば、`task.legacy_field` を出す。`hh doctor --fix` は、タスク 1 件の段の関数で組み込みの項目へ移す。移し先のトップレベルにすでに値があるタスクは、どちらが新しいか分からないので移さず、指摘を残す（利用者が `hh edit` で決める。2026-11-09、利用者の決定）。日時を日付に直して時刻を落とした値は、変換と同じく移し、落とした時刻を `--fix` の出力にタスクと元の値で一覧する（2026-11-09、利用者の決定）。Part 1 の種類・置き場所の戻し方（指摘を見て `hh edit`）は今のまま。ガイドの回復の手順に `--fix` を足す。

### 全段に共通の規則

- テンプレート（`templates/*.md`）の項目と子も、タスクと同じく書き換える（2026-11-09、利用者の決定）。テンプレートの項目にも、タスクと同じ組み込みの項目（関連 4 つ、プロパティ 5 つ）をトップレベルに持たせ、子は再帰で直す。関連はタスクの blocked_by と同じ扱い（展開でそのまま写す）。ラベルがリストにないときは、タスクと同じく変換で外す。テンプレートを展開するとき、リストにないラベルがあれば作成を拒否する（タスクの値の検査と同じ）。doctor が指摘するので、そこからテンプレートを直す。
- ビュー（`views/*.yaml`）の `query` と `table.columns`、`workflow.required` に残る古い書き方も、機械的に直せるものは変換で書き換え、意味が変わるものは書き換えずに dry run の報告へ一覧する（2026-11-09、利用者の決定）。段ごとの中身は下の「段 2→3 の細部」。
- 変換で書き換えたタスクの `updated` は、段 2→3・3→4 では動かさない（2026-11-09、利用者の決定）。キーの置き場所を変えるだけで更新とみなさず、別々に変換したクローンが同じファイルを作る。段 1→2 は、今までどおり今の時刻にする。

### 段ごとの変換の中身

| 対象 | 変換 |
|---|---|
| 種類 | 名前が組み込みと同じならそのまま。独自の種類は、グループの役割ならワークスペース直下のものは project、それ以外は epic。アイテムの役割なら task。`--kind` で種類ごとに移し先を指定できる |
| 合わない配置 | ストーリー・タスク・バグの下のストーリー・タスク・バグは step にする。step の下の子は、いちばん近いストーリー・タスク・バグの直下へ上げて step にする。プロジェクトの下のプロジェクト、エピックの下のエピックは、親の親の直下へ上げる |
| ワークスペース直下 | プロジェクト以外のタスクがあれば、そのワークスペースに「未分類」プロジェクトを 1 つ作り、そこへ移す |
| 関連 | duplicates・causes・relates はそのまま組み込みの項目へ。独自の task_ref のプロパティは relates へ。今の relates は、保存されていた側から付けた向きありの relates になる |
| 組み込みのプロパティ | `props:` の中の priority・start・due・estimate・points をトップレベルへ移す。priority の値のリストは今の定義から `priorities:` へ。型が合わない値（例: points が text）があれば一覧にして止める |
| ラベル | `labels:` のリストにないラベルはタスクから外す。dry run で外れるラベルを一覧するので、残したいものは先にリストに足す。automations の同期する項目から `labels` を取り除く |
| schema.yaml | `kinds` と task_ref のプロパティと組み込みと同じ名前のプロパティを消す。`kinds[].template` を `templates.default` へ移す。Store 全体の `templates.only` を消す（変換の報告に 1 行出す） |

### 段 2→3 の細部

- 動かすのは task_ref 型のプロパティの値だけ（2026-11-09、利用者の決定）。duplicates・causes・relates・clones の名前で task_ref 型の定義を持つ値は同名の項目へ（clones は 2026-11-09、利用者の決定）、それ以外の独自の名前の task_ref は relates へ動かす。定義が schema.yaml から消えて値だけ `props` に残った duplicates・causes・relates・clones は、値が ULID なら関連として動かす。ULID の形でない値は、下の値の検査と同じく一覧にして止める（`--drop-bad-values` で外す）。task_ref でない独自プロパティが duplicates・causes・relates・clones の名前を持っていれば、変換を 422 `convert.prop_name_taken` で止め、重なる名前と型を一覧して、名前を変えるよう案内する。旧形式の Store は `hh` で編集できないので、ガイドに、schema.yaml とタスクのファイルを手で直してコミットする手順を書く。逆方向の名前（blocks・caused_by・related_by・duplicated_by・cloned_by）と同名の独自プロパティは止めない。変換では何もせず、doctor の既存の警告（`prop_name.query_key`）が出る。
- A に B・B に A が両方保存されていた relates は、2 本とも向きありの relates として残し、報告に「相互の組 N 件」と出す（2026-11-09、利用者の決定）。
- 値の検査: ULID の形でない値だけを一覧にして止める（422 `convert.bad_value`、タスクと値の一覧）。`--drop-bad-values` を付けたときだけ、外して報告にすべて出す（段 3→4 と同じ仕組み）。存在しない・削除済み・自分自身を指す値は、blocked_by と同じくそのまま動かす。単一の値は 1 要素のリストにし、重複は 1 つにまとめる（2026-11-09、利用者の決定）。
- 報告: 独自の task_ref のプロパティごとに「<名前>: N 件を relates へ」を 1 行出す。確認は求めない（2026-11-09、利用者の決定）。
- ビュー等の書き換え（2026-11-09、利用者の決定）: `<名前>.inverse:` は逆方向の名前に（`causes.inverse:` → `caused_by:`、`blocked_by.inverse:` → `blocks:`）。独自の task_ref のキーは `relates:` に。独自の `<名前>.inverse:` と、逆方向の表示名のキーは `related_by:` に（指されている側を求めるため。2026-11-09、利用者の決定。逆方向の表示名は、その版の schema.yaml を生のまま読んで拾う）。`table.columns` から、消える名前（独自の task_ref、duplicates・causes・relates の列）を外す。`workflow.required` の独自の task_ref の名前は `relates` に。元の `relates:X` は両方向に当たっていて意味が変わるので書き換えず、dry run の報告に一覧する。形式 2 で双方向だった名前（`relates` と、`symmetric: true` を付けた独自の task_ref）のキーと `.inverse:` も同じく書き換えずに報告する（その版の schema.yaml を生のまま読んで `symmetric` を拾う。独自の名前のキーは変換後に未知のキーになるので、利用者が `relates:`・`related_by:` に直す。2026-11-09、利用者の決定）。表の列や並べ替えに使っていた人にも、この報告で知らせる。`sort:`・`group:`・`group_by` に消える名前（関連と独自の task_ref）があれば、列と同じく外して報告に一覧する（2026-11-09、利用者の決定）。
- schema.yaml の duplicates・causes・relates の定義（表示名や逆方向の表示名を変えたものも）は消える。`workflow.required` の duplicates・causes・relates は同名の組み込みになるので、そのまま有効。

### 段 3→4 の細部

- ラベル（2026-11-09、利用者の決定）: `labels:` のリストにないラベルは、タスクとテンプレートから外す。リストは、変換のときに format 3 の schema.yaml にすでにあるトップレベルの `labels:`（priority の `priorities:` と同じ考え方）。ない Store は空のリストと同じで、全ラベルが外れる。残したいラベルは、変換の前に schema.yaml にトップレベルの `labels:` を手で書いてコミットする。旧形式の Store は `hh` での編集が止まるので、これが唯一の手段。この手順をガイド（stores.md）に書く。照合は大文字小文字を無視し、保存はリストの綴りにする。dry run は外れるラベルを一覧する。
- priorities（2026-11-09、利用者の決定）: すでに `priorities:` があればそれを使い、なければ priority の定義の `values`、定義が enum でなければ既定の low・mid・high・urgent。リストにない値を持つタスクは、下の型が合わない値と同じ扱い。照合は大文字小文字を無視し、保存はリストの綴り。
- 形式 4 の検査に通らないリスト（2026-11-09、利用者の決定）: priorities・labels のリストに大文字小文字だけ違う重複（`[High, high]` など）があれば、先に書かれた綴り 1 つに畳み、タスクとテンプレートの値もその綴りにする。`priorities: []` は、空でない次の出どころ（priority の定義の values → 既定）を使う。どちらも変換の報告に 1 行ずつ出す（止めない）。
- 型が合わない値（2026-11-09、利用者の決定）: 値が組み込みの型として読めるかで調べる。失わずに直せるものは直す。定義が text などで値が `"3"` の points は 3 に。datetime は、書かれたオフセットのまま日付だけを取る（例: `2026-11-08T15:30:00+09:00` → `2026-11-08`）。時刻が 00:00 でないものは時刻を落としたことになるので、そのタスクと元の値を報告に一覧する（止めない。2026-11-09、利用者の決定）。1 件だけの配列はその値に。空文字は外す。それ以外で読めない値（数の estimate など）は直せない値で、1 つでもあれば全体を止める（422 `convert.bad_value`、タスクと値の一覧。止めたときは `--drop-bad-values` を案内する）。`--drop-bad-values` を付けると、直せない値を外し、外した値を報告にすべて出す。dry run は止める場合と同じ一覧を出し、終了コード 1 で終わる。
- トップレベルと `props` に同じ名前のキーが両方あるものは、上の一覧に入れて止める（2026-11-09、利用者の決定）。`--drop-bad-values` を付けたときは、形式 3 で使われていた `props` 側の値を組み込みへ移し、トップレベルの値を外して報告に出す（2026-11-09、利用者の決定）。
- GitHub の跡（2026-11-09、利用者の決定）: automations.yaml の `labels` に加えて、各タスクの `gh.issues[].synced` の `labels` と、リンクごとの `fields` の `labels` も取り除く。全タスクを書く変換のコミットの中で済ませる。`labels` を取り除いてリンクの `fields` が空になるリンク（ラベルだけを同期していた）は、`sync` を `link`（同期しない）にし、報告に一覧する。空の `fields` は既定の項目で同期する意味になるため（2026-11-09、利用者の決定）。
- inbox の取り消し（2026-11-09、利用者の決定）: 変換より前に記録された `props.priority`・`props.start`・`props.due`・`props.estimate`・`props.points` の上書きの取り消しは、同じ名前のトップレベルの項目へ読み替えて戻す（値の意味は変わらないため。関連と違い、取り消せないとはしない）。今のリストにない優先度など、戻せない値なら理由を出して何も変えない。
