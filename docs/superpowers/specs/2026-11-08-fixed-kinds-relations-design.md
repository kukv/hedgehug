# 種類・関連・組み込みのプロパティを固定する 設計

- 日付: 2026-11-08
- 置き換える部分: 親設計（Hedgehug 設計ドキュメント）の、種類・関連・プロパティ・クエリの関連のキーの記述。`docs/superpowers/specs/2026-10-30-phase1a-model-format-design.md` の `kinds` と `props` の記述。`docs/superpowers/specs/2026-11-08-schema-gui-edit-design.md` のうち、種類・関連・プロパティのマージの編集

## 目的

種類と関連は、追加・変更・階層の組み替えが自由にできる。しかし実際にはカスタマイズして使う場面がほとんどなく、機能が過剰になっている。そこで、種類・関連・よく使うプロパティを固定の概念にし、使い方を Jira の標準に近い形でそろえる。あわせて、GitHub と同期する項目にコメントを足す。

ステータスは今までどおり Store ごとに自由に定義できる（この変更に含めない）。

## 決定の一覧（2026-11-08、利用者の決定）

| # | 対象 | 決定 |
|---|---|---|
| 1 | 種類 | Project・Epic・Story・Task・Bug・Step の 6 つに固定する。追加・変更・プロジェクトごとの上書きはできない |
| 2 | 階層 | ワークスペースの直下はプロジェクトだけ。エピックはプロジェクトの下だけ。ストーリー・タスク・バグはプロジェクトかエピックの下。ステップはストーリー・タスク・バグの下だけで、子を持てない |
| 3 | 関連 | blocked_by・causes・relates・duplicates・clones の 5 つに固定する。どれも向きがある。追加・変更はできない |
| 4 | プロパティ | priority・start・due・estimate・points・labels を組み込みにする。プロパティ一覧に出さず、値のリストを持つ priority と labels だけ専用の欄で値を編集する |
| 5 | 独自のプロパティ | 今までどおり追加・変更できる。ただし task_ref 型はなくし、プロパティのマージはなくす。ステータスと値のマージは残す |
| 6 | 進捗 | ストーリー・タスク・バグを数える。ステップは数えず、親の行に内訳を出す |
| 7 | GitHub | 同期する項目にコメントを足す |
| 8 | 既存のデータ | 変換コマンドを用意する |

## 種類と階層

| 名前 | 表示名 | 役割 | 置ける場所 | 子に置ける種類 |
|---|---|---|---|---|
| project | Project | グループ | ワークスペースの直下 | epic・story・task・bug |
| epic | Epic | グループ | project の下 | story・task・bug |
| story | Story | アイテム | project・epic の下 | step |
| task | Task | アイテム | project・epic の下 | step |
| bug | Bug | アイテム | project・epic の下 | step |
| step | Step | アイテム | story・task・bug の下 | なし |

- ストーリー・タスク・バグは同じ階層の兄弟。「ストーリーの下にタスク」は置けない。
- プロジェクトは階層の一部というより、全体の入れ物として扱う。プロジェクトの下にプロジェクトは置けない。
- schema.yaml の `kinds` はなくす。種類の名前・表示名・役割・置ける場所・アイコン・色はコードに固定する。アイコンは今の 5 つの形に、ステップの形を 1 つ足す。色は今の既定（バグは赤、ほかは既定のアイコンの色）。
- 種類を指定せずにタスクを作ると、親に合わせて決める（2026-11-08、利用者の決定）: 親がなければ project、親が project か epic なら task、親が story・task・bug なら step。CLI の `hh add`、画面での作成、テンプレートの中の種類を省いた子のどれも同じ。schema.yaml の `default` はなくなる。
- 親を指定せずにプロジェクト以外の種類を指定して作る要求は、今の配置の誤りと同じく拒否する。CLI で `hh use` のプロジェクトがあれば、今までどおりそれが親になる。
- `hh gh import` は取り込み先の親が必須（2026-11-08、利用者の決定）。`--parent` がなければ `hh use` のプロジェクトを使い、それもなければ 422 `import.parent_required`（「--parent で取り込み先を指定してください」）で止める。取り込んだタスクの種類は親に合わせて決まる。
- 種類ごとの既定のテンプレート（今の `kinds[].template`）は、schema.yaml の `templates.default`（種類 → テンプレート）へ移す。形はプロジェクトの上書きの `templates.default` と同じ。
- プロジェクトの上書き（`scoped`）は、今までどおりプロジェクトかエピック（グループの役割）に付けられる。上書きできるのはステータス・ワークフロー・テンプレートだけ（今と同じ）。

### 親子の修復（同期の自動修復と hh doctor --fix）

親子の関係が壊れたタスク（親が削除された、親が別の Store へ移った、同時の編集で親子が循環した）は、今はワークスペースの直下へ移している。直下にはプロジェクトしか置けないので、次のように変える（2026-11-08、利用者の決定）。

- いちばん近い、置ける祖先の下へ移す。祖先は、循環なら共通の祖先の版（base）での親、それ以外は元の親の祖先を近い順にたどる。
- 見つかった祖先の下に今の種類のままでは置けず、種類がステップで、祖先がプロジェクトかエピックなら、種類を task に変えて置く。
- 置ける祖先がなければ、そのワークスペースの「未分類」プロジェクト（なければ作る）の下へ移す。ステップなら task に変える。
- 移したこと（種類を変えたならそれも）は、今と同じく通知（inbox）に出す。


| 名前（タスクの項目） | 表示名 | 逆方向の名前 | 逆方向の表示名 | 表すもの |
|---|---|---|---|---|
| blocked_by | Blocked by | blocks | Blocks | 作業の順番・依存（これから先の話） |
| causes | Causes | caused_by | Caused by | 問題の原因と結果（すでに起きた問題） |
| relates | Relates to | related_by | Related by | 関係がある |
| duplicates | Duplicates | duplicated_by | Duplicated by | 同じ内容の重複。片方を閉じるときに使う |
| clones | Clones | cloned_by | Cloned by | 複製として作った元と先 |

- 5 つとも、今の `blocked_by` と同じくタスクの組み込みの項目（ULID のリスト）として保存する。`props:` には入れない。参照できるのは今までどおり同じ Store のタスクだけ。
- どれも向きがある。付けた側に表示名、付けられた側に逆方向の表示名で出す。今の relates は向きのない双方向だったが、向きを持たせる。
- 循環の検査は、今の blocked_by と同じく blocked_by だけにする。
- クエリのキーは上の表の「名前」と「逆方向の名前」（例: `causes:WEB-1`、`caused_by:WEB-1`）。`<名前>.inverse` の書き方（2026-11-08 の F8）はなくす。
- task_ref 型のプロパティは作れなくなる。
- workflow.required には 5 つの関連の名前を書ける（今の blocked_by と同じ）。

## 組み込みのプロパティ

| 名前 | 表示名 | 型 | 値のリスト |
|---|---|---|---|
| priority | 優先度 | enum | 編集できる。既定は low・mid・high・urgent |
| start | 開始日 | date | なし |
| due | 期限 | date | なし |
| estimate | 見積もり | duration | なし |
| points | ポイント | number | なし |
| labels | ラベル | multi_enum | 編集できる。既定は空 |

- 6 つともタスクの組み込みの項目として、`props:` の外のトップレベルのキーに保存する（labels は今もトップレベル）。
- labels は今は自由入力だが、値のリストにある値だけを付けられるようにする。
- 値のリストは schema.yaml のトップレベルの `priorities:` と `labels:` に書く。値の追加・名前の変更・削除・並べ替え・マージは、独自の enum の値と同じ規則で行う（使用中の値はマージせずに消せない）。
- schema.yaml の `props` に、組み込みと同じ名前のプロパティは定義できない（今の組み込みのフィールドと同じ扱い）。
- workflow.required には 6 つの名前を書ける。

## 独自のプロパティ

- 型は text・number・bool・date・datetime・duration・enum・multi_enum・user・url（task_ref をなくす）。
- 追加・名前の変更・表示名・値の編集・削除・並べ替えは今までどおり。
- プロジェクトごとの上書きの対象には、今までどおりプロパティを含めない（組み込みも独自も）。
- プロパティどうしのマージをなくす。画面のボタンと API、CLI の `hh migrate` のプロパティのマージ（マージ先が既存のプロパティの場合）をなくし、422 で拒否する。名前の変更は残す。

## スキーマ画面

- 「種類」タブと「関連」タブをなくす。
- 「プロパティ」タブは独自のプロパティだけを出す。型の候補から task_ref を外し、「マージ」ボタンをなくす。
- 「優先度」タブと「ラベル」タブを足す。どちらも値のリストを、プロパティの編集ダイアログと同じ値の編集欄で編集する。値ごとに使っているタスクの件数で削除の可否を決める。
- ステータスのタブは今のまま。

## 進捗

- プロジェクト・エピックの進捗は、子孫のストーリー・タスク・バグを数える。ステップは数えない。
- ストーリー・タスク・バグの行には、子のステップの内訳（例: 2/3）を出す。

## GitHub のラベルの同期をやめる（2026-11-08、利用者の決定）

- タスクのラベルと GitHub の issue のラベルの同期をやめる。同期する項目（`hh automation fields`）から `labels` をなくし、push・mirror・issue の作成のどれでもラベルを送らず、取り込まない。
- 理由: ラベルの使い方はリポジトリごと、Organization ごとに違い、hedgehug の値のリストとそのまま対応づけられない。GitHub のラベルとの対応づけは別に検討する。
- `hh gh import --label` の絞り込み（取り込む issue を GitHub のラベルで選ぶ）は同期ではないので残す。
- 既存の automations の `labels` の項目は、変換の段 3→4 で取り除く。

## GitHub のコメント同期

- 同期する項目（`hh automation fields`）に `comments` を足す。既定では push・mirror のどちらにも含めない（利用者が足す）。
- push モード: hedgehug のコメントを issue のコメントとして作る。編集・削除も反映する。GitHub 側で編集されたコメントは、次の push で上書きし、今の push と同じく上書きを `hh inbox` に知らせる。
- mirror モード: issue のコメントを hedgehug のコメントとして取り込む。編集・削除も反映する（削除は hedgehug のコメントの削除と同じ扱い）。取り込んだコメントは hedgehug で編集・削除できない（422）。作者は `github:<login>` とする。
- どのコメントがどの GitHub のコメントに当たるかは、コメントのファイルの `gh` に、リンクごとの GitHub のコメントの ID を持って対応づける。
- 同期の時機・レート制限・失敗の扱いは、今の issue の同期と同じ。

## 形式の番号と変換コマンド

### 形式の番号

- Store の形式の番号（`.hedgehug/store.yaml` の `format`、`model.StoreFormat`）を、形式を変える PR ごとに 1 つ上げる。今は 1。種類と階層で 2、関連で 3、組み込みのプロパティで 4 にする（GitHub のコメント同期は、コメントのファイルに `gh` を足すだけで、古い hedgehug も知らないキーとして保つので上げない）。
- 新しい形式の Store は、今までどおり開かずに「hedgehug を更新してください」と出す。
- 古い形式（`format` が最新より小さい）の Store は、変換するまで開かない（2026-11-08、利用者の決定）。`hh store convert` と `hh doctor` だけを通し、ほかの操作は 422 `store.old_format`（「hh store convert で新しい形式にしてください」）で止める。画面も同じ文を出す。古い形を読むコードは変換の中にだけ持つ。

### 変換コマンド

- `hh store convert [--dry-run] [--kind <今の種類>=<新しい種類>]…`。
- 変換は「1→2」「2→3」のように 1 段ずつの手順として持ち、今の番号から最新まで順に当てる。2 つ以上前の形式でも 1 回のコマンドで変換できる。段を足すときは、前の段に手を入れず、新しい段を 1 つ足す。
- `--dry-run` は、段ごとに変わる内容を一覧するだけで、何も書かない。実行は全段を 1 コミットで書き換え、`format` を最新にする。
- 同期している Store では、変換は同期が済んだ状態（取り込んでいないリモートのコミットも、push していないローカルのコミットもない）でだけ実行し、そのまま push する。そうでなければ 409 `store.convert_unsynced` で止める。
- ほかのクローンで、push していないコミットを残したまま、新しい形式に変換されたリモートを取り込むと、同期は 409 `sync.format_diverged` で止まる。このときは `hh store convert` が、ローカルのまだ push していない変更を新しい形式に変換してから、同期で合わせる。
- doctor は古い形式を見つけたら、このコマンドを案内する。画面は doctor の指摘を出す（変換は CLI でする）。

### 段ごとの変換の中身

| 対象 | 変換 |
|---|---|
| 種類 | 名前が組み込みと同じならそのまま。独自の種類は、グループの役割ならワークスペース直下のものは project、それ以外は epic。アイテムの役割なら task。`--kind` で種類ごとに移し先を指定できる |
| 合わない配置 | ストーリー・タスク・バグの下のストーリー・タスク・バグは step にする。step の下の子は、いちばん近いストーリー・タスク・バグの直下へ上げて step にする。プロジェクトの下のプロジェクト、エピックの下のエピックは、親の親の直下へ上げる |
| ワークスペース直下 | プロジェクト以外のタスクがあれば、そのワークスペースに「未分類」プロジェクトを 1 つ作り、そこへ移す |
| 関連 | duplicates・causes・relates はそのまま組み込みの項目へ。独自の task_ref のプロパティは relates へ。今の relates は、保存されていた側から付けた向きありの relates になる |
| 組み込みのプロパティ | `props:` の中の priority・start・due・estimate・points をトップレベルへ移す。priority の値のリストは今の定義から `priorities:` へ。型が合わない値（例: points が text）があれば一覧にして止める |
| ラベル | `labels:` のリストにないラベルはタスクから外す。dry run で外れるラベルを一覧するので、残したいものは先にリストに足す。automations の同期する項目から `labels` を取り除く |
| schema.yaml | `kinds` と task_ref のプロパティと組み込みと同じ名前のプロパティを消す。`kinds[].template` を `templates.default` へ移す |

## 進め方

spec は 1 本、PR は 4 本に分ける。変換コマンドと形式の番号の仕組みは 1 本目で作り、各 PR が自分の段を 1 つ足す。

1. 種類と階層の固定（種類の固定、階層、進捗、テンプレートの移動、スキーマ画面の種類タブの削除、変換: 種類・配置・ワークスペース直下）
2. 関連の固定（組み込みの項目、クエリのキー、画面、変換: 関連）
3. 組み込みのプロパティとラベル（トップレベルのキー、値のリスト、画面の優先度・ラベルのタブ、プロパティのマージの廃止、GitHub のラベルの同期の廃止、変換: プロパティ・ラベル）
4. GitHub のコメント同期

## テスト

- 種類と階層: 置ける場所と置けない場所のすべての組、子を持てないステップ、ワークスペース直下の拒否、既定の種類、進捗の数え方。
- 関連: 5 つの関連と逆方向の表示とクエリ、`.inverse` が使えないこと、task_ref のプロパティが作れないこと。
- プロパティ: トップレベルの読み書き、値のリストの編集、リストにないラベルの拒否、プロパティのマージの拒否。
- 変換: 表の各行を、変換前と変換後の Store で確かめる。dry run が何も書かないこと。2 回目の実行で何も変わらないこと。2 段以上前の形式から 1 回で最新になること。古い形式の Store でほかの操作が止まること。同期していない Store での変換の拒否と、format_diverged からの戻り方。
- GitHub: push と mirror のそれぞれで、コメントの追加・編集・削除の同期（偽の GitHub API で）。
- E2E: 新しい Store で、プロジェクト → エピック → ストーリー → ステップを作る通し。スキーマ画面の優先度とラベルのタブ。
